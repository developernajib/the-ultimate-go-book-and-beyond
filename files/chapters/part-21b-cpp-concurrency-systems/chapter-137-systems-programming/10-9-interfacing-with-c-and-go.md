## 9. Interfacing with C and Go

### extern "C": The C++ to C Bridge

C++ name mangling makes symbols incompatible with C by default. `extern "C"` disables mangling, enabling C code to call C++ functions and vice versa.

```cpp
// mylib.h -- C-compatible header
#ifdef __cplusplus
extern "C" {
#endif

typedef struct MyHandle MyHandle;

MyHandle* mylib_create(const char* config);
int       mylib_process(MyHandle* h, const void* data, size_t len);
void      mylib_destroy(MyHandle* h);

#ifdef __cplusplus
}
#endif
```

```cpp
// mylib.cpp -- C++ implementation behind C interface
#include "mylib.h"
#include <string>
#include <memory>

struct MyHandle {
    std::string config;
    std::vector<uint8_t> buffer;
};

extern "C" MyHandle* mylib_create(const char* config) {
    try {
        auto* h = new MyHandle();
        h->config = config;
        return h;
    } catch (...) {
        return nullptr;  // Never let C++ exceptions cross the C boundary
    }
}

extern "C" int mylib_process(MyHandle* h, const void* data, size_t len) {
    try {
        const auto* bytes = static_cast<const uint8_t*>(data);
        h->buffer.assign(bytes, bytes + len);
        // Process...
        return 0;  // Success
    } catch (...) {
        return -1;  // Error
    }
}

extern "C" void mylib_destroy(MyHandle* h) {
    delete h;
}
```

**Critical rules for `extern "C"` boundaries:**

1. Never throw exceptions across the boundary. Catch everything in the C++ side.
2. Use opaque pointer types (`typedef struct X X;`) to hide C++ internals.
3. Return error codes, not exceptions. Define a clear error reporting convention.
4. Manage memory explicitly, the caller must know who owns each allocation.

### CGO Bridge: Calling C++ from Go

Go can call C functions directly via CGO. To call C++ code, you expose a C-linkage wrapper and link against the C++ library.

```go
package mylib

/*
#cgo LDFLAGS: -L/path/to/lib -lmylib -lstdc++
#cgo CFLAGS: -I/path/to/include
#include "mylib.h"
#include <stdlib.h>
*/
import "C"
import (
    "errors"
    "runtime"
    "unsafe"
)

// Handle wraps the C++ library handle with Go safety.
type Handle struct {
    h *C.MyHandle
}

// New creates a new library instance.
func New(config string) (*Handle, error) {
    cConfig := C.CString(config)
    defer C.free(unsafe.Pointer(cConfig))

    h := C.mylib_create(cConfig)
    if h == nil {
        return nil, errors.New("mylib_create failed")
    }

    handle := &Handle{h: h}
    runtime.SetFinalizer(handle, func(h *Handle) {
        h.Close()
    })
    return handle, nil
}

// Process sends data through the C++ library.
func (h *Handle) Process(data []byte) error {
    if len(data) == 0 {
        return nil
    }
    ret := C.mylib_process(h.h, unsafe.Pointer(&data[0]), C.size_t(len(data)))
    if ret != 0 {
        return errors.New("mylib_process failed")
    }
    return nil
}

// Close releases the C++ resources.
func (h *Handle) Close() {
    if h.h != nil {
        C.mylib_destroy(h.h)
        h.h = nil
    }
}
```

**CGO performance considerations:**

- Each CGO call costs approximately 50-100ns of overhead due to goroutine stack switching and signal mask manipulation. Batch calls when possible.
- CGO calls pin the calling goroutine to an OS thread (`runtime.LockOSThread` internally). Long-running C calls reduce the goroutine scheduler's flexibility.
- Passing Go-managed memory to C requires careful handling. The Go garbage collector may move objects, use `C.CBytes` or pin memory explicitly.
- Consider using `//go:nosplit` and `//go:linkname` for performance-critical paths, but be aware these are unsafe and may break across Go versions.

### Calling Go from C++

The reverse direction is also possible. Compile Go code as a C shared library:

```go
package main

import "C"
import "fmt"

//export GoProcess
func GoProcess(input *C.char) *C.char {
    goStr := C.GoString(input)
    result := fmt.Sprintf("Processed: %s", goStr)
    return C.CString(result)  // Caller must free this
}

func main() {} // Required but unused
```

Build with: `go build -buildmode=c-shared -o libgolib.so golib.go`

```cpp
// C++ code calling Go
#include "libgolib.h"  // Generated by go build
#include <iostream>
#include <cstdlib>

int main() {
    char* result = GoProcess(const_cast<char*>("Hello from C++"));
    std::cout << result << "\n";
    free(result);  // Must free C.CString allocations
    return 0;
}
```

**Architecture decision:** When bridging C++ and Go, decide which language "owns" the process. If Go owns it (CGO calling C++), you get goroutines and the Go scheduler but pay CGO overhead. If C++ owns it (embedding Go as a library), you get full control over threading but lose goroutine scheduling benefits. For most systems, one language should be the clear host. Avoid deep bidirectional calls.
