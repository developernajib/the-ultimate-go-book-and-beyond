# Chapter 37I: Caching Strategies & Patterns

*"There are only two hard things in Computer Science: cache invalidation and naming things."* - Phil Karlton

A well-placed cache can reduce database load by 90%, cut p99 latency from hundreds of milliseconds to single digits, and allow a system to absorb traffic spikes that would otherwise cascade into outages. But caching is not a free lunch. Every cache introduces consistency risk: the moment data is copied out of its authoritative source, there exists a window during which the copy and the source can diverge. The engineer's job is to make a deliberate choice about how wide that window is allowed to be - and to build the mechanisms that control it.

The patterns that govern caching are not arbitrary conventions. Cache-aside (lazy loading) emerged as the dominant pattern for read-heavy workloads because it loads data only when needed, naturally distributing cache population across request traffic. Write-through guarantees that the cache is always consistent with the store but doubles write latency. Write-behind (write-back) trades durability for write throughput, buffering writes in the cache before flushing them asynchronously - a pattern used heavily in database buffer pools and message broker acknowledgment systems. Refresh-ahead proactively rehydrates cache entries before they expire, preventing the thundering herd problem that occurs when thousands of requests simultaneously encounter a cold cache for a popular key.

Go's concurrency model fits caching infrastructure well. The `sync.Map` type and `groupcache` library - originally built by Brad Fitzpatrick for Google - show how goroutines and channels can implement singleflight deduplication, where hundreds of concurrent requests for the same uncached key collapse into a single upstream fetch. For in-process caches, `dgraph-io/ristretto/v2` (generics, TinyLFU admission) remains the canonical choice. `maypok86/otter/v2` now offers higher hit rates on OLTP workloads using an adaptive W-TinyLFU algorithm aligned with Java's Caffeine. For distributed caching, Redis dominates production deployments, and since Redis Ltd.'s 2024 license change a growing share of teams run the Linux Foundation's **Valkey** fork (see Chapter 35) - both speak the same RESP protocol and work transparently with `go-redis`. This chapter builds the mental model and the concrete Go implementation for all of these patterns.

**What you'll learn in this chapter:**
- Implement multi-layer caching (L1 in-process `sync.Map`/`ristretto`, L2 Redis cluster, L3 CDN) with correct promotion and demotion logic
- Apply cache-aside, write-through, write-behind, and read-through patterns in idiomatic Go with the repository pattern
- Build production Redis caching with proper serialization (protobuf/msgpack), TTL policies, and LRU/LFU eviction configuration
- Implement singleflight deduplication using `golang.org/x/sync/singleflight` to eliminate thundering herd under cold cache conditions
- Design consistent hashing rings for distributed cache clusters with virtual nodes and rebalancing
- Build cache-aware data access layers using the decorator pattern over repository interfaces
- Measure cache effectiveness with hit rate, byte hit rate, and latency percentile metrics exposed via Prometheus
- Apply probabilistic early expiration (PER/XFetch) and TTL jitter to prevent coordinated cache expiry storms in high-traffic systems
- Cache negative results (not-found lookups) to shield the origin from repeated scans for non-existent keys

**Why this matters at scale:**
Twitter's timeline architecture is the canonical caching case study: timelines are materialized into massive Redis clusters by the famous fan-out design, so a home-timeline read is a cache read, not a query. Facebook's memcache infrastructure, described in their 2013 NSDI paper, handles over a billion requests per second across their data centers, built on the cache-aside pattern at planetary scale. Delivery platforms cache restaurant menus write-through with per-entity TTLs precisely so a Super Bowl traffic spike hits Redis, not the database. And singleflight deduplication in front of hot lookups (the pattern `golang.org/x/sync/singleflight` codifies) is how payment-grade services prevent retry storms from amplifying load.

**Prerequisites:** Chapters 37-37H (database fundamentals), Go concurrency (goroutines, channels, `sync` package from Chapter 11), and basic Redis familiarity (data types, CLI commands).

### Junior → FAANG: entering the caching world from a standing start

If you have never built a cache beyond a `map[string]string` guarded by a `sync.RWMutex`, start by internalising the vocabulary the rest of the chapter assumes. A **hit** is a lookup that finds a valid entry. A **miss** forces a fetch from the authoritative source. **Hit rate** is hits divided by total lookups, and **byte hit rate** weights each hit by the size of the returned payload. A cache with 95 percent hit rate but which only caches tiny metadata can still send megabytes of body data to the origin on every miss, so byte hit rate is the more honest metric for CDN and object-cache tiers.

Work the following first-job example on paper before touching code. A product service receives 10,000 requests per second. Of those, 100 unique product IDs account for 80 percent of traffic (a Zipfian head), and the long tail accounts for the remaining 20 percent across roughly 200,000 IDs. Origin latency is 40ms p50 and 200ms p99. If you cache the head in a 256-entry L1 LRU sized by entry count, you will hit on nearly every head request. The long tail misses every time, because 200,000 IDs will not fit in 256 entries. Your observed hit rate will hover near 80 percent, your p50 will fall to sub-millisecond for the head, but p99 will still be dominated by origin latency. The lesson is that hit rate alone hides workload shape. Recruiters at the FAANG tier ask candidates to reason about head versus tail and to pick a sizing that covers the working set, not a round number.

Interview entry points you should be able to answer cold: what is the difference between write-through and write-behind, why does `sync.Map` perform poorly under mixed read/write workloads compared to a sharded map, and what does `golang.org/x/sync/singleflight` actually do. The short answers are: write-through writes to cache and store synchronously inside one request, write-behind writes to the cache first and flushes asynchronously, `sync.Map` is optimized for append-once/read-many and degrades under heavy writes because its dirty map must be promoted, and singleflight deduplicates concurrent calls for the same key so only one goroutine pays the origin cost while the rest wait on a shared result. If you can answer those three questions with a whiteboard sketch you are ahead of most junior candidates walking into a systems-design loop.

One worked example to cement the vocabulary. A user-profile endpoint reads from Postgres on every call, costing 8ms. Putting a 60 second TTL cache in front of it drops the average to 200 microseconds after warm-up, but every 60 seconds each popular key refetches, and if 50 instances all expire the same key at the same second they all hit Postgres together. The fix is TTL jitter: store the entry with a TTL of `60s + rand(0, 10s)` so expiries spread out. That one line of code is the difference between a cache that smooths traffic and a cache that creates synchronized stampedes.

### Senior @ FAANG: tiered cache coherence as a distributed systems problem

At staff and principal level, caching stops being a latency optimization and becomes a distributed systems problem. A production stack at scale typically has four tiers. **L1** is the in-process cache on each service replica, holding hot keys with microsecond access and no network cost. **L2** is the distributed cache tier (Redis Cluster, Valkey, or Memcache), shared across replicas, with sub-millisecond latency and bounded memory per shard. **L3** is the CDN or edge cache tier (Fastly, CloudFront, Cloudflare), caching full HTTP responses near users. **L4** is the database's own internal buffer pool (Postgres shared_buffers, InnoDB buffer pool), which you do not control directly but whose behavior you must reason about. Each tier has its own admission policy, eviction policy, TTL model, and invalidation story. The staff-level problem is keeping them coherent without building a custom consensus protocol.

Coherence fails in specific ways. A write that updates L2 but not L1 leaves every replica with a stale L1 copy until its TTL fires. A write that updates the database but fails to invalidate L2 leaves every replica serving stale data until the L2 TTL fires. A CDN purge that lags behind an L2 update means users see old HTML while service-to-service calls see new JSON. The staff-level ADR decision is choosing an invalidation mesh: pub/sub broadcast over Redis, a Kafka topic partitioned by cache key, or an explicit version-stamp approach where every cached entry carries a monotonic version and readers reject entries older than the version they have seen. Pub/sub is cheap but lossy under network partition. Kafka is durable but adds latency and operational weight. Version stamps avoid broadcast entirely but require every reader to know the expected version, which pushes complexity into the caller.

Eviction policy selection is the other senior-level lever. LRU is simple and ships in most libraries but performs poorly on scan-heavy workloads where a one-time sequential read blows out the working set. LFU corrects this by weighting by frequency but adapts slowly to shifting access patterns. ARC (IBM 2003) splits the cache between recency and frequency and adapts the split online, but is patent-encumbered in some implementations. W-TinyLFU (used in Caffeine and Ristretto) combines a count-min sketch frequency estimator with a small LRU admission window, and dominates empirical benchmarks across mixed workloads. SIEVE (NSDI 2024) offers LRU-like simplicity with LFU-like hit rates by marking visited entries and skipping them on the eviction hand. S3-FIFO (SOSP 2023 from CMU) extends SIEVE with a small, main, and ghost FIFO queue structure and now outperforms SIEVE on most production traces. The staff engineer does not pick an eviction policy by reflex. They profile the workload, classify it as recency-biased, frequency-biased, or scan-heavy, and write an ADR that states the chosen policy, the measured hit rate, the memory budget, and the fallback behavior if the policy assumption proves wrong.

The final senior concern is cascading failure. A cache that improves the 99th percentile latency by an order of magnitude also creates an implicit capacity ceiling on the origin. If the cache fails or flushes, the origin receives the full uncached request rate, which may be 20x its normal load. This is how cache outages turn into database outages and then into full site outages. Mitigations include request shedding at the cache layer when miss rate spikes, a circuit breaker that fails fast rather than piling load onto a wounded origin, and capacity planning that sizes the origin to handle some fraction of total traffic with zero cache (often 20 to 30 percent is the minimum survivable target). These choices belong in the capacity ADR, not in the code.
