# Chapter 37J: Cache Invalidation & CDN Engineering

*"Cache invalidation is hard not because the mechanism is complicated, but because knowing when the truth has changed is a distributed systems problem in disguise."* - Martin Fowler

Phil Karlton's famous quip about cache invalidation being one of the two hard problems in computer science has endured for thirty years because it points at something genuinely deep. The mechanism of invalidation - deleting a key, broadcasting a message, incrementing a version counter - is straightforward. The hard part is knowing, with certainty, that the cached value no longer reflects reality. In a single-process application this is tractable. In a distributed system where multiple services write to the same data, where network partitions can delay invalidation signals, and where CDN edge nodes are geographically scattered across dozens of points of presence, building a correct invalidation system requires careful architectural thinking.

Content Delivery Networks add a second dimension to this problem. CDNs are designed to serve content from the edge - as close to the end user as possible - caching responses at hundreds of PoPs worldwide. When a user in Singapore requests a product page, Cloudflare serves it from a Singapore edge node, not from an origin server in us-east-1. This reduces latency from 200ms to 20ms. But when the product price changes, that update must propagate to every edge node that has cached the old value. The naive approach - waiting for TTL expiry - can mean serving stale prices for hours. Surrogate key systems (cache tags in Cloudflare, Surrogate-Key headers in Fastly) solve this by associating cached responses with logical keys, enabling instant targeted purges across all edges with a single API call.

The modern approach to cache invalidation is event-driven. When a product is updated in the database, a CDC event flows through Kafka to a cache invalidation service that issues targeted purges to Redis, Memcache, and the CDN simultaneously, all within milliseconds of the write committing. Stale-while-revalidate and stale-if-error directives provide graceful degradation: serve the stale entry immediately while revalidating in the background, or continue serving stale content when the origin is unreachable. This chapter covers the invalidation service, CDN integration layer for Cloudflare, Fastly, and CloudFront, and the application-level patterns that tie them together.

**What you'll learn in this chapter:**
- Implement event-driven cache invalidation pipelines in Go using Kafka consumers and Redis `DEL`/`UNLINK` operations
- Design surrogate key (cache tag) systems and integrate with Cloudflare and Fastly purge APIs from Go HTTP clients
- Apply `Cache-Control`, `Surrogate-Control`, and `Vary` headers correctly from Go HTTP handlers for optimal CDN behavior
- Build stale-while-revalidate and stale-if-error patterns using Go middleware and Redis fallback logic
- Prevent cache stampede under invalidation storms with probabilistic locking and coalesced revalidation
- Implement cache poisoning defences: input normalization, `Vary` header hygiene, and host header validation
- Design geographically distributed invalidation with consistent eventual propagation guarantees
- Measure CDN cache hit ratio, byte hit ratio, and origin shield effectiveness using CDN analytics APIs

**Why this matters at scale:**
The New York Times uses Fastly's surrogate key system to invalidate cached article pages within seconds of editorial updates, serving 100 million monthly readers without sacrificing freshness. Shopify processes hundreds of thousands of product updates per minute during flash sales. Their CDN invalidation pipeline, built on Kafka and Fastly tag purging, ensures that price and inventory changes propagate to edge nodes within two seconds globally. GitHub uses stale-while-revalidate extensively for repository pages, serving cached responses immediately while refreshing in the background - achieving sub-50ms TTFB for 99% of requests even during traffic spikes. Cloudflare Workers let companies implement personalization and A/B testing at the edge without any origin round-trip, cutting latency by running the logic close to the user instead of at a distant origin.

### Junior → FAANG: why invalidation is the whole game

If you are coming from a first job where you wrote `redis.Set(key, value, 5*time.Minute)` and moved on, the gap here is not syntax, it is worldview. A TTL is a confession that you do not know when the data changed, so you guess a number that balances staleness against load. That is fine for a product catalog that updates overnight. It is catastrophic for a pricing page during a flash sale, a permissions check after an admin revoke, or an account balance after a transfer. The interview entry-point questions cluster around one worked example: "user changes their email, why do they still see the old one after clicking save?" Trace the path. The PUT hits the API, the API writes Postgres, the API returns 200, the browser navigates, the GET hits a read-through cache that still holds the old row for another 270 seconds. You have three options and you must be able to name all three. First, TTL-only, accept the window. Second, active invalidation, the write path deletes the cache key before returning. Third, versioned keys, the write bumps `user:v42` to `user:v43` and readers naturally miss. Each has a failure mode. Active invalidation races with concurrent reads that repopulate the stale value between the DB commit and the DEL. Versioned keys leak memory unless you expire old versions. TTL-only is never correct for data with user-visible edits. Build one small Go service that demonstrates all three on the same endpoint and you will answer 80% of caching questions at a phone screen.

### Senior @ FAANG: the invalidation taxonomy and why Phil Karlton was right

Phil Karlton's aphorism ("there are only two hard things in computer science, cache invalidation and naming things") is routinely misquoted as a joke about complexity. It is not. It is a precise claim that invalidation is a distributed consensus problem wearing a different hat. To invalidate correctly you must answer: whose write wins, how do all readers learn about it, and what do they serve in the interval. Staff-level design reviews evaluate a proposal against a taxonomy you should carry in your head. On the correctness axis: TTL-only (eventual, bounded staleness), active invalidation (stronger but racy without careful ordering), versioned-key (monotonic, race-free, expensive in memory), and write-through (synchronous, latency-coupled to cache availability). On the idempotency axis: idempotent invalidation (DEL, PURGE by tag, re-executing is safe) versus non-idempotent (incrementing a counter, applying a delta, reordering breaks correctness). At FAANG scale you always choose idempotent primitives because your delivery layer is at-least-once and your consumers will replay. On the ordering axis: causal consistency (a read after a write by the same session sees the write, enforced by sticky sessions or read-your-writes tokens) versus global ordering (every replica sees writes in the same order, usually overkill and expensive). The design pattern that wins most reviews is "outbox plus CDC plus tag purge": the write transaction inserts into an outbox table in the same commit, Debezium tails the WAL, emits to Kafka partitioned by aggregate ID so per-entity ordering holds, a fanout worker issues idempotent purges to Redis and the CDN using surrogate keys. This gives you a bounded staleness window (p99 under 2 seconds globally at Shopify and Stripe scale), correct ordering per entity, at-least-once delivery tolerated by idempotent PURGE, and a replayable audit log. When someone proposes a dual-write (app writes DB, app writes cache, app writes CDN) you reject it because partial failure leaves permanent divergence and no reconciliation path. RFC 9111 (the 2022 refresh of HTTP caching semantics) formalizes the rules your CDN layer must honor, and Cloudflare's tag-based purge plus Tiered Caching architecture is the practical implementation you will operate. The rest of this chapter teaches the mechanics, but the judgment is the taxonomy: every caching decision reduces to picking a quadrant on those three axes and defending it against the failure modes of the others.
