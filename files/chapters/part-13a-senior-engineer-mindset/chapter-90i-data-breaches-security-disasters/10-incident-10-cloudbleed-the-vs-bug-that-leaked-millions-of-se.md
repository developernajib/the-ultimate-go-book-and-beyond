## 90I.10 Cloudbleed - The `==` vs `>=` Bug That Leaked Millions of Secrets (2017)

### The Attack Timeline

On February 17, 2017, Google Project Zero researcher Tavis Ormandy contacted Cloudflare about a critical bug he
had discovered: Cloudflare's edge servers were leaking memory contents into HTTP responses served to random users.
The leaked data included HTTP cookies, authentication tokens, HTTP POST bodies, and even HTTPS private keys from
other Cloudflare customers. Ormandy described it as "catastrophic" - search engine crawlers were caching the leaked
data, making it publicly searchable.

**The Bug**

Cloudflare's HTML parser, written in Ragel (a state machine compiler that generates C code), had a buffer
overrun bug. The parser was used for several features including email obfuscation, Server Side Excludes, and
Automatic HTTPS Rewrites. The relevant code (simplified) contained:

```c
/* Check if we've reached the end of the buffer */
if (p == pe) {  /* BUG: should be p >= pe */
    /* Stop parsing */
}
```

The `==` check only triggered when the pointer `p` was exactly at the end of the buffer `pe`. But due to how
the Ragel-generated state machine advanced the pointer, `p` could skip past `pe` without ever equaling it. When
this happened, the parser continued reading memory beyond the buffer - into whatever data happened to be adjacent
in memory, which included data from other HTTP requests being processed on the same server.

**The Scale**

Cloudflare processes approximately 10% of all HTTP requests on the internet. The bug was triggered approximately
1 in every 3.3 million requests for about five months (September 22, 2016 to February 18, 2017). The data
leaked included:
- Authentication cookies for major websites
- API keys and OAuth tokens
- Passwords from HTTP POST bodies
- HTTPS private keys
- Other customers' HTTP request and response data

Google, Bing, and other search engines had cached pages containing leaked data, which had to be urgently purged.

### Technical Root Cause Analysis

The root cause was a single character: `==` instead of `>=`. This is a classic off-by-one/bounds-check error in
C code generated by a code generator (Ragel). The generated code was difficult to audit because it was machine-
generated and optimized for the state machine's execution model, not human readability.

### Go Code: Bounds Checking by Design

Go prevents Cloudbleed-class bugs through automatic bounds checking on all slice and array access:

```go
package bounds

import (
	"errors"
	"fmt"
	"unicode/utf8"
)

var (
	ErrBufferOverflow  = errors.New("buffer boundary exceeded")
	ErrInvalidPosition = errors.New("invalid buffer position")
)

// SafeParser demonstrates a buffer parser that cannot over-read memory.
// In Go, attempting to read past the end of a slice causes a runtime panic
// (which can be recovered), but proper defensive coding avoids even that.
type SafeParser struct {
	data []byte
	pos  int
}

// NewSafeParser creates a parser for the given data.
func NewSafeParser(data []byte) *SafeParser {
	return &SafeParser{
		data: data,
		pos:  0,
	}
}

// Remaining returns the number of unread bytes.
func (p *SafeParser) Remaining() int {
	return len(p.data) - p.pos
}

// AtEnd returns true if there are no more bytes to read.
// This uses >= (not ==), which is the fix for the Cloudbleed bug.
// In Go, this is natural because we compare against len(), which
// always returns the true length.
func (p *SafeParser) AtEnd() bool {
	return p.pos >= len(p.data) // >= not ==. This is the Cloudbleed fix.
}

// ReadByte reads a single byte, returning an error if at end of buffer.
func (p *SafeParser) ReadByte() (byte, error) {
	if p.pos >= len(p.data) {
		return 0, fmt.Errorf("%w: position %d, length %d",
			ErrBufferOverflow, p.pos, len(p.data))
	}
	b := p.data[p.pos]
	p.pos++
	return b, nil
}

// ReadN reads exactly n bytes, returning an error if insufficient data remains.
func (p *SafeParser) ReadN(n int) ([]byte, error) {
	if n < 0 {
		return nil, fmt.Errorf("%w: negative read size %d", ErrInvalidPosition, n)
	}
	if p.pos+n > len(p.data) {
		return nil, fmt.Errorf(
			"%w: tried to read %d bytes at position %d, but only %d bytes remain",
			ErrBufferOverflow, n, p.pos, p.Remaining(),
		)
	}

	// This slice operation is safe because we verified bounds above.
	// Even without the check, Go would panic (not silently over-read).
	result := make([]byte, n)
	copy(result, p.data[p.pos:p.pos+n])
	p.pos += n
	return result, nil
}

// ReadUntil reads bytes until the delimiter is found or the buffer ends.
// Returns the data read (not including the delimiter) and whether the
// delimiter was found.
func (p *SafeParser) ReadUntil(delimiter byte) ([]byte, bool) {
	start := p.pos
	for p.pos < len(p.data) { // < not <=, and certainly not ==
		if p.data[p.pos] == delimiter {
			result := make([]byte, p.pos-start)
			copy(result, p.data[start:p.pos])
			p.pos++ // Skip the delimiter.
			return result, true
		}
		p.pos++
	}
	// Delimiter not found - return everything remaining.
	result := make([]byte, p.pos-start)
	copy(result, p.data[start:p.pos])
	return result, false
}

// ReadUTF8Rune reads a single UTF-8 encoded rune, handling multi-byte
// sequences safely. This demonstrates that even variable-width encodings
// cannot cause over-reads in Go.
func (p *SafeParser) ReadUTF8Rune() (rune, int, error) {
	if p.AtEnd() {
		return 0, 0, ErrBufferOverflow
	}

	r, size := utf8.DecodeRune(p.data[p.pos:])
	if r == utf8.RuneError && size <= 1 {
		// Invalid UTF-8 byte. Advance by 1 to avoid infinite loops.
		p.pos++
		return utf8.RuneError, 1, nil
	}

	p.pos += size
	return r, size, nil
}

// Peek returns the next n bytes without advancing the position.
func (p *SafeParser) Peek(n int) ([]byte, error) {
	if n < 0 {
		return nil, fmt.Errorf("%w: negative peek size", ErrInvalidPosition)
	}
	available := p.Remaining()
	if n > available {
		n = available // Peek returns what's available, never more.
	}
	result := make([]byte, n)
	copy(result, p.data[p.pos:p.pos+n])
	return result, nil
}

// Skip advances the position by n bytes, with bounds checking.
func (p *SafeParser) Skip(n int) error {
	if n < 0 {
		return fmt.Errorf("%w: negative skip size", ErrInvalidPosition)
	}
	if p.pos+n > len(p.data) {
		return fmt.Errorf(
			"%w: skip %d at position %d would exceed buffer length %d",
			ErrBufferOverflow, n, p.pos, len(p.data),
		)
	}
	p.pos += n
	return nil
}

// HTMLTagParser demonstrates parsing HTML tags safely, similar to what
// Cloudflare's Ragel parser was doing when Cloudbleed occurred.
func HTMLTagParser(html []byte) ([]string, error) {
	parser := NewSafeParser(html)
	var tags []string

	for !parser.AtEnd() {
		b, err := parser.ReadByte()
		if err != nil {
			break
		}

		if b == '<' {
			tagData, found := parser.ReadUntil('>')
			if !found {
				// Unclosed tag at end of input - safe, just stop.
				break
			}
			if len(tagData) > 0 {
				tags = append(tags, string(tagData))
			}
		}
		// Non-tag content is safely skipped - no over-read possible.
	}

	return tags, nil
}
```

### Engineering Lessons

1. **Use `>=` not `==` for boundary checks.** This is the single-character fix for Cloudbleed. In Go, using
   `>=` is natural because `len()` always returns the true length, and slice access is bounds-checked by the
   runtime regardless of your code.

2. **Memory-safe languages prevent information leakage.** In Go, reading past the end of a slice causes a panic,
   not a silent over-read. This means a Cloudbleed-equivalent bug in Go would cause a service crash (which is
   immediately visible and debuggable) rather than silently leaking secrets for months.

3. **Generated code needs the same security scrutiny as handwritten code.** Cloudbleed was in Ragel-generated C
   code that was difficult to audit. If you use code generators, their output must be reviewed for security
   properties.

4. **Code at the edge processes everyone's data.** Cloudflare's position as a CDN/proxy meant that a single bug
   leaked data for millions of websites. The higher the position in the stack, the greater the blast radius.

### Junior → FAANG: Comparison Operator Bugs and Off-by-One Errors as Interview Topics

Cloudbleed is the interview answer to "what is an off-by-one error and why is it a security vulnerability?" The Ragel-generated HTML parser used `==` instead of `>=` to check buffer boundaries. When a specially crafted HTML tag caused the parser to read past the end of a buffer, it continued into adjacent memory and included that memory in the HTTP response. For FAANG interviews, the lesson is specific: boundary checks must use `>=` (or `<=`) rather than `==` (or `!=`) because exact equality is fragile. A check `if ptr == end` misses the case where `ptr > end`, which is exactly how off-by-one errors produce reads beyond buffer boundaries. In Go, this class of vulnerability in the language itself is impossible because slice bounds are checked at runtime. But when you interface with CGO or process raw bytes using `unsafe`, the same vigilance applies. Generated code needs the same security review as handwritten code: the Cloudbleed parser was generated by Ragel, but the output was C code with C's memory safety model.

### Senior @ FAANG: High-Traffic Path Security and Generated Code Review as Platform Standards

At L6, Cloudbleed reveals a risk amplification pattern: Cloudflare's CDN position meant a single bug in the HTML parser exposed data from millions of customer websites simultaneously. The blast radius was proportional to the platform's position in the stack. At staff level, you identify the highest-position components in your architecture (shared reverse proxies, API gateways, shared middleware libraries) and apply additional security scrutiny proportional to the blast radius. A bug in a shared reverse proxy that processes all traffic for all customers is not the same risk as a bug in a single tenant's service handler. The production readiness review for platform components has a higher bar: independent security review, fuzzing of all input parsing paths, and explicit blast-radius documentation. For generated code specifically (protoc-generated serialization, Ragel-generated parsers, code generation templates), the platform standard includes a review of the generator's safety model: does the generator produce bounds-checked code, or does it assume the caller provides valid input? If the latter, the generated code must be wrapped in bounds-checking validation at every input boundary before it processes external data.
