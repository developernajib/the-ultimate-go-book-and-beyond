## 112D.10 Interview Questions

**Q: What's the difference between pseudonymization and anonymization under GDPR?**

**What FAANG expects:** Pseudonymization is reversible (a key or mapping exists). Data is still personal data under GDPR (Article 4(5)). Anonymization is irreversible and falls outside the regulation (Recital 26). The *test* is whether re-identification is possible using means "reasonably likely to be used", accounting for cost, time, and available technology. A keyed hash whose key is held separately is pseudonymization. k-anonymity with suppression of quasi-identifiers is a candidate for anonymization, and the choice of k is a risk decision for your dataset rather than a number the regulation supplies. Bonus for naming the Netflix Prize or AOL search log re-identification cases as why anonymization is harder than it looks.

A: **Pseudonymization** replaces PII with a pseudonym (like a UUID or an HMAC) that can be reversed with a key or a lookup table. The original is still recoverable by someone holding it, so pseudonymized data is still personal data. It reduces risk but does not exempt you from GDPR obligations. **Anonymization** irreversibly severs the link to the individual, including via indirect identifiers, so that no one can re-identify them even with additional data. Genuinely anonymized data is not personal data under GDPR. Key distinction: if anyone retains a technically feasible path back to the individual, it is pseudonymization.

Push on the erasure claim if the interviewer raises it, because the sloppy version of this answer is that anonymization "satisfies" Article 17. The defensible version: anonymizing a record can be an acceptable way to fulfill an erasure request, since what remains is no longer personal data. But anonymization is itself a processing operation, it must be irreversible in practice and not merely in intention, and residual data that still singles the person out has erased nothing. Candidates who state it as a blanket equivalence usually cannot answer what happens to the backups.

**Q: How do you implement PCI DSS tokenization without storing PANs?**

A: (1) PAN enters through a PCI-scoped network segment only, (2) the tokenization service encrypts the PAN with AES-256-GCM, stores the ciphertext in a token vault, and returns an opaque token to the caller, (3) downstream systems store only the token, which is what makes a descoping argument possible for them, (4) last four digits and card brand may be stored and displayed in the clear, since PCI DSS permits a masked display of first six and last four, (5) detokenization is restricted to the small set of services in the authorization flow that genuinely need a PAN, and the check is enforced in code rather than documented in a runbook, (6) every detokenization request is audit-logged, including denials, (7) the CVV is never stored at any point, tokenized or otherwise, because Requirement 3.3.1 prohibits retaining sensitive authentication data after authorization and offers no encrypted-storage exception.

Say the scope part carefully, because overclaiming it is a fast way to lose the room. The goal is to minimize PCI scope, and tokenization is what makes downstream systems arguably out of scope: they hold values that cannot be reversed to a PAN without the vault. But scope is a determination your QSA makes about your actual environment, not a property that tokenization confers automatically. Systems with network connectivity to the CDE can be pulled back in as connected-to systems even if they never touch a PAN. The mature answer is "tokenization plus segmentation is how we argue these systems out of scope, and here is the evidence", not "they store tokens, therefore they are out of scope".

**Q: What are SOC 2 Trust Service Criteria and how do they map to engineering controls?**

A: Start by getting the framing right, because it is a cheap signal and most candidates miss it: SOC 2 is an AICPA attestation engagement, not a certification. Nobody is "SOC 2 certified". A CPA firm issues a report expressing an opinion on your controls. There are five Trust Services Categories, and only Security, the common criteria, is required. The other four are included in scope only if you choose them, typically because a customer contract asks for them.

**Security** (CC1-CC9) covers access controls, encryption, vulnerability management, and incident response. **Availability** (A1) covers uptime monitoring, disaster recovery, and capacity planning. **Processing Integrity** (PI1) covers input/output validation, error handling, and complete and accurate processing. **Confidentiality** (C1) covers data classification, encryption, and access controls for confidential data. **Privacy** (P1-P8) covers consent, data minimization, retention, DSAR, and disclosure limits. Most engineers primarily implement Security (logical access, encryption, change management) and Availability controls. The key insight: SOC 2 does not specify how to implement controls, it specifies what must be demonstrably true, and you write the control descriptions the auditor then tests you against. Automated evidence collection is what separates Type II (operating effectiveness across an observation window, commonly three to twelve months) from Type I (design of controls at a point in time).

**Q: How does HIPAA's minimum necessary standard translate to engineering controls?**

A: HIPAA requires that covered entities access and use only the minimum PHI necessary to accomplish the intended purpose. In Go code this means: (1) **Role-based field access**, billing staff see demographic/insurance fields only, clinical staff see clinical fields, researchers see only de-identified fields. (2) **PHI type wrapper**, a `PHI[T]` type that logs every `.Access()` call with actor, purpose, and timestamp. (3) **Purpose validation**, every PHI access requires an explicit stated purpose that is checked against a policy table. (4) **Automatic log redaction**, PHIMasker patterns applied to all log fields before they reach log pipelines. (5) **Audit log retention**, retained separately from application logs with their own lifecycle policy. Be precise about where six years comes from, because the common version of this answer is wrong: 164.316(b)(2)(i) requires HIPAA-mandated *documentation* to be kept six years from creation or last effective date. The Security Rule does not set a retention period for the access logs themselves. Six years is the prevailing industry practice, driven by that documentation rule plus state law and the six-year enforcement lookback, and it is a defensible default. It is a practice you adopt, not a number the rule states.

Also worth flagging: minimum necessary is a Privacy Rule standard, and it does not apply to disclosures to a healthcare provider for treatment purposes. That exception is why the `clinical` role in the policy table above is granted all fields rather than a narrowed list. Candidates who apply minimum necessary uniformly to every role reveal they learned the slogan and not the rule.

**Q: What is a DSAR (Data Subject Access Request) and how do you automate it?**

A: A DSAR is the Article 15 right of access, by which a data subject can request confirmation that you process their data, a copy of it, and supporting information such as the purposes, the recipients, and the retention period. The deadline comes from Article 12(3): one month from receipt, extendable by two further months for complex requests if you notify the subject within the first month. It is free, with Article 12(5) allowing a reasonable fee or refusal only for manifestly unfounded or excessive requests.

Distinguish it from Article 20 portability, which interviewers often conflate with it and which is narrower: portability covers only data the subject provided, only where processing rests on consent or contract, and only where it is automated. That is the right that demands a "structured, commonly used and machine-readable format", which JSON or CSV satisfies. Article 15 has no such format requirement, though a copy has to be intelligible.

Automating it requires: (1) a data inventory that maps every table and field containing personal data to a user ID, (2) an export pipeline that queries each mapped store for the subject's records and fails loudly rather than silently skipping one, (3) the metadata Article 15 requires alongside the data itself, not just the rows, (4) a consent and legal-basis record showing what was collected when and why, (5) a suppression list that prevents erased users from being re-ingested from backups or upstream feeds. Without a data inventory, DSARs require manual engineering work per request, which at scale is operationally unsustainable.

**Q: How do you handle an erasure request (GDPR right to be forgotten) for a user whose ID appears in audit logs?**

A: This is a deliberate tension in GDPR: Article 17 (erasure) against Article 17(3)(b), which disapplies erasure where processing is necessary to comply with a legal obligation. Audit logs frequently sit on the exempt side.

Get the retention figures right, because the folklore numbers are wrong and an interviewer in this domain will know. PCI DSS is the only one of the three that names a period: Requirement 10.5.1 asks for at least twelve months of audit log history, with the most recent three months immediately available for analysis. SOC 2 prescribes no retention period at all, since you define your own control and the auditor tests you against the period you committed to. HIPAA's six years applies to required documentation, not to the logs themselves. Longer retention is usually driven by SOX, tax and financial record rules, or litigation posture rather than by the security frameworks people credit for it.

The correct approach: (1) **Anonymize the personal data within the log entry**, replace the user ID with a pseudonymous reference, replace their name/email with `[DELETED]`, keep the event type and timestamp. (2) The anonymized log entry satisfies the legal retention requirement without containing personal data. (3) **Delete all primary data**, account records, profile, transaction data. (4) **Record the erasure event**, store an anonymized record that erasure was completed, with the request timestamp and confirmation, for compliance evidence. (5) Propagate erasure to all downstream systems using an event-driven pipeline.

**Q: What is the difference between SOC 2 Type I and Type II?**

A: **Type I** is a point-in-time report: the auditor opines that your controls are suitably designed as of a specific date. **Type II** covers an observation window, commonly three to twelve months, and opines on whether those controls also *operated effectively* throughout it. Design versus operation is the whole distinction. Type I says the control was built correctly, Type II says it actually ran.

Enterprise customers almost always require Type II, because a Type I proves only that everything looked right on the day someone checked. A common path is a Type I first to unblock deals, then a Type II covering the following window. The engineering implication: Type II requires continuous automated evidence collection, since you cannot retroactively prove a control worked for six months without logs and automated checks that were already running. Build evidence collection pipelines from day one, not as audit prep. Note also that a Type II with exceptions noted is a normal outcome rather than a failure. The report describes what the auditor found, including where a control lapsed and what you did about it.

### Junior → FAANG: Using These Questions to Frame Your Compliance Depth

These questions test whether you understand compliance as an engineering discipline, not a policy exercise. The pattern in each answer is the same: identify the regulatory requirement, map it to a concrete engineering control, and explain the evidence that proves the control is working. Practice answering each question at two levels. The first level is "what does the requirement say?" The second level is "what would you build and what would you show an auditor?" Stopping at the first level tells an interviewer you read the documentation. Reaching the second level demonstrates practical implementation depth.

Entry-level signal: correctly distinguish pseudonymization from anonymization and explain why re-identification risk determines which category applies. This question appears frequently because it is a common misconception that removing a name makes data anonymous.

### Senior @ FAANG: Bar-Raiser Signals in Compliance System Design

At the senior and staff level, interviewers extend these questions into system design territory. Expect to design a DSAR fulfillment system that handles 10,000 requests per month across 50 microservices, each with their own databases, caches, and event streams. The answer must cover: how the data inventory is maintained as services evolve, how fulfillment is orchestrated with retry and partial-failure handling, how the one-month statutory clock is tracked per request and escalated before it expires, how the output is assembled from heterogeneous data sources into a consistent portable format, and how the system proves to an auditor that every request was fulfilled completely and on time.

Another common senior extension is the erasure-versus-audit-log tension. The answer in this chapter covers the pattern (anonymize rather than delete log entries), but a bar-raiser follows up with: how do you handle audit logs stored in an immutable store like S3 Object Lock? The answer is that you cannot modify Object Lock-protected objects, so you write a suppression record to a separate overlay store that is consulted at query time to filter erased users from audit results. The audit log itself is untouched, satisfying the immutability requirement. The overlay provides the erasure behavior, satisfying GDPR. This dual-store pattern is the production answer for regulated environments.

SOC 2 Type I versus Type II comes up at L6 as an organizational question: how do you structure your engineering roadmap to achieve Type II without creating a compliance sprint every audit cycle? The answer is continuous control monitoring with automated evidence pipelines, so that the audit period evidence is produced as a side effect of normal operations rather than as a dedicated workstream. Candidates who can estimate the engineering investment for this infrastructure and frame it in terms of reduced audit cost and increased enterprise deal velocity are demonstrating L6 thinking.
