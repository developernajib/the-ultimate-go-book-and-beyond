## 77.8 Interview Tips

Choosing the wrong binary search template is the most common source of infinite loops and off-by-one errors in interviews. The two templates differ in how they maintain the invariant and shrink the search space: Template 1 keeps an inclusive `[left, right]` window and is best for exact-match searches, while Template 2 keeps a half-open `[left, right)` window that converges to a single boundary point, making it the right choice for lower-bound and upper-bound queries.

### Binary Search Template Comparison

```
┌─────────────────────────────────────────────────────────────────┐
│            BINARY SEARCH TEMPLATES                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  Template 1: left <= right                                      │
│  • Search space: [left, right] (inclusive)                      │
│  • Termination: left > right                                    │
│  • Use: Find exact match                                        │
│  • Update: left = mid + 1, right = mid - 1                      │
│                                                                 │
│  Template 2: left < right                                       │
│  • Search space: [left, right) (exclusive right)                │
│  • Termination: left == right                                   │
│  • Use: Find boundary (lower/upper bound)                       │
│  • Update: left = mid + 1, right = mid                          │
│                                                                 │
│  Common Pitfalls:                                               │
│  1. Infinite loop: wrong update or condition                    │
│  2. Off-by-one: boundary handling                               │
│  3. Overflow: use left + (right-left)/2 instead of (l+r)/2      │
│  4. Empty array: check length first                             │
│                                                                 │
│  Tips:                                                          │
│  • Always verify with test cases: empty, 1 element, 2 elements  │
│  • Check: target exists, target doesn't exist                   │
│  • Check: target at beginning, at end, in middle                │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### When to Use Binary Search

| Scenario | Approach |
|----------|----------|
| Sorted array | Direct binary search |
| Rotated sorted array | One pass, deciding which half is sorted at each step |
| Search on answer | Binary search on range |
| Find boundary | Lower/Upper bound |
| Peak finding | Compare with neighbor |
| Minimize maximum | Binary search on answer |

### Junior -> FAANG: Using the Template Comparison to Avoid Infinite Loops

The most dangerous moment in a binary search interview is when your first attempt causes an infinite loop and you do not know why. The diagnostic is simple: check whether `left` or `right` changes every iteration. If either can stay the same, you have an infinite loop.

For Template 2 (`left < right`): `right = mid` is safe because `mid < right` (since `mid = left + (right-left)/2` always rounds down, so `mid < right` when `left < right`). But `left = mid` is dangerous because when `right = left + 1`, `mid = left`, and `left = mid = left` makes no progress. Always write `left = mid + 1` in Template 2.

The "When to Use Binary Search" table above is an interview quick-reference. Note that the rotated-array row says one pass, not "find the pivot, then search". Locating the pivot first and then running a second search is a common instinct, and Section 77.2 walks through why it is the worse plan: it doubles the number of boundary conditions you have to get right for no gain in complexity. Deciding which half is sorted at each step does the whole job in a single loop.

Add two more rows to your mental version of the table: "monotone predicate on any ordered domain" maps to binary search on answer, and "find a value in a sorted sequence of unknown length" maps to exponential search, where you double the right bound until it overshoots the target and then binary search the bracketed range.

### Senior @ FAANG: Template Selection in Code Generation and Frameworks

Many frameworks generate binary search code from high-level specifications. Protocol buffer binary search over field tags, database B-tree node searches, and sorted set lookups are all generated by template instantiation. A senior engineer who designs such a framework must choose the correct template as the default and provide clear affordances for the alternative.

The Go standard library's `sort.Search` is Template 2 (lower bound, `left < right` equivalent) with the right bound as a half-open sentinel. This is the correct default because the most common production use case is insertion point or lower bound, not exact match.

Its midpoint line is worth reading, since it is a third answer to the overflow question this chapter keeps circling: `h := int(uint(i+j) >> 1)`. The sum is computed in `uint`, where a carry into the top bit is not overflow but an ordinary large value, and the logical shift divides it back into range. The result is correct even if `i+j` would have overflowed a signed `int`. It is a nice piece of engineering, and it is also a reminder that the library author thought about a case that, for `int` on a 64-bit machine, cannot actually arise. Standard library code is held to that standard. Your interview code is not, which is why `left + (right-left)/2` is the form to write. Exact match is then built on top: search for the lower bound and check equality. Teams that roll their own binary search and choose Template 1 by default encounter subtle bugs when they try to find the first occurrence of a duplicate value, because Template 1 with an early return can stop at any occurrence. Document the template choice in your framework's API and provide worked examples for both exact-match and boundary use cases.
