# Chapter 52I: Stream Processing & Change Data Capture

Consider a fraud detection system that runs nightly: it ingests the previous day's transactions in a batch, scores them, and flags suspicious activity by morning. By the time analysts review the results, the fraudster has long since moved on. Now consider the same system rebuilt on stream processing: every transaction is scored within 200 milliseconds of being written to the database, the fraud signal fires before the payment settles, and the customer's card is blocked before the second fraudulent charge lands. Stream processing replaces scheduled batch jobs with continuous, stateful pipelines that react to data as it changes, not hours after the fact.

Change Data Capture takes this philosophy one step further: instead of requiring application code to explicitly publish events, CDC reads the database's internal write-ahead log and converts every INSERT, UPDATE, and DELETE into a structured event stream. This approach solves the dual-write problem - the race condition where your application writes to a database and then tries to publish an event, risking inconsistency if the publish fails - because the database write is the only write, and CDC derives the event from it atomically. Tools like Debezium have made PostgreSQL WAL-based CDC production-ready, and Go consumers on Kafka can react to database changes with sub-second latency without any modification to the services that own those databases.

Go is an excellent language for building stream processors. Its goroutines and channels map directly onto the windowing and aggregation patterns that define stream processing: tumbling windows become time-bounded batches dispatched to worker goroutines, sliding windows map naturally onto ring buffers, and stateful aggregations fit cleanly into mutex-protected maps or external Redis state stores. This chapter covers the full spectrum - from implementing window aggregators in pure Go, to deploying Debezium connectors against a PostgreSQL WAL, to building end-to-end CDC pipelines that feed ClickHouse analytics and Elasticsearch search indexes in real time.

**What you'll learn in this chapter:**
- Stream processing fundamentals - tumbling, sliding, and session window types, watermark-based late data handling, and stateful vs stateless processing tradeoffs
- Implementing generic window aggregators in Go using goroutines, channels, and time-based tick triggers
- Understanding CDC concepts - log-based vs query-based CDC, PostgreSQL WAL internals, logical replication slots, and the Debezium change event envelope format
- Configuring Debezium Kafka Connect connectors against PostgreSQL for production CDC with schema evolution and snapshot handling
- Solving the dual-write problem with the transactional outbox pattern and CDC-based relay - the correct solution for reliable event publishing
- Building exactly-once CDC pipelines with idempotent sinks, deduplication windows, and offset checkpointing in Go consumers
- Designing end-to-end event-driven data pipelines: PostgreSQL → Debezium → Kafka → Go transformer → ClickHouse and Elasticsearch
- Handling schema changes, tombstone events, and consumer rebalancing without pipeline downtime

**Why this matters at scale:**
LinkedIn pioneered the CDC pattern to synchronize their primary MySQL databases with Elasticsearch search indexes and Samza stream processors - their Databus CDC system now underpins real-time people-search for over 900 million users. Stripe uses CDC-derived event streams to maintain consistent read models across their payment processing microservices, where the outbox pattern ensures that every payment state transition is reliably published to downstream fraud and analytics systems without two-phase commits.

### Junior -> FAANG: What Stream Processing and CDC Actually Mean for Your First Job

Most engineers encounter stream processing as an academic concept before they encounter it in production. The gap between "I understand event-time windowing" and "I can debug a stalled pipeline at 2 AM" is large, and FAANG interviewers know it.

Start by anchoring on the core vocabulary. A stream is just an unbounded sequence of events. A batch job is a bounded one. Stream processing is the discipline of computing over that unbounded sequence incrementally rather than waiting for all the data to arrive. CDC is the mechanism for generating that stream from a database without requiring application code to publish events explicitly.

The dual-write problem is the first concrete thing to understand deeply. When an application writes to a database and then tries to publish a Kafka event, those two operations are not atomic. One can succeed and the other can fail. The outbox pattern, where the event is written inside the same database transaction as the business data, is the industry-standard solution. Being able to explain why naive dual-writes are broken, draw the outbox table and relay, and articulate that the relay gives at-least-once delivery will put you in the top quartile of junior candidates.

For CDC specifically, understand the distinction between query-based polling and log-based CDC before your first interview. Polling misses deletes, is slow, and adds database load. Log-based CDC reads the write-ahead log, which is already being written, adds no meaningful database load, captures deletes and all intermediate states, and delivers events in commit order. Debezium is the tool that makes this practical for PostgreSQL, MySQL, MongoDB, and several other databases.

In your first job, you will almost certainly consume CDC events from a Kafka topic rather than configure Debezium yourself. Focus on the consumer side: parsing the Debezium envelope correctly, distinguishing `op: c/u/d/r`, handling tombstone messages, using `source.ts_ms` rather than `ts_ms` for event-time logic, and committing offsets only after writing to the downstream sink.

Common first-job mistakes: committing offsets before the sink write succeeds (causes data loss on crash), treating snapshot events (`op: r`) the same as insert events (causes constraint violations on non-upsert sinks), and ignoring replication slot lag until a disk-full incident.

### Senior @ FAANG: Platform Thinking, Governance, and the CDC Maturity Model

At the senior level, stream processing and CDC stop being individual-service concerns and become platform concerns. You are not building one CDC pipeline. You are deciding how CDC pipelines are built, monitored, and governed across dozens of teams.

**CDC as a platform capability, not a project.** The shift from "my team runs one Debezium connector" to "my platform manages 200 connectors" requires an operator model. Connectors must be provisioned via API or GitOps (Strimzi KafkaConnector CRDs or Confluent's control plane), not via manual REST calls. Schema registration must be enforced at connector bootstrap, not discovered after a breaking change lands in production. Connector health must feed a centralized SLO dashboard, not individual team Slack channels.

**The replication slot governance problem.** At scale, replication slot accumulation is the most dangerous failure mode in the CDC stack. A single abandoned slot can take down a primary PostgreSQL instance by filling the WAL directory. Platform-level governance means: (a) automated alerts on per-slot lag wired to on-call, not individual team dashboards, (b) `max_slot_wal_keep_size` configured defensively on every production PostgreSQL instance, (c) a runbook and automation for slot invalidation and connector recovery that any on-call can execute without subject-matter expertise, and (d) a policy requiring slot ownership to be declared in a team catalog so that orphaned slots can be attributed and cleaned up.

**Exactly-once: the governance question.** Most teams claim exactly-once semantics and mean at-least-once plus idempotent sinks. The distinction matters in regulated industries. For a payment processing pipeline, "we use idempotent upserts keyed by LSN" is a defensible answer under audit. "We enabled exactly-once mode" without being able to explain the sink's idempotency contract is not. A senior engineer defines the exactly-once contract for each pipeline segment and documents it: what is the deduplication key, what is the TTL on the dedup store relative to Kafka retention, and what happens when the dedup store is unavailable.

**Schema evolution governance.** At FAANG scale, schema changes in CDC topics affect downstream consumers across org boundaries. A column rename in a source database, without coordination, can silently break a consumer in another team's service. Platform-level governance means: (a) Schema Registry with enforced compatibility modes (`BACKWARD` at minimum, `FULL` preferred), (b) a consumer registry mapping which teams consume which topics so that schema change owners can notify affected consumers, (c) a schema change review process for breaking changes, analogous to API versioning, and (d) synthetic canary consumers that parse every CDC topic and alert on deserialization failures before production consumers see the issue.

**ADR framing: Go consumers vs Flink vs Kafka Streams.** When a team asks whether to build their streaming logic in Go or migrate to Flink, the decision record should articulate: (a) does the workload require durable cross-restart state? If yes, Go is not the right choice without explicit Redis or Postgres backing and a checkpoint/restore protocol, (b) does the workload require event-time windowed joins across multiple input streams? If yes, Flink, (c) is the team already JVM-based? Kafka Streams may minimize operational overhead, (d) is the transform stateless or lightly stateful with external state? Go or Benthos/Redpanda Connect. The correct answer is almost never "let's rewrite Flink in Go." The correct answer is "let's define the state boundary and pick the right runtime for each side of it."

**Multi-tenant CDC at platform scale.** The tenancy model of the source database drives the connector architecture. Shared-schema tenants (one table, `tenant_id` column) share a connector but risk noisy-neighbor saturation. Database-per-tenant requires a connector control plane that can provision, monitor, and tear down thousands of connectors automatically and that respects data-residency requirements for GDPR and similar regulations. Schema-per-tenant is a middle ground that simplifies residency but complicates schema evolution. A staff-level engineer drives the decision based on regulatory requirements, cost model, and the team's operational capacity, not on engineering preference alone.

**Bar-raiser signal: end-to-end latency SLO ownership.** At L6/L7, you do not just instrument the pipeline. You own the SLO and negotiate it with product. "99th percentile DB change visible in sink within 2 seconds" is a product SLO, not an engineering metric. You define the measurement methodology (synthetic heartbeat rows injected at the source, measured at the sink), the alert threshold, the escalation path for SLO breaches, and the architectural levers available to improve latency if the SLO degrades (reduce batch flush interval, increase consumer concurrency, add a dedicated connector for high-priority tables). Owning an SLO end-to-end, with instrumentable proof, is what separates L5 from L6 in this domain.
