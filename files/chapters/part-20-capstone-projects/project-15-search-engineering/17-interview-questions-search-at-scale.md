## Interview Questions: Search at Scale

**Q: How would you design the search infrastructure for a 500M-document corpus?**

A: The core architecture has three layers. (1) **Indexing pipeline**: Documents flow through a Kafka topic → Flink/Go consumer → Elasticsearch bulk indexer. Shard count = total data / 40 GB per shard ≈ 12, 20 primary shards for 500M average-sized docs. Use ILM for hot-warm-cold tiering. (2) **Query layer**: Stateless Go search API behind a load balancer, with an application-level cache (Redis) for the top 1% of queries that generate 50% of traffic. Elasticsearch `_search` with `preference=_local` to route replicas. Cross-cluster search for geo-distributed shards. (3) **Ranking**: First-pass BM25 retrieval of top-1000, then a second-pass GBDT reranker (leaves library) scoring top-50. Pre-compute static features (PageRank, CTR) nightly, and compute query-dependent features (BM25 scores) at query time. Target p99 latency < 200ms end-to-end.

**Q: How do you handle typo correction in a search system?**

A: Multiple layers work together. (1) **Offline dictionary**: Build a frequency-ranked vocabulary from your corpus. At query time, for each unknown query term, generate edit-distance-1 and edit-distance-2 candidates and rank by frequency. This handles most common typos in < 1ms. (2) **Trigram index**: Index every term as its set of character trigrams. A query term shares 2+ trigrams with its likely correction. Trigrams scale better than exhaustive edit-distance scan over large vocabularies. (3) **Elasticsearch `fuzziness: AUTO`**: Automatically applies edit distance 0, 1, or 2 based on query term length. Simple to deploy, with less control over candidate ranking. (4) **Neural spell correction**: A seq2seq model (BERT-based) that understands context - "apple iphone" correctly predicts "iphone" is a product name, not a typo. Use neural correction for the long tail where dictionary methods fail.

**Q: What is learning to rank and when would you use it?**

A: LTR replaces a hand-tuned scoring formula with a model trained on relevance labels. You extract a feature vector for each (query, document) pair - BM25 scores, click-through rate, document freshness, user affinity - and train a ranker (typically LambdaMART / LightGBM) to predict relevance. Use LTR when: (1) your product has accumulated enough click logs or human judgments to train reliably (typically 10K+ labeled query-doc pairs), (2) you have multiple heterogeneous signals that are hard to hand-tune together, (3) you've hit the ceiling on BM25 tuning and manual feature engineering. Avoid LTR for cold-start systems with no behavioral data - fallback to BM25 with manual boosts until you have training data.

**Q: How does Google's PageRank algorithm work conceptually?**

A: PageRank models the web as a directed graph where a link from page A to page B is a "vote" for B. A page's rank is the probability that a random surfer, following links at random, will land on that page. Formally: `PR(A) = (1-d)/N + d × Σ(PR(B)/OutLinks(B))` for all pages B linking to A. `d` is the damping factor (0.85 - the probability of following a link rather than jumping to a random page), and `N` is total pages. The algorithm iterates until convergence. Key properties: a link from a high-PR page is worth more than many links from low-PR pages, and pages with many outbound links dilute their votes. Modern Google uses PageRank as one of 200+ signals. It is less dominant than in 2003 but still signals document authority at web scale.

**Q: How would you implement search result deduplication?**

A: Deduplication removes near-duplicate documents that would waste result space. (1) **Exact deduplication**: Hash document content (SHA-256 of normalized body) and deduplicate at index time. (2) **Near-duplicate detection with SimHash**: Compute a 64-bit fingerprint where each bit is determined by the sign of a weighted sum of term feature vectors. Two documents with Hamming distance ≤ 3 on their SimHashes are near-duplicates. SimHash comparison is O(1) per pair after fingerprinting. (3) **URL canonicalization**: Normalize URLs (strip tracking params, lowercase, resolve redirects) to catch the same page indexed under multiple URLs. (4) **Clustering at query time**: For a result set, cluster by SimHash proximity and show only the highest-ranked representative from each cluster. This is how Google collapses "more results from example.com."

**Q: How do you measure search quality improvements?**

A: Use a two-stage evaluation strategy. **Offline (development)**: Maintain a judgment set of 500, 2000 (query, document, label) triples annotated by raters. After each ranking change, compute NDCG@10 and MRR against the judgment set. Require NDCG@10 improvement ≥ 0.002 (statistically meaningful) before considering deployment. **Online (validation)**: Run an A/B test with 10% of traffic on the new ranker for 1, 2 weeks. Primary success metric: session success rate (session with ≥1 long click). Guard metrics: CTR must not regress by more than 1%, zero-result rate must not increase. Require p < 0.05. Also track segment metrics (tail queries, mobile, non-English) to catch regressions in underrepresented groups.

**Q: What is semantic search and when does it outperform keyword search?**

A: Semantic search uses dense vector embeddings (e.g., from a bi-encoder like sentence-transformers) to match queries to documents by meaning rather than term overlap. A query for "cheap flights" matches "affordable airfare" even with zero shared terms. Implementation: embed all documents offline into 768-dimensional vectors and store in a vector index (Elasticsearch HNSW, Pinecone, Weaviate). At query time, embed the query and retrieve nearest neighbors by cosine similarity. Semantic search outperforms keyword search for: (1) paraphrase queries - user uses different vocabulary than the document, (2) concept queries - "ways to improve memory" vs. documents mentioning "mnemonic techniques", (3) question-answering - "who invented the telephone?" vs. documents mentioning Bell. Keyword search outperforms for: (1) exact lookups - product SKUs, error codes, proper names, (2) rare entities - terms not well represented in the embedding model's training data. **Hybrid search** (BM25 + dense retrieval, fused via Reciprocal Rank Fusion) combines both strengths and is the production benchmark for search engines.
