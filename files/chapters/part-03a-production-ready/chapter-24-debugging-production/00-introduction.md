# Chapter 24: Debugging Production Systems

*In production, you don't debug code. You debug systems.*

Production debugging is an entirely different discipline from development debugging. You cannot set a breakpoint in a service handling 50,000 requests per minute. You cannot restart the process to reproduce the issue, because the restart might be what clears it. You often cannot reproduce the problem locally at all, because it depends on the specific combination of load, timing, data state, and infrastructure configuration that exists only in production. What you can do is build the observability and diagnostic infrastructure in advance so that when an incident strikes, you are reading a rich stream of evidence rather than firing blind into a running system.

Go's runtime is unusually cooperative with live diagnostics. The `net/http/pprof` package registers diagnostic endpoints that can be enabled with a single import, exposing CPU profiles, heap profiles, goroutine stacks, mutex contention, and block profiles from a live service with no restart. Two of those need a deliberate opt-in: the mutex and block profiles record nothing until you call `runtime.SetMutexProfileFraction` and `runtime.SetBlockProfileRate`, so an untouched service returns an empty profile for both. A goroutine dump taken at the moment of a deadlock is often the only artifact needed to understand the root cause. A heap profile taken during a memory spike shows which call sites are allocating, allowing a precise fix rather than a speculative refactor, though it is a sample rather than a census: the runtime records roughly one allocation per 512KB by default. The execution tracer, run for even a few seconds against a production service, can reveal GC pressure, goroutine scheduling stalls, and network latency patterns invisible to all other tools.

The Delve debugger (`dlv`) extends these capabilities to scenarios that require interactive inspection: attaching to a running process to inspect live state, analyzing a core dump post-mortem after an OOM kill, setting conditional breakpoints in staging environments, and remote debugging through a secure tunnel. Distributed tracing ties the individual service view to the system view: a single trace ID threads through every log line, metric label, and span across all services involved in a slow request, collapsing the search space from "somewhere in 40 services" to "this specific database query in service X, called from handler Y, initiated by user Z." When these tools work together, the mean time to diagnose a production incident drops from hours to minutes.

**What you'll learn in this chapter:**

- How to safely expose `net/http/pprof` endpoints in production with authentication and rate limiting, and how to capture profiles during live incidents
- How to use `dlv attach` to connect to a running Go process, inspect variables, and evaluate expressions, and why attaching halts every goroutine until you detach
- How to analyze core dumps generated by an OOM-killed container using `dlv core` and extract goroutine stacks, heap state, and global variables
- How to read a goroutine dump (`SIGQUIT` or `/debug/pprof/goroutine`) to identify deadlocks, goroutine leaks, and blocking call sites
- How to implement a `/debug/diagnostics` endpoint that exposes runtime stats, build info, and configurable log-level changes without a restart
- How to correlate pprof profiles with distributed traces to identify which specific user requests are responsible for CPU or memory spikes
- How to set up continuous profiling with Pyroscope or Google Cloud Profiler to build a historical baseline that makes anomaly detection automatic
- How to use `GOMEMLIMIT` and `GOGC` tuning to reduce GC pressure in latency-sensitive services while you investigate the root cause of allocations, and why the old memory ballast trick has been obsolete since the soft memory limit landed in Go 1.19

**Why this matters at scale:**

Google's SRE book dedicates an entire chapter to the principle that production observability must be designed in, not added after incidents. Cloudflare engineers have publicly documented debugging live Go services under millions of requests per second using pprof endpoints captured during incident response windows. Infrastructure teams operating large Go fleets have built tooling that auto-analyzes goroutine dumps, precisely because a deadlock diagnosed by hand can burn hours that automated stack-pattern matching collapses to minutes. Datadog's Go agent team uses continuous profiling data to catch memory regressions in pre-production before they reach customer fleets.

**Prerequisites:** Chapters 1, 23. Familiarity with pprof basics, distributed tracing concepts, and Linux process signals.

**Chapter navigation by career stage.**

- **Junior or mid-level:** learn pprof, goroutine dumps, log-based debugging.
- **Senior:** diagnose production incidents, lead on-call, drive observability improvements.
- **Staff or Principal:** own the debugging infrastructure and make every service production-debuggable by default.

**Staff and Principal lens: debugging infrastructure is prevention cost.** The time spent building it is saved many times over during incidents. Teams that invest in debugging tooling resolve incidents in minutes. Teams that do not spend hours.
