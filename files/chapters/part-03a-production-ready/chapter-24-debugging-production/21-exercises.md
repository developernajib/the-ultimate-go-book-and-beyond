## Exercises

1. **Remote pprof Profiling**: Set up an HTTP server that registers `net/http/pprof` endpoints on a separate port, bound to `127.0.0.1:6060` rather than `:6060`. Implement a CPU-intensive handler, such as a recursive Fibonacci or a tight prime-sieve loop, that runs for at least 30 seconds when called. While the workload is running, capture a CPU profile with `go tool pprof http://localhost:6060/debug/pprof/profile?seconds=30`. Open the interactive prompt and use the `top`, `list`, and `web` commands to identify the hot function responsible for the most CPU time. Expected outcome: you should be able to name the exact function and line number consuming the majority of CPU cycles.

2. **Memory Leak Investigation**: Write a Go program that spawns a goroutine on each incoming HTTP request, appending to a package-level slice without ever releasing the memory (e.g., `cache = append(cache, make([]byte, 1<<20))`). Capture a heap profile before sending traffic (`go tool pprof .../heap`) and another after sending 100 requests. Use `pprof`'s `top` and `list` commands to diff the two profiles and identify the allocation site. Expected outcome: the `inuse_space` diff should clearly point to the appending goroutine as the leak source, and you should document which object type and call path is responsible.

3. **Distributed Tracing with OpenTelemetry**: Instrument a 3-service chain, an API gateway, a business-logic service, and a simulated database service, using the OpenTelemetry Go SDK (`go.opentelemetry.io/otel`). Propagate trace context via HTTP headers (`traceparent`) between each hop, creating a child span in each service. Remember to call `otel.SetTextMapPropagator` at startup: the global propagator is a no-op by default, and without it `Inject` writes no `traceparent` header at all and you get three disconnected single-span traces instead of one. Export spans to a local Jaeger v2 instance (`docker run -p 16686:16686 -p 4317:4317 jaegertracing/jaeger:2.20.0` - the v1 `all-in-one` image is deprecated). Send a request through the full chain and open the Jaeger UI to verify that all three spans share the same `traceID`, that the API span is the root, and that service and DB spans are correctly nested as children. Expected outcome: the Jaeger trace view shows a single trace with three spans in the correct parent-child hierarchy, with service names and durations clearly visible.

4. **Analyzing Goroutine Dumps**: Write a program that deliberately causes a goroutine leak, for example launching 10 goroutines that each block forever on an unbuffered channel that is never written to. After the goroutines are blocked, capture a goroutine dump via `curl http://localhost:6060/debug/pprof/goroutine?debug=2 > goroutine.txt` (or send `SIGQUIT` on Unix to get a stack trace to stderr). Open the dump and identify the blocking goroutines: note their state (`chan receive`), the file and line number where they are stuck, and how many goroutines share the same stack. Expected outcome: you should produce a written summary identifying the exact blocking call site and explaining why those goroutines will never unblock.

5. **Core Dump Analysis**: Getting a core out of a Go program requires two switches, and both are mandatory. `ulimit -c unlimited` lifts the kernel's core size limit, which defaults to 0 on most systems, and `GOTRACEBACK=crash` tells the Go runtime to re-raise the fatal signal so the kernel actually writes a dump instead of the runtime printing a traceback and calling `exit(2)`. Set only one and you get no file. Verify this for yourself: run the program with `ulimit -c unlimited` but without `GOTRACEBACK=crash`, confirm no core appears, then add `GOTRACEBACK=crash` and watch one show up.

    Build the binary without stripping, since `-ldflags="-s -w"` removes the DWARF that Delve needs. Trigger a deliberate panic after a few seconds (an out-of-bounds slice access in a goroutine works well). Load the result with `dlv core <binary> <corefile>` and use `goroutines`, `bt`, and `frame` to reconstruct the call stack at the moment of the crash. Note that `go tool pprof` is not an alternative here: it reads pprof profile files, not core dumps, and pointing it at a core will not work. Expected outcome: you identify the panicking goroutine, its function, the line number, and the variable state that caused the crash, all without re-running the program. If your dump also has to survive a container, check where the host's `/proc/sys/kernel/core_pattern` actually sends it.

6. **Production Incident Runbook**: Design a 5-step runbook for diagnosing a production latency spike using only pprof, distributed traces, and structured logs, with no code changes or restarts allowed. Step 1: capture a 30-second CPU profile and a heap profile from the live process to rule out CPU saturation or memory pressure. Step 2: query your tracing backend (Jaeger/Tempo) for the 99th-percentile slowest traces in the last 10 minutes and identify which span (service, endpoint, or DB call) accounts for the added latency. Step 3: pull structured logs correlated to the slow trace IDs and look for error rates, retries, or upstream timeouts. Step 4: capture a goroutine dump to check for goroutine pile-up or lock contention in the affected service. Step 5: check runtime metrics (GC pause time, goroutine count, heap size) via the `/debug/vars` or Prometheus endpoint to confirm whether the spike is resource-driven. Expected outcome: a written runbook document that, when followed, produces a definitive root-cause hypothesis (CPU-bound, memory pressure, slow dependency, goroutine leak, or GC pauses) with supporting evidence from each tool.
