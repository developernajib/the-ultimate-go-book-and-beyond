## Exercises

1. **Table-Driven Tests with Subtests**: Write a table-driven test suite for a `Calculate` function that handles addition, subtraction, multiplication, division, and modulo operations. Each test case must be a named struct with fields for `name`, `op`, `a`, `b`, `want`, and `wantErr`. Run every case as a named subtest using `t.Run(tc.name, ...)` so failures report the exact case. Include at least three edge cases per operation (zero values, negative numbers, overflow). Add a parallel subtest group using `t.Parallel()` inside the loop and verify the test output with `go test -v -run TestCalculate` shows each subtest name. Expected outcome: 30+ test cases, all passing, clearly identified by name on failure, with full parallel execution confirmed by the `-v` output.

2. **Testify Mocking with Interfaces**: Build an `OrderService` that depends on a `PaymentGateway` interface and an `InventoryRepository` interface. Using `github.com/stretchr/testify/mock`, generate mock implementations for both interfaces. Write unit tests for `PlaceOrder` covering: successful order, payment gateway returning an error, inventory repository returning insufficient stock, and a scenario where payment succeeds but inventory update fails (verify the payment is rolled back via a mock assertion). Use `mock.AssertExpectations(t)` at the end of every test. Expected outcome: four test cases with zero real I/O, all mock call expectations explicitly declared and verified, and a demonstrated rollback path confirmed by mock call counts.

3. **Integration Test with testcontainers-go**: Write an integration test for a `UserRepository` backed by PostgreSQL. Use `testcontainers-go` to start a real PostgreSQL container at test start, run your schema migrations against it, and tear it down when the test ends. The test must cover: `Create` (verify row exists via direct SQL query), `FindByID` (happy path and not-found error), `Update` (verify persisted changes), and `Delete` (verify row is gone). Use a build tag `//go:build integration` to gate the test so it only runs with `go test -tags integration ./...`. Expected outcome: a self-contained test file that requires no pre-existing database, runs green in CI with Docker available, and is skipped in standard `go test ./...` runs.

4. **Golden File Testing**: Implement a golden file test harness for an HTML report generator that takes a `ReportData` struct and produces an HTML string. Store expected outputs as `.golden` files under `testdata/`. On first run (or when `--update` flag is passed via `flag.Bool("update", false, "...")`), write actual output to the golden files. On subsequent runs, read the golden file and `assert.Equal` the actual against it. Write tests for at least four distinct report configurations (empty data, single record, large dataset, special characters requiring HTML escaping). Expected outcome: golden files committed to the repository, a failing test when the generator output changes unexpectedly, and a documented workflow for updating golden files when the output intentionally changes.

5. **Fuzz Testing a Parser**: Write a fuzz test for a custom CSV-like parser that accepts lines of the form `key=value,key2=value2`. The fuzz target must call `Parse(data)` and verify two invariants regardless of input: (1) the function never panics, and (2) if `Parse` returns a non-nil result, serializing it back with `Serialize(result)` and re-parsing must produce an identical map (round-trip property). Seed the fuzz corpus with at least five representative inputs including an empty string, a line with Unicode values, and a line with escaped commas. Run `go test -fuzz=FuzzParse -fuzztime=30s` and fix any crashes found. Note that only *failing* inputs are written to `testdata/fuzz/FuzzParse/`, which is what you commit. The corpus of interesting inputs the fuzzer builds while exploring lives in the build cache, not in your repository. Expected outcome: a fuzz target that passes a 30-second run without panics or round-trip violations, plus a committed `testdata/fuzz` entry for every crasher you found and fixed, each now serving as a permanent regression test.

6. **Benchmark Testing with Memory Allocation Tracking**: Write benchmark functions for three implementations of a `WordFrequency(text string) map[string]int` function: one using `strings.Split` with a plain map, one using `bufio.Scanner` with a `sync.Pool`-backed map, and one using a pre-allocated map with a single-pass byte scanner. Use `for b.Loop()` and `b.ReportAllocs()`. Do **not** add `b.ResetTimer()` or a sink variable: `b.Loop` already resets the timer on its first call and keeps the loop body alive, so both are redundant, and part of this exercise is proving that to yourself by removing them and confirming the numbers do not move. Then produce a real A/B comparison: capture a baseline (`go test -bench=. -benchmem -count=10 > old.txt`), change one implementation, capture `new.txt`, and run `benchstat old.txt new.txt`. Add a `BenchmarkWordFrequency_Parallel` variant using `b.RunParallel` for the fastest implementation. Expected outcome: a written analysis (as a code comment) explaining which implementation wins on ns/op and allocs/op, why the winner is faster at the memory level, and `benchstat` output that reports either a significant delta or `~` for noise.

7. **Testing HTTP Handlers with httptest**: Write a full test suite for a REST handler set (`POST /users`, `GET /users/{id}`, `PUT /users/{id}`, `DELETE /users/{id}`) using only `net/http/httptest`, with no real server and no open ports. Each handler test must: construct an `httptest.NewRecorder()`, build a request with `httptest.NewRequest`, inject a mock service via the handler's closure or struct, call the handler directly, and assert on the response status code, `Content-Type` header, and JSON body using `json.Unmarshal`. Add a test for middleware (authentication via `Authorization` header) that verifies protected routes return `401` when the header is missing and `200` when it is valid. Expected outcome: 12+ handler test cases covering happy paths and error paths, zero open network connections during tests, all assertions using `t.Fatal` or `testify/assert`, and full coverage of every handler branch.

The key insight is that good tests are an investment in code quality. Organizations that ship reliably at scale invest heavily in testing infrastructure, and they do it because it pays back in reliability and development speed, not out of principle.

### Senior at FAANG Track

8. **Test-suite economics audit.** For one production service, measure wall-clock CI time, flake rate, and meaningful coverage. Propose specific improvements. Track against targets for a quarter.

9. **`testing/synctest` migration.** Find tests that use `time.Sleep` or real-time waits. Migrate to `testing/synctest` where applicable. Measure the speedup.

10. **Integration-test container sharing.** For a service's integration tests, refactor to share a single container across all tests in a package. Measure the speedup.

### Staff / Principal Track

11. **Org-wide test convention.** Write the org's testing guide: naming conventions, mocking policy, coverage expectations, flake response. Publish and maintain.

12. **Shared test-infrastructure library.** Build the org's reusable test helpers: database setup, HTTP builders, mock clock, common assertions. Drive adoption across services.

13. **CI test-time SLO.** Set and enforce CI wall-clock time targets per service tier. Investigate regressions immediately. Include in on-call responsibilities.

14. **Flake-rate tracking.** Implement automatic detection of flaky tests across the org's CI. Quarantine flakes, assign owners, and track resolution. Report flake rate as a team health metric.

15. **Testing incidents.** When a production incident traces to a missing test, document it. Add the test. Share the postmortem. Over years, the org accumulates teaching material that prevents similar incidents.
