## Key Design Decisions

These decisions reflect the fundamental tension in exchange design: the matching engine must be as fast as possible (sub-millisecond), but it must also be perfectly correct (no lost orders, deterministic replay). Every decision below resolves this tension by isolating the fast path from anything that could introduce variability.

**One Goroutine Per Symbol:** Each security's order book runs in a dedicated goroutine consuming from a dedicated channel. No locking is needed within a symbol because only one goroutine ever touches that order book. With 10,000 listed securities, this means 10,000 goroutines, trivial for Go's scheduler, which handles millions of goroutines efficiently. The key benefit is that orders for AAPL never contend with orders for GOOGL for lock access. Cross-symbol order routing needs no lock at all: the symbol-to-channel map is built once at startup and never written again, so `SubmitOrder` reads it freely and sends the order into the channel without touching a global lock.

The single-writer property is not just a performance trick, it is what makes the engine correct. Two goroutines matching the same book concurrently would race for the same resting quantity, and price-time priority would depend on which one won, which is precisely the fairness guarantee an exchange sells. So the parallelism is per symbol and never within one. This design scales linearly: to handle more symbols, you add more nodes with a deterministic hash-based routing scheme (`hash(symbol) % node_count`).

**Write-Ahead Log (WAL):** Every order is persisted to the WAL before matching begins. On recovery, the system replays the WAL from the last snapshot to reconstruct the exact in-memory order book state. This guarantees zero order loss even if the process crashes mid-match. The WAL write uses `O_DIRECT` and `fsync` to bypass the OS page cache and ensure the data hits stable storage, which adds roughly 50 microseconds of latency on NVMe SSDs. This is the only disk I/O on the critical path, and it is the unavoidable cost of durability. Periodic snapshots (serializing the full order book state to disk) limit the amount of WAL that must be replayed on recovery. The snapshot interval is not a free parameter, it falls directly out of the recovery target, and the arithmetic is worth doing out loud because interviewers ask. Replay runs at roughly 500,000 entries per second (each entry is a parse plus a heap operation). The budget is 30 seconds, and loading the 2GB snapshot itself costs about 5, which leaves 25 seconds, or 12.5 million entries. At a peak of 1M orders/sec, that is a snapshot every 10 seconds. Hourly snapshots would leave 3.6 billion entries and 720GB of WAL behind, and recovery would take two hours rather than half a minute.

**Price in Integer Cents:** Floating-point arithmetic introduces rounding inconsistencies that are unacceptable in financial systems. Adding a penny to a nickel, `0.05 + 0.01`, produces `0.060000000000000005` in `float64`, which is not the same value as `0.06`, so two orders that display an identical price are not at an identical price as far as the engine is concerned. (Reach for the famous `0.1 + 0.2` here and be careful: written as literals in Go it compares equal to `0.3`, because untyped constants are folded exactly at compile time. The inequality only appears once the values live in `float64` variables at runtime.) Stock prices are stored as `int64` values representing the smallest price increment (cents for US equities, ticks for futures). This ensures that matching is deterministic across nodes, the same sequence of orders will always produce the same sequence of trades, which is critical for the hot standby to stay in sync. The trade-off is that display formatting must convert cents back to dollars, but this is a trivial presentation concern.

**Market Data Lossy OK:** Order book updates are published at high frequency (potentially hundreds per second per symbol) and are designed to tolerate message loss. If a subscriber's send buffer is full, the update is dropped rather than blocking the broadcast loop for all subscribers. This is acceptable because each order book update in the reference implementation is a complete snapshot of the current state, not a delta, so a missed update is simply superseded by the next one. That property is what buys the right to drop messages, and it is worth being precise about: the moment a feed switches to incremental deltas for bandwidth, as production feeds do, dropping a message silently corrupts the client's book. Delta feeds therefore carry a per-symbol sequence number so a client can detect the gap and re-sync from a snapshot instead of trading on a book it has quietly reassembled wrong. Trade executions, by contrast, are guaranteed delivery through a separate persistent channel (Kafka), because trades have legal and financial significance and cannot be missed.
