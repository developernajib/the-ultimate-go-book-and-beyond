## Common Mistakes and How to Avoid Them

These are the pitfalls that interviewers see repeatedly in video streaming design answers. Each mistake reveals a gap in understanding scale, and avoiding them signals that you have thought deeply about production realities. Review this list before your interview and make sure your design does not fall into any of these traps.

1. **Uploading through API servers**, at 500 hours per minute of video, routing raw uploads through your API tier would require dozens of 10Gbps servers dedicated solely to proxying bytes. Use presigned S3 URLs so clients upload directly to object storage.
2. **Ignoring CDN**, serving 208 Tbps of video bandwidth from origin servers is physically impossible. Over 95% of video segment requests must be served from CDN edge nodes, with only cache misses reaching origin.
3. **Single quality level**, without adaptive bitrate streaming, users on slow connections buffer constantly while users on fast connections get unnecessarily low quality. Transcode to 6 quality levels and use HLS/DASH for per-segment quality switching.
4. **Synchronous transcoding**, a single 1-hour video takes minutes to hours to transcode. Running this inside an API request handler would time out immediately. Use SQS-driven worker fleets that process jobs asynchronously.
5. **Strong consistency for view counts**, at 1 billion views per day, requiring real-time strongly consistent counters would need distributed locks on every view event. Use Kafka-based streaming aggregation with 30-second batch updates.
6. **Single-pass recommendations**, applying an expensive ranking model to a catalog of hundreds of millions of videos on every request is not affordable at 11,574 QPS. Use a two-stage pipeline: cheap candidate generation narrows to ~500, then a ranker predicting expected watch time selects the top 20. Make sure the two stages score differently, or the second one is just the first one again at higher cost.
7. **No DRM for Netflix model**, without Widevine, FairPlay, or PlayReady, premium content can be downloaded and redistributed. DRM is a contractual requirement from content licensors, not an optional feature. The opposite mistake is claiming DRM makes content uncopyable, which it does not.
8. **Equal popularity assumption**, view counts follow a steep power law: a small fraction of the catalog absorbs the large majority of views, while a long tail is watched almost never. CDN caching, transcoding priority, and storage tiering all have to differentiate between viral, popular, and long-tail content. Quote a specific split only if you can source it, and otherwise reason from the shape of the distribution, which is what actually drives the design.
9. **Flat S3 key structure**, storing every segment in a flat namespace makes prefix-based operations (listing, lifecycle rules, invalidation) slow or impossible. Organize keys as `videos/{video_id}/{quality}/seg_{n}.m4s` so one lifecycle rule can tier a whole rung.
11. **A key layout the writer and reader disagree about**, the transcoder writes one path and the player requests another. Nothing catches this: the pipeline reports success, the job is marked complete, the dashboards are green, and every single stream 404s. Derive keys from one shared helper called by both sides, and make an end-to-end playback check part of the pipeline rather than trusting that both halves agree.
10. **No content moderation pipeline**, both YouTube and Netflix face regulatory requirements (CSAM detection, copyright enforcement). Content moderation must run as an async post-upload stage before setting a video's status to "ready."
