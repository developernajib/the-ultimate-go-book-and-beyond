# System Design: YouTube / Netflix - Video Streaming Platform

> Video streaming is the perfect test of distributed systems. A dropped frame is a user complaint. A dropped second is a churned subscriber.

Video streaming is the most bandwidth-intensive system design problem you will encounter. Two public figures anchor the exercise: YouTube has said it serves over 1 billion hours of video per day, and it has long reported roughly 500 hours of new video uploaded every minute. Everything else in this chapter is derived from those two numbers plus stated assumptions, which is exactly how you should handle capacity questions in an interview. Transcoding each uploaded hour into 6 quality levels (240p through 4K) produces roughly 8.6 petabytes of new storage per day. At an average of 5 Mbps per stream the model works out to about 208 terabits per second of sustained CDN egress, spread across a global edge footprint.

The three hardest engineering problems are: (1) the transcoding pipeline, which must absorb 1.8 million seconds of raw video every minute (30,000 seconds arriving per second) using 15,000 parallel workers while remaining fault-tolerant to individual worker failures, (2) adaptive bitrate streaming with HLS/DASH, where 6-second video segments must be independently cacheable at CDN edges while allowing seamless quality switching based on the viewer's bandwidth, and (3) the recommendation engine, which must rank hundreds of millions of videos per user at 11,574 queries per second using a two-stage pipeline that narrows candidates from millions to 20.

This chapter contrasts YouTube's reactive CDN caching with Netflix's predictive pre-loading strategy, the approach Netflix's Open Connect network is publicly built around. You will implement the full upload-to-playback pipeline in Go: presigned S3 uploads, FFmpeg-based transcoding workers driven by SQS, HLS manifest generation, signed CDN token streaming, and a two-stage recommendation engine using collaborative filtering and embedding similarity. The design decisions section explains why each architectural choice was made and what you sacrifice in return.

The chapter opens with learning objectives and a problem statement, then moves into capacity estimation to quantify storage, bandwidth, and transcoding throughput. The high-level architecture section lays out the major services before dedicated sections cover the video upload and processing pipeline, Netflix-specific predictive CDN pre-loading, and the recommendation engine. Database schema and key design decisions follow, explaining the data model and the trade-offs behind it. The API design section defines the upload, playback, and search interfaces, and four deep dives explore content moderation, adaptive bitrate client algorithms, view count aggregation, and DRM with content protection. The chapter continues with scaling strategy, failure handling, an interview scoring rubric, and common mistakes, then closes with follow-up questions, Redis data structure patterns, production Go implementations of the video search, notification, and analytics event pipeline services, extended SQL schemas for comments and interactions, Cassandra watch history models, multi-region deployment, production considerations, a performance testing checklist, scale and technology reference summaries, and extended scenarios covering live streaming and emerging markets.
