# System Design: Google Docs - Collaborative Document Editing

> The hard part of collaborative editing isn't the algorithm, it's making conflict resolution invisible to users while 50 people type simultaneously.

Real-time collaborative editing is one of the few system design problems where correctness is non-negotiable and the user's tolerance for latency is measured in individual keystrokes. With 1 billion documents, 100 million daily users, and the potential for 50+ simultaneous editors per document, the system must process and broadcast every character insertion within 50ms or the editing experience feels laggy. At 200K concurrently edited documents generating 2 million operations per second, the OT (Operational Transform) engine must guarantee convergence, every participant must see exactly the same document state, even when operations arrive out of order from different network paths.

The three hardest engineering challenges are: (1) implementing a correct OT transform function that satisfies the convergence property (applying A then transform(B, A) must equal applying B then transform(A, B)) across all operation type combinations, (2) maintaining document server stickiness via consistent hashing so that each document has a single authoritative server without requiring distributed locking, and (3) handling offline editing where a user accumulates hundreds of local operations that must be transformed against everything that happened on the server during the disconnection.

This chapter covers the full design. Section 1 defines the problem scope and scale requirements. Section 2 provides capacity estimation for documents, operations throughput, and storage. Section 3 presents the stateful server architecture with consistent hashing. Sections 4-5 detail the core OT engine implementation and database schema. Section 6 covers key design decisions (OT vs CRDT, server authority, document stickiness). Section 7 addresses interview follow-ups. Section 9 defines the REST and WebSocket API. The deep dives in Sections 10-12 explore CRDTs as an alternative to OT, offline editing and sync, and comment anchoring. Sections 13-14 cover scaling strategy and failure handling. Sections 15-17 provide the scoring rubric, common mistakes, and follow-up questions. The remaining sections cover Redis data structures, production Go implementations for document export, suggestion mode, search, and cursor broadcasting, extended schemas, multi-region deployment, and performance testing.
