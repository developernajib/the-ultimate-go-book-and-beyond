## Key Design Decisions

Each decision below shapes a different aspect of the system's behavior. The OT-vs-CRDT choice determines the conflict resolution algorithm. Server authority determines the consistency model. Stickiness determines the partitioning strategy. Together they form a coherent design where trade-offs reinforce each other.

**OT vs CRDT:** Google Docs uses Operational Transform (OT). CRDTs (like Yjs/Automerge) are simpler to implement because they do not require a central server, any two replicas can merge independently. However, CRDTs have higher memory overhead for complex rich text (each character carries a unique ID and tombstone metadata), and they are harder to implement correctly for rich text with formatting attributes. OT requires a central server to serialize operations, which is acceptable given Google Docs' server-centric architecture. The trade-off: OT is harder to prove correct (the transform function must handle all operation-type combinations), but it produces smaller operation payloads and lower memory overhead.

**Server Authority:** All operations pass through the document server. The server serializes concurrent ops, applies OT transforms, and broadcasts the transformed ops to all clients. Clients apply their own operations optimistically to the local copy for instant feedback, then reconcile when the server responds with the canonical result. This means the server's operation order is the ground truth, if two clients disagree, the server's version wins.

**Document Server Stickiness:** Consistent hashing routes all requests for a `doc_id` to the same server. This avoids distributed locking entirely, the server is the single authority for its documents. If a server fails, the consistent hash ring redistributes its documents to other servers, and clients reconnect automatically. The new server rebuilds document state from the snapshot + operation log. The downside is that hot documents (viral shared docs with 50+ editors) cannot be load-balanced across servers, but even 50 editors typing at 3 ops/sec generate only about 150 ops/sec for that document, well within a single server's capacity.

**Snapshot + Op Log:** Full document state is saved to S3 every 30 seconds (or every 1000 ops, whichever comes first). The operation log stores every individual operation between snapshots. Recovery loads the latest snapshot and replays all ops since that snapshot's revision. This is the same pattern as database WAL (Write-Ahead Log) + checkpoints: snapshots bound recovery time, while the operation log provides complete durability. Without periodic snapshots, recovery would require replaying the entire document history from creation.

**Offline Editing:** The client queues operations locally while disconnected, each tagged with its base revision (the last server revision the client saw). On reconnect, the client sends all queued ops to the server. The server transforms them against every operation applied since that base revision, applies the transformed result, and sends back the full set of catch-up ops so the client can reconcile its local state. This works because OT's convergence property guarantees that the transform produces the correct result regardless of how many operations have accumulated during the disconnect.
