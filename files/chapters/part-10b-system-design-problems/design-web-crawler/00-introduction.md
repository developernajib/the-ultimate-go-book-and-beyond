# System Design: Web Crawler - Large-Scale Internet Crawling

> The indexable web runs to roughly 10 billion pages. A crawler that processes 10K pages/sec needs about 11.5 days for a full pass. The real challenge is doing it politely, without overwhelming any single site.

A web crawler is a fundamentally adversarial system: you are downloading content from millions of servers that did not ask to be crawled, at a throughput (10,000 pages per second) that could easily constitute a denial-of-service attack if not carefully throttled. The design must balance three conflicting goals: high throughput across the internet, strict politeness toward individual domains (max 1 request per second per site), and efficient deduplication across billions of URLs and pages.

The scale numbers frame the challenge. Ten billion pages at 100KB average yields 1 petabyte of raw HTML (approximately 200TB compressed). The URL frontier holds roughly 1 billion queued URLs at any given time. A Bloom filter provides approximate URL deduplication in 12GB of memory versus 1TB for an exact set. The 200-worker fleet sustains 10K pages per second, with each worker handling 50 concurrent goroutines. A full crawl pass takes approximately 11.5 days and costs roughly $22,000 to run on AWS, at about $1,900 per day. Notably, none of that is bandwidth: AWS charges nothing for inbound data transfer, so the 86TB a day this crawler pulls down is free, unless you route it through a NAT Gateway and turn it into the largest line on the bill.

The two hardest engineering problems are politeness-constrained parallelism and duplicate detection. Politeness means you achieve throughput by crawling many domains in parallel, not by hammering individual sites faster. Kafka partitioning by domain hash makes this natural. Duplicate detection operates at two levels: URL dedup (Bloom filter plus Redis) prevents re-fetching visited pages, while content dedup (SimHash fingerprinting with banding) catches mirror sites serving identical text under different URLs.
