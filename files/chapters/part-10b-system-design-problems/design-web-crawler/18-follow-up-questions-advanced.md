## Follow-up Questions, Advanced

These questions probe areas beyond the core crawl loop. Strong answers demonstrate awareness of real-world constraints like JavaScript rendering costs, deep web discovery, and operational measurement.

**Q: How handle JavaScript-rendered pages (SPAs)?**
A headless browser (Puppeteer or Playwright) renders JavaScript but is approximately 10x slower than a plain HTTP fetch (5 seconds versus 500 milliseconds per page). The practical approach is a two-pass strategy: first, fetch raw HTML with a standard HTTP client. If the extracted body text is empty or below a word-count threshold (indicating JS rendering is required), queue the URL for a second pass through the headless browser pool. In practice, only 10-20% of pages require rendering, so the headless pool can be much smaller than the main worker fleet. The headless workers run as a separate service with their own scaling and resource limits (each Chromium instance uses approximately 200MB of RAM).

**Q: How crawl the deep web (behind search forms)?**
Deep web content is not linked from any public page, so traditional link-following cannot discover it. The approach is form detection and query generation: identify HTML forms on pages, classify their purpose (search, date picker, location selector), and submit them with dictionary-generated inputs. API discovery via JavaScript file parsing can reveal hidden endpoints. Sitemap.xml files provide structured deep URL lists for sites that publish them, and they are the polite option, so exhaust them first. This is a separate, specialized crawler with much lower throughput (hundreds of pages per second) because form submission and response parsing are more expensive than simple page fetching.

Say the constraint out loud in an interview, because this is the answer where a candidate can talk themselves into describing an attack. **Submit `GET` forms only, never `POST`.** `GET` is defined as safe and idempotent, while `POST` is how the web spells "change something": submitting POST forms with generated inputs is how a crawler creates accounts, posts comments, or fires off orders. Robots rules still apply to the resulting URLs, `nofollow` on a form still means what it says, generated queries still count against the domain's politeness budget, and dictionary-driven query generation against a site's search endpoint is a load pattern the operator did not sign up for, so it needs a tighter rate limit than ordinary crawling and not a looser one. The line between deep-web discovery and enumerating someone's database is intent and restraint.

**Q: How build a focused/topic crawler?**
An ML relevance classifier scores each crawled page on a scale from 0.0 to 1.0 for the target topic. The crawler only follows outbound links from pages that score above 0.5, pruning irrelevant branches early. A diminishing-returns heuristic tracks per-domain relevance: if the last 100 pages from a domain scored below 0.3, the entire domain is deprioritized in the frontier. This focuses crawl bandwidth on the most productive domains and avoids wasting resources on sites that are tangentially linked but not topically relevant.

**Q: How handle geo-distributed crawling?**
Deploy worker fleets in US, EU, and Asia regions. Regional workers prefer domains geographically local to their region, reducing network latency and avoiding geo-IP-based content blocking. The URL frontier remains centralized (or uses cross-region Kafka replication) to prevent duplicate crawling across regions. CDN edge caching means regional workers often get faster responses from nearby CDN nodes. The trade-off is operational complexity: managing crawler fleets across three regions requires coordinated deployment, monitoring, and capacity planning.

**Q: How measure crawler effectiveness?**
Five key metrics: (1) Coverage, compare your crawled URL set against the Common Crawl index to measure what percentage of the known web you have reached. (2) Freshness, the time between when a page changes and when the crawler detects the change, measured by comparing content hashes across consecutive visits. Be honest about what that measurement can see: consecutive hashes tell you a page changed *somewhere* between two visits, not when, so the recrawl interval bounds your resolution and you are really measuring detection lag, an upper bound on staleness. `Last-Modified` and `ETag` tighten it where servers set them truthfully, which many do not. (3) Throughput, actual pages per second versus target (10K). (4) Error rate, percentage of fetch attempts that fail, broken down by error type (timeout, DNS, HTTP error, parse failure). (5) Duplicate rate, percentage of crawled pages that are near-duplicates of previously indexed content (should be below 5% after SimHash filtering). Downstream, search relevance metrics (NDCG, mean reciprocal rank) measure whether the crawled content actually improves search quality.
