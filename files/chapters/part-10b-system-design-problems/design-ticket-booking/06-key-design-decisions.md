## Key Design Decisions

Every decision in this system is shaped by the extreme traffic asymmetry between normal operation and sale events. The choices below are what you should be prepared to defend in an interview, including the trade-offs you are accepting.

**Virtual Queue:** The virtual queue is THE key design element, without it, 5 million users hitting the booking service simultaneously would exhaust database connections and cause cascading failures within seconds. A Redis sorted set provides FIFO ordering with O(log N) insertion and deduplication (each user can only enter once). The admission controller releases users in controlled batches, matching the downstream booking service's actual throughput capacity. Users receive position updates via WebSocket or polling with signed tokens that prevent queue-jumping. The trade-off is user experience: waiting in a queue is not ideal, but it is far better than a crashed site that serves no one.

**Seat Hold with TTL:** When a user selects seats, they are "held" in Redis with a 10-minute TTL rather than locked in the database. This is critical because holding a database row lock open across a user's checkout, which can last minutes and includes a call out to a payment processor, converts every popular seat into a contention point and every abandoned cart into a stuck transaction. A Lua script makes check-and-hold atomic: it runs as one uninterruptible unit, so it verifies availability and claims the seats with no window in between for a second caller to slip through.

Be precise about what the TTL does, because this is where the design most often goes wrong on a whiteboard. Expiring the *hold key* does not return seats to inventory. The seat map is a separate Redis hash, and a lapsed TTL deletes the hold while leaving every one of its seats reading `held` forever. That is why the design carries an expiry index and a reaper: the sweep is what actually restores inventory. A system that relies on the TTL alone quietly bleeds seats all sale long and then displays a sold-out banner over a half-empty arena.

**Oversell Prevention:** Two layers, and they are not equal. Redis is the fast path: the Lua script means only one of ten thousand callers racing for a seat gets the hold, and the rest are rejected without ever reaching PostgreSQL. That is a throughput property. It is not a guarantee, because holds expire, get reaped, and are lost outright if a Redis replica is promoted mid-sale.

The guarantee is PostgreSQL: `UPDATE seats SET status = 'sold', booking_id = $1 WHERE event_id = $2 AND id = ANY($3) AND status = 'available'`. The row lock serializes concurrent transactions, the loser re-evaluates the predicate against the committed row, sees `sold`, and gets `RowsAffected = 0`. Note the predicate is `status = 'available'`: there is no `held` state and no `held_by` column in the database, because the hold never lived there. A conditional update against a state nothing writes matches zero rows and fails every booking in the system.

Worth naming the reason this is enough here, since the same reasoning does not transfer to every booking problem. Seat rows are created up front with the event, so the row you need to lock always exists. In a design where the unit of inventory is a *range* rather than a row, such as booking a room across dates, there is no row yet to lock and `SELECT ... FOR UPDATE` cannot prevent two transactions from inserting overlapping reservations. That problem needs an exclusion constraint or an advisory lock. Seats are the easy case, and it is worth knowing why.

**Barcode Security:** Static QR codes can be screenshotted and duplicated. HMAC-signed barcodes bind the ticket ID, event ID, and owner into one signature, so a barcode cannot be forged or re-pointed at a different event without the server key. Venue scanners verify the HMAC in constant time before admission, then burn the ticket with an update conditional on `is_used = false`: two gates scanning the same screenshot at the same moment resolve to exactly one admission, whereas reading the flag and then writing it lets both people in. For high-value events, SafeTix-style dynamic QR codes that rotate on a short time window make screenshots worthless within seconds.
