## Key Design Decisions

These decisions directly determine GPU cost efficiency and user-perceived latency. Each one addresses a fundamental constraint of LLM inference that does not exist in traditional web serving.

**Continuous Batching:** Unlike static batching (wait for N requests, then process all at once), continuous batching adds new requests to the decode batch as others finish. The GPU stays busy processing tokens from all active sequences simultaneously, new requests slip into the batch when a slot opens because another request completed its generation. This is possible because the decode phase (generating one token at a time) is memory-bandwidth-bound rather than compute-bound, so adding more sequences to a batch has minimal impact on per-token latency until memory bandwidth saturates. The result is 5-10x better GPU utilization compared to naive batching. Without it, the GPU sits idle between batches while waiting for enough requests to fill the next batch, an unacceptable waste at $2-8/hour per GPU.

**KV Cache Prefix Sharing:** Many API consumers share identical system prompts (for example, "You are a helpful coding assistant" or a long set of instructions). The system caches the KV computation for these shared prefixes, keyed by SHA-256 hash of the exact token sequence. When a new request arrives with a known prefix, the cached KV state is loaded from NVMe SSD (a ~1,200-token system prompt produces roughly 400MB of KV state, which loads in about 12ms at 32GB/s) instead of being recomputed on the GPU (which would take hundreds of milliseconds). This saves 30-50% of compute for high-reuse prefixes. The cache uses exact prefix matching rather than fuzzy matching to guarantee mathematical equivalence between cached and fresh computation, any token difference would invalidate the entire KV state.

**Speculative Decoding:** A small "draft" model (7B parameters) generates N candidate tokens quickly. The large "oracle" model (70B) then verifies all N tokens in a single forward pass (parallel acceptance/rejection). If all N tokens are accepted, the system achieved N tokens of progress for the cost of one oracle forward pass, a 3-5x speedup. If some tokens are rejected, the system falls back to the first rejected position and generates one correct token from the oracle. The net result is a 2-3x speedup for many query types, with no quality degradation because the oracle model always has the final say. The trade-off is additional complexity and the cost of running two models, but the throughput gain more than compensates.

**Request Priority Queue:** Free-tier users are placed in a low-priority queue and may wait during peak traffic. Paid-tier users are placed in a high-priority queue and are served first. Implemented as two Redis lists per model: `queue:high:{model}` and `queue:low:{model}`. Workers drain the high-priority queue completely before pulling from the low-priority queue. This ensures paid customers always experience low latency while free-tier traffic fills GPU capacity that would otherwise be idle. The priority system also enables more aggressive cost optimization: free-tier requests can be batched into larger, more efficient batches since they tolerate higher latency.
