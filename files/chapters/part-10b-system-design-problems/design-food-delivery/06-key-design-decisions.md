## Key Design Decisions

Each decision below addresses a specific coordination challenge in the three-party system. Understanding why each trade-off was made, not just what was chosen, is what interviewers look for.

**Order State Machine:** The state machine is the backbone of the entire system. Ten states with explicitly defined valid transitions prevent bugs like charging a customer for an order the restaurant never accepted, or dispatching a driver to a canceled order. Every transition is logged in the `order_status_history` table for debugging and dispute resolution. Status updates are broadcast via Kafka so downstream services (notifications, tracking, analytics) react independently without coupling to the Order Service. The trade-off is complexity: adding a new state requires updating the transition map, all downstream consumers, and the client apps.

**Two-Phase Driver Dispatch:** The dispatch service first identifies candidates using a Redis GEO radius search (a geohash-indexed sorted set query), then scores them on a weighted combination of proximity (60%), driver rating (30%), and historical acceptance rate (10%). The top-scoring driver receives a time-limited offer with a 30-second acceptance window. If the driver declines or times out, the offer passes to the next candidate. This two-phase approach prevents "ghost assignments" where a driver is assigned but never picks up the order. The trade-off is added latency: the 30-second timeout per attempt means worst-case dispatch could take 90 seconds across three attempts. The search radius doubles on each retry (2km, 4km, 8km) to increase the candidate pool.

**ETA Calculation:** The ETA combines three independent time estimates: restaurant prep time (predicted by an ML model using restaurant history, queue depth, item complexity, and time of day), driver-to-restaurant travel time (from a routing API with real-time traffic), and restaurant-to-customer travel time (also from the routing API). The critical insight is that driver travel and food preparation happen in parallel, so total ETA equals `max(prep_time, driver_to_restaurant) + restaurant_to_customer + buffer` rather than the sum of all three. A historical error buffer (minimum 2 minutes) accounts for systematic under-prediction. The ETA updates continuously as the driver moves, using live GPS data to recalculate remaining travel time.

**Location Update Cadence:** The driver app sends GPS coordinates every 4 seconds while on an active delivery, producing 50K writes per second system-wide. Redis GEO stores each update for spatial indexing, and a separate Redis hash with a 30-second TTL tracks whether the driver is still online. If the TTL expires without a fresh update, a cleanup job removes the driver from the active pool. WebSocket connections push location updates to tracking customers immediately on receipt. The 4-second interval balances tracking smoothness against battery drain on the driver's phone, more frequent updates drain the battery faster without meaningfully improving the customer experience.
