## Key Design Decisions

Every decision in a payment system must be evaluated for its impact on correctness first, performance second. A fast system that occasionally double-charges customers is worthless. These decisions reflect the principle that it is better to reject an ambiguous transaction than to risk processing it twice.

**Idempotency:** Every payment request requires a merchant-provided idempotency key, which is a unique string (typically a UUID) that the merchant generates on their side. If the merchant retries a request with the same key, because their initial request timed out and they do not know whether the charge succeeded, the system returns the cached result from Redis without re-processing. A distributed lock (Redis `SETNX` with 30-second TTL) collapses two concurrent retries of the same key so they cannot both miss the cache and both charge. Be precise about what that lock is worth, because interviewers probe here: a lock with a TTL is not a correctness guarantee, since a slow request can still be running when its lease expires. The guarantee is the `UNIQUE` constraint on the idempotency key in PostgreSQL, which a duplicate hits regardless of what Redis did. Redis makes the common case fast and quiet, and the database makes the rare case correct. Cached results expire after 24 hours, which is long enough to cover any realistic retry while keeping the cache bounded, but the key records themselves are kept, so a key reused months later is still recognized rather than silently treated as a new charge.

**Exactly-Once Semantics:** The three-phase approach works as follows: (1) write the transaction to PostgreSQL as "pending" before making any external call, this is the point of no return, (2) call the card processor's charge API, which may succeed, fail, or timeout, (3) update the transaction status to "captured" or "failed" based on the processor's response. If the system crashes between steps 2 and 3, a background reconciliation job queries the processor's API for the status of all "pending" transactions older than 5 minutes and updates the database accordingly. This achieves "effectively exactly-once" without distributed two-phase commit (2PC), which would add unacceptable latency and complexity. The processor's own idempotency (using our transaction ID as their idempotency key) ensures that re-querying the status never triggers a duplicate charge.

**Double-Entry Ledger:** Every payment creates exactly two journal entries: a debit from the customer account and a credit to the merchant account. The entries always sum to zero. This is not just an accounting formality, it is a data integrity check. If the sum of all ledger entries is nonzero, you know that data has been corrupted or a transaction was only partially recorded. Merchant balances are a materialized running total, incremented in the same database transaction that writes the ledger entries, so the balance and the entries that justify it commit together or not at all. The invariant to hold onto is that the balance must always be reproducible by summing the ledger from scratch. That is what makes it a cache of the ledger rather than a second, competing source of truth, and it is exactly what reconciliation recomputes. You never update a balance on its own, since a balance that no longer follows from the entries has quietly become an unauditable number.

**PCI DSS Compliance:** The system never stores, processes, or transmits raw card numbers. Card data flows directly from the customer's browser to the processor via their client-side SDK (for example, Stripe.js). The processor returns a token (like `pm_xxx`) that represents the card, and all subsequent operations use this token. This reduces PCI scope to SAQ A (the lightest compliance level), which requires annual self-assessment rather than expensive on-site audits. The trade-off is a dependency on the processor for tokenization, but this is universally accepted as the right approach.

**Fraud at Scale:** The two-layer approach is designed to minimize latency while maximizing detection. Hard rules (blocklists, country restrictions, amount limits) run first because they are deterministic, require no external lookups beyond a Redis set membership check, and complete in under 1ms. Only transactions that pass the hard rules are evaluated by the ML model (a gradient-boosted tree trained on velocity features like transactions per hour and amount z-score), which adds up to 50ms. Note the asymmetry in what the two layers are for. Hard rules reject only a small fraction of traffic, well under 1% on healthy merchants, so they are not a meaningful cost saving on the ML layer, which still runs on essentially every transaction. They exist because some rejections are not risk judgments at all: a sanctioned-country charge is a legal prohibition, and you do not want a probability attached to it. The ML layer handles everything that is genuinely a question of likelihood, and its threshold is a business decision, since moving it trades revenue lost to false positives against fraud lost to false negatives.
