## Key Design Decisions

Each decision below addresses a specific scaling bottleneck or operational challenge that would otherwise prevent the system from handling its target throughput.

**ClickHouse for TSDB:** ClickHouse was chosen over InfluxDB, TimescaleDB, and Prometheus for several reasons. Its columnar storage achieves 10:1 compression on time-series data because columns of similar values (like timestamps that increment by 10 seconds, or CPU values that hover around 40-60%) compress far better than rows of mixed types. The MergeTree engine supports TTL-based automatic data expiration, which eliminates the need for a separate cleanup job. Native time-bucketed aggregation functions like `toStartOfInterval` are optimized at the storage engine level rather than being computed at query time. A single ClickHouse node handles 1M writes/sec, and the cluster scales horizontally with sharding. The trade-off versus InfluxDB is that ClickHouse requires more operational expertise and does not have a built-in query language as ergonomic as InfluxQL, but the performance advantage at this scale is decisive.

**Two-Tier Retention:** Raw 10-second data is kept for 7 days to support detailed incident investigation, when an outage happens, engineers need fine-grained data to identify the exact moment things went wrong. After 7 days, a nightly downsample job aggregates the raw data into 1-minute resolution buckets (storing avg, min, max, and count per window) for long-term capacity planning and SLO reporting. The query service automatically selects the right tier based on the requested time range: queries within the last 7 days hit the raw table, while queries spanning weeks or months hit the aggregated table. This is transparent to the user, they see seamless data across both tiers.

**Pre-aggregation in Stream Layer:** Keeping 1M raw data points per second at full resolution for a year would produce enormous storage costs. The stream aggregator (Flink or a custom Go service) groups incoming metrics into 1-minute tumbling windows and emits summary statistics (avg, min, max, count) for each unique metric-plus-tags combination. This cuts the long-term write volume roughly 6x, from 1M points/sec to about 167K rollup rows/sec, because the six 10-second points a series reports per minute collapse into a single aggregated row. The trade-off is up to a one-minute delay in rollup freshness, which is acceptable for historical dashboards but not for real-time alerting (which evaluates against the raw table instead).

**Alert Deduplication:** Without deduplication, a metric that stays above its threshold would generate a new notification every evaluation cycle (every minute), flooding on-call engineers with duplicate pages. Redis stores the current state of each alert rule (ok, alerting, or no_data). Notifications are sent only on state transitions: when an alert moves from ok to alerting, and again when it moves from alerting back to ok (the "resolved" notification). This means engineers receive exactly two notifications per incident: one when it starts and one when it ends. Additional protection against alert fatigue comes from the flapping guard, which requires multiple consecutive threshold violations before firing, preventing transient spikes from triggering pages.
