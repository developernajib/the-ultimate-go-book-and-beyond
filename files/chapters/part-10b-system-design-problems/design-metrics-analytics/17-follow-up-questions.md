## Follow-up Questions

These questions probe advanced observability topics that distinguish a monitoring system from a full observability platform.

**Q: Anomaly detection?** Static thresholds (alert if CPU > 90%) work for simple cases but fail for metrics with natural variability or seasonal patterns. Three progressively sophisticated approaches: (1) Z-score from a rolling mean, compute the mean and standard deviation over a sliding window (for example, the last 24 hours), and alert when the current value exceeds 3 standard deviations from the mean, (2) seasonal decomposition, which separates the signal into trend, seasonality, and residual components, then alerts only when the residual is abnormally large (this handles metrics like request rate that naturally spike during business hours), and (3) ML-based methods like isolation forests or autoencoders trained on historical data, which can detect complex anomaly patterns that statistical methods miss. The trade-off is that ML methods require training data and are harder to explain to operators.

**Q: Cardinality explosion?** This is the most common operational crisis in metrics systems. Prevention is multi-layered: tag validation at the ingest layer (reject any tag key not in the per-metric allow-list), a hard limit of 30 tags per metric point, real-time cardinality monitoring using HyperLogLog that alerts when any metric exceeds 10,000 distinct series, value bucketing for legitimate high-cardinality dimensions (hash user IDs into 1,000 buckets to reduce cardinality by orders of magnitude while preserving aggregate statistics), and automatic expiration of metrics that have not reported new data in 30 days (cleaning up abandoned series from decommissioned hosts).

**Q: Histograms at scale?** Two approaches for computing percentiles across distributed agents: (1) pre-bucketed histograms where each agent reports counts per predefined bucket boundary (for example, <10ms, <50ms, <100ms, <500ms, <1s, <5s), which can be merged by summing bucket counts across agents, this is how Prometheus histograms work, with the limitation that bucket boundaries must be chosen upfront, (2) T-Digest sketches, which store approximately 100 centroids and provide less than 1% error at extreme percentiles (P99, P99.9), T-Digest sketches are mergeable across agents and time windows, making them ideal for distributed aggregation. ClickHouse supports `quantileTDigest()` natively.

**Q: Distributed tracing?** Spans (individual operation timings with trace_id, span_id, parent_span_id, service name, duration, and tags) are stored in a ClickHouse spans table partitioned by timestamp. At 1M requests/sec, storing every span is expensive. Two sampling strategies: (1) head-based sampling at 1% (decide at the trace root whether to sample, then propagate the decision to all downstream services), which is simple but misses interesting traces, (2) tail-based sampling at 100% capture, where all spans are collected temporarily and the system retroactively keeps only traces that are slow, errored, or match specific criteria. Tail-based sampling catches rare problems but requires a buffer and post-processing step. Flame graphs and service dependency maps are computed from the span data.

**Q: SLO dashboards?** Define a Service Level Indicator (SLI) like "P99 latency < 200ms" and a Service Level Objective (SLO) like "99.9% of requests meet the SLI over a 30-day rolling window." The error budget is `(1 - SLO) * window = 0.1% * 30 days = 43.2 minutes` of allowed violations per month. Burn rate alerting detects when the error budget is being consumed too quickly: if the current violation rate would exhaust the monthly budget in 6 hours (a "fast burn"), page immediately, if it would exhaust in 3 days (a "slow burn"), send a warning. Multi-window alerting (checking both 1-hour and 6-hour windows) catches both sudden spikes and gradual degradation.

**Q: Multi-region ingestion?** Each region writes to a local Kafka cluster and a local ClickHouse, so regional writes survive inter-region network partitions. A global aggregator reads from all regional Kafka topics via MirrorMaker 2 and produces the unified cross-region view. Dashboards query the regional ClickHouse for local views and the global aggregator for fleet-wide views.

**Q: What happens when a pipeline component fails?** Kafka is the primary durability buffer (24-hour retention). If ClickHouse is down, consumers pause and Kafka absorbs the backlog. If Kafka is unreachable, agents buffer to local disk (up to 1GB) with WAL rotation. If the stream aggregation layer fails, raw data still flows to ClickHouse, queries keep working but are slower without pre-aggregation. The alert evaluator runs an independent hot standby with leader election so alerting never depends on a single instance.

**Q: Dashboard performance for hundreds of concurrent users?** Five layers work together: a result cache keyed by (query hash, time range, step) with a 10-second TTL for auto-refreshing dashboards, query deduplication so identical in-flight queries share one ClickHouse execution, pre-materialized views for the most popular dashboards refreshed on a schedule, parallel panel execution (a 12-panel dashboard issues 12 concurrent queries), and adaptive step size that widens the aggregation interval for wide time ranges.
