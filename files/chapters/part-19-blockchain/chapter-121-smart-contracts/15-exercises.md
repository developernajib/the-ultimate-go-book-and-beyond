## Exercises

1. **ERC-20 Token Deployer and Manager**: Write a Go program that deploys an ERC-20 token contract to a local Hardhat network using `abigen`-generated bindings. Execute a sequence of `transfer`, `approve`, and `transferFrom` calls from different accounts, verify resulting balances and allowances match expected values, and assert that transferring more than the available balance reverts with the correct error. Expected outcome: a full integration test suite for an ERC-20 contract that runs against a local EVM and passes in under 30 seconds.

2. **Smart Contract Event Stream Processor**: Build a Go service that subscribes to `Transfer` and `Approval` events from a deployed ERC-20 contract via WebSocket, decodes the ABI-encoded log data using `go-ethereum/accounts/abi`, and maintains an in-memory balance ledger updated by every event. Periodically reconcile the ledger against on-chain `balanceOf` calls and log any discrepancies. Expected outcome: a real-time balance tracker that stays synchronized with contract state and detects reconciliation mismatches within one block.

3. **CREATE2 Address Prediction and Deployment**: Implement a Go utility that predicts the `CREATE2` deployment address for a contract given a deployer address, salt, and bytecode hash using `keccak256(0xff ++ deployer ++ salt ++ keccak256(bytecode))[12:]`. Deploy the contract to Hardhat and assert the actual deployed address matches the prediction exactly. Expected outcome: a deterministic deployment tool that can reserve and publish contract addresses before deployment, verified by an end-to-end Hardhat test.

4. **Gas Optimization Benchmarker**: Write a Go benchmarking harness that deploys two versions of the same contract (optimized vs. unoptimized) to a Hardhat fork and calls each function 100 times, recording gas used from transaction receipts. Produce a comparison report showing per-function gas savings and assert the optimized version uses at least 10% less gas for the target function. Expected outcome: a data-driven gas optimization tool that quantifies Solidity-level optimization impact from Go integration tests.

5. **Multi-Sig Wallet Coordination Service**: Using `abigen` bindings for a Gnosis Safe-style multi-sig wallet contract, build a Go coordination service where multiple signers each call a `/sign` HTTP endpoint. The service aggregates signatures and submits the `execTransaction` call once the required threshold is met. Implement a 10-minute timeout that expires the pending transaction and notifies signers. Expected outcome: a threshold coordination service that submits exactly one on-chain transaction after collecting the required signatures, with integration tests covering the threshold-met and timeout-expired paths.

6. **Contract Upgrade Proxy Manager**: Implement a Go manager for the OpenZeppelin Transparent Proxy upgrade pattern that deploys a proxy pointing to an implementation contract, calls functions through the proxy, deploys a new implementation, calls `upgradeTo` via the proxy admin, and verifies that post-upgrade calls use the new implementation's logic while preserving storage state. Write a test asserting that a storage variable set in v1 is still accessible and correct after upgrading to v2. Expected outcome: a proxy lifecycle manager demonstrating correct state persistence across upgrades, verified by a storage continuity assertion.

### Junior → FAANG: Smart Contract Exercises as Your Competency Validator

The exercises in the smart contracts chapter are your self-assessment tool before applying for blockchain engineering roles. If you cannot complete the fundamental exercises (generate abigen bindings, deploy a contract to a simulated backend, read contract state, decode an event), you are not ready for the junior engineer interview screen. If you can complete the advanced exercises (multi-signature workflow, gas optimization measurement, mainnet fork integration test), you are well-positioned for a senior engineer screen.

Timing yourself on the exercises is a useful calibration: a junior engineer ready for a blockchain role should be able to complete the "deploy and interact" exercise in under 30 minutes and the "event listener with restart handling" exercise in under 2 hours. If exercises take significantly longer, the bottleneck is usually familiarity with the go-ethereum API (which requires more practice) or understanding of the underlying concepts (which requires more reading).

Sharing your exercise solutions on GitHub with a clear README is the most impactful thing you can do to improve your blockchain engineering candidacy before having a formal interview. Recruiters and hiring engineers who review candidates' GitHub profiles look for: working code (not just a skeleton), tests (even minimal ones signal professionalism), and written explanation (a README that describes what the code demonstrates and what you learned). Exercises with all three components consistently outperform resumes without code samples.

For interview preparation specifically, be ready to walk through any exercise solution in a technical screen. The interviewer may ask: "Why did you choose this approach?", "What would you change for production?", and "How would you test this?". Having answers to these three questions for each exercise is the preparation discipline that converts coding exercises into strong interview performance.

### Senior @ FAANG: Smart Contract Exercises as Team Development Infrastructure

At staff level, the smart contract exercises are the foundation of a structured team development program. Converting them into a learning path with defined entry and exit criteria (demonstrable competency in each exercise, verified by a senior engineer), expected completion times (as a check against the time investment required for onboarding), and escalation paths (when an exercise reveals a knowledge gap that requires additional resources) produces a repeatable onboarding process rather than an inconsistent mentorship experience.

Exercise maintenance at the platform level includes: verifying that all exercises compile and run correctly after go-ethereum version upgrades, updating exercises when the Ethereum protocol changes make old patterns obsolete (e.g., exercises that used the legacy gas price API need to be updated for EIP-1559), and adding new exercises when new capabilities are required by the team's work (e.g., adding a blob transaction exercise after the Dencun upgrade makes blobs available on mainnet).

Using exercises as interview take-homes requires careful scoping and clear rubrics. The best take-home exercise for a senior smart contract integration role is not the most complex exercise in the chapter but one that reveals the candidate's judgment: how they handle edge cases, how they structure error handling, and how they think about production requirements that the exercise prompt does not explicitly mention. An exercise that is easy to complete naively but reveals depth when done thoughtfully is the most informative take-home.

Automated exercise evaluation (a CI system that compiles submitted solutions, runs the provided test cases, and reports results) reduces the time burden on senior engineers who review take-home submissions. The automated system should evaluate: correctness (does the code pass the tests?), compilation (does the code compile without warnings?), and basic code quality (does the code pass `go vet` and `golint`?). Human review then focuses on: design judgment, error handling completeness, and explanation quality. This division of labor makes the take-home evaluation process scalable.

Bar-raiser candidate signals in exercise submission: a candidate who completes the basic exercise correctly and then adds a `go test -fuzz` harness that tests the event decoding against randomly generated log data is demonstrating the kind of thoroughness that distinguishes L5 and L6 engineers. Similarly, a candidate who writes a benchmark for the ABI encoding step and notes that Multicall3 would reduce the total gas cost by a specific factor is showing the performance-aware thinking expected at senior levels.
