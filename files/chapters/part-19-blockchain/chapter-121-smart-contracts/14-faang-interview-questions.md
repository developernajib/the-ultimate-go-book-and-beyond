## 121.13 FAANG Interview Questions

**Q1: How does `abigen` generate type-safe bindings for complex Solidity types like tuples and dynamic arrays, and how do you handle contract upgrades?**
A: `abigen` parses the contract ABI JSON and maps EVM types to Go types: `uint256` to `*big.Int`, `address` to `common.Address`, `bytes32` to `[32]byte`, and Solidity structs/tuples to generated Go structs. For upgradeable contracts (e.g., ERC-1967 transparent or UUPS proxies), the Go service points the generated binding to the immutable proxy address. When the implementation changes, the service regenerates bindings if the external interface expands, while routing all runtime transactions through the proxy to maintain execution context (`delegatecall`).

**Q2: What is the ERC-20 approval race condition, and how should a Go backend mitigate it?**
A: If an owner changes an allowance from `N` to `M` via `approve`, a malicious spender monitoring the mempool can front-run the second transaction to spend `N` tokens first, and then spend `M` tokens after inclusion, effectively spending `N+M`. A Go service mitigates this by either resetting the allowance to 0 before setting the new value (`approve(spender, 0)` followed by `approve(spender, newAmount)`), using OpenZeppelin's `increaseAllowance`/`decreaseAllowance`, or adopting EIP-2612 `permit` for atomic off-chain signature approvals.

**Q3: Why can `eth_estimateGas` fail or return inaccurate estimates for state-dependent contract calls, and how do you safeguard transactions in production?**
A: `eth_estimateGas` executes the transaction locally against the pending state at a single point in time. If intermediate state changes (e.g., oracle price updates, token balance shifts, or competing liquidations), the actual execution branch may require substantially more gas or revert. Production Go backends add deterministic safety headroom (typically 20% to 30% over the estimate), enforce a strict sanity upper bound to prevent catastrophic fee burns, and verify contract pre-conditions (e.g., pause flags and token allowances) prior to broadcasting.

**Q4: How does a Go service orchestrate multi-signature execution with Gnosis Safe?**
A: The service constructs the Safe transaction payload (`to`, `value`, `data`, `operation`, gas parameters, and `nonce`), calculates the EIP-712 typed-data transaction hash via `safe.GetTransactionHash`, collects off-chain signatures from threshold signers, and sorts the concatenated signatures in ascending order of signer address (`bytes.Compare(addrA, addrB) < 0`). Any relayer or authorized caller can then submit the final `execTransaction` to the Safe contract on-chain.

**Q5: What are the trade-offs between using go-ethereum's in-process `backends.SimulatedBackend` versus an Anvil/Hardhat mainnet fork for integration testing?**
A: `backends.SimulatedBackend` runs a local EVM directly in the Go test process with zero external dependencies, providing microsecond execution and deterministic manual block mining (`Commit()`), making it ideal for CI unit testing of ABI encoding and event decoding. However, it lacks realistic mempool dynamics and does not possess existing deployed mainnet contract state. Forking mainnet via Anvil or Hardhat enables testing Go code directly against live liquidity pools, oracles, and third-party protocols at a specific block number, catching production state divergences that synthetic tests miss.
