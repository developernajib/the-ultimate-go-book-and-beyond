## Exercises

1. **RPC Load Balancer with Health Checking**: Implement a Go RPC load balancer that maintains a pool of Ethereum JSON-RPC endpoints and routes requests using weighted round-robin. Add active health checks that call `eth_blockNumber` every 15 seconds, remove endpoints returning stale block numbers (more than 3 blocks behind the best), and restore them automatically once they catch up. Expected outcome: a load balancer that survives the failure of any single provider with zero dropped requests, verified by a test that kills one endpoint mid-stream.

2. **Blockchain Event Indexer with The Graph Integration**: Build a Go service that fetches historical Uniswap V2 swap events using The Graph's GraphQL API, persists them to a PostgreSQL table with proper indexes, and exposes a REST endpoint `GET /swaps?pair={address}&from={timestamp}&to={timestamp}` with cursor-based pagination. Expected outcome: a subgraph-backed indexer that serves historical swap data in under 20 ms for date-range queries on a table of 1 million events.

3. **IPFS Content-Addressed Storage Client**: Implement a Go IPFS client that pins JSON metadata objects via the Kubo RPC API, retrieves them by CID, and verifies integrity by recomputing the CID from fetched content using `go-cid`. Build a local CID-to-URL mapping cache in Redis and implement a fallback to public IPFS gateways when the local node is unavailable. Expected outcome: a resilient IPFS client where content integrity is always verified and fallback gateway latency is under 2 seconds for any pinned CID.

4. **Multi-Chain Infrastructure Manager**: Design a Go `ChainManager` that manages connections to multiple EVM-compatible chains (Ethereum, Polygon, Arbitrum) using a chain ID registry. Implement `SendTransaction(chainID uint64, tx *types.Transaction) (common.Hash, error)` that routes to the correct client, manages per-chain nonce state, and respects each chain's gas model (legacy vs. EIP-1559). Write integration tests using separate Hardhat instances for each simulated chain. Expected outcome: a chain-agnostic transaction submission layer that correctly handles different fee models and independent nonce sequences per chain.

5. **Transaction Mempool Monitor**: Build a Go service that subscribes to pending transactions via `eth_subscribe("newPendingTransactions")`, decodes transaction calldata against a known ABI to identify contract function calls, and emits structured events for transactions calling target function selectors. Implement WebSocket reconnection with exponential backoff. Expected outcome: a real-time mempool watcher that identifies and logs all pending calls to a monitored contract within 500 ms of submission, surviving WebSocket disconnections transparently.

6. **Block Explorer Backend with Analytics**: Build a Go REST API that indexes a local chain's blocks and transactions into PostgreSQL and exposes: `GET /stats` (total transactions, avg block time, avg gas price over last 100 blocks), `GET /blocks?page=N` (paginated block list with tx count), and `GET /address/{addr}/portfolio` (ETH balance plus ERC-20 token balances). Implement all aggregations as parameterized SQL with indexes verified by `EXPLAIN ANALYZE`. Expected outcome: a block explorer backend where all endpoints return in under 100 ms against a 10,000-block indexed chain.

### Junior → FAANG: Web3 Infrastructure Exercises as Your Portfolio Foundation

The Web3 infrastructure exercises are the portfolio projects that demonstrate you can build production-quality blockchain backend systems, not just use blockchain APIs. For blockchain infrastructure roles at FAANG-adjacent companies, hiring managers want to see projects that work end-to-end, handle errors correctly, and maintain tests. The exercises in this chapter give you exactly that material if you complete them fully.

Prioritize the exercises in order of production impact: first, implement a multi-provider RPC client with fallback (foundational to everything else), then a minimal event indexer with startup replay and reorg detection (demonstrates the hardest infrastructure problem), then a transaction monitoring system with confirmation tracking (demonstrates financial-grade reliability thinking). These three exercises, done well, are a complete Web3 infrastructure portfolio.

For interview preparation, time your completion of each exercise and identify the bottlenecks: if you spent most of your time debugging the RPC connection rather than implementing the business logic, you need more practice with the go-ethereum API. If you spent most of your time on the database schema, you need more practice with SQL design for append-heavy workloads. These timing signals guide your additional preparation.

Go test coverage for infrastructure exercises is different from application code coverage: the most important tests are the failure-path tests (what happens when the RPC node returns an error, what happens when the database write fails). A test suite that only covers the happy path is insufficient for infrastructure that must be reliable in production. Write at least three negative test cases for each exercise component.

### Senior @ FAANG: Web3 Infrastructure Exercises as Team Development Capital

At staff level, the Web3 infrastructure exercises are the foundation of a structured team development program. Converting them into a learning path with defined completion criteria, code review standards, and expected time estimates produces a repeatable onboarding experience for new infrastructure engineers. This investment in structured learning reduces the time from "new hire" to "productive contributor" by weeks.

Exercise rubrics for senior hire evaluation should assess production readiness, not just correctness. For a senior infrastructure engineer take-home exercise based on the event indexer exercise, the rubric should weight: correct reorg handling (40 percent), comprehensive error handling and logging (25 percent), test coverage including failure scenarios (20 percent), and code clarity and documentation (15 percent). A correct implementation without the failure handling and tests is a 40 percent score, not adequate for a senior infrastructure role.

Automated validation for exercise submissions reduces evaluation overhead. A CI system that runs the submitted code against a local Geth devmode node, triggers simulated reorgs using `debug_setHead`, and verifies that the indexer correctly detects and recovers from the reorg can validate the hardest exercise requirement without manual review. Staff engineers who build this validation infrastructure improve the evaluation process for the entire team.

Contributing new exercises that cover emerging Web3 infrastructure topics is a staff-level community contribution. An exercise for implementing an EIP-4844 blob fetcher (which requires connecting to the beacon node REST API rather than the execution layer JSON-RPC), or an exercise for building a Portal Network data fetcher, would fill gaps in the current exercise set and keep the curriculum current with Ethereum's protocol evolution. Staff engineers who contribute these exercises are cultivating the future cohort of blockchain infrastructure engineers.

Exercises that are deployed as open-source reference implementations (on the organization's GitHub, with a permissive license) contribute to the blockchain engineering community's collective knowledge while also serving as a recruiting signal. Organizations that publish high-quality open-source reference implementations of Web3 infrastructure components attract engineers who value technical excellence and contribute to the community. Staff engineers who champion this open-source strategy as a hiring and community investment are thinking at the organizational level.
