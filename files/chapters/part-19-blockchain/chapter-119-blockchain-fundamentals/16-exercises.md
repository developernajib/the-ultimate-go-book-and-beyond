## Exercises

1. **UTXO Transaction Engine**: Implement a UTXO (Unspent Transaction Output) model in Go where each transaction consumes a set of input UTXOs and creates new output UTXOs. Enforce that the sum of inputs equals the sum of outputs plus a miner fee, validate that inputs are unspent, and sign each input with the spender's ECDSA private key using `crypto/ecdsa`. Build a UTXO set backed by a `sync.Map` and write tests that attempt double-spend and assert they are rejected. Expected outcome: a functionally correct UTXO engine that prevents double-spending and enforces conservation of value.

2. **P2P Node with Gossip Protocol**: Implement a minimal peer-to-peer node in Go using TCP that discovers peers via a hardcoded bootstrap list, propagates new transactions and blocks using a gossip protocol (forward to all peers except the sender), and de-duplicates messages by caching the last 1000 message hashes in a fixed-size LRU cache. Run three nodes locally and verify that a transaction submitted to one propagates to all three within 500 ms. Expected outcome: a working gossip network where every node converges on the same transaction set without a central coordinator.

3. **Proof-of-Work Miner with Adjustable Difficulty**: Implement a PoW miner that finds a `nonce` such that `SHA-256(block_header || nonce)` starts with `N` leading zero bits, where `N` is recalculated every 10 blocks to target a 10-second average block time. Measure actual block times and log difficulty adjustments. Expected outcome: a miner that empirically converges on the target block interval after 3-4 adjustment cycles, demonstrated by a test that mines 40 blocks and asserts average block time is within 20% of the target.

4. **Merkle Tree and SPV Proof**: Build a Merkle tree from a list of transaction hashes. Implement `GenerateProof(txHash string) []MerkleNode` that returns the sibling path from a leaf to the root, and `VerifyProof(txHash, root string, proof []MerkleNode) bool` that recomputes the root from the proof path. Write a test that inserts 128 transactions, generates a proof for a random leaf, mutates one byte of the proof, and asserts verification fails. Expected outcome: a Merkle proof library that enables light clients to verify transaction inclusion without downloading the full block.

5. **Transaction Signing and Address Derivation**: Implement Go functions for generating secp256k1 key pairs, deriving an Ethereum-compatible address from a public key (Keccak-256 of the uncompressed public key, last 20 bytes, EIP-55 checksum), signing a transaction hash with the private key using `crypto/ecdsa`, and recovering the signer's address from a signature. Write a round-trip test confirming that the recovered address matches the signing address. Expected outcome: a cryptographic identity layer compatible with Ethereum address standards, verified by comparing derived addresses with known-good test vectors.

6. **Block Explorer REST API**: Build a Go HTTP API backed by a SQLite database that indexes a local blockchain. Expose endpoints: `GET /blocks` (paginated list), `GET /blocks/{hash}` (block detail with transactions), `GET /tx/{hash}` (transaction detail), and `GET /address/{address}/txs` (transaction history for an address). Implement all queries as parameterized SQL with appropriate indexes on hash and address columns. Expected outcome: a functional block explorer backend that indexes a 1000-block chain and serves all endpoints with under 50 ms response time.

### Junior → FAANG: Turning Exercises into Portfolio and Interview Assets

Exercises in a blockchain fundamentals chapter are not graded homework but portfolio-building opportunities. Every exercise you complete, test, and publish to a public GitHub repository becomes evidence of competence that you can point to in interviews. A repository named `go-blockchain-fundamentals` with clean, well-tested implementations of hash-linked blocks, ECDSA signing, and Merkle proofs communicates more credibly than "I understand blockchain fundamentals" on a resume.

The most valuable exercises to prioritize for interview preparation are those that force you to handle the error cases and edge conditions: what happens when you try to mine a block with an extremely high difficulty target (your implementation must not block forever), what happens when you verify a signature with the wrong public key (you must return a clear error, not a panic), and what happens when you try to add a block with an incorrect previous hash to your chain (validation must reject it with a specific, testable error).

For Go-specific skill building within the exercises, use the blockchain exercises as an opportunity to practice table-driven tests with `testing.T`, benchmarks with `testing.B` (measure how long it takes to mine a block at various difficulty levels), and Go's `race` detector (`go test -race`) on any code that uses goroutines. These testing skills directly transfer to the Go coding assessments used by many blockchain companies.

Interview entry point habit: after completing each exercise, spend five minutes writing down the key decision you made (which library, which data structure, which error handling approach) and why. This reflection produces the material for the "walk me through a technical decision you made" question that appears in almost every senior interview.

### Senior @ FAANG: Exercises as the Foundation for Team Standards and Hiring Rubrics

At staff level, the exercises in a fundamentals chapter are the raw material for designing take-home assessments, onsite coding challenges, and onboarding projects for new team members. A well-designed exercise reveals whether a candidate has the specific skills your team needs: not just "can they write Go" but "can they write Go that correctly implements cryptographic operations with proper error handling and is testable."

Designing a take-home assessment based on these exercises requires careful scoping: the ideal take-home takes three to five hours, tests two or three key concepts rather than comprehensive coverage, and has a clear evaluation rubric. For a blockchain infrastructure role, a good take-home might ask the candidate to implement a transaction signing function, write three test cases covering the happy path and two error cases, and write a brief explanation of their implementation choices. The rubric evaluates correctness, error handling quality, test design, and written communication, in roughly equal measure.

ADRs for team onboarding programs should specify which exercises from the fundamentals chapter are required versus optional for different roles. A new engineer on the node operations team might be required to complete the P2P networking exercises but may skip the smart contract exercises. A new engineer on the DeFi integration team has the opposite priority. This customization ensures that onboarding time is spent on the knowledge gaps most relevant to the role.

Benchmarking exercises produce data that informs architecture decisions. If the exercise reveals that your Go implementation of SHA-256 hashing runs at 500 MB/s on the hardware your team uses, you can estimate whether a proposed batch verification approach that hashes 1 TB of data daily is feasible within a time budget. This connection between exercise benchmarks and architectural estimates is a skill that staff engineers use regularly.

The exercises also provide the testing material for automated code review tools. A team that establishes patterns through the fundamentals exercises can configure linting rules and code review checklists that enforce those patterns across all production code. "Always use `types.NewLondonSigner` for Ethereum post-EIP-1559 transaction signing, never the legacy `HomesteadSigner`" is a pattern that emerges from the exercises and should be enforced automatically rather than relying on manual review to catch deviations.

Bar-raiser hiring signals in exercise review: a candidate who completes the Merkle proof exercise and also adds a benchmark, a fuzz test using Go's `testing/fuzz` package, and an explanation of what input would cause the worst-case performance is demonstrating L5/L6 thinking. The exercise asks for a correct implementation. The candidate is delivering a production-ready one. That gap in initiative and depth is exactly what FAANG-level blockchain roles require.

Staff-level contribution to the exercises themselves: updating exercise specifications when protocol changes make old approaches obsolete (e.g., updating gas price exercises after EIP-1559), adding new exercises that reflect current technology (e.g., EIP-4337 account abstraction, EIP-4844 blob transactions), and maintaining a solutions reference with multiple acceptable approaches and discussion of their trade-offs. This maintenance work is a form of technical leadership that benefits every engineer who uses the chapter.
