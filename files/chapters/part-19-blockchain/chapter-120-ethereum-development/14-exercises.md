## Exercises

1. **HD Wallet with BIP-44 Derivation**: Implement a Go HD wallet that generates a BIP-39 mnemonic phrase, derives the BIP-32 master key, and produces child key pairs following the BIP-44 path `m/44'/60'/0'/0/n` for Ethereum accounts. Expose a `DeriveAddress(index uint32) (common.Address, error)` function and verify the first three derived addresses match known-good test vectors from the BIP-44 specification. Expected outcome: a deterministic wallet that reproduces identical addresses across runs from the same mnemonic, confirmed by test vectors.

2. **ERC-20 Token Interaction Client**: Using `abigen`-generated bindings for a standard ERC-20 ABI, build a Go client that queries token balance for an address, approves a spender allowance, and transfers tokens - all on the Sepolia testnet. Implement nonce management using a thread-safe counter that fetches the pending nonce on startup and increments atomically for concurrent transfers. Expected outcome: a concurrent transfer client that submits 10 transfers without nonce collisions, verified by checking all transaction receipts show status 1.

3. **Transaction Receipt Poller with Confirmation Depth**: Implement a `WaitForConfirmations(ctx context.Context, txHash common.Hash, confirmations uint64) (*types.Receipt, error)` function that polls for the receipt, checks that `currentBlock - receipt.BlockNumber >= confirmations`, and handles chain reorganizations by re-fetching the receipt if a previously seen receipt disappears. Expected outcome: a reliable confirmation waiter that correctly handles reorgs in a local Hardhat environment where reorgs are triggered programmatically via the `hardhat_revert` JSON-RPC method.

4. **Dynamic EIP-1559 Gas Price Strategy**: Build a gas estimation service that queries the `eth_feeHistory` JSON-RPC method for the last 10 blocks, computes the 25th, 50th, and 75th percentile `maxPriorityFeePerGas` values, and exposes three fee tiers (slow, standard, fast) via an HTTP endpoint. Refresh estimates every 12 seconds. Expected outcome: a fee estimation service returning current EIP-1559 recommendations that remain valid for the next block under normal network conditions, verified against a local Hardhat fork.

5. **Event Log Indexer with Reorg Handling**: Build a Go event indexer that fetches `Transfer` events from an ERC-20 contract using `FilterLogs` with block range pagination (1000 blocks per request). Store events in SQLite with `(block_number, log_index, tx_hash)` as the primary key. On startup, detect and roll back events from blocks no longer on the canonical chain by comparing stored block hashes against the live chain. Expected outcome: an indexer that correctly re-indexes after a 2-block reorg injected via Hardhat's fork manipulation.

6. **Multi-Signature Transaction Builder**: Implement a Go m-of-n multi-signature transaction system using off-chain threshold signing with `crypto/ecdsa`. A `MultiSigBuilder` collects `(signer_address, signature)` pairs for a transaction hash, validates each signature by recovering the signer address, and assembles a final transaction once `m` valid unique signatures are collected. Write tests covering: fewer than m signatures (rejected), duplicate signer (rejected), invalid signature (rejected), and valid m-of-n collection (approved). Expected outcome: a threshold signing library that enforces all four invariants, with each invariant covered by a dedicated test case.

### Junior → FAANG: Ethereum Development Exercises as Skill Validators

The exercises in this chapter are the most direct way to verify that your understanding of Ethereum development is correct rather than approximately correct. Blockchain development has a very low tolerance for "approximately correct": a transaction signed with the wrong signer parameters is rejected, an event decoded with the wrong ABI produces silently wrong data, and a nonce management bug causes stuck transactions in production. Exercises force the precision that production requires.

Prioritize exercises that require you to handle error cases: what does your code do when the RPC node returns a `context deadline exceeded` error, when a transaction receipt shows a revert, or when `eth_getLogs` returns a rate limit error? Writing the error handling code is often more complex than writing the happy path, and it is exactly this kind of robustness that distinguishes production-quality code from tutorial code.

For interview preparation, after completing each exercise, add it to your portfolio repository with a README that explains: what the exercise demonstrates, what the most important implementation decision was, and what would need to change for production use. This documentation habit demonstrates communication skill alongside technical skill, which is a differentiating factor in senior engineering interviews.

Use the exercises to benchmark your Ethereum development speed. A junior engineer should be able to complete the "connect to a node and read a block" exercise in 10 minutes and the "send a signed transaction" exercise in 30 minutes. If an exercise takes significantly longer, that is a signal that you need more practice with that specific component before tackling a production integration.

### Senior @ FAANG: Ethereum Development Exercises as Hiring and Onboarding Tools

At staff level, the exercises in this chapter are the raw material for technical assessments. A well-designed take-home exercise for a blockchain engineering role derives from one or two of these exercises, adds a production concern (error handling, observability, or concurrent correctness), and asks the candidate to write a brief explanation of their design choices. This structure assesses technical skill, production judgment, and communication simultaneously.

Rubrics for exercise evaluation at the staff level go beyond "is the code correct?" Correct code that lacks error handling, that uses magic numbers for chain IDs and gas limits, or that has no tests is not production-ready. The rubric should weight correctness (50 percent), production readiness including error handling and configuration (30 percent), and test coverage and design explanation (20 percent). These weights reflect the distribution of importance in real blockchain engineering work.

Onboarding exercises derived from the chapter exercises provide a structured way to verify that new team members have reached the knowledge bar before they write production code. An onboarding program that requires completing five specific exercises against the team's local development environment (Geth devmode node with a pre-configured genesis) and having the solutions reviewed by a senior engineer produces better outcomes than self-directed study alone.

Exercise automation is a staff-level contribution: building CI infrastructure that runs the exercises against a live testnet (Sepolia or Holesky) nightly verifies that the exercise solutions remain correct as the Ethereum protocol evolves and as go-ethereum versions change. This automated validation of educational content is an investment in the team's long-term knowledge quality.

The exercises also serve as regression tests for the Ethereum development platform. When a go-ethereum version upgrade changes the API for transaction construction or event decoding, the exercise CI tests will fail, providing early warning before the change affects production code. This use of educational exercises as platform regression tests is a creative application of existing infrastructure that reduces maintenance burden.

Bar-raiser signals: designing a new exercise that tests a concept introduced by a recent EIP (for example, an exercise that implements EIP-4337 user operation construction and submission through a bundler), or identifying an exercise in the current set that tests a deprecated pattern (pre-EIP-1559 gas price setting) and updating it to reflect current best practices. These contributions to the educational infrastructure demonstrate genuine ownership of the team's knowledge base.
