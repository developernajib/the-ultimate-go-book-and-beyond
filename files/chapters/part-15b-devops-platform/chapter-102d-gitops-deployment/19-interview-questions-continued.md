**Q16: How do you handle secrets in GitOps - Sealed Secrets vs External Secrets vs Vault?**

Each approach sits at a different point on the spectrum between simplicity and operational power. **Sealed Secrets**: the `kubeseal` CLI encrypts a Kubernetes Secret with a cluster-scoped public key. The resulting `SealedSecret` CRD is safe to commit to Git. The controller decrypts it at runtime using a private key stored in the cluster. Upside: zero external dependencies, simple operator. Downside: the decryption private key is cluster-local - losing it without a backup means losing access to every secret. Rotation requires re-sealing all secrets. Best for: small teams, single cluster, getting started fast. **External Secrets Operator (ESO)**: stores the actual secret value in an external provider (AWS Secrets Manager, GCP Secret Manager, Azure Key Vault, HashiCorp Vault) and creates a `ExternalSecret` CRD in Git (not sensitive). The controller syncs the value into a native Kubernetes Secret on a configurable refresh interval. Automatic rotation: update the secret in the provider, the controller syncs within minutes. Best for: teams already on a cloud provider, multi-cluster setups, automatic rotation requirements. **HashiCorp Vault with Vault Agent sidecar or ESO Vault provider**: full secret lifecycle - dynamic secrets (database credentials that expire after 1 hour, automatically renewed), fine-grained policies per service account, audit log of every secret read. Vault Agent injects secrets directly into the pod filesystem - the secret never exists as a Kubernetes Secret, reducing exposure. Most powerful, most operationally complex. Best for: regulated environments, dynamic credentials, cross-cloud or on-premises setups. Decision matrix: start with Sealed Secrets for simplicity, migrate to ESO when you need rotation or multi-cluster, adopt Vault when you need dynamic credentials or cross-platform secret sharing.

**Q17: How do you roll back a broken deployment in ArgoCD?**

Three layers of rollback, ordered from fastest response to most architecturally correct: (1) **Argo Rollouts abort** - if the deploy was a canary or blue-green Rollout, `kubectl argo rollouts abort shopapp` immediately stops promotion and returns all traffic to stable. Fastest - takes seconds. (2) **ArgoCD CLI/UI rollback to a previous Git revision** - `argocd app rollback shopapp-production --revision <git-sha>` syncs the cluster to a prior Git SHA without modifying the repository. The cluster diverges from Git temporarily, but production is restored in under a minute. Use for emergencies when you cannot wait for a git revert PR. (3) **Git revert** - `git revert HEAD` creates a new commit that undoes the breaking change. Push to trigger ArgoCD auto-sync. This is the correct GitOps approach: all changes are in Git history, the cluster converges to the reverted state automatically, and the audit trail is intact. After any emergency ArgoCD CLI rollback, always follow up with a git revert - otherwise the next auto-sync re-applies the broken state.

**Q18: Describe a GitOps promotion pipeline from dev to production.**

Full pipeline: (1) Developer merges a PR to `main` in the application source repo. CI builds, runs tests, pushes `ghcr.io/acme/shopapp:sha-abc123`. CI also commits `newTag: sha-abc123` to `overlays/dev/kustomization.yaml` in the config repo. (2) ArgoCD detects the config change and syncs the dev Application. DORA lead time metric is recorded. (3) A promotion bot (GitHub Actions triggered by ArgoCD webhook on dev `Healthy`) verifies the dev Application health, then opens a PR against `overlays/staging/kustomization.yaml` with the same tag. PR body includes the tag, source environment, and a link to the dev sync event. (4) A senior engineer reviews - the diff must be exactly one line change (the newTag). Merges. ArgoCD syncs staging. Integration tests run. (5) After a 30-minute soak on staging, the bot opens a second PR for `overlays/prod`. This PR requires two approvals and a passing status check from a staging smoke test suite. (6) After approval, the prod PR merges. Prod has `autoSync: false` - an ops engineer inspects the ArgoCD UI diff and clicks Sync. Argo Rollouts executes the canary steps with Prometheus analysis gates before full promotion. Every step has a Git commit SHA, actor, and timestamp - a complete audit chain requiring no external tooling.

**Q19: How does Flux differ from ArgoCD - when would you choose each?**

Core philosophical difference: ArgoCD is **centralized** (one server manages N clusters, strong web UI, ApplicationSet for bulk Application generation). Flux is **decentralized** (each cluster runs its own independent controller set, no central server, CLI-first). ArgoCD advantages: rich web UI valuable for platform teams managing many clusters from one place. ApplicationSet generates hundreds of Applications dynamically. Mature RBAC controls who can sync which Application. Large enterprise community. Flux advantages: each cluster is fully autonomous with no dependency on a central control plane (no single point of failure). Image Automation Controller watches a registry and auto-commits updated image tags to Git - no external bot required. `OCIRepository` source type pulls Kustomize configs packaged as OCI artifacts without needing Git access. More Kubernetes-native (standard controller-runtime, works well with GitOps Toolkit). Choose **ArgoCD** when: platform team needs multi-cluster visibility from one pane of glass, you need fine-grained RBAC (different teams own different Applications), or ApplicationSet's generators (cluster, Pull Request, SCM provider) solve your multi-cluster rollout problem. Choose **Flux** when: each cluster must be self-sufficient with no dependency on external infrastructure, you value Image Automation for auto-tag updates, or you are embedding GitOps into a product where running a full ArgoCD server is impractical.

**Q20: How do you test GitOps configurations before applying to production?**

Testing at each layer: (1) **Schema validation in CI** - `kustomize build overlays/prod | kubeconformist` catches invalid API fields immediately on every PR. (2) **OPA/Conftest policy tests** - write Rego rules asserting all Deployments have `resources.limits`, all Services have matching NetworkPolicies, no `latest` image tags. Run `conftest test overlays/prod` in CI before merge. (3) **Server-side dry run** - `kubectl apply --dry-run=server` runs the full admission webhook chain (including Gatekeeper constraints) without creating resources. Catches policy violations and webhook rejections that schema validation misses. (4) **ArgoCD diff in PR comments** - a GitHub Actions step runs `argocd app diff shopapp-production --revision <PR-head-sha>` and posts the output as a PR comment. Reviewers see exactly what will change in the cluster before approving. (5) **Preview environments** - ArgoCD ApplicationSet with PR generator deploys each config repo PR to `preview-pr-<number>` namespace. Automated smoke tests run against the preview. If smoke tests fail, the PR is blocked. (6) **Unit tests for Helm charts or Kustomize generators** - `helm unittest` or custom Go test that runs `kustomize build` and asserts on the output manifests (correct replica count, correct image tag format, required labels present).

**Q21: How do you handle database migrations in a GitOps workflow?**

Database migrations are the hardest GitOps concern because they are stateful and often irreversible. Three patterns from simplest to safest: (1) **Init container** - add a migration init container to the Deployment that runs `migrate up` before the application starts. Simple but fragile: if the migration exceeds Kubernetes pod restart thresholds, the pod enters `CrashLoopBackOff` mid-migration. Acceptable only for fast (sub-30-second) idempotent migrations. (2) **ArgoCD PreSync Job** - a Kubernetes Job annotated `argocd.argoproj.io/hook: PreSync` and `argocd.argoproj.io/hook-delete-policy: HookSucceeded` runs before ArgoCD syncs any other resource. ArgoCD waits for the Job to succeed. If it fails, the entire sync is aborted and no application resources are updated. This is the recommended pattern: the migration is atomic with the deployment from ArgoCD's perspective. Add `argocd.argoproj.io/sync-wave: "-1"` to ensure the Job runs before Deployments in the same sync wave. (3) **Expand-contract (two-phase) migrations** - for true zero-downtime: deploy phase 1 adds new nullable column, application code handles both old and new schema, deploy phase 2 (after all pods are on new code) removes old column. This decouples the database change from the application change, allowing safe rollback of either independently. Always test migrations on a production-sized database dump in staging before applying to production.

**Q22: How do you implement an emergency hotfix process in GitOps?**

The GitOps principle - all changes via Git with code review - creates friction that is normally beneficial but is a liability during a production outage. The emergency process must be designed and documented before an incident occurs. Four-part framework: (1) **Rollback first, hotfix second** - if the incident was caused by a recent deployment, `argocd app rollback` or `kubectl argo rollouts abort` restores the previous known-good state in under a minute, buying time to write a proper fix. Make this step 1 in every incident runbook. (2) **Break-glass branch with relaxed protection** - maintain a `hotfix/` branch in the config repo with branch protection rules that allow a single approval by oncall engineers (instead of the usual two). ArgoCD production Applications watch both `main` and `hotfix/` (using `targetRevision: HEAD` with a source that checks `hotfix/` first). After the emergency, the hotfix is cherry-picked to `main` via a standard PR. (3) **Direct ArgoCD sync bypass** - ArgoCD administrators can `argocd app sync shopapp-production --revision <specific-sha>` from a pre-tested SHA without waiting for any PR process. This bypasses Git workflow entirely - document it as a last resort, require a security alert to be triggered whenever it is used. (4) **Post-incident cleanup** - all emergency bypasses must result in a follow-up PR that captures the change in `main` with full context (what broke, why this fix works, what monitoring was added). Treat every break-glass event as a security event: alert the security team, document in the incident record, and review whether the normal promotion process needs adjusting to prevent recurrence.

### Junior → FAANG: Building Depth on Continued Questions

Questions 16-22 are designed for L4-L5 interviews where interviewers probe operational experience. The pattern in each answer is: name the options, explain the trade-offs, state which option applies to which context, and describe what you would do in your current or most recent role.

For Q16 (secrets comparison): the decision matrix (Sealed Secrets for simplicity, ESO for rotation, Vault for dynamic credentials) is the answer expected at L4. At L5, add the rotation failure mode for Sealed Secrets and explain when you would trigger a migration from Sealed Secrets to ESO.

For Q21 (database migrations): the three patterns form a complexity-safety ladder. Init container is simple but brittle for long migrations. PreSync Job is the recommended pattern for most cases. Expand-contract is the only option for truly zero-downtime on breaking schema changes. Knowing when to apply each, and being able to justify that decision to a product team that wants to merge the migration immediately, is the L5 operational judgment component.

Q22 (emergency hotfix) is the most important question to have a specific, practiced answer for. Interviewers asking this question want to understand whether you have actually been in a production incident with a GitOps system and what you did. A vague answer ("we would use a hotfix branch") signals no operational experience. A specific answer ("we maintain a hotfix/ branch with single-approval protection, the on-call triggers the ArgoCD sync manually, and the post-incident PR is required within 4 hours of the incident resolution") signals that you have designed and tested this process.

### Senior @ FAANG: These Questions as L6 System Design Seeds

At L6, questions 16-22 are starting points for system design conversations, not standalone interview answers. Each question has a natural extension that probes organizational design and platform thinking.

Q17 (rollback strategy) at L6: the bar-raiser follow-up is "how do you ensure that a successful `argocd app rollback` is followed by a git revert and not left as a diverged state?" The answer involves an automated reconciliation check: a scheduled job that alerts when any ArgoCD Application's live revision differs from its configured target revision for more than N minutes. This alert fires when emergency bypasses are used and have not been cleaned up.

Q19 (Flux vs ArgoCD) at L6: the ADR framing is "you are choosing the GitOps tool for a 200-engineer organization starting from zero. What information do you need and what is your recommendation?" The expected answer covers: organizational structure (centralized platform team vs distributed ownership), cluster count and topology (single region vs multi-region), existing observability stack (Datadog vs Prometheus), security team requirements (audit log format, SIEM integration), and on-call model (platform team on-call vs embedded SREs). The recommendation follows from these inputs, not from a generic preference.

Q22 (emergency hotfix) at L6: the ADR framing is "how do you balance GitOps discipline with incident response speed?" The answer involves defining explicit SLO thresholds that determine when break-glass is appropriate, implementing automatic break-glass detection (alert when any production Application is synced to a non-main revision), and designing the post-incident review process to capture lessons that improve the normal promotion process. At this level, the emergency hotfix process is a feedback loop into the GitOps maturity model, not an exception to it.
