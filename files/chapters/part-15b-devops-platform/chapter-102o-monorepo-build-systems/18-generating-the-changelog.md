## 102O.16 Generating the Changelog & Release Automation

### Generating the Changelog

Generate changelog for the next release:

```bash
# Generate changelog since last tag
git cliff --output CHANGELOG.md

# Generate for a specific range
git cliff v1.2.0. HEAD --output CHANGELOG.md

# Preview next version based on commits
git cliff --bumped-version
# Output: v1.3.0
```

### Semantic Versioning for Go Modules

Go modules have specific requirements for semantic versioning that differ from other ecosystems.

**v0 and v1**: No import path suffix required.

```
module github.com/mycompany/mylib

go 1.27
```

**v2+**: The module path must include the major version suffix. This is Go's "import compatibility rule" - if the major version changes, it is a different module from the consumer's perspective.

```
module github.com/mycompany/mylib/v2

go 1.27
```

Consumers upgrade explicitly:

```go
// Before
import "github.com/mycompany/mylib"

// After upgrading to v2
import "github.com/mycompany/mylib/v2"
```

In a monorepo with multiple modules, manage major version bumps carefully:

```bash
# Bump major version of a shared library
cd libs/auth
# Update go.mod module path to . ./v2
sed -i 's|module mycompany.com/libs/auth$|module mycompany.com/libs/auth/v2|' go.mod

# Update all internal importers
grep -r '"mycompany.com/libs/auth"' . /. --include="*.go" -l | \
 xargs sed -i 's|mycompany.com/libs/auth"|mycompany.com/libs/auth/v2"|g'
```

### Automated Release PR Bot in Go

A Go program that watches for merged PRs with conventional commits and opens a release PR with a bumped version and generated changelog.

```go
package main

import (
 "context"
 "fmt"
 "log"
 "os"
 "os/exec"
 "strings"

 "github.com/google/go-github/v60/github"
 "golang.org/x/oauth2"
)

type ReleaseBot struct {
 client *github.Client
 owner string
 repo string
}

func NewReleaseBot(token, owner, repo string) *ReleaseBot {
 ts := oauth2.StaticTokenSource(&oauth2.Token{AccessToken: token})
 tc := oauth2.NewClient(context.Background(), ts)
 return &ReleaseBot{
 client: github.NewClient(tc),
 owner: owner,
 repo: repo,
 }
}

// DetermineNextVersion runs git-cliff to compute next semver tag.
func (b *ReleaseBot) DetermineNextVersion() (string, error) {
 out, err := exec.Command("git", "cliff", "--bumped-version").Output()
 if err != nil {
 return "", fmt.Errorf("git-cliff: %w", err)
 }
 return strings.TrimSpace(string(out)), nil
}

// GenerateChangelog produces CHANGELOG.md content for the new version.
func (b *ReleaseBot) GenerateChangelog(version string) (string, error) {
 out, err := exec.Command("git", "cliff", "--tag", version, "--unreleased").Output()
 if err != nil {
 return "", fmt.Errorf("generate changelog: %w", err)
 }
 return string(out), nil
}

// CreateReleasePR opens a pull request to bump the version.
func (b *ReleaseBot) CreateReleasePR(ctx context.Context, version, changelog string) error {
 branchName := "release/" + version
 title := "chore(release): " + version
 body := "## Automated Release\n\n" +
 "This PR was automatically generated by the release bot.\n\n" +
 "### Changelog\n\n" + changelog

 // Create branch via GitHub API
 ref, _, err := b.client.Git.GetRef(ctx, b.owner, b.repo, "refs/heads/main")
 if err != nil {
 return fmt.Errorf("get main ref: %w", err)
 }

 newRef := &github.Reference{
 Ref: github.String("refs/heads/" + branchName),
 Object: ref.Object,
 }
 if _, _, err = b.client.Git.CreateRef(ctx, b.owner, b.repo, newRef); err != nil {
 return fmt.Errorf("create branch: %w", err)
 }

 // Open PR
 pr := &github.NewPullRequest{
 Title: github.String(title),
 Head: github.String(branchName),
 Base: github.String("main"),
 Body: github.String(body),
 MaintainerCanModify: github.Bool(true),
 }
 created, _, err := b.client.PullRequests.Create(ctx, b.owner, b.repo, pr)
 if err != nil {
 return fmt.Errorf("create PR: %w", err)
 }

 log.Printf("Release PR created: %s", created.GetHTMLURL())
 return nil
}

func main() {
 bot := NewReleaseBot(
 os.Getenv("GITHUB_TOKEN"),
 os.Getenv("GITHUB_OWNER"),
 os.Getenv("GITHUB_REPO"),
 )
 ctx := context.Background()

 version, err := bot.DetermineNextVersion()
 if err != nil {
 log.Fatalf("determine version: %v", err)
 }
 log.Printf("Next version: %s", version)

 changelog, err := bot.GenerateChangelog(version)
 if err != nil {
 log.Fatalf("generate changelog: %v", err)
 }

 if err := bot.CreateReleasePR(ctx, version, changelog); err != nil {
 log.Fatalf("create release PR: %v", err)
 }
}
```

### Release Trains

Release trains are scheduled, time-based releases rather than feature-based releases. Every two weeks (or every sprint), whatever is merged to main ships, regardless of feature completeness.

```yaml
# .github/workflows/release-train.yml
name: Release Train

on:
 schedule:
 - cron: '0 10 * * 1' # Every Monday at 10:00 UTC (biweekly via workflow condition)

jobs:
 release:
 runs-on: ubuntu-latest
 steps:
 - uses: actions/checkout@v4
 with:
 fetch-depth: 0
 token: ${{ secrets.RELEASE_BOT_TOKEN }}

 - name: Check if release is due (biweekly)
 id: check
 run: |
 # Only release on even-numbered weeks
 WEEK=$(date +%V)
 if (( WEEK % 2 == 0 )). Then
 echo "release=true" >> $GITHUB_OUTPUT
 else
 echo "release=false" >> $GITHUB_OUTPUT
 fi

 - name: Determine next version
 if: steps.check.outputs.release == 'true'
 run: |
 VERSION=$(git cliff --bumped-version)
 echo "VERSION=$VERSION" >> $GITHUB_ENV

 - name: Create git tag
 if: steps.check.outputs.release == 'true'
 run: |
 git tag "${{ env.VERSION }}"
 git push origin "${{ env.VERSION }}"

 - name: Create GitHub Release
 if: steps.check.outputs.release == 'true'
 env:
 GH_TOKEN: ${{ secrets.RELEASE_BOT_TOKEN }}
 run: |
 NOTES=$(git cliff --tag "${{ env.VERSION }}" --unreleased)
 gh release create "${{ env.VERSION }}" \
 --title "${{ env.VERSION }}" \
 --notes "$NOTES"
```

### Go Module Proxy for Internal Modules

Internal modules should be served through a private Go module proxy to: enforce access control, cache external dependencies for reproducibility, and prevent external dependency changes from breaking builds.

```bash
# Athens - self-hosted Go module proxy
docker run -p 3000:3000 \
 -e ATHENS_STORAGE_TYPE=disk \
 -e ATHENS_DISK_STORAGE_ROOT=/var/lib/athens \
 -v /data/athens:/var/lib/athens \
 gomods/athens:latest
```

Configure developers and CI to use it:

```bash
# Route internal modules to private proxy, everything else to public
export GONOSUMCHECK="mycompany.com/*"
export GONOSUMDB="mycompany.com/*"
export GOFLAGS="-mod=mod"
export GOPROXY="https://proxy.mycompany.com|https://proxy.golang.org|direct"
export GOPRIVATE="mycompany.com/*"
```

Athens can be configured to exclude private modules from the public sum database check while still caching public dependencies:

```toml
# athens config.toml
[Storage]
 [Storage.Disk]
 RootPath = "/var/lib/athens"

NoSumPatterns = ["mycompany.com/*"]
NoSumDB = ["mycompany.com/*"]

[Proxy]
 RecursionBaseURL = "https://proxy.golang.org"
```

### Junior → FAANG: Conventional Commits Are a Professional Habit, Not a Convention

The conventional commit format (`feat:`, `fix:`, `feat!:`) is not just a team convention. It is the input format for an entire class of automated tooling: version bumping, changelog generation, release PR bots, and CHANGELOG rendering in GitHub releases. Writing clear conventional commits is a first-job habit that signals professional maturity because it shows you understand that commit history is documentation.

The most common mistake: writing `fix: stuff` instead of `fix(auth): return 401 instead of 500 when JWT is expired`. The scope and the description are what make the commit useful to humans reading the changelog and to automated tools computing the version bump.

For interviews: be ready to explain how conventional commits drive automated semantic versioning. The key chain is: commit type determines version bump (feat = minor, fix = patch, feat! = major), automated tooling reads commits since the last tag to compute the next version, and the release bot opens a PR with the bumped version and a generated CHANGELOG.

### Senior @ FAANG: Release Engineering as a Platform Capability

Release engineering in a monorepo is a platform capability with reliability, security, and governance dimensions that are often underappreciated until something goes wrong. Reliability: if the release bot fails silently, services accumulate unreleased changes and teams lose confidence in automated releases. Security: a release pipeline that can be triggered by any engineer without approval for any service is a supply chain risk. Governance: without a defined policy for what constitutes a release (every merge, weekly train, or manual trigger), teams make inconsistent choices that make release history hard to reason about.

The governance framework for release engineering: define a release policy per service tier. Tier-1 critical services require manual approval and signed artifacts. Tier-2 services auto-release on merge with a mandatory security scan. Tier-3 internal tools release freely. Enforce tier classification through the CI pipeline, not through documentation. A service under `critical-services/` automatically inherits the tier-1 pipeline with approval gates and artifact signing.

The Go module proxy (Athens) is the infrastructure component that makes release engineering reliable at scale. Without a private proxy, CI depends on the public internet for every build, creating a reliability dependency on `proxy.golang.org` and `sum.golang.org`. A self-hosted Athens instance that caches all external dependencies, combined with `GONOSUMCHECK` for internal modules, makes builds reproducible and internet-independent. This is a requirement for any organization with SOC 2 Type II or FedRAMP compliance, where dependency provenance must be auditable.
