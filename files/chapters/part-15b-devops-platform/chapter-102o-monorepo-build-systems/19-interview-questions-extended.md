## 102O.17 Advanced Interview Questions

**Q: What are the core tradeoffs between monorepo and polyrepo architectures?**

A: Monorepo advantages: atomic commits across services (refactor an API and update all callers in one PR), unified tooling and dependency versions (one `go.mod` or workspace), easier code sharing, and simplified developer onboarding (one clone). Disadvantages: tooling complexity grows with repo size, access control is harder (all code visible to all developers), CI must be smart about what to build (otherwise every commit builds everything), and repository operations (`git clone`, `git log`) slow down over time. Polyrepo advantages: clean team ownership boundaries, independent CI/CD, smaller attack surface per repo. Disadvantages: dependency hell across services, difficult atomic changes, inconsistent tooling, code duplication. Most large tech companies (Google, Facebook, Twitter) converged on monorepos and built custom tooling to solve the scaling problems.

**Q: How does Bazel achieve hermetic builds?**

A: Bazel achieves hermeticity through several mechanisms. First, every action (compilation, linking, test) runs in a sandbox that only has access to explicitly declared inputs - no access to the host filesystem, environment variables, or network unless whitelisted. Second, Bazel computes a content-addressed cache key from all inputs: source file hashes, toolchain version, compiler flags, and rule definitions. Third, Go rules use `pure = "on"` to disable CGO, eliminating dependency on host shared libraries. Fourth, toolchains are hermetically downloaded and pinned by hash in the WORKSPACE file, so all developers and CI workers use the exact same compiler. The result is that the same source always produces bit-for-bit identical outputs, making remote caching safe - you can trust a cache hit from a different machine.

**Q: What is affected analysis and how does it speed up CI?**

A: Affected analysis computes the minimal set of services and packages that need to be rebuilt and retested given a specific set of changed files. In a monorepo with 50 services, a change to one service's internal code should only rebuild and test that one service. Affected analysis works by: (1) computing a dependency graph of all packages and services, (2) finding which packages contain changed files (`git diff --name-only`), (3) traversing the dependency graph upward to find all services that transitively depend on those packages, and (4) only running CI for that affected set. The speedup is dramatic: a change that touches one service in a 50-service monorepo runs 1/50th of the CI pipeline. The Nx project graph, Bazel's incremental build graph, and custom scripts using `golang.org/x/tools/go/packages` all implement variants of this.

**Q: How do you manage Go module dependencies in a monorepo?**

A: There are three main strategies. Single-module monorepo: one `go.mod` at the root, all packages share dependencies, simplest approach but forces all services to upgrade dependencies together. Multi-module with `go.work`: each service has its own `go.mod`, `go.work` allows them to reference each other locally during development, and each service is published independently. This is the recommended approach for large monorepos as it allows independent versioning and deployment. Multi-module without `go.work` (pre-1.18): use `replace` directives in `go.mod` to point to local paths, but these are tedious to maintain and must be removed before publishing. For internal shared libraries, pin to specific versions in each service's `go.mod` and use Dependabot or Renovate to automate version bumps.

**Q: What is go.work and when should you use it?**

A: `go.work` is a Go workspace file introduced in Go 1.18 that allows multiple modules to be developed together without publishing intermediate versions. Use it when: you have a monorepo with multiple interdependent Go modules that are developed together, you want to test changes to a shared library against all its consumers before publishing, or you want to avoid `replace` directives which leak into the published `go.mod`. Do not use `go.work` in published modules - it is a development tool only. `go.work.sum` should be committed to ensure reproducible builds in CI. The workspace file is analogous to `package.json` workspaces in the Node ecosystem or a multi-project Gradle build.

**Q: How does Google scale their monorepo to 2 billion lines of code?**

A: Google's monorepo (internally called "the repository" or Piper) achieves scale through several innovations. Storage: Piper uses a distributed file system where developers only sync the parts of the repo they need (sparse checkout), so no developer ever has all 2 billion lines locally. Builds: the internal build system (Blaze, open-sourced as Bazel) uses hermetic, content-addressed caching with a global remote cache shared across all employees. A build that was run anywhere in the company is cached and reused. The critical path for any build is typically under 5 minutes because most actions hit the cache. Code search: a custom code search tool (Kythe) indexes the entire codebase and provides semantic search, call graph navigation, and cross-reference analysis. Dependency management: all dependencies are checked into the monorepo (including third-party) in a `third_party/` directory, with one version of each dependency enforced globally. This eliminates diamond dependency problems entirely.

**Q: What is trunk-based development and how does it relate to monorepos?**

A: Trunk-based development (TBD) is a source control branching model where all developers commit directly to a single branch ("trunk" or "main") or use very short-lived feature branches (less than 2 days). It contrasts with long-lived feature branches and Gitflow. TBD pairs naturally with monorepos because: (1) it enables the atomic commits that make monorepos valuable - if everyone commits to main, a refactor in a shared library and its callers ships as one commit, (2) it forces continuous integration - code is always in a releasable state, (3) it reduces merge conflicts that become catastrophic in large monorepos with long-lived branches. Feature flags are the key enabler: incomplete features are committed behind a flag (`if featureFlags.Get("new-checkout-flow")`) and enabled only when ready. Google, Facebook, and most large-scale monorepo teams practice TBD.

**Q: How do you handle breaking changes to shared libraries in a monorepo?**

A: Several strategies, from least to most formal. Expand-contract (also called parallel change): add the new API alongside the old, migrate all consumers in the same commit or PR, then delete the old API. This works well in a monorepo because all consumers are in the same repo and can be migrated atomically. Feature flags on the library side: the library supports both behaviors, a flag controls which is active, allowing gradual rollout. Semantic versioning with major version suffix: introduce `libs/auth/v2` as a new Go module, migrate consumers gradually, deprecate v1. Large-scale refactoring tools: use `gopls` refactoring, `gofmt -r` rewrite rules, or `ast` manipulation to mechanically update all call sites in one commit. In Google's monorepo, large-scale changes (LSCs) are managed through a dedicated tooling pipeline that can atomically update thousands of files. The key principle: never leave the monorepo in a broken state between commits. If a breaking change requires multiple commits, use feature flags or the expand-contract pattern to maintain a green build throughout.

### Junior → FAANG: Answering Depth Questions Confidently

These seven questions cover the full breadth of monorepo system design. For each one, practice answering in two phases: a 30-second summary that hits the key points, followed by a 2-minute deep dive when the interviewer probes further. The 30-second summary is what you say first. The deep dive is what you have ready when they ask "can you say more about that?"

For the trunk-based development question, the detail that most candidates miss is feature flags. TBD without feature flags is impractical because incomplete features would ship to users. Feature flags are what make it possible to commit daily to main without exposing half-built functionality. Being able to articulate this dependency shows systems-level thinking.

For the "how does Google scale" question, the detail that earns points is sparse checkout: no engineer has all 2 billion lines locally. They sync only the subtrees they need. This is a fundamental difference from how most engineers think about a monorepo (as a large single directory that everyone clones).

### Senior @ FAANG: Bar-Raiser Design Questions Behind Each Answer

Each of these interview questions has a follow-up system design question that appears in L6/L7 bar-raiser rounds. For the hermetic builds question: "design a remote cache architecture for a 1,000-engineer organization. Include storage sizing, eviction policy, access control, and how you handle cache poisoning." For the affected analysis question: "you have a monorepo with 3,000 packages and your affected analysis is taking 90 seconds to compute. Diagnose the bottleneck and redesign the system to compute in under 5 seconds." For the trunk-based development question: "design a feature flag system that allows 500 engineers to safely commit to main daily. Include how flags are defined, how they propagate to services, how they are cleaned up after a feature ships, and how you prevent flag sprawl."

These questions test whether you can move from conceptual understanding to concrete system design with trade-off analysis. The answers require knowledge of specific technologies (Bazel's query language, content-addressed storage, flag management systems) combined with organizational process design. Practicing these design questions, not just the conceptual answers, is what distinguishes a hire at L6 from a strong pass at L5.
