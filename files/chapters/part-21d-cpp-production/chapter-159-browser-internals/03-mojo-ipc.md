## 159.3 Mojo IPC

Mojo is Chromium's IPC system. It replaced the legacy `IPC::Channel` system over the period 2016 through 2020 and is now the only sanctioned way to communicate across Chromium processes. Every API surface between renderer and browser, between browser and GPU, between any pair of processes, is a Mojo interface.

### Why Mojo Exists

The legacy `IPC::Channel` system was a single message pipe per process pair, with manually-numbered message IDs, manual serialization, and no notion of interfaces. Adding a feature meant editing a giant `.h` file of message IDs in `content/`, and routing was a nightmare. Worse, Channel had no way to pass new pipes across, so the entire process topology was static.

Mojo gives you:

1. **Typed interfaces** declared in `.mojom` IDL, generated into C++ (and JS, Java) bindings.
2. **Message pipes** that can be passed over other message pipes, allowing dynamic process topologies.
3. **Data pipes** for byte streams (uploads, video frames, large blobs).
4. **Shared buffers** for zero-copy memory regions.
5. **Validation** generated from the IDL: every message is bounds-checked before reaching your handler.

### The .mojom Language

A trimmed example from `services/network/public/mojom/url_loader.mojom`:

```mojom
module network.mojom;

import "services/network/public/mojom/url_request.mojom";
import "services/network/public/mojom/url_response_head.mojom";

interface URLLoader {
  // Follow a redirect that the client previously paused.
  FollowRedirect(array<string> removed_headers,
                 array<HttpHeader> modified_headers,
                 url.mojom.Url? new_url);

  // Set request priority mid-flight.
  SetPriority(RequestPriority priority,
              int32 intra_priority_value);
};

interface URLLoaderClient {
  OnReceiveResponse(URLResponseHead head,
                    handle<data_pipe_consumer>? body);
  OnReceiveRedirect(URLRequestRedirectInfo redirect_info,
                    URLResponseHead head);
  OnComplete(URLLoaderCompletionStatus status);
};
```

The `mojom` compiler turns this into C++ headers with concrete classes. `URLLoader` becomes:

- `network::mojom::URLLoader`: pure virtual interface.
- `mojo::Remote<network::mojom::URLLoader>`: a typed proxy you call.
- `mojo::Receiver<network::mojom::URLLoader>`: holds your implementation, dispatches incoming messages.
- `mojo::PendingRemote<...>`, `mojo::PendingReceiver<...>`: serializable handle types you can pass over IPC.

### Implementing and Binding an Interface

Define the interface (renderer-to-browser, say a settings reader):

```mojom
// chrome/common/foo.mojom
module chrome.mojom;

interface FooSettings {
  GetUserName() => (string user_name);
  SetTheme(string theme_id);
};
```

Implement it in the browser process:

```cpp
// chrome/browser/foo_settings_impl.h
#include "chrome/common/foo.mojom.h"
#include "mojo/public/cpp/bindings/receiver.h"

class FooSettingsImpl : public chrome::mojom::FooSettings {
 public:
  explicit FooSettingsImpl(
      mojo::PendingReceiver<chrome::mojom::FooSettings> receiver)
      : receiver_(this, std::move(receiver)) {}

  // chrome::mojom::FooSettings:
  void GetUserName(GetUserNameCallback callback) override {
    std::move(callback).Run(profile_->GetUserName());
  }

  void SetTheme(const std::string& theme_id) override {
    if (!IsValidThemeId(theme_id))
      return;  // Drop invalid input from compromised renderer.
    profile_->SetTheme(theme_id);
  }

 private:
  mojo::Receiver<chrome::mojom::FooSettings> receiver_;
  raw_ptr<Profile> profile_;
};
```

Hand the renderer a remote:

```cpp
// In the browser, when creating a renderer:
mojo::PendingRemote<chrome::mojom::FooSettings> remote;
auto impl = std::make_unique<FooSettingsImpl>(
    remote.InitWithNewPipeAndPassReceiver());
// Pass `remote` to the renderer through the existing BrowserInterfaceBroker.
```

Renderer side:

```cpp
mojo::Remote<chrome::mojom::FooSettings> settings;
GetBrowserInterfaceBroker()->GetInterface(
    settings.BindNewPipeAndPassReceiver());

settings->GetUserName(base::BindOnce([](const std::string& name) {
  // Runs on the same sequence that called Get/Bind.
  LOG(INFO) << "Got user name: " << name;
}));
```

The callback for `GetUserName` is generated by the bindings because the IDL declared a return value with `=> (...)`. Methods without a return value are fire-and-forget.

### Message Pipes vs Data Pipes vs Shared Buffers

Three primitives, three use cases.

**Message pipes** carry typed messages. Ordered, reliable, bidirectional. Each Mojo interface lives on a message pipe. Good for control plane. Not good for streaming.

**Data pipes** carry untyped bytes. One producer, one consumer, unidirectional. Internally a ring buffer in shared memory. Good for streaming response bodies, file uploads, video frames. The `URLLoaderClient::OnReceiveResponse` example above passes the body as a `handle<data_pipe_consumer>`.

**Shared buffers** (`mojo::ScopedSharedBufferHandle`) are raw shared memory regions. Used for the V8 snapshot, large texture uploads, audio ring buffers. Caller is responsible for synchronization. The compositor uses these heavily for tile uploads.

### Sync Calls and Why You Should Avoid Them

Mojo supports `[Sync]` methods that block the calling thread until a reply arrives. They exist for legacy reasons (porting `IPC::SyncMessage`) and for cases where async genuinely cannot work (synchronous DOM APIs reading clipboard contents). They are expensive: the calling thread blocks, but the bindings still pump messages internally to avoid deadlock, which means re-entrancy can happen mid-call.

Rule: if your interface has more than one or two sync methods, the design is wrong. Refactor to async with callbacks.

### Associated Interfaces

A standalone Mojo interface lives on its own message pipe. Two messages on different pipes have no ordering guarantee relative to each other, even within the same process pair. This matters when you have a control interface ("navigate to URL") and a content interface ("DOM mutated") that need to be ordered.

Associated interfaces share a single underlying pipe with another interface. Messages across all interfaces associated with that pipe are FIFO. The cost: only one of them can dispatch at a time.

```mojom
interface Frame {
  // ...
};

interface FrameNavigationClient {
  // Associated to Frame's pipe - navigation messages are ordered with
  // other Frame messages.
};
```

### Validation and Sandbox Trust

Generated bindings validate every incoming message before invoking your handler:

- Struct fields are bounds-checked.
- Handle counts match the descriptor.
- Required fields are present.
- Enum values are in range.

If validation fails, Mojo kills the sending process. This is correct behavior: a malformed message means the sender is buggy or compromised, and you do not negotiate with a compromised process.

Validation does not check semantic correctness. The `SetTheme(string theme_id)` example above must validate `theme_id` itself in the implementation. The sandbox-escape attack pattern is: compromise renderer, send a syntactically-valid but semantically-malicious Mojo message that exploits a bug in the browser-side handler. This is why Mojo handlers in the browser process are scrutinized by security review.

### The Generated Code

The mojom compiler generates roughly 5x to 10x as many lines of C++ as the original `.mojom`. For a typical interface you get:

- Interface base class with pure virtual methods.
- `Proxy_` class implementing `Remote<T>::operator->()` calls.
- `StubDispatch_` class that decodes incoming messages and calls into your impl.
- Validation code per struct.
- A `*::DataView` type for zero-copy reads off the wire.

Read the generated `*.mojom.h` and `*.mojom.cc` once for any non-trivial interface. The patterns are mechanical, but understanding them helps when debugging crashes inside Mojo dispatch.

### Tracing and Debugging

`chrome://tracing` (or perfetto) categories `mojom` and `ipc` show every message with its interface name, method name, and pipe ID. A typical regression hunt:

1. Record a trace covering the slow operation.
2. Filter to `mojom` events.
3. Find the long-poll messages or sync waits.
4. Cross-reference with the `cc` and `blink` categories on the same timeline.

`tools/diagnostics/mojo` has scripts for dumping the entire pipe topology of a running Chrome.
