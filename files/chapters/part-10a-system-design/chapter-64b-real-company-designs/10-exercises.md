## Exercises

1. **Reverse-Engineer Netflix's CDN Architecture**: Given that Netflix serves 15% of global internet traffic, design the CDN architecture from first principles before reading Netflix's published engineering blog posts. Specify the number of PoP locations (justify by continent), the cache hierarchy (edge vs regional vs origin), the content pre-positioning strategy for new releases, the failover path when an edge node goes down, and how Netflix handles the "new season premiere" traffic spike (10× normal for the first 2 hours). Compare your design to Netflix's actual Open Connect architecture and document the three biggest differences.

2. **Google Spanner Consistency Model Analysis**: Spanner achieves external consistency (a stronger guarantee than linearizability) across globally distributed data centers using TrueTime. Implement a simplified version of the TrueTime API in Go that simulates clock uncertainty with a configurable epsilon (7ms by default), implement a commit wait protocol that delays a write transaction's commit until the uncertainty window passes, and demonstrate with a test that two transactions T1 (commit in US-East) and T2 (commit in EU-West, starts after T1 commits) always observe T1's writes. Document the latency cost of commit wait and the trade-off with availability during a GPS clock failure.

3. **Discord's Message Storage Evolution**: Discord migrated from MongoDB to Cassandra to ScyllaDB as their message storage grew from millions to billions of messages. Design each stage of this evolution: (a) the MongoDB document schema for a message with reactions, threads, and attachments, and explain at what scale it breaks. (b) the Cassandra partition key design that enables efficient channel timeline queries and the tombstone problem that emerges at scale. (c) the ScyllaDB schema improvements and the hot partition mitigation strategy. For each stage, identify the primary bottleneck that forced the migration and the data migration strategy used without downtime.

4. **Slack's WebSocket Architecture**: Implement a simplified version of Slack's WebSocket gateway in Go that supports 10M concurrent connections across a fleet of gateway servers, routes messages to the correct server using a Redis pub/sub channel per connected user, handles reconnection with session resumption (client sends last received message ID and server replays missed messages from a 60-second buffer), and performs rolling restarts that drain connections gradually to avoid a thundering herd. Write a load test that sustains 100K concurrent connections per server instance and measures message delivery latency at p50, p95, and p99.

5. **Uber's Microservices Migration Lessons**: Uber migrated from a monolith to 2,000+ microservices and then began consolidating back into "macro-services." Design a migration strategy for a monolithic ride-hailing application (drivers, riders, trips, payments, notifications in one service) that extracts the payments service first. Define the strangler fig pattern implementation, the database decomposition strategy (shared DB to separate DB with dual-write transition), the contract testing approach to prevent regressions, the rollback plan if the payments service has a critical bug post-migration, and the success metrics that would validate the migration. Identify the top three failure modes from Uber's actual experience and how your design avoids them.

6. **Stripe's Idempotency Layer**: Design and implement a Stripe-style idempotency layer in Go that allows clients to safely retry any API request using an `Idempotency-Key` header. The system must store the request fingerprint (method + path + body hash) and response for each key for 24 hours, return the cached response for duplicate requests without re-executing the business logic, handle the case where the original request is still in-flight (return 409 Conflict), use a distributed lock to prevent concurrent execution of the same idempotency key across multiple API server instances, and clean up expired keys efficiently. Write tests for concurrent duplicate requests, in-flight collision, expiry, and a full end-to-end payment retry scenario.

### Junior -> FAANG: Choosing Which Exercise Demonstrates Breadth vs Depth

These six exercises span six different real-world companies and six different architectural problems. For interview preparation, you do not need to implement all six. You need to understand the core decision in each one and be able to explain it verbally.

Exercises 1 (Netflix CDN) and 3 (Discord storage evolution) are primarily analytical: they require reasoning about a published architecture, not implementing one. Practice explaining the trade-offs verbally. "Netflix separates the control plane (authentication, resolution) from the data plane (video bytes) because the data plane volume would overwhelm an AWS-hosted control plane, and edge servers are cheaper at volume than origin servers" is the level of explanation expected.

Exercises 2 (Spanner consistency) and 6 (Stripe idempotency) are primarily implementation exercises. For your portfolio, implement exercise 6. It is the most transferable: idempotency is a correctness concern in payment systems, notification systems, webhook delivery, and any other system that makes external calls with side effects. A correct, tested idempotency layer is a demonstrable artifact that interviewers can review.

Exercises 4 (Slack WebSocket) and 5 (Uber migration) are system design exercises with implementation components. Exercise 4's load test requirement (100K concurrent connections per server instance) is a concrete target that forces you to think about Go's goroutine scheduler, WebSocket frame allocation, and connection pooling at a level that most tutorials skip.

### Senior @ FAANG: The Meta-Lesson Across All Six Companies

Each exercise is grounded in a real migration that a real team executed under production constraints. The meta-lesson is that none of these migrations were planned from the beginning. They were responses to specific failure modes that emerged at specific scale thresholds.

Discord's MongoDB-to-Cassandra migration (exercise 3) was forced by a specific failure: MongoDB's WiredTiger storage engine could not maintain sub-10ms read latency for channel history queries as the messages collection grew past 100 million rows. The migration was not a preference for Cassandra's API. It was a necessity driven by a measured performance regression at a specific scale.

Uber's microservices consolidation (exercise 5) was forced by a different specific failure: operational complexity grew faster than team size. With 2,000 microservices and a finite on-call rotation, the mean time to diagnose a production incident grew to unacceptable levels because understanding a request's execution path required context about 15-20 interdependent services. Consolidating into macro-services reduced the cognitive overhead of debugging without sacrificing the scalability benefits of service decomposition.

The staff-level skill these exercises develop is the ability to identify the specific failure mode that an architectural change is designed to solve, and to verify that the proposed change actually solves that failure mode rather than introducing a different one. Cassandra solved Discord's read latency problem but introduced the tombstone accumulation problem. macro-services solved Uber's operational complexity problem but required careful API contract management between consolidated services. Every architectural change trades one problem for another. The engineer's job is to make that trade consciously, with full awareness of what is being given up.
