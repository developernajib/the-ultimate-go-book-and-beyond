## 60.9 Testing

The URL shortener test suite uses testify assertions and interfaces to isolate each service component from its dependencies, replacing the real Redis cache and PostgreSQL store with in-memory fakes that implement the same interfaces. This approach makes tests fast and deterministic without requiring running infrastructure, while still exercising the service logic, URL creation, short ID generation, redirect resolution, and expiration handling, with realistic scenarios. Boundary tests covering expired URLs, duplicate short IDs, and invalid long URL formats ensure the service handles edge cases that are common sources of production bugs.

```go
// service/url_service_test.go
package service

import (
    "context"
    "fmt"
    "testing"
    "time"

    "github.com/stretchr/testify/assert"
    "github.com/stretchr/testify/require"
)

func TestURLService_CreateAndGet(t *testing.T) {
    // Setup (use testcontainers or mocks)
    service := setupTestService(t)
    ctx := context.Background()

    // Test creating a short URL
    req := ShortenRequest{
        LongURL: "https://example.com/very/long/path/to/resource",
    }

    result, err := service.CreateShortURL(ctx, req)
    require.NoError(t, err)
    assert.NotEmpty(t, result.ShortID)
    assert.Equal(t, req.LongURL, result.LongURL)

    // Test retrieving the URL
    longURL, err := service.GetLongURL(ctx, result.ShortID)
    require.NoError(t, err)
    assert.Equal(t, req.LongURL, longURL)
}

func TestURLService_Deduplication(t *testing.T) {
    service := setupTestService(t)
    ctx := context.Background()

    req := ShortenRequest{
        LongURL: "https://example.com/dedupe-test",
    }

    // Create first URL
    result1, err := service.CreateShortURL(ctx, req)
    require.NoError(t, err)

    // Create same URL again
    result2, err := service.CreateShortURL(ctx, req)
    require.NoError(t, err)

    // Should return same short ID
    assert.Equal(t, result1.ShortID, result2.ShortID)
}

func TestURLService_CustomAlias(t *testing.T) {
    service := setupTestService(t)
    ctx := context.Background()

    req := ShortenRequest{
        LongURL:  "https://example.com/custom",
        CustomID: "myalias",
    }

    result, err := service.CreateShortURL(ctx, req)
    require.NoError(t, err)
    assert.Equal(t, "myalias", result.ShortID)

    // Try duplicate custom alias
    req2 := ShortenRequest{
        LongURL:  "https://example.com/other",
        CustomID: "myalias",
    }

    _, err = service.CreateShortURL(ctx, req2)
    assert.Error(t, err)
}

func TestURLService_Expiration(t *testing.T) {
    service := setupTestService(t)
    ctx := context.Background()

    // Create URL that expires immediately
    expiry := time.Now().Add(-1 * time.Second)
    req := ShortenRequest{
        LongURL:   "https://example.com/expired",
        ExpiresAt: &expiry,
    }

    result, err := service.CreateShortURL(ctx, req)
    require.NoError(t, err)

    // Should not be retrievable
    _, err = service.GetLongURL(ctx, result.ShortID)
    assert.Error(t, err)
}

func BenchmarkGetLongURL_Cached(b *testing.B) {

    ctx := context.Background()

    // Warm cache
    service.GetLongURL(ctx, result.ShortID)

    for b.Loop() {

    }
}
```

### Junior → FAANG: Writing Tests That Actually Catch Bugs

The test file in this section demonstrates the correct structure for service-layer tests. Understanding the choices made here helps you write tests that are useful rather than decorative.

**In-memory fakes beat mocks for service tests.** The tests use `setupTestService(t)` which returns a service with in-memory implementations of the cache and repository. This is better than mock objects (generated by mockgen or testify/mock) for the service layer because it exercises the actual interface contract rather than the mock's expectation. A mock that says `repo.GetByShortID("abc") returns URL{...}` does not test that your repository's `GetByShortID` correctly handles expiration. An in-memory fake that implements the full interface does.

**Test deduplication, not just the happy path.** `TestURLService_Deduplication` verifies that creating the same long URL twice returns the same short ID. This is a business rule, not just a code path. Tests that only cover the happy path miss bugs that surface in the interaction between components. The boundary cases to cover for a URL shortener: expiration (create with a past expiry, verify it returns an error on redirect), duplicate custom aliases (create "myalias", try to create it again, verify it fails), and empty short ID (verify the endpoint returns a 400, not a 500).

**Benchmark tests expose performance regressions.** The `BenchmarkGetLongURL_Cached` and `BenchmarkGetLongURL_Uncached` benchmarks give you a baseline number: how fast is the cached redirect path? If a future change doubles this number, the benchmark catches it before production. Run benchmarks as part of your CI pipeline with `-benchmem` to also catch allocations that add GC pressure.

**`testcontainers` is the right tool for integration tests.** The `setupTestService` function is a placeholder. In a real project, use `testcontainers-go` to spin up a real Redis and PostgreSQL in Docker, run the tests against them, and tear them down after. This tests the actual SQL queries, the actual cache serialization, and the actual Redis Lua scripts. Unit tests with fakes are fast but cannot catch bugs in the database interaction layer.

### Senior @ FAANG: Test Strategy, Coverage Governance, and Load Testing as a First-Class Concern

At L6/L7, testing is a discipline with its own strategy, tooling, and governance. It is not just writing unit tests until coverage reaches an arbitrary percentage.

**Test pyramid ownership at the service level.** A URL shortener service should have: many unit tests covering business logic (expiration, deduplication, collision handling), a smaller number of integration tests using `testcontainers-go` covering the repository and cache layers against real infrastructure, a handful of end-to-end tests covering the redirect flow from HTTP request to database and back, and load tests covering the redirect path under sustained 100K RPS. Each layer has a different owner and a different run frequency: unit tests run on every commit (fast, no infrastructure), integration tests run on pull request merge (slower, containerized infrastructure), load tests run weekly and before major releases.

**Race detector is mandatory in CI.** The URL shortener has concurrent components: the in-process cache (sync.Map or a mutex-guarded map), the analytics channel (concurrent producers, single consumer), and the singleflight group (concurrent goroutines waiting on a single fetch). Run all tests with `-race` in CI. The race detector adds approximately 5-10x overhead, which is acceptable in CI but not in production. Any test that passes without `-race` but fails with it reveals a data race that will corrupt state in production under load.

**Load testing the redirect path requires realistic traffic distribution.** A naive load test that hits a single short URL 100K times per second measures cache performance, not system performance. A realistic load test uses a power-law distribution (80% of traffic to the top 20% of URLs) to measure the steady-state cache hit rate, the database read rate, and the analytics pipeline backpressure. Tools like `k6` or `vegeta` support custom request distributions. The load test should verify three things: (1) p99 redirect latency stays below the SLA under sustained load, (2) the error rate stays below 0.01%, and (3) the analytics channel does not back up (channel utilization stays below 80%). These are the acceptance criteria for the load test, and they must pass before a major release.

**Chaos testing for the fallback paths.** The graceful degradation tests in the codebase test the fallback by injecting a mock cache that returns errors. In a production readiness review, a bar-raiser will ask: "Have you tested this fallback with a real Redis failure?" The answer requires a chaos test: inject a Redis network partition using Toxiproxy or chaos-mesh, run the load test, and verify that the service continues to serve redirects (with higher database load) without returning errors to clients. This is not optional for a service at FAANG scale. Document the chaos test results and the failure mode observed, including how long it took for the service to detect the failure and switch to the fallback.
