## Exercises

1. **At-Least-Once Delivery Guarantee**: Implement an at-least-once delivery system in Go where a producer writes messages to a WAL before acknowledging to the caller, a consumer commits offsets only after successful processing, and the broker retries unacknowledged messages after a configurable visibility timeout (default 30s). Write a chaos test that kills the consumer process mid-processing and verifies that no messages are lost and duplicates are detectable via a message ID field. Document the exactly-once upgrade path using idempotent consumers.

2. **Message Ordering with Partitions**: Design a partitioned message queue that guarantees ordering within a partition but allows parallel processing across partitions. Implement a partition assignment strategy based on a consistent hash of the message key, demonstrate with a test that two messages with the same key always land on the same partition and are processed in order, and show that two messages with different keys can be processed concurrently. Measure the throughput difference between a single-partition (ordered) and 16-partition (parallel) configuration under identical load.

3. **Dead Letter Queue Handling**: Build a dead letter queue (DLQ) system that automatically moves messages to a DLQ after 3 failed processing attempts, preserves the original message along with a failure audit trail (attempt count, last error, timestamps), exposes a reprocessing API that moves messages from DLQ back to the original topic with a configurable delay, and alerts when DLQ depth exceeds a threshold. Implement in Go and write tests covering the retry exhaustion path, manual reprocessing, and the alerting threshold trigger.

4. **Message Deduplication with Idempotency Keys**: Design a message deduplication system that uses producer-supplied idempotency keys to deduplicate messages within a 24-hour window. The implementation must handle 100M unique keys per day, use a Redis bitmap or Bloom filter for O(1) duplicate detection, fall back to an exact-match store for bloom filter false positives, and add no more than 2ms to the publish latency at p99. Write a correctness test that replays 1M messages with 10% duplicates and verifies zero duplicate processing.

5. **Consumer Group Rebalancing**: Implement a consumer group rebalancing protocol in Go where a coordinator detects consumer joins and leaves via heartbeat timeouts (10s), triggers a rebalance by pausing all consumers in the group, reassigns partitions using a round-robin strategy, and resumes processing. The rebalance must complete within 30 seconds, must not result in duplicate processing of any message processed before the rebalance, and must not drop any messages assigned during the transition. Write an integration test simulating a 3-consumer group with one consumer crashing mid-rebalance.

6. **Backpressure Mechanism**: Design and implement a backpressure mechanism for a message queue consumer that monitors processing latency and consumer lag, automatically reduces the fetch batch size when p99 processing latency exceeds 500ms, pauses fetching entirely when lag exceeds 1M messages and the downstream service reports unhealthy, and resumes with exponential ramp-up once the downstream service recovers. Implement in Go with a configurable policy interface so teams can plug in custom backpressure strategies. Benchmark the mechanism under a 5× traffic spike and verify no OOM crashes occur.

### Junior -> FAANG: Turning Exercises into Portfolio Evidence

These six exercises represent the full surface area of a FAANG-level message queue design interview. Completing them is not enough. completing them with observable correctness is what differentiates a portfolio project from tutorial code.

For each exercise, write at minimum three tests: a happy-path test, a crash-recovery test (simulate a process kill mid-processing and verify no message loss and bounded duplication), and a concurrency test (run multiple producers and consumers simultaneously and verify the consistency invariants hold under race conditions). Run all tests with `-race` to catch data races that the logic tests miss.

When you present these exercises in an interview, lead with the invariant you are preserving, not the code you wrote. "This processor guarantees that a message is committed only after its side effects are durably recorded" is a stronger statement than "I used a database transaction to wrap the processing." The first statement reveals that you understand what property the code must preserve. The second reveals only that you know a Go API.

### Senior @ FAANG: Design Critiques of the Exercise Specifications

Exercise 4 (deduplication with Bloom filters) has a subtle specification gap: it asks for "zero duplicate processing" but a Bloom filter is probabilistic and allows false positives. A false positive means a unique message is incorrectly identified as a duplicate and dropped. This is a correctness violation, not an efficiency trade-off. The specification should say "zero undetected duplicates," with false positives falling back to an exact-match check, which is what the text describes. This distinction matters in a code review because a junior engineer who implements only the Bloom filter check and omits the exact-match fallback satisfies a naive reading of the specification but introduces correctness bugs.

Exercise 5 (consumer group rebalancing) specifies a 30-second completion SLO for the rebalance. This is achievable with small consumer groups but becomes the dominant operational concern at large scale. With 200 consumers and 800 partitions, the JoinGroup/SyncGroup round trip involves 200 concurrent network calls to the coordinator. The coordinator serializes these under a lock, adding latency proportional to group size. The exercise should require testing with at least 20 consumer instances to surface this scaling characteristic before it is discovered in production.

Exercise 6 (backpressure) specifies a policy interface, which is the right abstraction, but does not specify how the policy decision is communicated back to the fetch loop. A poorly designed interface puts the decision in a polling loop (inefficient). A well-designed interface uses a `BackpressureSignal` channel that the policy sends to when it wants to change the fetch rate. This is the difference between an interface that composes with Go's concurrency model and one that fights it.
