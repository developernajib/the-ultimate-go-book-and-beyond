## Exercises

1. **QPS/Storage/Bandwidth for Instagram Scale**: Instagram has 500M DAU. Each user views 50 photos and posts 0.1 photos per day. Calculate average and peak read RPS (3× average), average and peak write RPS, daily and 5-year storage requirements assuming 3MB per photo with 3× replication, daily CDN bandwidth at an average delivery size of 500KB per photo served (accounting for resizing), and the number of PostgreSQL read replicas needed if each handles 5,000 QPS at 70% utilization.

2. **Capacity Model as Go Code**: Build a capacity planning model in Go as a runnable CLI tool that accepts parameters (DAU, actions per user per day, data size per item, retention days, replication factor, cache hit rate, RPS per server) and outputs a formatted capacity report covering traffic (average RPS, peak RPS), storage (raw, with replication, with 20% overhead), bandwidth, server count, and months of runway given a growth rate input. Include unit tests for the calculation functions and a sample run for a Twitter DM system with 300M DAU.

3. **Auto-Scaling Triggers Based on Custom Metrics**: Design an auto-scaling system that uses composite metrics - CPU utilization (weight 40%), request queue depth (weight 40%), and p99 latency (weight 20%) - to compute a single scaling score. When the score exceeds 0.75, scale out by 25% of current capacity (min 1 instance), and when below 0.3 for 10 consecutive minutes, scale in by 10% (min 2 instances). Implement the scoring and decision logic in Go, add a cooldown period of 5 minutes between scaling actions, and write tests for scale-out, scale-in, cooldown enforcement, and the composite score calculation.

4. **Database Connection Pool Sizing**: Model the optimal connection pool size for a Go application where each request takes 10ms of database time, the application must handle 5,000 concurrent requests, each database query takes on average 5ms, and the PostgreSQL instance supports a maximum of 500 connections. Use Little's Law (L = λW) to derive the pool size, account for connection overhead (2ms to acquire from pool), and implement a simulation in Go that measures request latency percentiles at pool sizes of 10, 50, 100, 200, and 500. Document at which pool size latency stops improving and explain why.

5. **Storage Growth Prediction with Time Series**: Implement a storage growth forecasting tool in Go that ingests 90 days of daily storage measurements, fits both a linear regression model and an exponential growth model to the data, selects the better fit using R² score, projects storage for the next 180 days with 90% confidence intervals, and outputs the predicted date when storage will reach 80% capacity (the alert threshold). Test the tool against synthetic datasets for linear growth (10GB/day), exponential growth (5% per week), and seasonal patterns (high on weekdays, low on weekends).

6. **Load Shedding Strategy**: Design and implement a load shedding system in Go that activates when the system reaches 80% of its measured capacity (defined as the RPS at which p99 latency exceeds 500ms). The system must shed load using three tiers - at 80% capacity shed non-authenticated requests, at 90% capacity shed requests from users with free-tier accounts, at 95% capacity shed all non-critical read requests - return `HTTP 503` with a `Retry-After` header, and automatically deactivate shedding when load drops below 70%. Implement with a token bucket gate per tier and write a load test verifying that critical requests maintain < 500ms p99 during a 3x traffic spike.

### Junior → FAANG: Turning Exercises into Interview Preparation

Each exercise in this list builds a specific skill that appears in FAANG interviews, either in system design rounds or in coding rounds that involve distributed systems concepts. Here is how to extract maximum value from each one.

**Exercise 1 (Instagram capacity model)** is a direct system design interview simulation. Run through it under time pressure: give yourself 10 minutes to produce all five outputs (read RPS, write RPS, storage, bandwidth, database count) without looking at the chapter. If you cannot complete it in 10 minutes, identify which step slowed you down and practice that step in isolation.

**Exercise 2 (Go CLI capacity tool)** is a coding interview problem disguised as a capacity planning exercise. The interesting engineering problems are: how to represent the capacity model as types (struct-per-resource, or a generic resource type?), how to compute runway using floating-point arithmetic without accumulating error, and how to format the report in a way that is readable for humans. Building this tool teaches you the formulas at the code level, which makes them more durable than reading them.

**Exercise 3 (auto-scaling triggers)** covers a topic that appears in FAANG behavioral interviews: "How would you design the auto-scaling policy for your service?" The composite metric approach (CPU plus queue depth plus latency) is more sophisticated than single-metric scaling and reflects how production auto-scaling systems actually work. Implementing the cooldown enforcement and the hysteresis between scale-out and scale-in thresholds requires careful state management that is a good coding exercise.

**Exercise 6 (load shedding)** is the most operationally sophisticated exercise and the one most directly relevant to senior-level interviews. Load shedding with priority tiers is a real pattern used by Google, Netflix, and Amazon. The key insight is that shedding in order of importance (unauthenticated first, free tier second, non-critical reads third) preserves service for the most valuable traffic during overload. Implementing this correctly requires understanding token bucket rate limiting and the ordering semantics of the tier gates.

**First-job habit:** Pick one exercise from this list each quarter and build it as a side project against a real (small-scale) backend. Running your capacity model against a real service you operate, even a toy one, immediately surfaces the assumptions that are wrong: the peak multiplier you chose, the RPS-per-server estimate that does not match reality, the cache hit rate that is lower than expected. Real feedback calibrates your estimation intuition faster than any textbook.

### Senior @ FAANG: Using Exercises to Develop Team Capacity Planning Competency

At senior level, these exercises are not things you do for yourself. They are the basis for team training, hiring evaluations, and engineering excellence programs.

**Exercise 1 as a team calibration exercise.** Run Exercise 1 as a team exercise during a tech talk or design review session. Have each engineer produce their own estimate independently, then compare results. The variance in the team's estimates reveals where assumptions differ and where knowledge gaps exist. Common divergence points: peak multiplier (2x versus 5x), derived photo sizes (1 MB versus 5 MB), connection pool sizing. The debrief discussion is more valuable than the estimates themselves, because it surfaces the reasoning gaps that affect your team's real-world design decisions.

**Exercise 2 as a hiring evaluation tool.** The Go capacity CLI exercise is a strong L4/L5 coding interview problem because it requires both systems knowledge (the estimation formulas) and Go engineering skill (struct design, CLI tooling, unit testing). A candidate who produces a clean solution with well-named types, tested calculation functions, and a formatted report demonstrates both breadth and depth. A candidate who hard-codes the formulas without tests or who cannot name the units correctly in the output reveals gaps in either systems or engineering fundamentals.

**Exercise 4 (connection pool sizing with Little's Law) as an engineering excellence topic.** Connection pool sizing is one of the most commonly wrong configurations in Go services connecting to PostgreSQL. The Little's Law derivation (L = lambda times W, where L is average queue depth, lambda is arrival rate, and W is average service time) gives the theoretically correct pool size for a given RPS and query latency. Most teams configure connection pools by convention (pool size of 10 or 20) rather than by derivation. Running this exercise as a team training topic, with your team's actual measured query latency and RPS as inputs, produces the correct pool size for your specific services and prevents the connection exhaustion incidents that are otherwise inevitable.

**Exercise 6 (load shedding) as a platform design input.** Load shedding at the platform level requires agreement on the priority tier definitions (what counts as "critical" versus "non-critical," which user segments are in which tier) and coordination across the services that must implement shedding consistently. A staff engineer who has built the load shedding system in Exercise 6 for a single service can generalize it to a platform-level shedding framework: a shared library that provides the token bucket gates and the tier decision logic, with configuration per service for the tier boundaries and shedding thresholds. This platform primitive ensures consistent shedding behavior across all services during a platform-wide overload event, which is when load shedding matters most.

**ADR: capacity planning exercises as part of the engineering onboarding curriculum.** New engineers joining a team that owns large-scale services need to develop capacity planning intuition quickly. An ADR for the team's onboarding program should include a capacity planning module that walks through Exercises 1 and 2 with the team's own services as the input: "Here is our actual DAU, our actual peak RPS, our actual storage growth rate. Run the estimation framework and compare your output to our real metrics." This exercise teaches the framework, calibrates the engineer's intuition to the team's actual scale, and surfaces knowledge gaps in the first week rather than the first incident.

**L6/L7 concern: exercise scope as a proxy for staff-level capacity thinking.** The difference between an L5 engineer and an L6 engineer on Exercise 2 (Go capacity CLI) is not in the code quality. It is in the scope of the solution. An L5 engineer builds a CLI that models one service correctly. An L6 engineer asks: how does this tool scale to model a portfolio of 50 services, each with different resource types and growth rates? The L6 solution has a configuration layer (YAML or JSON input), a resource abstraction that handles CPU, memory, storage, and network bandwidth as distinct resource types with different alert thresholds, and an output format that prioritizes services by urgency (shortest runway first). This scope difference is the bar-raiser signal that distinguishes L5 from L6 thinking in a technical evaluation.
