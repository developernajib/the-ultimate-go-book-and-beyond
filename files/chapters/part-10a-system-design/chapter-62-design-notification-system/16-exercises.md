## Exercises

1. **Push/Email/SMS Fan-Out Architecture**: Design a fan-out architecture for a notification system that must deliver a single event (e.g., a product going on sale) to 10M users across push, email, and SMS channels within 5 minutes. Define the queue topology, worker pool sizes per channel, and how you handle channel-specific rate limits (APNs: 1M/hour, SendGrid: 100K/hour, Twilio: 10K/hour). Calculate the minimum number of workers required for each channel.

2. **Notification Deduplication**: Implement a notification deduplication service in Go that prevents sending the same notification to a user within a configurable time window (default 24 hours). The solution must survive service restarts, handle distributed deployments across 10 instances, and not block the hot path by more than 1ms. Use Redis with a bloom filter for the first pass and a precise hash set for confirmation. Write tests for the false-positive rate and race conditions.

3. **Retry with Exponential Backoff for Failed Deliveries**: Build a retry system for failed notification deliveries that implements exponential backoff with jitter (base: 1s, max: 30min, multiplier: 2, jitter: ±20%). The system must distinguish between retryable failures (network timeout, rate limit) and terminal failures (invalid token, unsubscribed user), enforce a maximum of 5 retry attempts, and move messages to a dead letter queue after exhaustion. Implement in Go with tests covering each failure category.

4. **Notification Preferences Service**: Design a notification preferences service that stores per-user, per-channel, per-category opt-in/opt-out settings (e.g., user 123 wants email for order updates but not SMS, and no push for marketing). Define the data model supporting 10M users with an average of 15 preference combinations each, design the API contract, and implement a read-through cache with a 5-minute TTL. Measure and document the p99 latency impact of a cache miss on the notification hot path.

5. **Delivery Receipt Tracking**: Build a delivery receipt tracking system that ingests webhook callbacks from APNs, FCM, SendGrid, and Twilio, normalizes them into a unified delivery event schema, stores them for 30-day analytics, and exposes a real-time API for querying delivery status by notification ID. Design the ingestion pipeline to handle 50K webhook events per second at peak and implement idempotent processing to handle duplicate webhook deliveries.

6. **Notification Priority Queuing**: Design and implement a priority queue system for notifications with three tiers - critical (OTP, security alerts: SLA < 5s), transactional (order updates, password reset: SLA < 30s), and marketing (promotions: SLA < 5min). Implement queue isolation so marketing traffic cannot consume worker capacity needed for critical messages, add circuit breakers that shed marketing load when the critical queue depth exceeds 1,000 messages, and write a load test demonstrating SLA compliance under a 10x traffic spike.

### Junior -> FAANG: How to Use These Exercises

Work through exercises 1 and 2 first. Exercise 1 (fan-out architecture) tests your ability to reason about capacity and throughput from first principles: given the provider rate limits and your SLA target, calculate the number of workers required. Show your work. Exercise 2 (deduplication) tests a correctness property, not a performance property: the deduplication service must be correct under concurrent load before you optimize it.

For exercise 2 specifically: the bloom filter + hash set combination is the standard two-tier deduplication pattern. The bloom filter provides fast rejection (no false negatives: if the bloom filter says the key is new, it definitely is new), and the hash set provides precise confirmation (no false positives: if the hash set contains the key, it was definitely seen before). Know why both tiers are needed: the bloom filter alone has a false positive rate that grows with usage, causing legitimate notifications to be dropped, while the hash set alone is too slow for the hot path.

A first-job habit for all six exercises: write the test cases before writing the implementation. For exercise 5 (delivery receipt tracking), write a test that sends the same webhook event twice and verifies only one delivery event is recorded. For exercise 6 (priority queuing), write a test that fills the marketing queue to capacity and verifies that critical notifications still meet their SLA.

### Senior @ FAANG: Extensions That Make These Production-Grade

For exercise 1 (fan-out architecture): the real interview challenge is not calculating the minimum number of workers, it is designing the worker elasticity mechanism. How does the system add workers when the queue depth rises, and remove them when it falls? The answer involves Kubernetes Horizontal Pod Autoscaler scaled on a custom metric (Kafka consumer group lag), with separate HPA configurations per channel worker type so email workers scale independently of push workers.

For exercise 2 (deduplication): the false-positive rate measurement is the key staff-level concern. A bloom filter with a false-positive rate of 0.1% means 1 in 1000 legitimate notifications is incorrectly deduplicated. At 1M notifications per day, that is 1000 dropped notifications. Measure this rate in a staging environment with synthetic load, set an SLO on it (false-positive rate < 0.01%), and design the bloom filter capacity and hash function count to meet that SLO.

For exercise 6 (priority queuing): the circuit breaker that sheds marketing load when the critical queue depth exceeds 1000 messages is a cross-queue feedback mechanism. Implement it by exposing the critical queue depth as a metric, having the marketing worker pool subscribe to that metric via a shared atomic variable updated by a background goroutine, and pausing marketing processing when the threshold is exceeded. Test it by generating a critical queue backlog in a load test and verifying that marketing notifications stop being processed until the backlog clears.
