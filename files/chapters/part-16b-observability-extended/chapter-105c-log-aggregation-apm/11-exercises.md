## Exercises

1. **Implement Structured Logging with Full Signal Correlation**: Instrument a Go HTTP service with `log/slog` configured to emit JSON to stdout. Every log entry must include `trace_id`, `span_id`, `correlation_id` (generated or propagated from the `X-Correlation-ID` header), `service.name`, and `log.level`. Ship the logs to a local Elasticsearch instance via Fluent Bit. Write three Kibana queries that demonstrate: (a) all logs for a single `correlation_id` across multiple services, (b) all error logs in the last hour sorted by `http.status_code`, and (c) the p99 response time derived from a numeric `duration_ms` field in the log entries. Confirm that the `trace_id` in a log line matches a trace visible in Jaeger.

2. **Control Log Volume with Sampling and Level Management**: Configure the `log/slog` handler to emit all `ERROR` and `WARN` logs unconditionally and sample `INFO` logs at a rate of 1 in 10 using an atomic counter. Add a runtime-configurable log level that can be changed without restarting the service via a `POST /internal/log-level` endpoint protected by a bearer token. Run a load test and compare the log volume (bytes/second sent to Fluent Bit) with full `DEBUG` logging versus sampled `INFO` logging. Calculate the monthly Elasticsearch storage cost difference assuming a 10 GB/day baseline.

3. **Build an Index Lifecycle Management Policy**: Create an Elasticsearch ILM policy for a production log index that transitions documents through: hot phase (7 days, primary shard on SSD, 1 replica), warm phase (days 8-30, read-only, force-merged to 1 segment, 1 replica on HDD), cold phase (days 31-90, frozen, searchable snapshot), and delete phase (after 91 days). Apply the policy to a new index template and verify the transition by manually advancing the ILM clock in a test cluster. Document the expected storage cost reduction compared to keeping all logs in the hot tier indefinitely, and write a PromQL alert that fires when hot-tier disk usage exceeds 80%.

4. **Implement a Correlation ID Middleware**: Write a Go HTTP middleware that reads the `X-Correlation-ID` header from incoming requests and, if absent, generates a new UUID v4 and sets it on the request context. The middleware must also set the correlation ID on the outgoing response header so callers can reference it. Propagate the correlation ID into all outbound HTTP calls made during the same request using a custom `http.RoundTripper`. Write an integration test that makes a chain of three HTTP calls across two services and verifies the same correlation ID appears in the logs of both services and in all three response headers.

5. **Detect and Remediate Log-Driven Cardinality Issues**: Introduce a deliberately problematic log field, for example logging the raw `user_id` UUID as a structured field on every debug log line in a high-traffic handler. Run a load test that generates 10,000 requests. Observe the impact on Elasticsearch: check the number of unique values in the field using an aggregation, measure index size before and after, and note any query slowdown. Fix the issue by either removing the high-cardinality field from the log or hashing/bucketing the value. Re-run the load test and quantify the improvement. Document the rule you would add to a team linting policy to prevent this pattern recurring.

6. **Set Up APM Error Grouping and Alerting**: Configure an APM error tracking solution (OpenTelemetry Collector with an error grouping processor, Sentry, or Elastic APM) to receive unhandled errors from a Go service. Ensure that errors are grouped by their stack trace fingerprint rather than message, so that the same bug appearing in different request contexts counts as one issue. Simulate a new bug by deploying a code path that panics on a specific input, trigger it 50 times, and verify that exactly one error group is created with a count of 50. Configure an alert that pages if a new error group appears or if an existing group's count increases by more than 10 per minute.

### Junior → FAANG: Exercise Priority for Interview Preparation

Exercise 1 (structured logging with full signal correlation) is the highest-priority exercise. Being able to demonstrate a running service where every log line includes `trace_id` and can be correlated to a Jaeger trace is a concrete artifact that answers the interview question "how do you implement observability" more convincingly than any theoretical answer.

Exercise 4 (correlation ID middleware) is the second priority. Correlation ID propagation is tested in system design interviews and is a skill every backend engineer at FAANG is expected to have. Implement it from scratch, test it with three chained services, and understand every line of code.

### Senior @ FAANG: Exercises as Platform Acceptance Tests

At L6, exercises 1, 2, 4, and 5 form the acceptance test suite for the shared logging library. A new version of the library must pass all four exercises in a test environment before being released to the internal package registry. Exercise 2 (log volume control) verifies the sampling configuration. Exercise 4 (correlation ID) verifies the context propagation. Exercise 5 (cardinality issues) verifies the PII scrubbing and field allowlist. These tests are not optional: they are the quality gate that prevents a library regression from affecting 200 services simultaneously.
