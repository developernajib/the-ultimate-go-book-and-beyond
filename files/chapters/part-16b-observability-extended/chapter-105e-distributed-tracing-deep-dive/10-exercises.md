## Exercises

1. **Propagate W3C Baggage Across a Multi-Service Chain**: Build a three-service chain (API gateway → order service → inventory service) where each service communicates over HTTP. Inject a `tenant_id` and `experiment_group` into W3C Baggage at the gateway tier using `baggage.NewMember`. In each downstream service, read the baggage values from the context and attach them as span attributes and as structured log fields. Run a request through the chain and verify in Jaeger that all three spans share the same `tenant_id` attribute, then explain why baggage propagation is preferable to passing these values as explicit function parameters in a deep call stack.

2. **Implement Tail-Based Sampling**: Configure the OpenTelemetry Collector with a `tail_sampling` processor that applies the following policies. Always sample traces containing a span with status `ERROR`. Always sample traces where any span duration exceeds 500ms. Sample all other traces at 10%. Run a load test that generates 1,000 normal requests, 50 error requests, and 20 slow requests. Verify in Jaeger that 100% of error and slow traces are captured while approximately 100 of the normal traces are sampled. Compare the storage volume to an equivalent `TraceIDRatioBased(0.1)` configuration and explain why tail sampling is worth the additional Collector memory overhead.

3. **Detect and Fix N+1 Query Patterns via Trace Analysis**: Instrument a Go service that fetches a list of orders and, for each order, makes a separate database query to fetch the associated customer record. Export traces to Jaeger. Load the trace for a request that fetches 20 orders and use Jaeger's span timeline to count the number of `db.query` child spans. Confirm the N+1 pattern visually. Fix the issue by replacing the loop with a single batch query using `SELECT ... WHERE id IN (...)`. Re-run the same request, confirm the trace now shows exactly 2 database spans (one for orders, one for customers), and document the latency reduction observed in the trace timeline.

4. **Perform Critical Path Analysis on a Slow Trace**: Find or construct a trace that involves at least five services and takes over 1 second end-to-end. Write a Go program (or use the Jaeger API) that: retrieves the trace by ID, builds the span tree, identifies which spans are on the critical path (the longest chain of parent-child spans from root to leaf), and prints the critical path with each span's duration as a percentage of total trace duration. Use this analysis to identify the single span responsible for the most latency and propose a concrete optimization (caching, batching, parallelizing fan-out calls). Verify the optimization reduces the critical path duration by at least 30%.

5. **Test Tracing Instrumentation Without External Dependencies**: Write a suite of unit tests for a Go HTTP handler that is instrumented with OpenTelemetry. Use `tracetest.NewSpanRecorder` registered via `sdktrace.WithSpanProcessor` (or `sdktrace.NewSimpleSpanProcessor` wrapping a `tracetest.NewInMemoryExporter`) to capture spans in memory. For each test case assert: the correct number of spans was created, each span has the expected `http.method`, `http.route`, and `http.status_code` attributes, any error path sets `span.SetStatus(codes.Error, ...)` and calls `span.RecordError`, and the span kind is `trace.SpanKindServer`. Ensure the tests run with no external network calls, complete in under 100ms per test case, and can be run in parallel without span recorder interference.

6. **Instrument Asynchronous Work with Context Propagation Through Message Queues**: Add OpenTelemetry trace propagation to a Go service that publishes messages to a Kafka or NATS topic and a separate consumer service that processes them. Use the OTel propagation API to inject the trace context into message headers on publish and extract it on consume, creating a new span linked to the producer span via `trace.WithLinks`. Verify in Jaeger that the producer and consumer traces are linked and that the end-to-end latency (from publish to consumer span end) is visible. Explain the difference between a parent-child relationship and a span link, and why a link is the correct model for async messaging.

### Junior → FAANG: Which Exercises to Prioritize

Exercise 5 (unit testing with span recorder) is the highest priority. The ability to write instrumentation tests without external dependencies is a skill that demonstrates engineering maturity and is directly testable in a coding interview. Complete this exercise first and practice until you can write the setup from memory.

Exercise 3 (N+1 detection via traces) is the second priority. N+1 query patterns are one of the most common production performance problems, and being able to identify them in a trace waterfall and explain the fix demonstrates practical debugging skill that interviewers find credible.

### Senior @ FAANG: Exercises as Onboarding Infrastructure and Platform Validation

At L6, exercises 2 (tail-based sampling) and 4 (critical path analysis) define the minimum viable tracing infrastructure that a team must have before going to production. Exercise 2's Collector configuration should become the platform's default tail sampling configuration, version-controlled and applied to every new service via the platform's Collector deployment template. The storage comparison in exercise 2 is the cost justification for the tail sampling infrastructure investment.

Exercise 4's critical path analysis program should become a standing tool in the platform's performance engineering toolkit. Running it automatically on every trace that exceeds the p99 latency SLO threshold, aggregating the critical path results by operation name across all such traces over a week, and sorting by total latency contribution produces the platform's weekly performance hotspot report. This report prioritizes optimization investment more accurately than any other signal because it reflects actual user-experienced latency rather than synthetic benchmarks or average latency metrics.
