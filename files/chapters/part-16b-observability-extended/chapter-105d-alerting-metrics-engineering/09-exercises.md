## Exercises

1. **Audit and Fix an Alerting Configuration for Alert Fatigue**: Take an existing Prometheus alerting rule file (or use a provided sample with 20+ rules, several of which are cause-based CPU/memory alerts). For each alert, classify it as symptom-based or cause-based, determine whether it has a `runbook_url` annotation, and check whether it uses a `for` duration to suppress transient spikes. Remove or demote to dashboards all cause-based alerts that have no direct user impact. For every remaining alert, add a `runbook_url` and a `for` duration of at least 2 minutes. Run the cleaned rule file through `promtool check rules` and document the before/after alert count and your reasoning for each removal.

2. **Implement Anomaly Detection with Z-Score Alerting**: Write a Prometheus recording rule that computes the mean and standard deviation of your service's request rate over the previous 7 days using `avg_over_time` and a derived stddev metric. Create an alerting rule that fires when the current rate deviates by more than 3 standard deviations from the historical mean, with separate conditions for sudden spike and sudden drop. Test the alert by injecting a traffic anomaly (10× normal load for 5 minutes, then 0 traffic for 5 minutes) and verify both conditions fire. Explain the limitations of Z-score detection for services with strong diurnal or weekly seasonality and propose how you would extend the approach to handle it.

3. **Build a Dead Man's Switch for All Batch Jobs**: Identify every scheduled job in a service (cron jobs, Kubernetes CronJobs, or background workers). For each job, add a Prometheus gauge named `job_last_success_timestamp_seconds` that is set to `time.Now().Unix()` at the end of a successful run. Write a Prometheus alerting rule that fires when `time() - job_last_success_timestamp_seconds` exceeds 1.5× the expected job interval. Deploy a test CronJob that runs every minute, confirm the heartbeat metric is present, then disable the CronJob and verify the alert fires within the expected window. Write a runbook for the alert that distinguishes between a job that never started and one that started but failed.

4. **Configure Multi-Level AlertManager Routing with Inhibition**: Design an AlertManager routing tree for a production engineering team. Requirements: P1 alerts (SLO fast burn, complete outage) must route to PagerDuty with a 5-minute group wait. P2 alerts (slow burn, degraded performance) must route to Slack `#oncall`. P3 and below must route to Slack `#alerts-low-priority` with a 30-minute group interval to batch notifications. Add an inhibition rule that suppresses all P2 and P3 alerts for a service when a P1 alert for the same service is active. Test the full configuration using `amtool` to simulate alert delivery without a live Prometheus, and verify that inhibition works correctly by firing a P1 and a P2 alert for the same service simultaneously.

5. **Automate a Runbook Remediation Step**: Choose a runbook action that involves querying Prometheus, making a Kubernetes API call, or adjusting a feature flag (e.g., "if error rate > 10%, disable the experimental payment flow feature flag"). Implement a Go program that: checks the condition via the Prometheus HTTP API, performs the remediation action via the Kubernetes API or your internal feature flag service, logs what it did with a structured log line including the alert name and the action taken, and sends a Slack message with the action summary. The program must be idempotent (running it twice must not perform the action twice) and must include a dry-run mode. Write a unit test that mocks both the Prometheus and Kubernetes clients.

6. **Build and Version a Complete Grafana Dashboard as Code**: Use the Grafana HTTP API (not the UI) to create a dashboard with at least six panels covering: SLO compliance rate (stat), error budget remaining (gauge), p50/p95/p99 latency over time (time series), request rate by endpoint (bar chart), active alert count by severity (table), and a heatmap of request duration distribution. Parameterize the dashboard with a `service` template variable so it works for any service in your cluster. Export the dashboard JSON and store it in a Git repository. Write a CI script that uses `curl` or a Go HTTP client to automatically push the dashboard to Grafana on every merge to main, and verify idempotency by running the push script twice and confirming no duplicate dashboards are created.

### Junior → FAANG: Exercise 1 First, Then Exercise 3

Start with exercise 1 (audit an alerting configuration for alert fatigue). This exercise is immediately applicable: if your team has existing alerts, you likely have cause-based, threshold-without-for-clause, and runbook-less alerts. Auditing and fixing them is a real contribution that demonstrates SRE maturity.

Exercise 3 (dead man's switch for batch jobs) is the second priority. Every team has at least one batch job that has silently failed at some point. Adding a heartbeat metric and alert is a 30-minute task with permanent value.

### Senior @ FAANG: Exercises as Platform Launch Requirements

At L6, exercises 4 (AlertManager routing) and 5 (runbook automation) define the required state for a production-ready monitoring configuration. Before any service is permitted to enter the production environment, its AlertManager routing must be verified (exercise 4 validated with `amtool`) and its most common failure modes must have automated remediation scripts (exercise 5 implemented and tested). These requirements are enforced by the production launch checklist, not by engineering honor code.
