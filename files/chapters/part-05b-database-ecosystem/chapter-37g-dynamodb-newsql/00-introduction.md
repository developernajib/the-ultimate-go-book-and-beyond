# Chapter 37G: DynamoDB & NewSQL Databases

*"The art of NoSQL design is not about avoiding joins. It's about pre-computing answers to questions you already know."* - Rick Houlihan, AWS Principal Technologist

When Amazon launched DynamoDB in 2012, it changed how engineers think about scale. DynamoDB delivers single-digit millisecond latency at any throughput with no operational overhead, but it does not forgive poor data modeling. Engineers who struggle with it bring a relational mindset. Engineers who thrive study access patterns first and schema second. At companies like Amazon, Snapchat, and Lyft, DynamoDB tables serve hundreds of millions of requests per day because the data was modeled around how it is read, not how it is structured.

The rise of NewSQL represents a different philosophical response to the same problem. Google Spanner, CockroachDB, and TiDB prove that you do not have to sacrifice ACID guarantees to achieve horizontal scalability. Spanner, deployed internally at Google for years before its public release, underpins products like Google Ads and Google Cloud Spanner itself, handling globally distributed transactions at a scale that relational databases running on a single machine could never approach. CockroachDB brings that same distributed SQL model to the open-source world, with wire-compatible PostgreSQL interfaces that let teams migrate with minimal application changes.

This chapter covers both worlds using Go. You will model DynamoDB tables using single-table design (the technique Rick Houlihan popularized), where multiple entity types coexist in one table, related through composite key patterns and accessed through carefully designed Global Secondary Indexes. You will then work with DynamoDB Streams, which turn your table into an event log for CDC pipelines and real-time downstream processing. Finally you will connect to CockroachDB and Google Spanner from Go using `aws-sdk-go-v2`, `pgx`, and the Spanner client library, running distributed transactions that would have required exotic infrastructure just a decade ago.

**What you'll learn in this chapter:**
- Design DynamoDB single-table schemas driven entirely by access patterns, not entity structure
- Implement partition key strategies (composite keys, write sharding, and overloaded indexes) to eliminate hot partitions
- Build GSI and LSI query patterns for complex multi-entity access scenarios in Go
- Consume DynamoDB Streams using `aws-sdk-go-v2` for event-driven CDC and downstream processing
- Understand CockroachDB and Google Spanner architecture: Raft consensus, TrueTime, and distributed SQL execution
- Execute distributed transactions from Go across multi-region NewSQL deployments
- Apply the CAP theorem practically to choose between DynamoDB, CockroachDB, and Spanner for real use cases
- Benchmark and tune throughput provisioning, read/write capacity units, and connection pooling

**Why this matters at scale:**
Amazon itself runs its entire e-commerce order system on DynamoDB, handling Prime Day peaks exceeding 80 million requests per second. Snapchat uses DynamoDB for Stories storage, serving hundreds of millions of daily active users with consistent sub-10ms reads. Google Spanner powers Google Ads, where financial-grade consistency across data centers is non-negotiable. CockroachDB is used by Bose, Comcast, and DoorDash to run globally distributed workloads with PostgreSQL compatibility, enabling teams to scale without rewriting application code. Knowing how these systems work matters for any engineer building at internet scale. It is the difference between a system that survives growth and one that collapses under it.

**Prerequisites:** Chapters 36A, 36F (relational databases, connection pooling, query optimization), familiarity with Go structs and interfaces, basic understanding of distributed systems concepts (consistency, replication, partitioning).

### Junior to FAANG: entering the DynamoDB world from a relational background

If your background is Postgres or MySQL, DynamoDB will feel alien at first. The prerequisite gap that trips most juniors is not the API. It is the mental model. Relational design starts with entities and normalization, then you write queries against whatever shape the data took. DynamoDB inverts that. You enumerate every access pattern your application will issue, then design a key schema that answers each one in a single Query call. There are no joins. There is no ad-hoc `WHERE name LIKE 'foo%'`. If an access pattern was not designed into the keys or indexes, you cannot serve it cheaply.

Worked example. Imagine a URL shortener. Access patterns: look up a short code to get the long URL, list all links created by a user ordered by time, count clicks per link per day. In Postgres you would create `links(id, short_code, long_url, user_id, created_at)` and a `clicks` table, then write three queries. In DynamoDB you design one table where the partition key is `PK` and the sort key is `SK`. A link item stores `PK=LINK#abc123, SK=META, long_url=...`. A click aggregate stores `PK=LINK#abc123, SK=CLICK#2026-04-22, count=47`. A user index stores `PK=USER#42, SK=LINK#2026-04-22T10:00#abc123`. Three access patterns, one Query per pattern, no scans.

First-job context. At FAANG scale, on-call engineers are paged when a table starts throttling. The root cause is almost always a hot partition, meaning one `PK` value receiving more than 3000 read or 1000 write units per second. Juniors who understand that DynamoDB physically shards by partition key hash, and that one partition maps to at most one storage node, diagnose throttling in minutes instead of hours. Interview entry point: expect whiteboard questions like "model a Twitter-like timeline in a single DynamoDB table" or "why would you pick DynamoDB over Postgres for a session store". The expected answer is not "it scales". The expected answer walks through access patterns, explains how PK and SK support each one, and identifies the failure modes (hot partitions, scan costs, eventual consistency on GSIs).

### Senior at FAANG: strategic positioning of DynamoDB and NewSQL in a platform portfolio

At staff and principal level the question is rarely "how do I use DynamoDB". It is "when should my organization adopt DynamoDB, Spanner, CockroachDB, Aurora, or Cassandra, and what are the exit costs if we are wrong". Each system encodes a different set of CAP and PACELC tradeoffs, and the wrong choice becomes load-bearing architecture that costs tens of millions to unwind.

DynamoDB is the right choice when your workload is key-value or key-range access with predictable patterns, you need single-digit millisecond p99 at arbitrary scale, and you are already inside AWS. It is the wrong choice when you need ad-hoc analytics, complex joins, or cross-region strong consistency for financial transactions. Global Tables replication lag is typically sub-second in most regions, but it is still last-writer-wins at the item level, which is unacceptable for ledgers. Staff engineers writing an ADR for DynamoDB adoption should enumerate every current and projected access pattern, show that each one is answered by a Query or GetItem, estimate RCU and WCU consumption under peak load, model the cost of on-demand versus provisioned with auto-scaling, and explicitly list access patterns that will require a secondary system (OpenSearch for full-text, Redshift via zero-ETL for analytics, S3 for cold tier).

Spanner versus CockroachDB is the NewSQL decision. Spanner wins when you are already on GCP, need external consistency backed by TrueTime, and are willing to pay for the atomic clock infrastructure. CockroachDB wins when you need multi-cloud portability, PostgreSQL wire compatibility to avoid rewriting applications, and HLC-based serializable isolation is sufficient. Neither matches DynamoDB on raw throughput per dollar at key-value workloads, and neither matches Aurora on single-region OLTP latency. The honest staff framing is that NewSQL is a premium product. You pay 2 to 5 times more per transaction than Aurora or DynamoDB in exchange for horizontal scale plus SQL plus serializable isolation. Pick it only when all three properties are load-bearing for the business.

PACELC placement matters for on-call design. DynamoDB is PA/EL: under partition it favours availability, and else it favours low latency over consistency (default reads are eventual, strong reads cost 2x). Spanner is PC/EC: it favours consistency always, which is why Spanner writes pay a TrueTime commit wait. CockroachDB is PC/EC with HLC. When you draw the runbook for "region X is partitioned from the rest", the behavior of your database under that partition dictates whether writes fail fast, writes continue and diverge, or writes block. Senior engineers own this runbook before the outage, not during.

Exit cost is the final staff consideration. DynamoDB lock-in is real: single-table schemas with overloaded GSIs do not translate cleanly to any other database. A migration to Cassandra or ScyllaDB preserves the key model but loses streams, global tables, and PITR semantics. A migration to Aurora requires redesigning every access pattern back into a relational schema. AWS Keyspaces (managed Cassandra) offers a partial escape hatch but differs on consistency and secondary index semantics. Before adopting DynamoDB for a tier-0 system, staff engineers should explicitly document which business properties would force a migration and estimate the cost of that migration in engineer-years. If that number is uncomfortable, consider whether Aurora plus DAX or a NewSQL option provides enough scale with lower lock-in.
