# Chapter 37D: MongoDB & Document Databases

*The schema is the application, and the application should own it.*

Relational databases impose structure upfront: every column is declared before a single row is written. This discipline has served data engineering well for decades, but it creates real friction in the early and middle phases of product development, when the shape of data is still being discovered. MongoDB's document model turns this around: data is stored as rich, self-describing BSON documents, nested objects and arrays included, with a schema that is enforced by the application rather than the database engine. The result is a persistence layer that moves at the speed of product iteration, with zero migration ceremonies for additive changes and flexible evolution paths for structural ones.

The natural mapping between BSON documents and Go structs is one of MongoDB's most underappreciated strengths from a Go developer's perspective. Where SQL databases require a translation layer between relational rows and Go types (either through an ORM or hand-written scanning), the official `go.mongodb.org/mongo-driver` encodes and decodes Go structs directly to and from BSON, with struct tags that feel immediately familiar to any Go developer who has used `encoding/json`. Embedded documents map to nested structs. Arrays map to slices. Polymorphic fields map to `bson.D` or `any`. The result is idiomatic Go code that speaks the language of the database without ceremony.

At scale, MongoDB's capabilities extend far beyond simple document storage. Aggregation pipelines compose multi-stage data transformations (filtering, grouping, joining, windowing, and projecting) in a single round trip to the database. Change streams expose a real-time feed of every write operation, enabling event-driven architectures where downstream services react to data mutations without polling. Multi-document ACID transactions, introduced in MongoDB 4.0, provide the consistency guarantees required for financial and inventory use cases while retaining the flexibility of the document model. Atlas Search brings Lucene-powered full-text and vector search directly into the database, and Atlas Vector Search adds approximate nearest-neighbor retrieval for AI and recommendation applications. MongoDB is not a simpler alternative to a relational database. It is a different tool for a different set of problems, and knowing when to reach for it separates effective Go engineers from those who default to PostgreSQL for every workload.

One caveat every engineer must understand before deploying MongoDB: the server changed its open-source license to the Server Side Public License (SSPL) in October 2018, and the SSPL is not approved by the Open Source Initiative. The Go driver (`go.mongodb.org/mongo-driver/v2`) remains Apache 2.0 and is freely usable regardless, but the server itself cannot be offered as a managed service by third-party cloud providers without entering a commercial agreement with MongoDB Inc. This is why AWS maintains DocumentDB (a wire-compatible subset of MongoDB 5.0-era APIs, not the real engine) and why MongoDB Atlas is the canonical managed offering. The practical consequence for Go teams: choose Atlas for managed convenience, self-host on your own infrastructure, or use DocumentDB accepting its feature gaps (no change streams prior to 4.0 wire, no aggregation stages added after 5.0, no Atlas Search or Vector Search). As of Go driver v2 (released 2024, current v2.3 in 2026), the import path is `go.mongodb.org/mongo-driver/v2/...` - v1 is end-of-life and all new code should target v2.

**What you'll learn:**

- Design MongoDB document schemas optimized for Go, choosing between embedding and referencing based on access patterns and cardinality
- Perform full CRUD operations using `go.mongodb.org/mongo-driver` with idiomatic struct tags and BSON encoding
- Build multi-stage aggregation pipelines for grouping, joining, windowing, and analytics workloads
- Implement change streams in Go for real-time event-driven processing and CDC (Change Data Capture) patterns
- Use multi-document ACID transactions with proper session and error handling in Go
- Design compound, sparse, partial, and text indexes to optimize query performance and enforce data integrity
- Integrate Atlas Search and Atlas Vector Search for full-text and semantic similarity queries from Go
- Write production-grade Go code with connection pooling, retry logic, read preferences, and distributed tracing

**Why this matters at scale:**

Forbes runs its entire content platform on MongoDB, serving hundreds of millions of readers with document schemas that evolve continuously as editorial features are added. Bosch uses MongoDB to store and query billions of IoT sensor events, exploiting time-series collections (5.0+) for efficient columnar storage and up to 200 percent faster aggregations in MongoDB 8.0. Coinbase has used MongoDB's aggregation framework to power financial reporting pipelines processing millions of transactions. The `go.mongodb.org/mongo-driver/v2` is the official, actively maintained driver built in collaboration between the MongoDB team and the Go community, making it the natural choice for any Go service that needs the flexibility of a document model without sacrificing driver quality or long-term support. At the time of writing, MongoDB 8.0 (GA October 2024) is current production and 7.0 is the LTS line. Both support the v2 Go driver.

**Prerequisites:** Comfort with Go structs and interfaces, basic understanding of JSON and data modeling concepts, familiarity with context-based cancellation and error handling in Go. No prior MongoDB experience is required.

### Junior → FAANG: entering the document database world

If you are coming from a relational background, the mental shift is simple to state and hard to internalise. In Postgres you design tables first and queries follow. In MongoDB you design queries first and documents follow. Every embedding or referencing decision is a bet on how the document will be read, not on how it will be stored. A junior engineer who skips this step ends up with normalized documents that require four `$lookup` stages to answer a single page request, and a senior reviewer who wonders aloud why the team did not just pick Postgres.

Start with a concrete worked example. An e-commerce product catalog has products, reviews, and sellers. In Postgres you would write three tables and three foreign keys. In MongoDB the question is: when the product detail page renders, what data does it need in a single read? If it needs the product, the top five reviews, and the seller's display name, then those three things belong inside one document. Older reviews go in a separate `reviews` collection with a `product_id` reference, because loading ten thousand reviews into memory every time a price is read is wasteful. The product document carries a small `top_reviews` array that is refreshed on write. This is the extended reference pattern, and it is the single most common design choice you will make.

Interview entry-points tend to be very concrete. Expect questions like: "Why is the BSON document size capped at sixteen megabytes?" (answer: to prevent a single document from dominating memory and network buffers, and to force engineers to think about unbounded arrays before production hits them), "What does `bson` struct tag syntax look like in Go?" (answer: `bson:"field_name,omitempty"`, and the zero-value elision rules differ slightly from `encoding/json` around empty slices and maps), and "When would you pick MongoDB over Postgres?" (answer: when schemas evolve faster than migration windows allow, when reads are predominantly whole-document retrieval by primary key, or when the access pattern is naturally hierarchical, such as a CMS, a product catalog, or an event log).

The driver surface you need to be fluent in on day one is small. `mongo.Connect`, `Database.Collection`, and the five CRUD methods on a collection (`InsertOne`, `Find`, `FindOne`, `UpdateOne`, `DeleteOne`) cover ninety percent of first-job work. Learn to pass `context.Context` to every call, learn to check `errors.Is(err, mongo.ErrNoDocuments)` for the not-found case, and learn to decode results into typed Go structs rather than `bson.M` maps. That alone puts you ahead of most junior submissions during a code screen.

### Senior @ FAANG: staff-level positioning of MongoDB in 2026

At staff and principal level the conversation stops being about MongoDB versus Postgres and becomes about the full spectrum of document-shaped workloads: MongoDB Atlas, self-hosted MongoDB 8.0 on Kubernetes, AWS DocumentDB, Azure Cosmos DB for MongoDB, FerretDB as an open-source wire-compatible layer over Postgres, and Postgres with JSONB columns. Each has a distinct failure mode. DocumentDB's feature drift from upstream MongoDB means aggregation pipelines written against 7.x will fail on DocumentDB's 5.0-era surface, and there are no change streams before 4.0 wire compatibility. Cosmos DB's request-unit billing model punishes wide scans in ways that are invisible until the monthly invoice arrives. FerretDB is a pragmatic choice when license posture forbids SSPL but falls behind on aggregation parity. Postgres JSONB is often the right answer when the document model is a convenience rather than a hard requirement, because operational tooling, transactions, and RBAC are all more mature. A staff ADR on "why MongoDB" should explicitly enumerate these alternatives and justify the selection against the specific workload.

MongoDB 8.0, GA in October 2024 and the current production line as of 2026, introduced several features that matter at scale. Queryable encryption reached general availability with support for range queries on encrypted fields, which closes a long-standing gap in client-side field-level encryption where equality was the only supported predicate. This is the difference between "we encrypt PII at rest" and "we can actually run analytics on encrypted PII without decrypting it server-side." Time series collections, introduced in 5.0 and hardened through 8.0, provide columnar-like storage for metric and IoT workloads with up to two hundred percent faster group-by aggregations and native support for delayed-arrival data through the `bucketMaxSpanSeconds` parameter. Atlas-only features include columnstore indexes for analytical workloads and Atlas Vector Search with HNSW indexes for embedding-based retrieval, both of which represent modern capabilities for a document database in 2026.

The sixteen megabyte document size cap is not a bug, it is a design tool. It forces engineers to confront unbounded array patterns before they ship to production. The canonical response to an unbounded array is the bucket pattern: rather than appending to `measurements` forever, shard the array across documents keyed by time bucket (`device_id + hour`). This turns an O(n) document growth problem into O(1) per bucket, keeps working set documents small enough to fit in the WiredTiger cache, and aligns naturally with time series collections. The computed pattern (storing pre-aggregated fields on write to avoid recomputation on read) and the extended reference pattern (embedding a denormalized subset of a referenced document) round out the three embedding patterns every staff engineer should reach for reflexively.

Consistency semantics deserve explicit attention. MongoDB offers tunable read concerns (`local`, `majority`, `linearizable`, `snapshot`) and write concerns (`w:1`, `w:majority`, `w:<custom tag>`). The default in v2 of the Go driver is `w:majority` with `j:true`, which is the right default but costs a round trip to the majority of voting members. Services on the read path of a hot workload often want `readConcern:local` with a session-scoped causal consistency guarantee, which keeps reads fast while preventing the "read your own writes" bug. The ADR for any new MongoDB-backed service should document the chosen read and write concerns, the rationale, and the fallback behavior when a primary is unavailable. Mongo-go-driver v2 exposes these through `options.Client().SetReadConcern(...)` and per-operation overrides on the session. Pair this with an OpenTelemetry configuration that emits spans for every command and you have the observability baseline for a production service.
