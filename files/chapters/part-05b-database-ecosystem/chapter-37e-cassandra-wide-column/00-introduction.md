# Chapter 37E: Cassandra & Wide-Column Databases

*Design your tables around your queries, not your data.*

Most database design begins with the question "what is my data?" - entities, attributes, and the relationships between them. Cassandra forces a different question first: "how will my data be accessed?" This shift is not arbitrary. Cassandra's architecture is built around the premise that reads must be served by a single partition on a single node, with no cross-partition joins and no server-side aggregations that would require coordinating across the cluster. To satisfy that constraint with acceptable latency, the table design must pre-compute the exact access pattern the application needs. The result is a database that, when modeled correctly, delivers single-digit millisecond reads and writes at petabyte scale across multiple data centers - and when modeled incorrectly, becomes a source of unbounded latency and cascading failures.

Cassandra's distributed architecture is built on deliberate trade-offs. Every node in the ring is equal - there is no primary, no single point of failure, no leader election to slow down writes. Data is distributed by a consistent hash of the partition key across a configurable token ring, with each node owning a range of tokens and replication ensuring that each partition lives on multiple nodes. Writes are appended to a commit log and a memtable before being flushed to SSTables on disk - a design that makes writes extremely fast regardless of the size of the dataset. Consistency is tunable per-operation: a write with `QUORUM` consistency waits for acknowledgment from a majority of replicas, while `ONE` returns as soon as a single replica confirms, trading durability for latency. This tunability makes Cassandra uniquely suited to workloads that span the spectrum from "every write must be durable" to "best-effort, high-throughput event ingestion."

The `gocql` driver provides a mature, production-tested interface to Cassandra from Go, with support for prepared statements, token-aware routing, automatic retry policies, and connection pooling. Its companion library `gocqlx` adds struct binding and query builder ergonomics that feel natural to Go developers familiar with `sqlx`. Time-series and IoT workloads - sensor readings, log events, financial ticks, user activity streams - are Cassandra's natural home: the combination of time-based clustering columns, TTL-based expiry, and write throughput that scales linearly with cluster size makes it the database of choice for any application that needs to ingest and query billions of timestamped events. Knowing Cassandra's data model, operational characteristics, and Go driver internals equips you with a tool that no relational database, however well-tuned, can match for these workloads.

**What you'll learn in this chapter:**

- Understand Cassandra's ring topology, consistent hashing, vnodes, and how data is distributed and replicated
- Apply the query-first data modeling methodology: design tables for access patterns, not entities
- Choose partition keys and clustering columns that ensure even data distribution and efficient range queries
- Implement production Go applications using `gocql` with prepared statements, token-aware routing, and retry policies
- Use `gocqlx` for idiomatic struct binding, query building, and migration management in Go
- Build time-series and IoT data pipelines with TTL, bucket patterns, and compaction strategy selection
- Configure replication factors, consistency levels, and multi-datacenter topologies for disaster recovery
- Apply lightweight transactions (LWT), batches, and secondary indexes correctly, understanding their cost and when to avoid them

**Why this matters at scale:**

Apple operates one of the largest Cassandra deployments in the world - over 160,000 nodes storing more than 10 petabytes of data for iCloud and other services, requiring Cassandra's peer-to-peer architecture to avoid any single point of failure. Instagram used Cassandra to store and serve the social graph and activity feed for over a billion users, exploiting its linear write scalability to handle surges during major live events. Discord migrated their message storage to Cassandra specifically because it could sustain millions of writes per second across multiple regions without degrading read latency. For Go engineers building systems at the intersection of high write throughput, multi-region availability, and time-series access patterns, Cassandra is frequently the only database that fits the requirements without requiring a complete rethink of the architecture.

**Prerequisites:** Familiarity with Go structs, interfaces, and context-based error handling. Basic understanding of distributed systems concepts (replication, consistency) is helpful but not required. No prior Cassandra experience is assumed.

### Junior → FAANG: Prerequisite Gaps and Worked Entry Points

If you have only ever worked with PostgreSQL or MySQL, Cassandra will feel disorienting until you internalise one sentence. There are no joins, no foreign keys, no server side GROUP BY across partitions, and no ad hoc WHERE clauses that scan unknown columns. Every CQL query must hit a single partition by equality on the partition key, and any filtering beyond that must ride on clustering columns in the defined sort order. The first worked example you should run on a laptop is a three node Docker Compose cluster with `cassandra:5.0` images, a keyspace with `replication_factor = 3`, and a `posts_by_user` table keyed by `((user_id), created_at DESC)`. Insert ten thousand rows, then try `SELECT * FROM posts_by_user WHERE user_id = ? AND created_at > ?`. That works in one round trip. Now try `SELECT * FROM posts_by_user WHERE created_at > ?` without the user_id. Cassandra refuses unless you add `ALLOW FILTERING`, and the moment you do that in production you are scanning every node in the ring. That refusal is the feature, not the bug.

First job interviewers for backend roles that touch Cassandra, Scylla, DynamoDB, or Bigtable ask three entry level questions. What is a partition key and how does it differ from a clustering column. Why can you not run arbitrary WHERE clauses. What happens when a node goes down during a write at QUORUM with RF=3. The answers are short. The partition key decides which node stores the row via a Murmur3 hash. Clustering columns decide the order inside that partition. Arbitrary WHERE clauses would require a scatter gather across every node, which defeats the point of consistent hashing. At RF=3 with QUORUM you need two acknowledgments, so a single node failure is survivable and the coordinator stores a hinted handoff for the dead replica to catch up later. If you can speak those three answers cleanly you will pass the screen.

The gocql entry point is also a specific worked example. Open a session with `gocql.NewCluster("host1","host2","host3")`, set `Consistency = gocql.Quorum`, set `PoolConfig.HostSelectionPolicy = gocql.TokenAwareHostPolicy(gocql.RoundRobinHostPolicy())`, and always call `session.Query(cql).Bind(args...).Exec()` with prepared statements rather than string concatenation. CQL injection is real, and the fix is identical to SQL injection. Never build queries with `fmt.Sprintf`. The driver caches prepared statements per connection automatically, so the cost of `Prepare` is amortized across millions of executions.

### Senior @ FAANG: Staff and Principal Framing

At staff and principal level the Cassandra conversation is never about CQL syntax. It is about ecosystem selection, blast radius, and the second order costs of the query first model. The first decision is which wide column engine to run. Apache Cassandra 5.0 ships Storage Attached Indexes (SAI) that finally make secondary indexes tractable, trie based memtables and SSTables that cut read amplification, and unified compaction that collapses the LCS versus STCS decision tree. It remains a JVM process with heap tuning, G1GC pauses measured in tens of milliseconds under pressure, and a per node throughput ceiling typically in the low tens of thousands of writes per second on commodity hardware. ScyllaDB 6.0 rewrites the same wire protocol and data model in C++ on the Seastar framework, using a shard per core architecture where each CPU owns a slice of the data with no cross core locking, no JVM, and a user space network stack. In workloads that actually saturate a box, Scylla delivers ten to one hundred times the throughput per node at a fraction of the tail latency, and it is the default choice when your bottleneck is infrastructure cost per million operations. The tradeoff is ecosystem maturity on the edges, specifically around newer Cassandra features like SAI where Scylla lags by one or two minor versions, and a smaller set of managed operators.

Then there is the managed service matrix. ScyllaDB Cloud gives you Scylla with the operational pain taken out and a bring your own VPC story. AWS Keyspaces is a serverless Cassandra compatible API where you pay per read and write unit, which is attractive for spiky workloads but imposes hard limits on partition size, row size, LWT semantics, and several CQL features, and its latency floor is noticeably higher than self hosted Scylla. Azure Cosmos DB with the Cassandra API is a multi model wrapper over the Cosmos engine with request unit billing and its own consistency ladder that does not map cleanly onto Cassandra consistency levels. Picking between these is a staff level decision driven by workload shape, regulatory constraints, and the team's operational budget, not by feature checkbox comparisons.

The architecture details that matter in design review are gossip for cluster membership (an O(log N) epidemic protocol that converges in seconds but is the reason cluster topology changes are never instantaneous), hinted handoff for short outages where the coordinator buffers writes for a down replica up to a configurable window, read repair that opportunistically reconciles divergent replicas on the read path, and anti entropy repair driven by Merkle trees which you must schedule weekly within gc_grace_seconds or risk resurrected tombstones. Virtual nodes (vnodes, default 16 on Cassandra 5, default 256 on older clusters, often set to 4 on Scylla) control how token ranges are sliced per host and directly affect streaming speed during scale out. The partitioner is Murmur3Partitioner in practice. ByteOrderedPartitioner exists, and if anyone proposes it outside of a legacy migration you should treat it as a red flag because it guarantees hotspots.

Query first modeling at scale means denormalizing aggressively, one table per query pattern, and accepting that a single logical entity like a user post may be written to five or six tables in one LOGGED or application level fan out. Partition key design is the single highest-value choice in the schema. Cardinality must be high enough that data spreads across the ring, partitions must stay below the one hundred megabyte soft cap and ideally below ten megabytes for latency sensitive reads, and access frequency must be uniform enough that no single key becomes a hotspot. The wide partition anti pattern (a celebrity user's timeline, a global counter partition, a single sensor's year of data in one row) is the number one cause of Cassandra production incidents. The fix is bucketing by time window (`((sensor_id, day_bucket), ts)`) or by a hash salt (`((user_id, bucket), ts)` with bucket in `[0, N)`). Clustering columns define on disk order, which means range scans are free in that order and impossible against it, and you choose ASC or DESC at table creation because reversing it at query time is expensive. Static columns give you per partition metadata without replicating it across every row. Materialized views exist but have known consistency bugs under failure, and the senior level default is to maintain the denormalized table yourself in application code with an idempotent write path.

The Go driver story has two layers. gocql v1.7 is the low level protocol client with prepared statements, token aware routing, DC aware load balancing, exponential backoff retries, and speculative execution. gocqlx v3 sits on top and adds struct binding via reflection cached at prepare time, a query builder, and schema migration helpers. You use gocqlx for CRUD and gocql directly when you need to drop to raw protocol features. Prepared statements are cached per connection and must be re prepared automatically after a schema change, which gocql handles via the `UNPREPARED` response code, but if you have ever seen a thundering herd of re prepares after a rolling DDL you know why you stagger schema changes. Retry policy defaults are too aggressive for idempotent writes and too timid for reads. Explicitly set `RetryPolicy = &gocql.ExponentialBackoffRetryPolicy{NumRetries: 3}` and use `SimpleRetryPolicy` only for truly idempotent operations. Load balancing policy should always be `TokenAwareHostPolicy` wrapped around `DCAwareRoundRobinPolicy(localDC)` in multi region deployments so queries go to the replica that owns the token in the local datacenter.

Batches are the most misused feature in the driver. LOGGED batches write to the batchlog table first for atomicity across partitions, which roughly halves write throughput and only makes sense when you need all or nothing semantics across a small number of denormalized tables. UNLOGGED batches skip the batchlog and are fire and forget. UNLOGGED wins only when every statement in the batch targets the same partition, in which case the coordinator sends one message instead of many and you get a real throughput gain. UNLOGGED across partitions is an anti pattern because it gives you no atomicity and more coordinator load than parallel async sends. COUNTER batches are their own category for counter columns and cannot mix with non counter statements. TTL first modeling means every row gets an expiry at write time, and time window compaction strategy (TWCS) is tuned so entire SSTables expire together without tombstone generation. Time series partitioning always uses a composite partition key with a time bucket sized so that partitions stay under ten megabytes for your sample rate, which for a one hertz sensor is a day bucket, for a thousand hertz sensor is an hour bucket, and for a pre trade tick feed is a minute bucket. Get this sizing wrong and no amount of driver tuning will save the read path.
