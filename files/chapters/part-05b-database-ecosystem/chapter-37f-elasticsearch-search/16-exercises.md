## Exercises

1. **Index Mappings for E-Commerce Search**: Design a production Elasticsearch index mapping for a product catalog with 5M SKUs. The mapping must support: full-text search on `name` and `description` with a custom English analyzer (stemming, stop words, synonym expansion for common abbreviations), keyword filtering on `brand`, `category`, and `tags`, range queries on `price` and `rating`, and geo-distance filtering on `warehouse_location`. Disable `_source` on high-cardinality keyword fields to reduce storage. Implement the mapping in Go using the `go-elasticsearch` client, validate it with a test that indexes 10 sample products and asserts correct field mapping metadata via the Get Mapping API. Expected outcome: mapping JSON, Go setup code, and passing mapping-validation tests.

2. **Multi-Field Boosted Search Query**: Implement a Go search handler for an e-commerce platform that accepts a free-text query and returns ranked products using a `bool` query with `multi_match` across `name` (boost 4), `brand` (boost 2), `description` (boost 1), and `tags` (boost 1.5). Apply a `function_score` layer that multiplies the text score by a `field_value_factor` on `sales_rank` (modifier: `log1p`, factor: 0.5) and decays the score by recency using `gauss` on `updated_at` (scale: 30 days). Write integration tests against a local Elasticsearch instance that assert the top result for the query "wireless noise canceling headphones" is more relevant than results without the boosting configuration, measured by NDCG@5. Expected outcome: Go search handler, function_score query JSON, and NDCG-based relevance tests.

3. **Aggregations for Faceted Navigation**: Build a Go search API endpoint that executes a single Elasticsearch request returning both paginated hits and facet counts for a product catalog. The response must include: `terms` aggregation on `category` (top 20) and `brand` (top 50), `range` aggregation on `price` with configurable buckets, `stats` aggregation on `rating`, and a `filter` aggregation to show "in-stock only" count without affecting the main result set. Implement cursor-based pagination using `search_after` with a `point_in_time` ID for stable deep pagination beyond 10,000 results. Expected outcome: Go API handler, Elasticsearch DSL query, response struct with facets and pagination token, and integration tests asserting facet counts match manual counts for a seeded dataset.

4. **Index Lifecycle Management Policy**: Design an ILM policy for a high-volume application log index that implements: hot phase with one primary shard, rollover at 50GB or 7 days with `force_merge` to 1 segment. Warm phase entered after 7 days with replica reduction to 0 and `best_compression` codec. Cold phase after 30 days mounted as a searchable snapshot on S3. Delete phase after 90 days. Apply the policy to a data stream using an index template in Go. Write a test that simulates rollover by setting `max_docs: 10` in the policy, indexes 15 documents, calls the rollover API, and asserts a new write index was created with the correct generation suffix. Expected outcome: ILM policy JSON, index template, Go setup code, and rollover simulation test.

5. **Bulk Indexing 10 Million Documents Efficiently**: Write a Go bulk indexing pipeline that indexes 10M product documents from a PostgreSQL source into Elasticsearch as fast as possible without overwhelming the cluster. The pipeline must: use the `go-elasticsearch` `esutil.BulkIndexer` with configurable worker count and flush thresholds, implement a producer-consumer pattern with a buffered channel between the PostgreSQL reader and the bulk indexer, track indexing errors and dead-letter failed documents to a separate `failed_docs` index, and emit structured log lines with throughput (docs/sec) and error rate every 10 seconds. Tune and document the optimal `numWorkers`, `flushBytes`, and `flushInterval` settings found through benchmarking. Expected outcome: Go pipeline code, benchmark results showing achieved throughput, error-handling test, and a tuning notes document.

6. **Autocomplete with Edge N-Grams**: Implement a real-time product search autocomplete endpoint backed by Elasticsearch edge n-grams. Define a custom analyzer with an `edge_ngram` token filter (`min_gram: 2`, `max_gram: 20`) applied only at index time and a `standard` analyzer at query time to avoid n-gram expansion on the query side. Store both the `autocomplete` sub-field (edge n-gram) and the original `name` field (keyword) on the same mapping field using `fields`. Write a Go handler that queries the `autocomplete` field and returns the top 10 distinct product names sorted by `popularity_score`. Add a second handler using the `completion` suggester as an alternative and benchmark both approaches for latency and relevance at p50/p95. Expected outcome: index mapping with custom analyzer, two Go handler implementations, latency benchmark comparing edge n-gram vs completion suggester, and a written trade-off analysis.

The key insight: **Elasticsearch is a search engine, not a database**. Design your queries first, then build mappings to support them efficiently.

### Junior to FAANG: How To Submit These Exercises Like A Hireable Candidate

A FAANG hiring manager will not read 2000 lines of undocumented code. Package each exercise as a small portfolio project. The package is as important as the code.

Per exercise deliverable layout. A README with the problem statement in your own words, the design decisions made and the ones rejected, how to run it, how to test it, measured results with a table (latency, throughput, NDCG), and open questions you would address next. A `docker-compose.yml` for reproducibility. A `Makefile` with `make test`, `make bench`, `make load`. Code organized by clean boundaries (handler, service, repository, search client).

Prerequisite skills to demonstrate. Idiomatic Go (context propagation, error wrapping, structured logging via `slog`), defensive clients (retry with backoff, circuit breaker on the ES client), testable design (interface at the search boundary so you can mock). Skipping these makes your code look like a tutorial copy.

Worked example for Exercise 5. A junior submission indexes 10M documents and claims success. A strong submission indexes 10M documents, reports throughput over time, identifies the bottleneck (usually `flush_threshold_size` on the translog or bulk queue saturation), tunes it with before and after numbers, and adds a graceful shutdown that drains in flight bulks before exiting. That is three extra hours of work for dramatically stronger signal.

"Why did this fail" reflex for exercises. Indexing throughput plateaus early, check `thread_pool.write.rejected` and bulk queue size. Search latency climbs under load, check segment count (too many small segments from rapid refresh), check GC pressure. Relevance drops after a mapping change, check analyzer symmetry at index versus query time.

Interview entry point. Bring one completed exercise to a system design interview as evidence. Walk through it for 10 minutes. This converts a theoretical design conversation into a demonstrable one and moves you from L4 to L5 signal in a single turn.

### Senior at FAANG: Staff Scope Extensions and Governance For Each Exercise

Elevate each exercise to staff scope. The rubric is, does the extension produce durable platform artifacts, not just code.

Exercise 1 staff extension, mapping governance. Build a Go linter that validates proposed mappings against policy (no top level `text` without `.keyword` sibling if the field is in a documented filter set, no `ignore_above` over 8192, no dynamic mapping without an explicit opt in). Wire it into a CI workflow. Deliverable, the linter plus a policy document.

Exercise 2 staff extension, relevance evaluation harness. Create a graded judgment set of 200 queries. Integrate `pytrec_eval` (call via Go subprocess or reimplement NDCG in Go). Every change to the query shape runs the harness and reports delta NDCG at 10 and delta MRR. Gate merges on a 2 percent regression threshold. Deliverable, the harness, the judgment set, and a week of trended results.

Exercise 3 staff extension, facet pre aggregation. For facets that are expensive at 5M docs, precompute per filter cardinalities in a secondary rollup index refreshed every 60 seconds. Build the refresh pipeline in Go. Compare query latency with and without rollup. Deliverable, the rollup pipeline, the SLA for staleness, and a fallback path when rollup is cold.

Exercise 4 staff extension, disaster recovery drill. Simulate a cluster loss by restoring from searchable snapshots into a fresh cluster. Measure restore time per TB. Document the RTO and RPO achieved. Deliverable, a DR runbook and a quarterly drill schedule.

Exercise 5 staff extension, zero downtime reindex pipeline. Extend the bulk pipeline to support a full reindex from Postgres while live writes continue. Use aliases plus dual write plus backfill. Verify parity with a document diff tool. Deliverable, a runbook, a parity report, and a rollback procedure tested end to end.

Exercise 6 staff extension, LTR reranker. Train a LightGBM model on click through data. Serve it as a rerank sidecar. Rerank top 100 from the completion suggester. Measure the lift on CTR at 5 through A/B test. Deliverable, the model artifact, the rerank service, the A/B test report.

Governance deliverables required for any staff submission. An ADR per decision of consequence. A cluster sizing document. A shard budget table. A kNN profile registry entry if vector search is touched. A script catalog entry if any Painless is introduced. Without these the work is L4, regardless of the code quality.

Bar raiser aggregate challenge. Combine exercises 1, 2, 5, and 6 into a single search platform for an e commerce company. Multi tenant. Multi region with CCR. Relevance evaluation in CI. LTR pipeline. Zero downtime reindex. Published SLOs. Cost per query budget. Quarterly portfolio decision ADR. A clean submission at this scope is L6 signal and opens staff engineer conversations.

Maturity model for your exercise portfolio itself. L1 code compiles. L2 tests pass. L3 load tested with reported SLOs. L4 governance artifacts attached. L5 migration and DR plans rehearsed. Submit at L4 for senior interviews and at L5 for staff.
