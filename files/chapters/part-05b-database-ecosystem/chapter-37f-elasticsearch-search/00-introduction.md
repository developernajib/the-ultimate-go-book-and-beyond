# Chapter 37F: Elasticsearch & Search Engineering

*Search is not a feature. For many products, search is the product.*

When users interact with a product through a search box, they are not executing a SQL `LIKE` query. They are expressing intent in natural language, with typos, abbreviations, synonyms, and domain vocabulary that no exact-match system can reliably handle. Full-text search requires a fundamentally different storage and retrieval model: the inverted index. Rather than storing documents and scanning them for matches, Elasticsearch builds an index from terms to the documents that contain them, enabling relevance-ranked retrieval across millions of documents in milliseconds. This is the core capability that makes Elasticsearch the backbone of search for GitHub, Wikipedia, Shopify, and hundreds of other products where finding the right result quickly is the difference between a great user experience and a frustrating one.

The ecosystem has also been reshaped by a licensing saga worth understanding before committing. In 2021 Elastic relicensed Elasticsearch and Kibana from Apache 2.0 to a dual SSPL/Elastic License, which was not OSI-approved. AWS responded by forking the last Apache 2.0 release and launching OpenSearch (now stewarded by the Linux Foundation's OpenSearch Software Foundation). In September 2024 Elastic added AGPLv3 as a third license option, restoring an OSI-approved open-source path for Elasticsearch itself. Today production teams choose between Elasticsearch 9.x (AGPLv3, SSPL, or Elastic License, with the official `github.com/elastic/go-elasticsearch/v9` client) and OpenSearch 3.x (Apache 2.0, with the `github.com/opensearch-project/opensearch-go` client). The query DSL remains largely compatible, but newer features such as ELSER sparse-vector semantic search, Better Binary Quantization for kNN, the `retriever` RRF construct, and ES|QL are Elastic-only.

Elasticsearch is built on Apache Lucene and extends it with a distributed, REST-native architecture. An index is divided into shards (self-contained Lucene indices) that are distributed across a cluster and replicated for fault tolerance. When a query arrives, the coordinating node fans it out to every shard, collects the top results, merges them by relevance score, and returns a ranked response. This architecture scales horizontally: adding nodes increases both storage capacity and query throughput, with no application-level sharding logic required. Field mappings define how each field is indexed, whether as a full-text `text` field analyzed into tokens, a `keyword` field for exact matching and aggregations, a `date` for range queries, or a `dense_vector` for k-nearest-neighbor semantic search. Getting mappings right is the most consequential design decision in any Elasticsearch-backed system. A wrong choice requires a full reindex, which for large datasets means hours of downtime or a complex zero-downtime reindex pipeline.

The official `go-elasticsearch/v9` client provides a type-safe, low-level interface to the Elasticsearch REST API from Go, with support for bulk indexing, PIT + `search_after` pagination (the scroll API is effectively legacy for user-facing workloads), connection pooling, and automatic retry with exponential backoff. A parallel `typedapi` surface offers strongly-typed request/response structs for teams that prefer compile-time checks over raw JSON maps. Building on top of it, Go services can implement not only basic search but the full spectrum of Elasticsearch capabilities such as multi-field boosting, function score queries, nested document search, geographic distance filtering, faceted navigation through aggregations, hybrid BM25 + kNN retrieval via the `retriever`/RRF API, and real-time alerting through percolator queries. Index Lifecycle Management (ILM) automates the rollover and deletion of time-series indices, keeping storage costs bounded as data volumes grow. For Go engineers building products where search quality directly affects user retention and conversion, Elasticsearch's query language, mapping design, and operational model are essential skills.

**What you'll learn in this chapter:**

- Understand Elasticsearch's distributed architecture: shards, replicas, routing, segment merging, and the inverted index
- Design production index mappings with appropriate field types, multi-fields, custom analysers, and dynamic templates
- Implement full-text, fuzzy, geospatial, and k-NN vector search using the `go-elasticsearch` client in Go
- Build complex search queries: boolean logic, function score, nested objects, and multi-match with field boosting
- Construct aggregation pipelines for faceted navigation, histograms, top-N metrics, and statistical analysis
- Implement high-throughput bulk indexing with error handling, retry logic, and backpressure in Go
- Design index templates, data streams, and ILM policies for time-series and log data at scale
- Integrate Elasticsearch into Go microservices with structured error handling, observability, and zero-downtime reindexing patterns

**Why this matters at scale:**

GitHub ran code search on Elasticsearch for years, with custom analyzers that understood programming-language tokens, before outgrowing it and building the custom Blackbird engine in 2023, a lifecycle worth remembering: Elasticsearch carried them past a hundred million repositories before specialization paid. Shopify relies on Elasticsearch to power product search for millions of merchants and their customers, where relevance tuning directly correlates with merchant revenue. Wikimedia runs Elasticsearch to serve search across all Wikipedia language editions, handling hundreds of millions of queries per month with strict latency SLOs. The `go-elasticsearch` client is the official client maintained by Elastic, providing first-class Go support with full compatibility guarantees against each major Elasticsearch version, making it the production-safe choice for any Go service that needs search, analytics, or log aggregation at scale.

**Prerequisites:** Familiarity with Go's `net/http` and JSON encoding, understanding of basic database indexing concepts, comfort with Go error handling patterns and context propagation.

### Junior → FAANG: Entry points, prerequisite gaps, and first-job context

If you are coming from a CRUD SQL background, the first conceptual leap is that Elasticsearch is not a database you use in place of Postgres. It is a secondary index optimized for full-text retrieval, faceted aggregations, and approximate nearest neighbor vector search. The system of record stays in your OLTP store (Postgres, MySQL, DynamoDB), and a change-data-capture pipeline or dual-write fans updates into Elasticsearch. Juniors who treat Elasticsearch as a primary store will eventually lose data during a reindex, discover that `_source` disagrees with the real world, or get paged at 3 AM because a node ran out of disk during a force merge. Treat it as a projection, not a source.

The prerequisite gap most juniors hit is the inverted index itself. Walk through a worked example by hand: index three documents with the text `"the quick brown fox"`, `"a quick test"`, `"brown cow jumps"`. The standard analyser lowercases and tokenises into `[the, quick, brown, fox]`, `[a, quick, test]`, `[brown, cow, jumps]`. The inverted index stores `quick -> [doc1, doc2]`, `brown -> [doc1, doc3]`, `the -> [doc1]`. A query for `quick brown` now becomes a posting-list intersection, and BM25 scores each match by term frequency, inverse document frequency, and field length normalization. Once you understand that every `text` field is preprocessed through an analyser chain and stored as posting lists, the behavior of stemming, synonyms, stopwords, and case sensitivity stops feeling arbitrary.

First-job context for a new grad on a search team usually looks like one of three patterns. You ship a feature behind a boolean filter on an existing index. You tune the `should` clauses of an existing query to nudge relevance, measured with `_rank_eval` or an offline judgment set. Or you own a bulk reindexer that moves documents from the OLTP store into Elasticsearch without taking a read outage. Interview entry-point questions at this level tend to be concrete: explain `text` vs `keyword`, write a `bool` query that combines a required filter with optional boosts, design a mapping for a product catalog, explain why `match_phrase` behaves differently from `match`, or walk through how you would reindex without downtime using aliases. The strong answer to the last one is always the same pattern: write to both old and new through an alias, backfill with the reindex API, flip the alias atomically, and delete the old index only after verification.

The single most useful habit a junior can build is reading the response metadata. `took`, `timed_out`, `_shards.failed`, `hits.total.relation`, and the `profile` API output tell you more about what is happening than any staring at the query DSL. If `_shards.failed` is non-zero, your search returned partial results and the client did not raise an error. Noticing that on day one separates people who will grow into senior search engineers from those who will keep filing tickets against the platform team.

### Senior @ FAANG: Staff and principal search architecture

At staff level the first decision is almost never a query question. It is a platform and governance question. In 2026 the viable options are Elasticsearch 9.0 under AGPLv3 or Elastic License v2, OpenSearch 3.0 under Apache 2.0 governed by the OpenSearch Software Foundation with AWS, Oracle, and SAP as principal stewards, Vespa for large-scale ranking with tensor evaluation in the serving path, Typesense or Meilisearch for embedded and small-corpus search where operational simplicity beats feature depth, and the vector-native stack of Qdrant and Weaviate for workloads dominated by semantic retrieval. The honest framing for a technology selection ADR is that Elasticsearch 9 gives you ELSER sparse embeddings, Better Binary Quantization, the retriever RRF construct, and ES|QL, at the cost of license complexity and vendor gravity. OpenSearch 3 gives you clean Apache 2.0, a credible governance body, strong AWS integration, and a diverging plugin ecosystem (k-NN via FAISS and Lucene engines, Neural Search, the SQL plugin), at the cost of lagging the Lucene-native features that ship first in Elastic. Vespa wins when you need to run learned rankers with hundreds of features per document inside the serving path. Qdrant and Weaviate win when the workload is 90 percent vector and 10 percent keyword. Anything that reads "we chose Elasticsearch because that is what we already use" is not an ADR, it is a rationalization.

The architectural primitives that matter at scale are shard sizing, data tiers, and routing. The field-tested sweet spot for a primary shard is 20 to 50 GB on hot tier NVMe, with roughly one shard per 30 million documents as a first approximation and adjustment based on segment merge cost. Oversharding is the single most common failure mode. A cluster with 10,000 tiny shards spends its heap on cluster state and its CPU on fan-out overhead. Undersharding forces expensive splits and constrains parallelism. The data tier model in modern Elasticsearch and OpenSearch separates hot (frequent writes, low-latency search on NVMe), warm (read-mostly on dense SSD), cold (read rare, on spinning disk or object storage), and frozen (searchable snapshots backed directly by S3 or equivalent, with a local cache). Frozen searchable snapshots are the single biggest cost lever for time-series and log workloads. A 100 TB logging cluster that used to sit entirely on hot nodes can be reshaped so 95 percent of the data lives in frozen on S3 at roughly one tenth the cost, with p99 search latency on cold queries in the single-digit seconds, which is the right tradeoff for compliance and forensic search.

Mapping design at senior level is a contract, not a convenience. The default dynamic mapping is a production hazard because any caller can pollute the schema by sending a new field, and mapping explosion can crater a cluster. The staff-level posture is `"dynamic": "strict"` on every index, or `"dynamic": "runtime"` when you genuinely need late-bound fields materialized at query time without committing storage. Multi-fields are the canonical idiom for dual-purpose fields. A product title is indexed as `text` with a language analyser for full-text match, and as `title.raw` keyword for exact term aggregations and sort. Dynamic templates are for families such as `*_id -> keyword, index: false, doc_values: true` and `*_count -> long`. The analyser chain of character filters, tokenizer, and token filters is where domain knowledge lives. For a code search index, a custom tokenizer that preserves camelCase splits and symbol boundaries changes recall dramatically. For a multilingual catalog, the decision between a single per-field `icu_analyzer` with language detection and a per-language subfield strategy is a real tradeoff worth writing down. Synonyms deserve their own governance pipeline. Query-time synonyms let you iterate without reindexing but cost recall correctness on phrase queries. Index-time synonyms are faster at query time but every change is a reindex. The mature pattern is query-time expansion during the learning phase and a promotion to index-time only after a synonym set stabilises, with the synonym file versioned in git and loaded via the `_reload_search_analyzers` endpoint.

Ingest architecture is the second place seniors earn their keep. The choice between Elasticsearch ingest pipelines, Logstash, Vector, and a bespoke Go ingester is driven by three questions. Where is backpressure handled, where is schema validation enforced, and where is poison-message quarantine implemented. Ingest pipelines are cheapest operationally but run on the coordinating nodes and can starve search capacity. Logstash has rich transforms but is a JVM and a separate fleet to operate. Vector in Rust is the current default for log shipping at scale because it is cheap, has a strong disk buffer, and ships a usable transforms language. A Go ingester using `go-elasticsearch/v9` bulk indexer is correct when you need tight schema control, circuit breakers aware of your business rules, and first-class observability. The bulk API pattern that matters is the one that respects 429 backpressure with exponential jitter, splits oversized batches on `413`, and routes poison documents to a dead-letter index with the full failure reason, rather than logging and dropping. `_update_by_query` and `_delete_by_query` are idempotent only if you are disciplined about `if_seq_no` and `if_primary_term` versioning. Treat them as migrations, run them through a changelog, never let an on-call engineer run one interactively against production.

Query and ranking is where junior instincts most often mislead senior decisions. The `bool` query is not a set of equals, it is a scoring contract. `filter` and `must_not` are boolean, cacheable, and non-scoring. `must` and `should` contribute to `_score`. Writing `must` where `filter` is correct doubles query cost for no benefit. `function_score` and `script_score` let you encode business rules such as recency decay, popularity priors, and inventory boosts, but they defeat query caching and should be the last resort after field-level boosts and rank features. `rank_features` and `rank_feature` queries are the right primitive for precomputed document-level scores such as PageRank, review-count priors, or a learned popularity feature. Learning to rank through the Elasticsearch LTR plugin or OpenSearch's equivalent is the step-change when a hand-tuned query plateau is reached, and it requires a judgment pipeline, offline `_rank_eval` scoring, and a feature store that reconciles train-serve skew. Hybrid search with BM25 and dense vectors fused via reciprocal rank fusion is now table stakes, and the `retriever` construct in Elasticsearch 9 or the `hybrid` query in OpenSearch 3 is what you should be writing, not hand-rolled score normalization. The go-elasticsearch v9 typed API makes all of this safer by forcing compile-time validation of the query shape, which matters enormously when a mistyped key silently falls into the JSON body and produces a 200 with zero results instead of an error. Senior engineers prefer typed builders, reject raw `map[string]any` except in one-off tooling, and gate every production query behind a golden-set `_rank_eval` regression in CI.
