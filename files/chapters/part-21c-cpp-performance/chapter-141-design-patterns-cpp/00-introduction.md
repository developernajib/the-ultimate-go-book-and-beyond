# Chapter 141: Design Patterns in Modern C++

> "Design patterns are discovered, not invented.", Ralph Johnson

Most programmers encounter design patterns through the Gang of Four book: 23 patterns described in 1994, illustrated in C++ and Smalltalk, all rooted in runtime polymorphism and virtual dispatch. That taxonomy remains valid, but it was written before move semantics, variadic templates, `constexpr`, `std::variant`, concepts, and ranges reshaped what C++ actually is. Modern C++ does not merely implement the GoF patterns, it replaces many of them entirely. A `std::variant` with `std::visit` outperforms and out-expresses the classical Visitor in almost every scenario. Policy-based design via template parameters eliminates the Strategy pattern's vtable overhead on hot paths. RAII with move semantics delivers a safer, more composable version of everything the GoF called "resource management." This chapter is about those replacements and additions, the patterns that production C++ engineers actually reach for in 2024.

The chapter opens with RAII taken to its logical conclusion: ScopeGuard and TransactionGuard, giving you Go's `defer` semantics with C++ precision. It then covers the Pimpl idiom as a compilation firewall, a pattern with no Go equivalent that becomes indispensable in large codebases. Type erasure gets its own section because it is the foundation underneath `std::function`, `std::any`, and every custom polymorphic container you will ever write. Policy-based design (Alexandrescu's contribution from "Modern C++ Design") shows how template parameters compose behaviors at compile time with zero runtime cost. The middle sections cover `std::variant`-based Visitor, variant-based state machines, and the Strategy pattern examined across three implementation axes, templates, virtual dispatch, and `std::function`, with honest benchmark guidance. The back half addresses Observer/EventBus with lifetime safety, the Builder pattern with CRTP for inheritance, dependency injection without a framework, and Entity-Component-System architecture for data-oriented performance. A Go-engineer perspective closes the chapter with a direct pattern-mapping table and practical advice for engineers crossing between the two languages. Every pattern is shown with production-quality code targeting C++17 or C++20, accompanied by explicit notes on when the pattern is worth its complexity and when a simpler alternative wins.
