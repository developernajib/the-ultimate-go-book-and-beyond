## Static Analysis: clang-tidy, cppcheck, and PVS-Studio

Static analysis examines source code without running it to find bugs, style violations, and security vulnerabilities. In a language with undefined behavior as pervasive as C++, static analysis is not optional on production codebases, it is the first line of defense against entire classes of memory corruption, null dereferences, and logic errors that the compiler's own warnings miss.

### clang-tidy

clang-tidy is the LLVM project's linting tool. It is not a simple pattern matcher, it uses the full Clang AST, meaning it understands types, templates, and control flow. It ships with 400+ checks organized into groups, and its output is precise enough that many checks include automatic fixes.

#### Running clang-tidy

Static analysis tools examine source code without executing it, flagging common bugs, style violations, and security vulnerabilities early in the development cycle. Integrating a linter into the CI pipeline ensures that issues are caught before code review rather than in production.
```bash
# Basic run on a single file
clang-tidy src/scheduler.cpp -- -std=c++20 -Iinclude

# Run on a compilation database (generated by CMake)
# CMAKE_EXPORT_COMPILE_COMMANDS=ON generates compile_commands.json
clang-tidy -p build/ src/scheduler.cpp

# Run on all files using run-clang-tidy.py (parallel, from llvm-utils)
run-clang-tidy -p build/ -j$(nproc)

# Apply automatic fixes (creates a .cpp.orig backup)
clang-tidy -p build/ src/scheduler.cpp --fix

# Run specific checks only
clang-tidy -p build/ \
  -checks="-*,bugprone-*,modernize-use-nullptr,readability-const-return-type" \
  src/scheduler.cpp
```

#### Important Check Groups

clang-tidy organizes its checks into named groups: `bugprone-*` catches runtime hazards like use-after-move and unchecked optional access, `modernize-*` upgrades C++98/11 idioms to C++17/20 equivalents, and `performance-*` flags inefficiencies like unnecessary copies of `std::string` arguments. Enabling all groups in CI and treating warnings as errors prevents entire categories of bugs from ever reaching production.
```
# Check groups and what they find

bugprone-*
  bugprone-use-after-move           -- using a moved-from object
  bugprone-integer-division         -- int/int truncation assigned to float
  bugprone-signed-char-misuse       -- signed char used as bool/int
  bugprone-unchecked-optional-access -- dereferencing nullopt
  bugprone-unused-return-value      -- ignoring [[nodiscard]] returns

cppcoreguidelines-*
  cppcoreguidelines-pro-bounds-*    -- bounds-safe array access
  cppcoreguidelines-pro-type-*      -- type safety (no C-style casts)
  cppcoreguidelines-avoid-magic-numbers -- literal numbers in code

modernize-*
  modernize-use-nullptr             -- replace NULL with nullptr
  modernize-use-override            -- add override keyword
  modernize-loop-convert            -- convert index loops to range-for
  modernize-use-emplace             -- push_back -> emplace_back
  modernize-use-auto                -- use auto where obvious

readability-*
  readability-const-return-type     -- return type const on value types
  readability-identifier-naming     -- enforce naming conventions
  readability-magic-numbers         -- same as cppcoreguidelines version
  readability-simplify-boolean-expr -- !x == false -> x

performance-*
  performance-unnecessary-copy-initialization
  performance-move-constructor-init
  performance-for-range-copy        -- for (auto x : v) -> for (const auto& x : v)
```

#### .clang-tidy Configuration

Static analysis tools examine source code without executing it, flagging common bugs, style violations, and security vulnerabilities early in the development cycle. Integrating a linter into the CI pipeline ensures that issues are caught before code review rather than in production.
```yaml
# .clang-tidy (YAML, placed at project root)

# Start with all checks off, then enable specific groups
Checks: >
  -*,
  bugprone-*,
  cppcoreguidelines-*,
  modernize-*,
  performance-*,
  readability-*,
  -cppcoreguidelines-avoid-magic-numbers,
  -readability-magic-numbers,
  -modernize-use-trailing-return-type,
  -cppcoreguidelines-pro-bounds-pointer-arithmetic

# Treat all enabled warnings as errors (enforced in CI)
WarningsAsErrors: "*"

# Apply fixes for these checks automatically (safe auto-fixes only)
FixNotes: true

CheckOptions:
  - key: readability-identifier-naming.ClassCase
    value: CamelCase
  - key: readability-identifier-naming.FunctionCase
    value: camelCase
  - key: readability-identifier-naming.MemberSuffix
    value: "_"
  - key: readability-identifier-naming.ConstantCase
    value: UPPER_CASE
  - key: cppcoreguidelines-special-member-functions.AllowSoleDefaultDtor
    value: "1"
  - key: modernize-use-default-member-init.UseAssignment
    value: "1"

# Exclude third-party and generated code
HeaderFilterRegex: "^(?!.*/(third_party|generated|build)/).*\\.h$"
```

#### CMake Integration

CMake's `CMAKE_CXX_CLANG_TIDY` variable runs clang-tidy on every compilation unit. The example below gates this behind an `ENABLE_CLANG_TIDY` option so developers can skip it locally while CI enforces it.
```cmake
# Enable clang-tidy as part of the build (runs on each compilation)
# Set in CI preset or via command line - do NOT enable by default in dev
if(ENABLE_CLANG_TIDY)
    find_program(CLANG_TIDY_EXE NAMES clang-tidy-17 clang-tidy REQUIRED)
    set(CMAKE_CXX_CLANG_TIDY
        "${CLANG_TIDY_EXE}"
        "--config-file=${CMAKE_SOURCE_DIR}/.clang-tidy"
        "--warnings-as-errors=*"
    )
endif()
```

### cppcheck

cppcheck is an open-source static analyzer that focuses on finding actual bugs rather than style issues. It uses a different analysis approach than clang-tidy, it performs flow analysis and finds bugs that purely AST-based tools miss, particularly in error handling paths.

```bash
# Basic analysis
cppcheck --enable=all --std=c++20 --language=c++ src/

# With include paths and library knowledge
cppcheck \
  --enable=all \
  --std=c++20 \
  --library=posix \
  --library=gnu \
  --suppress=missingIncludeSystem \
  --error-exitcode=1 \
  -I include/ \
  src/

# Generate XML report for CI integration
cppcheck \
  --enable=all \
  --xml \
  --xml-version=2 \
  src/ 2> cppcheck-report.xml

# Check for specific categories
cppcheck --enable=performance,portability,unusedFunction src/
```

cppcheck excels at finding:
- Null pointer dereferences after failed allocations
- Resource leaks (files, sockets left open on error paths)
- Integer overflow in array indexing
- Use of uninitialized variables on specific paths
- Dead code and unused functions

### PVS-Studio

PVS-Studio is a commercial static analyzer used at Microsoft, Samsung, and across the aerospace and automotive industries. It finds a different class of bugs than the open-source tools, particularly in complex template code and cross-TU analysis.

```bash
# Run PVS-Studio on a compilation database
pvs-studio-analyzer analyze \
  -f build/compile_commands.json \
  -o pvs-studio.log \
  -j$(nproc)

# Convert log to readable formats
plog-converter \
  -a GA:1,2,3 \
  -t sarif \
  -o pvs-studio.sarif \
  pvs-studio.log
```

PVS-Studio uses suppression comments to mark known false positives:

```cpp
// Suppress a specific warning by its ID
auto* ptr = dangerous_cast(value);  //-V730 -- intentional, reviewed 2024-01-15

// Suppress for an entire block
//-V::522  -- suppress V522 (null dereference) for this function
void legacy_function() {
    // ... legacy code we cannot fix yet
}  //-V::522
```

### Running in CI: Ratcheting Pattern

The most effective CI strategy is the "ratchet": never allow new warnings, but do not block on pre-existing ones. This lets you integrate static analysis into an existing codebase without fixing 10,000 warnings first:

```yaml
# .github/workflows/static-analysis.yml

name: Static Analysis

on:
  pull_request:
    branches: [main]

jobs:
  clang-tidy:
    runs-on: ubuntu-22.04
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0  # Need full history for diff

      - name: Install tools
        run: |
          sudo apt install -y clang-17 clang-tidy-17 cmake ninja-build python3-pip
          pip3 install codechecker

      - name: Configure (generate compile_commands.json)
        run: |
          cmake -B build -S . -G Ninja \
            -DCMAKE_EXPORT_COMPILE_COMMANDS=ON \
            -DCMAKE_CXX_COMPILER=clang++-17

      - name: Run clang-tidy on changed files only
        run: |
          # Get list of changed C++ files in this PR
          CHANGED=$(git diff --name-only origin/main...HEAD | grep -E '\.(cpp|cxx|cc)$' || true)

          if [ -z "$CHANGED" ]; then
            echo "No C++ files changed"
            exit 0
          fi

          echo "Analyzing: $CHANGED"
          echo "$CHANGED" | xargs \
            clang-tidy-17 -p build/ \
              --config-file=.clang-tidy \
              --warnings-as-errors="*" \
              2>&1 | tee clang-tidy-output.txt

          if grep -q "warning:" clang-tidy-output.txt; then
            echo "clang-tidy found issues in changed files"
            exit 1
          fi

      - name: Upload results
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: clang-tidy-results
          path: clang-tidy-output.txt
```

### The Go Comparison

Go's `go vet` is built into the toolchain and runs automatically. `staticcheck` (a third-party but canonical linter) covers most of what clang-tidy's `bugprone-*` checks cover. The key difference is depth: Go's simpler type system and lack of manual memory management make analysis more tractable. There is no C++ equivalent of `go vet` running in under a second, clang-tidy on a 100K-line project takes 5-10 minutes even in parallel. This is why the ratchet pattern (analyze only changed files in PR) is essential.
