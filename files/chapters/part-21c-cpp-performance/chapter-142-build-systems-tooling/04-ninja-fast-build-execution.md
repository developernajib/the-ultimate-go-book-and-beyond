## Ninja: Fast Build Execution

Ninja was written by Evan Martin at Google in 2010 specifically to build Chrome. Make was too slow for a codebase that size: it spent significant time parsing its own Makefiles and re-evaluating rules that had not changed. Ninja's design philosophy is the inverse of Make's: do as little as possible in the build tool itself, and delegate everything else to the generator. The result is a build executor that starts in milliseconds and saturates available CPU cores from the first action.

### What Ninja Is and Is Not

Ninja is not a build system generator. You do not write business logic in Ninja files. You do not define how to find dependencies or locate compilers. Ninja takes a completely pre-computed build graph, generated by CMake, Meson, GN (used by Chrome and Fuchsia), or hand-written, and executes it as fast as possible.

This design makes Ninja trivially fast at its job. A Ninja file for a 100,000-line project parses in under 100ms. Make spends that time just loading its own rules before touching your project.

### The Ninja File Format

A minimal Ninja build file demonstrates the core concepts:

```ninja
# build.ninja -- typically generated, not hand-written

# Variables
cxx = clang++
cxx_flags = -std=c++20 -Wall -Wextra -O2 -fPIC
link_flags = -lpthread

# Rules define how to transform inputs to outputs
rule cxx_compile
  command = $cxx $cxx_flags -MMD -MT $out -MF $out.d -c $in -o $out
  description = CXX $out
  depfile = $out.d
  deps = gcc

rule cxx_link
  command = $cxx $link_flags -o $out $in
  description = LINK $out

rule ar
  command = ar rcs $out $in
  description = AR $out

# Build edges declare: output | inputs
build build/obj/scheduler.o: cxx_compile src/scheduler.cpp
  # Per-edge variable overrides
  cxx_flags = -std=c++20 -Wall -Wextra -O2 -fPIC -Iinclude

build build/obj/connection_pool.o: cxx_compile src/connection_pool.cpp
  cxx_flags = -std=c++20 -Wall -Wextra -O2 -fPIC -Iinclude

build build/obj/request_parser.o: cxx_compile src/request_parser.cpp
  cxx_flags = -std=c++20 -Wall -Wextra -O2 -fPIC -Iinclude

build build/lib/libfalcon.a: ar \
  build/obj/scheduler.o \
  build/obj/connection_pool.o \
  build/obj/request_parser.o

build build/obj/main.o: cxx_compile src/main.cpp
  cxx_flags = -std=c++20 -Wall -Iinclude

build build/falcon_server: cxx_link \
  build/obj/main.o \
  build/lib/libfalcon.a

# Default target
default build/falcon_server
```

The `depfile` and `deps = gcc` lines are important: Ninja reads the `.d` files generated by the compiler's `-MMD` flag to discover which headers each `.cpp` file includes. This gives Ninja accurate incremental rebuilds without scanning the file system.

### Running Ninja

Ninja defaults to running `nproc + 2` parallel jobs, saturating both CPU cores and disk I/O without requiring explicit `-j` flags. Passing `-d keeprsp` retains response files for debugging, while `-v` prints the full compiler command for each translation unit, useful when diagnosing unexpected flags injected by a CMake or Meson generator.
```bash
# Build the default target using all CPU cores
ninja

# Explicit parallelism (default is cores + 2)
ninja -j$(nproc)

# Build a specific target
ninja build/falcon_server

# Dry run: show what would be rebuilt
ninja -n

# Explain why each action runs
ninja -d explain

# Print each full command as it runs (verbose)
ninja -v

# Show build timing (generates .ninja_log)
ninja -d stats

# Clean: remove all build outputs listed in the build file
ninja -t clean

# List all available targets
ninja -t targets all

# Show all commands that would run (for debugging generated files)
ninja -t commands build/falcon_server
```

### The .ninja_log and Build Performance

Ninja writes a `.ninja_log` file after every build. The `ninja -t recompact` command trims old entries. You can parse it to find which files are slowest to compile:

```bash
# Sort compilation times from .ninja_log (columns: start_ms, end_ms, mtime, output, hash)
sort -t$'\t' -k2 -n .ninja_log | tail -20 | awk -F'\t' '{
    duration = ($2 - $1) / 1000.0
    printf "%.1fs  %s\n", duration, $4
}'
```

Typical output on a large project:

```
12.4s  build/obj/template_heavy.o
 8.7s  build/obj/parser_generated.o
 6.2s  build/obj/rpc_stubs.o
```

These are your precompiled header candidates (covered in the optimization chapter).

### Using CMake with Ninja

Switching CMake from Makefiles to Ninja requires only the `-G Ninja` flag at configure time. Ninja parallelizes by default and produces faster incremental builds than Make on multi-core machines.
```bash
# Configure: tell CMake to generate Ninja build files
cmake -G Ninja \
      -DCMAKE_BUILD_TYPE=Release \
      -DCMAKE_CXX_COMPILER=clang++ \
      -B build/release \
      -S .

# Build
cmake --build build/release --parallel $(nproc)

# The above is equivalent to:
cd build/release && ninja -j$(nproc)
```

### Ninja vs Make

| Property | Ninja | Make |
|----------|-------|------|
| Design intent | Speed, not flexibility | General-purpose scripting |
| Parsing time (large project) | ~50ms | ~2000ms |
| Built-in rules | None, must be generated | Many (CC, CXX, etc.) |
| Dependency tracking | depfiles, C dependencies | Manual `.d` include |
| Parallel by default | Yes | Requires `-j$(nproc)` |
| Debuggability | `-d explain` is excellent | `--debug=v` is verbose |
| Hand-writable | Possible but tedious | Common for small projects |
| Used by | Chrome, LLVM, Android, CMake | Older projects, simple scripts |

For any project that generates its build files (CMake, Meson, GN, Bazel outputs), always use Ninja. The build time savings on incremental builds are immediately noticeable from the first day.
