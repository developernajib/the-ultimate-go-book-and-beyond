## Exercises

1. **Layered Validation Pipeline**: Build a three-layer validation pipeline for a `POST /users` endpoint: (1) JSON decode and type validation, (2) struct-tag validation with `go-playground/validator`, (3) business rule validation (check username uniqueness against a repository). Each layer must return a distinct error type. The final HTTP response must always use the same `{"error": {"code": "...", "message": "...", "details": [...]}}` envelope regardless of which layer failed.

2. **Custom Validator Registration**: Register three custom validators with `go-playground/validator`: `e164` (E.164 phone number format), `slug` (lowercase letters, digits, and hyphens only), and `luhn` (Luhn algorithm for credit card numbers). Write table-driven tests for each validator with at least five valid and five invalid inputs per type.

3. **Centralized Error Middleware**: Implement an error-handling middleware using a typed `AppError` struct that carries an HTTP status code, a machine-readable `code` string, a human-readable `message`, and an optional `details` slice. Map standard Go errors (`sql.ErrNoRows` → 404, `context.DeadlineExceeded` → 503) to `AppError` values. Assert in tests that no raw Go error text ever leaks into the response body.

4. **Request Size and Timeout Guards**: Wrap every handler's request body with `http.MaxBytesReader` (limit: 1 MB) and apply a per-request `context.WithTimeout` (5 seconds). Write tests that send a 2 MB body and assert `413 Request Entity Too Large`, and a test that uses a slow fake handler to assert `503 Service Unavailable` or `504 Gateway Timeout` after the deadline expires.

5. **Path and Query Parameter Validation**: Write a reusable `ParseIntParam(r *http.Request, name string, min, max int64)` helper and a `ParseUUIDParam` helper. Both must return a structured `ValidationError` (not a plain string) when the parameter is missing, not parseable, or out of range. Use these helpers in at least two handlers and cover all error branches with tests.

6. **ReDoS-Safe Pattern Validation**: Go's `regexp` package uses RE2 and is immune to catastrophic backtracking, but many real-world systems call out to other languages or accept user-supplied patterns. Identify three PCRE-style regex patterns vulnerable to catastrophic backtracking (e.g., `(a+)+`, `(a|a)+`). Rewrite each as an RE2-compatible pattern (no lookaheads, no backreferences). Then build a `SafeMatch` function that runs the match in a goroutine under a 100 ms `context.WithTimeout`. Write up, in the package doc, exactly what that wrapper does and does not buy you: it bounds how long the caller waits, but Go cannot preempt a running match, so the goroutine keeps consuming CPU after the timeout fires. State plainly why the length cap ahead of it is the control that actually works. Finally, write a test that feeds a long adversarial input (say 50 `a` characters followed by `!`) and asserts it completes well within the timeout, then explain in a comment why that test passes trivially on RE2 and would not on a backtracking engine.

7. **Error Catalog Endpoint**: Implement a `GET /errors` endpoint that returns the full catalog of application error codes as a JSON array, each entry containing `code`, `http_status`, `message`, `cause`, and `resolution`. The catalog must be defined as a single source-of-truth Go map so that adding a new `AppError` type automatically makes it appear in the endpoint. Write a test that asserts every `AppError` used in the codebase appears in the catalog response.

### Junior → FAANG: How to Work These Exercises for Maximum Signal

Treat each exercise above as a mini take-home. Start with the tests. Write the failing assertions first, run them red, then fill in the implementation until they pass. This discipline is the difference between a portfolio project that reads as junior (code first, tests added later) and one that reads as FAANG-ready (tests drove the design).

Worked approach for Exercise 1. Write three tests before you write code: one that sends malformed JSON and asserts the envelope has `code: "INVALID_JSON"`, one that sends a type-valid but rule-violating body and asserts `code: "VALIDATION_ERROR"` with field-level details, and one that sends a valid body whose username is already taken and asserts `code: "ALREADY_EXISTS"` with status 409. Now implement the three layers. The test for the last case should use a fake repository, not a real database, so the test is fast and deterministic. If you reach for `sqlmock` you are probably testing the wrong layer.

Worked approach for Exercise 4. The trick most juniors miss is that `http.MaxBytesReader` does not error at wrap time, it errors on `Read`, which means your handler must be prepared to get a short read and detect the `*http.MaxBytesError` via `errors.As`. Write that test first. The timeout test is easier to get wrong, because a naive fake handler that just sleeps does not exercise `context.Done` propagation. The correct fake reads from `r.Context().Done()` in a select and exits when canceled, which mirrors what real database drivers do.

The "why did this fail" reflex tuned to these exercises. If Exercise 6 seems to hang, your `context.WithTimeout` is not wired into `SafeMatch`, or you forgot `defer cancel()`. If Exercise 7 fails because some `AppError` is missing from the catalog, you have proven the catalog is a source-of-truth violation, which is the whole point of the test. If Exercise 3 leaks Go error text, your middleware is calling `err.Error()` somewhere in the response path, probably behind a `fmt.Sprintf` you forgot about.

Prerequisite gaps these exercises will expose. Go generics (Exercise 5 is cleaner with `ParseParam[T]`). `errors.Is` and `errors.As` (Exercises 3, 4, 5 require them). `context.Context` propagation (Exercise 4 breaks without it). Table-driven tests with subtests and `t.Run` (every exercise). RE2 syntax and its intentional limitations (Exercise 6).

### Senior @ FAANG: Staff Extensions on Every Exercise

Each exercise above produces L3 code as written. The staff-level extension turns it into platform work that other teams consume.

Extension for Exercise 1. Replace the three-layer pipeline with a declarative validation pipeline defined in a small DSL (YAML or CUE), compiled to Go code at build time, with runtimes in TypeScript and Python for client-side and batch usage. The DTO, the rule set, and the error catalog entries are all generated from the same source file. Add a CI check that fails PRs modifying generated code directly. Extend the envelope to RFC 9457 Problem Details with a `violations` extension. Add a contract test published by the platform team that every service must pass in CI. Ship metrics per rule code so the platform team can see which validations fire most often across the organization.

Extension for Exercise 2. Wrap each custom validator in a typed API so that the rule, the error code, the i18n message ID, and the documentation URL are defined in one place and consumed by both runtime validation and OpenAPI spec generation. Add a deprecation marker field with a sunset date, and a lint rule that fails CI when a handler references a deprecated rule after sunset. Add property-based tests using `pgregory.net/rapid` that stress each rule with generated inputs. Use rapid rather than the standard library's `testing/quick` specifically because you want shrinking: `testing/quick` is frozen and reports whatever 200-character blob happened to fail, while rapid reduces it to the minimal reproducing input, which is the difference between a bug you can read and a bug you cannot. Add benchmarks so a rule that quietly becomes expensive (someone drops a `regexp.MustCompile` into the hot path) shows up as a regression rather than as a latency page.

Extension for Exercise 3. The middleware becomes platform middleware. It emits Problem Details, sets a request ID from `traceparent` or generates one, wraps `slog.Handler` with PII redaction by attribute regex, and fails closed (500 with a stable code) on unmapped errors in production while panicking loudly in development. Add a test that deliberately panics inside a handler and asserts the body has no file paths, no stack trace, and the correct shape. Add an integration with OpenTelemetry so the request ID is the trace ID, and every 5xx emits a metric with the error code as a label.

Extension for Exercise 4. Size and timeout guards are platform middleware, not per-handler. Caps are per-route and configured from the OpenAPI spec. Exceeding the size cap emits a metric and produces a Problem Details body with `code: "REQUEST_TOO_LARGE"` and the configured limit in an extension member so clients can display it. Timeout exhaustion returns the trace ID in the Problem Details body so the client can link its trace to the server trace. Do not reach for a `traceresponse` header here: it belongs to a separate, still unfinished W3C work item rather than to Trace Context itself, so nothing load-bearing should depend on it. Add a chaos test that injects latency at a fake downstream and asserts the handler returns 504 with the correct shape within the configured deadline.

Extension for Exercise 5. Parameter parsing is done by the router, not by helpers. Adopt a typed router (or generate one from OpenAPI) where path and query parameters arrive in the handler already parsed and validated. Errors at the parse step produce Problem Details automatically with field pointers. Write a code-generation tool that emits both the server handler signature and the client SDK method from the same spec so the types cannot drift.

Extension for Exercise 6. Regex patterns are declared as a typed list with safety class (RE2, RE2 with length cap, external PCRE with sandbox). Any pattern in an external class runs in a separate process with a cgroup memory limit and wall-clock timeout. A CI check rejects new regex usage outside the typed list. Add a fuzz test that feeds each pattern adversarial inputs and asserts completion under the wall-clock budget. Document the threat model explicitly in the package doc.

Extension for Exercise 7. The error catalog is not a handler. It is a published artifact with its own repository, semver, owners, and deprecation policy. The `GET /errors` endpoint serves the catalog from the published artifact, not from in-process code, so consumers can inspect historical versions. SDKs in five languages are code-generated from the catalog. A Spectral rule in CI rejects any OpenAPI spec whose error responses do not reference a `code` in the catalog. A weekly job diffs the catalog against the previous version and sends a changelog to API council. Breaking changes require a 90-day deprecation window.

ADR template for adopting these extensions. Context: exercises produce functional per-service code but do not scale to 500 services. Decision: treat validation, error handling, parameter parsing, size limits, regex policy, and the error catalog as platform obligations owned by a platform team with SLOs, versioning, and deprecation policies. Consequences: platform team exists with on-call, service teams consume rather than build, pitfall classes are closed at the framework layer, SDKs are code-generated and consistent, new services ship faster. Alternatives rejected: per-service implementations (does not scale), outsource to vendor (lock-in on contract surface too central).

Maturity model mapped to these exercises. L1: exercises are never done. L2: exercises are done per service with drift. L3: exercises produce shared libraries. L4: exercises produce platform middleware with CI enforcement. L5: exercises produce code-generated artifacts driven by a single spec. L6: exercises produce governance (API council, deprecation policy, catalog owners) alongside the artifacts. L7: exercises produce organizational commitments, business-level SLOs on developer experience, and cross-company standards contributions.

Bar-raiser prompt tying the set together. "Take all seven exercises and design the platform that makes them unnecessary for product teams to solve." Expected signal: an OpenAPI-driven pipeline that generates DTOs, validators, parameter parsers, error shapes, SDKs, and docs from one spec, a platform middleware stack that enforces size caps, timeouts, Problem Details emission, request ID propagation, and PII redaction, a governance layer with a catalog and a council, a migration plan for existing services, and a measurable SLO on developer onboarding time. Candidates who describe only code cap at L4. The answer the loop wants interleaves code, spec, governance, and adoption.
