# Chapter 40: Validation & Error Handling

*Never trust user input. Validate early, validate often, and fail gracefully.*

Every piece of data that enters your API from the outside world is potentially malicious, malformed, or simply wrong. SQL injection, stored XSS, path traversal, and integer overflow: the OWASP Top 10 is largely a catalog of what happens when applications fail to validate their inputs. But poor validation is not only a security problem. It is also a reliability problem. An API that returns a 500 Internal Server Error when a user omits a required field, or silently coerces `"abc"` to `0` without surfacing that to the client, will generate support tickets, frustrate developers, and erode trust in your platform. The difference between a hobby API and a production API often comes down to how carefully it handles the cases where input is wrong.

Go's approach to validation and error handling reflects the language's philosophy of explicitness. There are no unchecked exceptions, no implicit null coercions, and no magic that silently transforms bad data. Go errors are values, so they can be wrapped, inspected, and mapped to HTTP status codes with precision. The `validator` package brings struct-tag-based validation that mirrors what Rails and Laravel developers expect, while Go's type system lets you build layered validation pipelines where transport errors, format errors, and business rule violations are handled at the right level of abstraction.

This chapter builds a complete validation and error handling system in Go. You will design a consistent error envelope used across your entire API, implement layered validators that distinguish between malformed JSON and business rule violations, and write middleware that catches parsing errors before they reach your handlers. Every pattern maps to how Stripe, Google, and Microsoft structure their API error responses, formats that developers actually find useful when something goes wrong.

**What you'll learn in this chapter:**
- Designing a consistent JSON error envelope with machine-readable codes and human-readable messages
- Struct tag validation with `go-playground/validator`: required fields, format rules, and custom validators
- Layered validation architecture: transport errors (415), format errors (400/422), and business rules (409)
- Custom error types in Go: wrapping, unwrapping, sentinel errors, and mapping to HTTP status codes
- Validation middleware that handles JSON parsing failures, oversized payloads, and Content-Type mismatches
- Field-level error detail arrays that tell clients exactly which fields failed and why
- Internationalization patterns for serving error messages in the client's preferred locale
- Table-driven tests for validation logic and error response shape verification

**Why this matters at scale:**
Stripe's error response format (with its `type`, `code`, `message`, and `param` fields) became the template that hundreds of API teams adopted. Google's API error model, published in its API Improvement Proposals and shared across its public APIs, carries structured error details that clients use to drive UI feedback without parsing human-readable strings.

### Junior → FAANG: getting to a first validation layer that does not embarrass you

If you have never written a validation layer in production, start with the smallest thing that is still correct. Decode the request body with `json.NewDecoder(r.Body).Decode(&req)` and call `DisallowUnknownFields` so a typo like `usrname` surfaces as a 400 instead of silently becoming the zero value. Then pass `&req` to `validator.New().Struct(req)` from `github.com/go-playground/validator/v10`. That gives you required, min, max, email, uuid, and oneof rules via struct tags. Map the returned `validator.ValidationErrors` into a list of field errors and respond with HTTP 422 and a JSON body. That is the baseline junior implementation and it is already better than most internal tools.

The worked example interviewers love is a sign-up handler. You have `type SignupRequest struct { Email string validate:"required,email"; Password string validate:"required,min=12"; Age int validate:"gte=13,lte=120" }`. A senior interviewer will ask you five follow-ups in rising difficulty: what status code for a missing required field (422 or 400, defend your pick), what happens if the body is 2 GB (read limit via `http.MaxBytesReader`), what if `Content-Type` is `text/plain` (415), what if the JSON is valid but `age` is `-5` (422 with a field-level error), and what if email validation passes syntactically but the domain does not exist (that is a business rule, not input validation, and belongs in the service layer). If you can answer all five in under two minutes without saying "I would Google it," you pass the first-round phone screen at most FAANG adjacent shops.

The first-job context you need is that validation code is where security review, SRE, and product all collide. Security wants you to reject early and log carefully. SRE wants you to not return 500s on user input. Product wants error messages users can act on. Get comfortable with the fact that your validator file will have more stakeholders than any other file in the repo.

### Senior @ FAANG: validation as an architectural concern, not a library choice

At staff level the question is never "which validator library should I pick." It is "where in the architecture does validation live, what invariants does each layer enforce, and how do those layers compose without duplicating logic or leaking implementation details across boundaries." The canonical split for a hexagonal or ports-and-adapters service is three layers. The edge (HTTP handler, gRPC server, message consumer) enforces wire-format validity. The application or use-case layer enforces cross-field and cross-entity business rules. The domain layer enforces invariants that must hold for the type to exist at all, using smart constructors that return `(T, error)` so illegal states are unrepresentable. Alexis King's "parse, don't validate" essay is the canonical reference here and every senior Go engineer should have internalized it. A `UserID` is not a `string`, it is a type with a private field whose only constructor rejects empty, non-UUID, or reserved values. Once you have a `UserID` in hand, no further validation is ever needed. This is refined types in Go, and it eliminates entire categories of "did we remember to validate this" bugs.

Library choice then becomes a tactical question scoped to the edge layer. `go-playground/validator` v10 is the default because it integrates with `encoding/json`, supports custom validators via `RegisterValidation`, and handles cross-field rules via `eqfield` and `nefield`. Its weaknesses are that struct tags are stringly-typed and untestable in isolation, locale-aware messages require the `ut` and `translations` sub-packages, and complex conditional logic (validate X only if Y is set) ends up in awkward tag combinations. `ozzo-validation` uses a builder-style fluent API that is testable, refactorable, and plays well with DDD value objects, at the cost of more code per struct. `govalidator` is legacy and should be avoided in new code. For OpenAPI-first shops, `huma` v2 generates validation from the schema automatically, and `oapi-codegen` plus `kin-openapi` gives you schema-driven validation where your OpenAPI document is the single source of truth. For gRPC and event-driven systems, `buf`'s `protovalidate` (the successor to `protoc-gen-validate`) provides CEL-based validation expressions that compile into both server and client, giving you polyglot parity. CUE is the heavyweight option for contract validation across service boundaries when you need constraints that JSON Schema cannot express, such as relational invariants between fields in different messages.

Error response governance is where staff engineers earn their title. RFC 9457 (Problem Details for HTTP APIs, which formally obsoleted RFC 7807 in 2023) is the standard every new API should adopt. A problem document has `type` (a URI that identifies the problem class), `title`, `status`, `detail`, `instance`, and extension members. Your error catalog becomes a registry of `type` URIs, each with a stable code, an English title, localization keys, and a link to runbook documentation. Trace-ID correlation goes in an extension member so support engineers can jump from a user's screenshot directly to the OpenTelemetry trace. Field-level errors for 422 go in an `errors` array with `pointer` (JSON Pointer per RFC 6901), `code`, and `message`. This structure is what Stripe, GitHub, and Google converged on independently, and RFC 9457 now codifies it.

Internationalization deserves its own design doc. Never translate error messages at the point of validation. Emit a stable machine code and a set of parameters, then resolve the message at the edge using the `Accept-Language` header and `golang.org/x/text/message`. This keeps your validators locale-free and lets you add languages without touching business logic. For CQRS systems, command validation (is the request well-formed and authorized) belongs in the command handler or a decorator around it, while domain invariants (can this aggregate transition to this state) belong on the aggregate itself. Conflating the two is the single most common mistake in Go CQRS codebases. Finally, input sanitization is not validation. Unicode normalization (NFKC), bidi-override stripping, zero-width character removal, and homograph detection are a separate pipeline that runs after parsing and before persistence, and it must be reviewed by whoever owns your XSS and SQL injection threat model.
