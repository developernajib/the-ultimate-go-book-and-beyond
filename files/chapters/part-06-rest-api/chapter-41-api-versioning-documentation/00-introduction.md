# Chapter 41: API Versioning & Documentation

*A good API is documented from day one. A great API stays documented forever.*

The day you publish an API, you take on a commitment to everyone who integrates with it. Clients build workflows, write SDKs, and run production systems on top of your contracts. When those contracts change unexpectedly, whether a field is renamed, a status code changes, or a required parameter is added, integrations break at the worst possible moment. API versioning is the mechanism that lets you evolve your API without breaking existing consumers, and documentation is what makes those consumers trust that your contracts are intentional and reliable. Together, they are the difference between an API that accumulates users over years and one that burns through goodwill after the first breaking change.

The Go ecosystem has strong tooling for both versioning and documentation. OpenAPI 3.1 (aligned with JSON Schema 2020-12, which resolved years of schema fragmentation between the two specs) is the current target, though OpenAPI 3.0 remains widely deployed and fully supported by the same toolchain. The `swaggo/swag` annotation system generates specs from code comments (code-first), while `ogen-go/ogen` and `oapi-codegen/oapi-codegen` generate strongly-typed server and client code from a hand-written spec (spec-first). Interactive viewers such as Swagger UI, Redoc, and the ergonomic Scalar can be embedded directly in your Go binary with a single handler registration. The challenge is not tooling. It is strategy: when do you increment a version? How do you route traffic across versions without duplicating logic? How do you deprecate endpoints in a way that gives consumers enough warning to migrate? These are product decisions as much as engineering decisions, and getting them right requires understanding how companies like Stripe and GitHub have solved them at scale.

This chapter covers API versioning and documentation in Go from strategy through implementation. You will implement URL path versioning, header-based versioning, and content negotiation, evaluate their trade-offs, and build a version router that minimizes code duplication. You will generate OpenAPI specs programmatically, embed interactive documentation, and implement deprecation workflows with Sunset headers and usage tracking that give you the data to make safe sunsetting decisions.

**What you'll learn in this chapter:**
- URL path, request header, query parameter, content-type, and Stripe-style date-based versioning strategies with concrete trade-off analysis
- Building a version router in Go that shares business logic across versions without duplication
- The `Sunset` header (RFC 8594) and the `Deprecation` header (RFC 9745), successor-version `Link` relations, and per-client usage tracking to drive safe sunsetting decisions
- Generating OpenAPI 3.1 specifications with `swag` annotations (code-first) and `ogen`/`oapi-codegen` (spec-first), including when each approach fits best
- Embedding Swagger UI, Redoc, and Scalar as HTTP handlers directly in your Go binary
- Client SDK generation across languages via Stainless or Fern once the OpenAPI spec is stable
- Backwards-compatible change patterns: additive fields, optional parameters, and default value evolution
- API changelog design that communicates changes in a format developers actually read
- Contract testing with `dredd` and `schemathesis` to verify implementation matches specification

**Why this matters at scale:**
Stripe has kept every integration working on `/v1` since 2011 by pinning each account to a dated version and running requests through a chain of per-version transformations, so code written over a decade ago still gets the response shape it was built against. GitHub took the opposite route for REST: rather than a URL version, it versions through the `X-GitHub-Api-Version` header, which keeps one URL surface while letting dated versions evolve underneath. Both models work. What they share is the part that actually matters, which is knowing exactly which clients depend on which behavior before changing anything.

### Junior → FAANG: Why Versioning Exists Before You Need It

If you have only ever shipped internal services where you control every caller, the word "versioning" feels like overhead. Your mental model is probably "if I need to change the API, I just change the callers at the same time." That works inside one repo with one deploy. It stops working the second a mobile app, a partner integration, or a public SDK sits on the other side of the wire. The mobile binary on a user's phone is frozen at whatever shape of the API existed the day it shipped. The partner team is on a different release train. The SDK user upgraded once in 2023 and will not touch their code again until something breaks. Versioning is the contract that says "the shape you integrated against will keep working, and when it cannot, you will get warning."

The prerequisite gap most junior engineers have is not Go tooling, it is the distinction between additive and breaking changes. Adding a new optional field to a response is additive. Adding a new required field to a request is breaking. Renaming a field is breaking. Tightening validation (rejecting inputs you used to accept) is breaking. Loosening validation is additive. Changing a 200 to a 201 is debatable and in practice breaking because clients pattern-match on status codes. Changing the default value of an optional parameter is breaking for anyone who relied on the old default. Internalize this list before you touch a version router, because the whole point of versioning is to let you make breaking changes safely, and if you cannot tell which changes are breaking you will either version too often (annoying consumers) or not enough (breaking them silently).

A worked example for your first job. You own a `GET /users/:id` endpoint that returns `{"id", "email", "name"}`. Product asks you to split `name` into `first_name` and `last_name`. The junior instinct is to rename the field and call it a day. The correct move is to keep `name` in the response, add `first_name` and `last_name` alongside it, and mark `name` as deprecated in the OpenAPI spec with a `x-deprecated-at` extension. Existing clients keep working. New clients use the split fields. In six months, when usage metrics show `name` is no longer read by any active client, you remove it in v2. That is the entire loop: additive now, breaking later, gated by a version bump and usage data.

The interview entry-point question is almost always "how would you version an API?" The wrong answer is to pick one strategy and defend it. The right answer is to compare at least three (URL path, header, date-based) against three axes (cacheability, client ergonomics, ops overhead), name a company that uses each (GitHub for path and header, Stripe for date-based), and end with "it depends on whether your consumers are browsers, mobile apps, or server-to-server, and on whether you expect weekly or yearly breaking changes." That framing gets you through the first round at any FAANG API team.

### Senior @ FAANG: Versioning as Product Strategy, Governance, and Lifecycle

At staff and principal level, versioning stops being a routing problem and becomes a product and governance problem. The engineering mechanics (path prefix, header parsing, version-aware handler dispatch) are table stakes that a mid-level engineer can ship in a week. What separates senior work is the policy stack that sits on top: when does the org allow a breaking change, who approves it, how are consumers notified, what is the deprecation SLO, and how is compliance enforced across hundreds of services. This is where FAANG API platforms diverge sharply, and understanding those divergences is how you make defensible decisions for your own org.

Stripe's model is dated per-request versioning. Every request is pinned to a date (`Stripe-Version: 2024-03-15`) either via account default or per-request header. The server maintains a chain of transformation layers, one per dated version, and incoming requests flow through the chain from the client's version to the latest internal representation, then responses flow back through the inverse chain. This means Stripe has never truly deleted a v1 behavior since 2011. Every breaking change is a new dated version, and every dated version lives forever inside the transformation graph. The cost is a transformation layer that now has over a decade of accumulated rewrites, most of which are exercised by a long tail of old integrations. The benefit is zero forced migrations. An integration written in 2012 still works in 2026 because its pinned date still flows through the chain. The senior lesson is that dated versioning trades server-side complexity for absolute client stability, and it is the right call when your customers are running payments in production and cannot absorb migration risk.

Shopify runs quarterly stable versions (2024-01, 2024-04, 2024-07, 2024-10) with a guaranteed 12 month support window and an `unstable` channel for partners who want to preview. This is a governance choice: breaking changes are batched, not continuous. Partners know that a version released in April 2024 will be supported through April 2025, and they plan migrations against that calendar. The quarterly cadence gives the platform team a forcing function to bundle breaking changes into coherent releases rather than dribbling them out ad hoc. The tradeoff is that urgent breaking changes (usually driven by security or compliance) cannot wait for the next quarterly window, so there is an out-of-band process for emergency versions that partners hate. If you adopt quarterly versioning, budget for the emergency process from day one.

GitHub runs header-based versioning (`X-GitHub-Api-Version: 2022-11-28`) for REST and relies on GraphQL's built-in deprecation mechanism for the GraphQL API. The GraphQL side is worth studying specifically because it shows how schema evolution can replace versioning entirely when the query language lets clients ask for exactly the fields they want. You add new fields freely, mark old fields with `@deprecated(reason: "...")`, and use introspection-based tooling to track which clients are still selecting deprecated fields. No version number required, because the client's query is the version. The senior takeaway is that if you are greenfield and your consumers are sophisticated, GraphQL sidesteps half of the versioning problem. If you are REST, you pay the version tax.

AWS runs multi-year deprecation windows because EC2 and S3 are running nuclear power plant control systems and bank core ledgers. Google runs quarters because Cloud Console users are less safety-critical. Meta runs months with a strict SLO because the Graph API serves internal teams who can be forced to migrate. The deprecation timeline you pick is a function of the worst consumer you cannot afford to break, not of engineering convenience. When you propose a 90 day sunset, the question to answer is "what fraction of current callers cannot migrate in 90 days, and is losing them acceptable." If you cannot answer with a usage histogram broken down by customer tier, you do not yet have the data to deprecate.

The tooling stack that keeps all of this honest is non-negotiable at scale. Breaking change detection runs in CI on every PR that touches an OpenAPI spec, using `oasdiff breaking` for REST (it catches removed endpoints, changed types, tightened enums, new required fields) and `buf breaking` for protobuf. Spectral rulesets enforce linting (every endpoint has a summary, every response has examples, every 4xx has a documented error code). An API review board (or a lighter-weight async review via Spectral custom rules) gates changes that touch public contracts. The `Sunset` header (RFC 8594) and the `Deprecation` header (RFC 9745, which standardized it years after `Sunset`) are emitted on every response to a deprecated endpoint. `Sunset` carries an HTTP-date. `Deprecation` carries a timestamp in the `@`-prefixed Unix-seconds form, not the `true` value that older blog posts show, and a `Link` header carrying `rel="successor-version"` points to the replacement. Customer notification is a multi-channel fan-out: email to the API contact on file, status page post, in-app banner in the developer dashboard, and an RSS changelog feed that SDK maintainers subscribe to. The usage tracking layer tags every request with the version and the authenticated principal, so at deprecation time you can run a query like "list every customer who called v1 in the last 30 days, ranked by call volume and contract tier" and drive personal outreach to the top accounts. That query is the single single most useful piece of infrastructure in the whole versioning stack, because it converts sunset from a hope into a plan.

The lifecycle states to formalize are preview (unstable, may break without notice, behind a feature flag or opt-in header), GA (stable, breaking changes require a new version), deprecated (still works, Sunset header emitted, new integrations discouraged), and sunset (410 Gone with a Link header to the successor). Each transition has an owner, a checklist, and a communication template. If you cannot point at the runbook for moving an endpoint from GA to deprecated in your org, the governance layer is not yet built and that is your next project regardless of what the roadmap says.
