## Learning Objectives

After completing this chapter, you should be able to:

- **Implement multiple versioning strategies** including URL path, header, content negotiation, and Stripe-style date-based approaches used by major API providers
- **Design deprecation workflows** with the `Sunset` (RFC 8594) and `Deprecation` (RFC 9745) headers, successor-version links, migration guides, and per-client usage tracking for graceful API evolution
- **Generate OpenAPI 3.1 specifications** both programmatically (`kin-openapi`), code-first with `swag`, and spec-first with `ogen` or `oapi-codegen`
- **Build interactive documentation** with Swagger UI, Redoc, and Scalar integration
- **Create API changelogs** that communicate breaking vs. additive changes clearly to developers
- **Apply version routing patterns** that minimize code duplication and maintenance burden
- **Implement backwards-compatible changes** without requiring version increments (additive fields, optional parameters, default value evolution)
- **Evaluate code-first vs. spec-first trade-offs** and choose the approach that matches your team's contract-discipline

### Junior → FAANG: What These Objectives Really Cover

Read this list again with a translation layer. "Implement multiple versioning strategies" does not mean memorize five syntaxes, it means be able to defend why you chose one for a specific consumer profile. If your consumers are mobile apps with 18 month tail distributions of old versions, URL path versioning with multi-year support is the safe default. If your consumers are server-to-server integrations written by sophisticated engineers, date-based versioning with a transformation layer wins. If your consumers are internal services in a single company, header-based versioning with a 90 day SLO is enough. The objective is not the syntax, it is the match between strategy and consumer.

"Design deprecation workflows" is the objective that most junior engineers skip and most senior engineers obsess over. The prerequisite you need is the mental model of a deprecation as a six month project, not a one line header change. The six months are: month zero is the announcement (email, changelog, banner, Sunset header turned on), month one to four is the grace period (emit warnings, track per-customer usage, publish migration guide), month five is the escalation (personal outreach to top callers still on the old version), month six is the sunset (endpoint returns 410 Gone). The `Sunset` header is the tiniest mechanical piece of this whole arc. The real work is the communication and the data.

"Build interactive documentation" is a trap for juniors who think docs are an afterthought. At FAANG scale, the docs site is a production service with its own SLO, its own on-call rotation, and its own traffic patterns. Swagger UI vs Redoc vs Scalar is a UX choice, but the engineering choice underneath it is whether your spec is generated from code (drift risk, fast iteration) or hand written (no drift, slower iteration). Pick based on who writes the spec: if it is the same team that writes the handlers, code-first works. If it is a cross-functional API design team that hands specs to implementation teams, spec-first is the only option.

The interview angle for this objectives list is that any one of these bullets is a 45 minute system design conversation. The interviewer will pick one, you will pick a strategy, and the remaining 40 minutes are you defending the tradeoffs. Prepare by picking a real company's published approach for each bullet (Stripe for dated versioning, GitHub for Sunset headers, Shopify for quarterly releases) and being able to cite it from memory.

### Senior @ FAANG: Turning Objectives Into Org-Level Policy

At senior level, each of these objectives expands from "I can do it" to "I can write the policy that makes the entire org do it consistently." That shift is what the next layer of the career ladder grades on, and it is what this chapter's objectives actually encode once you read them through a staff-engineer lens.

"Implement multiple versioning strategies" becomes "write the org standard that specifies which strategy applies to which class of API." Internal gRPC services use protobuf field numbers and `buf breaking` in CI, no version prefix needed. External REST APIs use URL path versioning with a three year support SLO. Partner-facing APIs with payment semantics use date-based versioning with indefinite support, matching Stripe's model. Mobile-facing BFF APIs use header versioning with a 90 day SLO because you control both ends. The policy is a decision tree, published in the internal developer portal, reviewed annually, with exceptions requiring an API review board signoff. The senior deliverable is the tree and the review process, not any one implementation.

"Design deprecation workflows" becomes "operate the deprecation pipeline." That pipeline has four mandatory artifacts for every deprecation: the announcement template (markdown, with migration code samples), the usage query (SQL or equivalent against the API gateway logs, broken down by customer and contract tier), the outreach playbook (which account managers contact which top-N customers, on what cadence), and the sunset runbook (how traffic is cut over, what the rollback criteria are, who holds the pager during the cut). A senior engineer can pull up any active deprecation and show all four artifacts. A staff engineer owns the template library and the tooling that generates three of the four automatically from the OpenAPI spec diff.

"Generate OpenAPI 3.1 specifications" becomes "operate the spec as the source of truth for client SDKs, gateway routing, authorization policy, and rate limit configuration." At FAANG scale, the OpenAPI spec is not documentation, it is configuration. It generates the TypeScript, Python, Go, Java, and Swift SDKs (via Stainless or Fern). It configures the gateway's path matching and auth requirements. It feeds the rate limiter's per-endpoint budgets. It drives the contract tests that run in CI. The senior project is the build pipeline that takes a PR against the spec, runs `oasdiff breaking` to classify the change, routes additive changes to auto-merge and breaking changes to the review board, regenerates all five SDKs, opens PRs against the gateway config, and updates the contract test suite. That is a quarter of staff-engineer work and it is the objective hidden inside a bullet that sounds like a tutorial.

"Build interactive documentation" becomes "run the docs site as a tier-1 service." That means uptime SLO, CDN caching, search indexing (Algolia DocSearch or self-hosted Meilisearch), versioned docs that match the API versions (so a user on v2 sees v2 docs), interactive try-it-now consoles with sandbox API keys, and telemetry on which pages developers read before successful first API calls (the activation funnel). The most impactful metric is time-from-signup-to-first-successful-call, and the docs team owns it. If you cannot name that metric for your API, the docs layer is undermanaged.

"Apply version routing patterns" at senior level means making sure business logic lives in one place and version adapters are thin. The anti-pattern is forking the handler per version. The pattern is a single canonical handler that takes the latest internal type, plus a chain of per-version request and response transformers. When you add a new version, you add one transformer at the end of the chain, you do not touch the handler. This is the same architecture as Stripe's transformation graph, scaled down to a single service. If your codebase has `handler_v1.go`, `handler_v2.go`, and `handler_v3.go` with 80% overlap, you have already lost, and refactoring that out is a high-impact staff project in its own right.
