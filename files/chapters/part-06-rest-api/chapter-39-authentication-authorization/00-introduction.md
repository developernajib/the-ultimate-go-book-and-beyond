# Chapter 39: Authentication & Authorization

*Authentication tells you who someone is. Authorization tells you what they can do.*

Security breaches rarely happen because attackers discovered a novel cryptographic weakness. They happen because an API trusted a token it should not have, skipped an authorization check on a secondary endpoint, or stored credentials in a way that made them recoverable. The consequences are severe. The 2022 Optus breach exposed the records of 9.8 million customers through an effectively unauthenticated API endpoint. In 2023, attackers used a stolen signing key to mint valid tokens for Microsoft's cloud email service and read high-value mailboxes for weeks before detection (the Storm-0558 incident). Broken object level authorization (BOLA) sits at the top of the OWASP API Security Top 10 precisely because secondary endpoints skip the check the primary endpoint remembers. Authentication and authorization are not features you add to an API. They are the foundation the API is built on, and mistakes made early are extraordinarily expensive to fix after consumers have integrated.

Go provides the primitives to build authentication systems correctly from scratch, and the ecosystem has mature libraries for every major protocol. The language's type system makes it natural to model permission scopes as structured types, its crypto packages implement constant-time comparisons that prevent timing attacks, and goroutines make token revocation checks against Redis non-blocking. Understanding these mechanisms at the implementation level, rather than just calling a middleware you copied from a tutorial, is what allows you to reason about your security posture, respond to incidents, and evolve your auth system as your product grows.

This chapter builds a complete, layered authentication and authorization system in Go, grounded in the 2026 landscape: `golang-jwt/jwt/v5` (the v4 branch is maintenance-only), OAuth 2.1 (which consolidates best practices from a decade of OAuth 2.0 deployment: PKCE mandatory for *every* client, implicit flow and password grant removed, exact-match redirect URIs, refresh-token rotation recommended), Argon2id as the default password KDF, and the rapid move to passkeys/WebAuthn as phishing-resistant primary or second-factor authentication. You will implement JWT issuance and validation with rotation and blacklisting, an OAuth 2.1 authorization code flow with PKCE, API key management with hashed storage and scoping, and a role-based access control system with resource-level permissions. Every pattern is grounded in how Stripe, GitHub, and Cloudflare approach auth in production.

**What you'll learn in this chapter:**
- JWT structure, signing algorithms (RS256/ES256 asymmetric vs HS256 symmetric), validation, JWKS-based key rotation, and secure token rotation
- OAuth 2.1 authorization code flow with PKCE, the only standard flow for user-facing applications
- Session-based vs JWT trade-offs: when centralized session storage (Redis) beats stateless tokens, and how short-lived access tokens plus refresh rotation give you the best of both
- API key generation, bcrypt/argon2 hashing, scope enforcement, and lifecycle management
- Role-based access control (RBAC) with hierarchical roles and per-resource permission checks
- Multi-tenant isolation: preventing cross-tenant data access through middleware and query scoping
- Argon2id password hashing, constant-time string comparison, and timing-safe credential checks
- Token refresh flows, session invalidation, and graceful credential rotation without downtime
- Audit logging for security-relevant events: logins, permission changes, and data access
- Passkeys/WebAuthn as phishing-resistant MFA and passwordless primary factor using `go-webauthn`
- When to reach for external identity platforms (Keycloak, Ory, Auth0, WorkOS) vs rolling your own

**Why this matters at scale:**
Stripe's API keys are hashed with a secret key before storage so that even a full database dump cannot be used to authenticate, a pattern Go teams can replicate exactly. At streaming and social scale, authorization layers evaluate permission checks at rates where milliseconds of latency in auth middleware translate directly to user-visible response time degradation, which is why the check must be a local, cached decision rather than a network round trip.

### Junior → FAANG: entry points for authentication and authorization

If the words authentication and authorization blur together in your head, fix that first. OWASP draws the line this way. Authentication (authn) answers "who is this caller". Authorization (authz) answers "is this caller allowed to perform this action on this resource". A login endpoint does authn. A `GET /invoices/:id` handler that checks `invoice.TenantID == caller.TenantID` does authz. Most production breaches in the last five years were authz failures, not authn failures. The caller was correctly identified and then handed data they were never entitled to see.

The three classic authentication factors are worth memorizing because interviewers ask. Something you know (password, PIN). Something you have (phone with an authenticator app, hardware token, passkey private key bound to a device). Something you are (fingerprint, face scan, behavioral biometrics). Multi-factor authentication (MFA) means combining at least two of these categories. A password plus a second password is still single factor. A password plus a TOTP code from an app is two factor.

As a first worked example, implement a login endpoint that accepts email and password, looks up the user, compares the supplied password against an Argon2id hash using `crypto/subtle.ConstantTimeCompare` on the derived bytes, and returns a signed JWT with a 15 minute expiry. That single endpoint touches password storage, constant-time comparison, token issuance, and clock handling. It is the interview entry point for every backend auth question you will ever see.

Your first job will hand you an existing auth system built on a library like `golang-jwt/jwt/v5` or an external provider like Auth0. You are not expected to design the crypto. You are expected to understand the flow well enough to debug why a token is being rejected, add a new scope to a route, and spot when a junior colleague writes `if token != "" { allow() }` instead of validating the signature. Read the token end to end once. Decode the header and payload at `jwt.io`. Watch what `exp`, `iat`, `iss`, `aud`, and `sub` actually contain on your staging environment. That single hour of curiosity will put you ahead of most engineers who ship auth code without ever inspecting a token.

### Senior @ FAANG: the 2026 auth landscape and what staff engineers own

At staff and principal level you are not writing login handlers. You are owning the identity substrate that every service in the company depends on, and the decisions you make propagate for a decade. The landscape in 2026 looks materially different from the OAuth 2.0 plus JWT consensus that dominated 2015 to 2022, and senior engineers who have not updated their mental model are shipping insecure defaults.

Passwordless is the default, not the future. Passkeys (WebAuthn level 3, FIDO2 CTAP2.2) are now the primary authentication factor at Apple, Google, Microsoft, GitHub, Shopify, and Cloudflare for both consumer and workforce accounts. The private key never leaves the authenticator, phishing is cryptographically impossible because the origin is bound into the signed challenge, and password reset flows (historically the weakest link) collapse into device recovery flows handled by platform vendors. A staff engineer designing a new auth system in 2026 who defaults to password plus TOTP is shipping a legacy system on day one. Passkeys first, password as a fallback for account recovery, TOTP and SMS deprecated.

OAuth 2.1 (still an IETF draft as of 2026, but the de facto standard that consolidates RFC 6749 plus a decade of BCPs) is the floor. PKCE is mandatory for every client including confidential server-side clients. The implicit flow and resource owner password credentials grant are removed. Redirect URIs must match exactly, no wildcards. Refresh token rotation with reuse detection is the default. If a rotated refresh token is ever presented twice, the entire token family is revoked and the user is forced to re-authenticate. This is the Auth0 pattern and it is now table stakes. Layered on top, DPoP (RFC 9449, Demonstrating Proof of Possession) binds access tokens to a client-held key pair so a stolen bearer token cannot be replayed from a different origin. If you are not deploying DPoP or mTLS-bound tokens for high-value APIs in 2026, your threat model is stuck in 2019.

The JWT versus opaque token debate has settled pragmatically. Stripe, Google (for first-party APIs), and PayPal use opaque tokens with server-side introspection because it gives them instant revocation and zero risk of client-side token stuffing. Netflix, AWS STS, and most B2B SaaS use JWTs with short TTLs (5 to 15 minutes) plus refresh token rotation because introspection round-trips are unacceptable at their read volumes. The senior engineering call is not "JWT or opaque". It is "what is my revocation SLA, what is my token validation latency budget, and what is my blast radius if a signing key leaks". If your revocation SLA is under 60 seconds, you need either opaque tokens plus introspection, JWTs plus a Redis denylist checked in middleware, or token binding via DPoP. Pick one and document the trade-off.

JWT anti-patterns are where careers end. Stuffing user profile data into the token so it bloats past 8 KB and breaks HTTP headers on proxies. No `exp` claim, or an `exp` set to one year because "refresh is annoying". Accepting `alg: none` because an old library defaults to it (CVE-2015-9235 and its descendants still ship in production code). Key confusion where an RS256 public key is accepted as an HS256 shared secret, letting an attacker sign tokens with the public key. HS256 with a 16-character secret guessable by hashcat in minutes. A staff engineer reviews every JWT integration for these five specific failures before it ships.

Session cookies are not dead. For first-party web applications where the frontend and backend share a domain, a `__Host-` prefixed, `HttpOnly`, `Secure`, `SameSite=Lax` session cookie backed by Redis is simpler, more secure, and more performant than a JWT in `localStorage`. CSRF is mitigated by `SameSite` plus a double-submit token on state-changing routes. XSS cannot exfiltrate an `HttpOnly` cookie. The push to JWT everywhere was driven by mobile and SPA architectures where cookies were awkward, not because cookies are inferior. Choose the mechanism that matches your deployment topology.

Workload identity is the other half of the auth story and the half that junior engineers never see. Service-to-service authentication inside a FAANG mesh is not done with long-lived API keys. It is done with mTLS where certificates are issued by SPIRE based on SPIFFE IDs that encode the workload's identity (`spiffe://prod.corp/ns/payments/sa/checkout`), rotated every hour, and validated at the Envoy sidecar before the request ever reaches your Go handler. As a staff engineer you will be asked whether a new service should authenticate to the identity provider with a shared secret, a JWT bearer, or a SPIFFE SVID. The answer is almost always SPIFFE plus mTLS, with JWT-SVIDs for the handful of cases where the receiver cannot terminate TLS.

Build versus buy is a capital allocation question. Rolling your own authn in Go using `golang-jwt`, `go-webauthn`, and `argon2` is a two to four engineer-quarter investment plus ongoing maintenance for CVE response, new RFC support (DPoP, CIBA, FedCM), and compliance audits (SOC 2, ISO 27001, FedRAMP). Auth0, Okta, WorkOS, Clerk, Stytch, SuperTokens, and Kinde each solve 80 percent of this for a per-MAU fee. The honest trade-off: if authentication is not your product differentiator and you are under 10 million MAU, buy. If you are a security-sensitive B2B platform where enterprise buyers demand SAML 2.0, SCIM provisioning, and custom IdP federation, WorkOS or Auth0 Enterprise pays for itself in the first signed contract. If you are Google or Apple, you build because you are the identity provider for everyone else.
