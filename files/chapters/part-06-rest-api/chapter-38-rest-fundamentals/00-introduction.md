# Chapter 38: REST API Fundamentals

*REST is just HTTP done right.*

Almost every production application today is built on APIs. Whether you are fetching a timeline, processing a payment, or provisioning cloud infrastructure, REST sits at the center of how systems talk to each other. REST's dominance is not accidental: it maps naturally onto HTTP, builds on decades of web infrastructure, and can be understood by any developer with a browser and curl. Yet despite its apparent simplicity, REST is consistently misused: verbs masquerade as nouns in URLs, 200 OK responses hide errors, PUT and POST are used interchangeably, and pagination is bolted on as an afterthought. The cost of these mistakes compounds as your API gains consumers.

Go is exceptionally well-suited for building REST APIs. Its standard library `net/http` package is production-grade, its concurrency model handles high connection counts with minimal overhead, and the language's emphasis on explicitness aligns naturally with HTTP's stateless, resource-oriented design. Companies like Cloudflare serve hundreds of billions of HTTP requests per day from Go services, and Stripe's API, widely regarded as the gold standard for REST design, has inspired patterns that Go developers can implement directly. Understanding REST at the protocol level, not just the framework level, is what separates APIs that scale from those that become maintenance burdens.

This chapter builds a complete, production-ready REST API in Go from first principles. You will work through HTTP semantics, resource modeling, middleware composition, content negotiation, HATEOAS-style linking, and pagination, each concept grounded in real-world examples from Stripe, GitHub, and Twilio. By the end, you will have both the vocabulary and the code patterns to design APIs that other developers love to use.

**What you'll learn in this chapter:**
- The six REST constraints and why violating any one of them creates operational problems at scale
- HTTP method semantics: idempotency, safety, and the correct status code for every scenario
- Resource-oriented URL design following the conventions used by Stripe, GitHub, and Twilio
- Request parsing, response serialization, and content negotiation in Go's `net/http`
- Middleware chains for logging, request tracing, authentication, and panic recovery
- HATEOAS linking patterns that make APIs self-documenting and discoverable
- Cursor-based and keyset pagination for efficient traversal of large datasets
- Integration testing REST handlers with `httptest` and table-driven test patterns

**Why this matters at scale:**
Cloudflare's network handles tens of millions of HTTP requests per second, and correctness at that volume rests on strict HTTP semantics for caching, routing, and edge logic, disciplines its many Go services must honor as much as its C and Rust data planes. Stripe's REST API processes billions of dollars daily, and its design discipline around idempotency keys, consistent error envelopes, and stable versioning has become the reference implementation that every serious API team studies.

### Junior → FAANG: entering REST with the right mental model

If you have only built a few CRUD handlers with Gin or Echo, REST will feel like five verbs plus JSON. That view is the reason most junior APIs fail code review. Before touching code in this chapter, cement four prerequisites. First, HTTP is a transfer protocol with semantics, not just a pipe for JSON. Methods are contracts that caches, proxies, and clients rely on. GET is safe and cacheable, PUT is idempotent, POST is neither. Second, a resource is a noun identified by a URI, not an RPC endpoint. `/users/42/activate` is RPC wearing a costume. The REST form is `POST /users/42/activations` or `PATCH /users/42` with `{"status":"active"}`. Third, status codes are part of the API contract, not decoration. A 200 OK that contains `{"error":"not found"}` in the body is a bug because intermediaries cannot see the error. Fourth, idempotency is the property that makes distributed systems survivable. A `PUT /orders/abc` applied twice must leave the same state as applied once, and a client that retries after a network blip must not double-charge the customer.

Worked example for a first-job interview. You are asked to design an API to reset a user password. The RPC instinct produces `POST /resetPassword?email=...`. The REST answer models the reset as a resource. `POST /password-resets` with body `{"email":"a@b.com"}` creates a reset request and returns 202 Accepted with a `Location` header pointing at `/password-resets/{id}`. A follow-up `POST /password-resets/{id}/confirmations` with the token and new password completes the flow. The interviewer is listening for three signals. You named the resource as a noun. You chose 202 because the email delivery is async. You separated creation of the reset from confirmation so the second step can be idempotent by reset id. If you can articulate those three choices you are already above the bar for a junior backend role at any FAANG-tier shop.

Entry-point interview questions you should be able to answer cold. Why is PUT idempotent but POST is not. What does 201 Created require in the response (a `Location` header). Why should errors not return 200. What is the difference between authentication (401) and authorization (403). When would you choose 204 over 200. Why do we plural-ize collection names. What is the practical difference between PUT and PATCH. If you hesitate on any of these, re-read section 371 before moving on.

### Senior @ FAANG: protocol governance, the maturity ladder, and the real cost of wrong defaults

At staff and principal levels REST stops being about verbs and becomes about governance. The central question is not "is this RESTful" but "does this API contract compose with the rest of our platform over five years of drift." That reframing changes everything downstream.

Start with the protocol selection matrix, because choosing REST is itself a decision that needs defending. REST over HTTP wins when clients are heterogeneous (mobile, web, partner integrations, curl), when cache-ability at the edge matters, when observability must work with stock tooling (access logs, APM, WAF), and when the surface is resource-shaped. gRPC wins for internal service-to-service traffic where you control both ends, where streaming and strict typing through protobuf pay back the tooling cost, and where p99 latency budgets are measured in single-digit milliseconds. GraphQL wins when a small number of clients need wildly different projections of the same graph and you can afford the operational overhead of persisted queries, N+1 protection, and query cost analysis. tRPC wins inside a single TypeScript monorepo where the client and server share types and the team has zero appetite for schema duplication. JSON:API wins when you want a specification-level answer to pagination, sparse fieldsets, and relationships so teams stop re-inventing them per endpoint. JSON-RPC wins for blockchain and internal control planes where the method-call model matches the domain. The senior mistake is treating this as a religious choice. The correct framing is per-surface. Netflix exposes REST externally and moved internal service-to-service traffic to gRPC. GitHub exposes REST and GraphQL side by side. Pick per boundary, document the decision in an ADR, and make the default explicit so junior engineers do not re-litigate it every sprint.

Now revisit Fielding's 2000 dissertation with adult eyes. The six constraints (client-server, stateless, cacheable, uniform interface, layered system, optional code-on-demand) are architectural properties, not coding rules. The Richardson Maturity Model (Level 0 single endpoint, Level 1 resources, Level 2 HTTP verbs and status codes, Level 3 hypermedia controls) is a useful taxonomy but Level 3 HATEOAS is mostly aspirational in practice. Stripe, GitHub, Twilio, and AWS all sit at Level 2 with selective hypermedia (pagination links, next-page cursors, occasional action URLs). The reason is blunt. Client teams do not follow links, they hard-code paths, and the engineering cost of serving full hypermedia graphs does not pay back. The senior position is Level 2 with disciplined `Link` headers for pagination per RFC 8288 and hypermedia only where it removes real client coupling, such as signed upload URLs or webhook retry endpoints. Do not let a purist block a Level 2 design in review.

API-first design is now table stakes. In 2026 the default workflow is OpenAPI 3.1 as the source of truth, generated server stubs via oapi-codegen v2 for Go, and generated client SDKs via openapi-generator or Fern for every consumer language. The spec lives in the same repo as the service, CI fails if the implementation drifts from the spec (via oapi-codegen's strict server interface), and breaking changes are caught by openapi-diff in PR checks. The governance payoff is that product managers, SDK teams, docs teams, and security review all read the same artifact. The anti-pattern is code-first generation where handlers grow first and swag or swaggo extracts a spec after the fact. That pattern guarantees the spec is a lagging indicator and breaks consumers without warning.

Status-code governance deserves its own internal RFC. The common debates are worth settling platform-wide. 202 Accepted is correct for async work and must return a `Location` or operation id so clients can poll. 409 Conflict versus 422 Unprocessable Entity is the argument that never ends. The defensible split is 409 for state conflicts (optimistic concurrency, duplicate resource, version mismatch) and 422 for semantically invalid payloads that parsed as JSON but violated business rules. 400 stays for malformed syntax. 5xx versus 4xx taxonomy matters because SLOs and alerting depend on it. A 4xx is the client's fault and should never page on-call. A 5xx is your fault and should. The worst bug in REST governance is a service that returns 500 for validation errors because a junior added `return err` without classification. Fix it at the middleware layer with a typed error hierarchy and a single error-to-status mapper.

Idempotency is where senior engineers separate from staff. The Stripe `Idempotency-Key` header pattern is now being standardized as the IETF draft-ietf-httpapi-idempotency-key-header. The production requirements are non-negotiable. Keys are client-generated UUIDs or ULIDs, scoped per (account, endpoint), stored with the full response for 24 hours minimum, and reject replays that arrive with a different request body under the same key with 422. The storage is typically Redis with a fallback to Postgres for durability. Without this, retries during partial outages will double-bill customers, and you will learn this lesson via a postmortem.

URL and resource-naming governance is the most visible artifact of API quality. Read the Stripe API reference, the Google AIP corpus (aip.dev), and the Microsoft REST API Guidelines as primary sources. The converged defaults are plural collection nouns (`/invoices`, not `/invoice`), kebab-case path segments (`/payment-intents`, not `paymentIntents` or `payment_intents`), snake_case or camelCase JSON fields with one choice per org, depth limits of two for nested resources (`/customers/{id}/payment-methods` is fine, `/customers/{id}/payment-methods/{id}/transactions/{id}/refunds` is not), and versioning in the URL (`/v1/...`) for public APIs with header-based versioning (`Stripe-Version: 2026-04-01`) reserved for organizations that can afford the tooling and client SDK cost. Tenant scoping belongs in headers for multi-tenant SaaS (`X-Org-Id`) when the tenant is implicit from auth, and in the path when tenants are addressable by partners (`/orgs/{org}/repos/{repo}` as GitHub does). The decision is an ADR, not a preference.

Pagination is the single most-botched feature in REST. Offset pagination (`?page=5&per_page=50`) is simple and broken under writes because rows shift between requests. Cursor pagination (opaque base64 of the last seen sort key) is the correct default for append-only or mostly-stable collections. Keyset pagination (explicit `after_id=...&after_created_at=...`) is the most transparent and is what you want when clients need to resume precisely. The `Link` header per RFC 8288 carries `rel="next"` and `rel="prev"` and lets clients traverse without parsing the body. GitHub's implementation is the canonical reference. Never expose total counts on large collections because they force an extra scan that dominates query cost.

Filter and field-selection syntax round out the senior surface. RSQL (`filter=status==active;created_at=gt=2026-01-01`), OData (`$filter=status eq 'active'`), and JSON:API's `filter[status]=active` are the three established dialects. Pick one per platform and write a parser with an explicit allowlist of filterable fields, otherwise you will ship an accidental SQL injection vector or a query that takes out the database. Sparse fieldsets (`?fields=id,name,email`) reduce payload size and are trivial to implement with a struct-tag-driven projector. Document which fields are projectable, because clients will depend on the set and removing a field later is a breaking change.

The through-line for this chapter at senior level. REST is not a style guide, it is a contract surface with multi-year consequences. Every default you pick here (versioning scheme, error envelope, idempotency model, pagination style, filter dialect) becomes load-bearing the moment external clients integrate. Treat chapter 38 as the place to write your platform's API style guide, not as a tutorial.
