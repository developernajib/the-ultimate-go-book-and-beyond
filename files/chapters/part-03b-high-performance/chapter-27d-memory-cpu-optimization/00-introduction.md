# Chapter 27D: Memory and CPU Optimization in Go

*"Premature optimization is the root of all evil - but that doesn't mean you should ignore performance. It means you should measure first."* - Donald E. Knuth

Modern CPUs are extraordinary at executing code quickly - provided that code cooperates with the hardware's assumptions. An L1 cache hit costs 4 cycles. An L3 miss followed by a main-memory access costs 200, 300 cycles. A branch misprediction flushes a 15, 20 stage pipeline. A poorly aligned struct field straddles a cache line and forces two fetches where one would suffice. These are not theoretical concerns: in high-throughput Go services, the difference between cache-friendly and cache-hostile data layouts regularly accounts for 3, 5x throughput differences on identical hardware. Writing "correct" Go code is necessary but not sufficient. Writing hardware-conscious Go code is what extracts the full performance the machine can deliver.

Go's toolchain exposes a surprisingly rich set of levers for working with the hardware rather than against it. Escape analysis reports (`-gcflags="-m"`) reveal which values escape to the heap and which stay on the stack. The compiler's inlining heuristics and mid-stack inlining in recent versions mean that small, hot functions can become zero-overhead abstractions. `sync.Pool` and hand-rolled arenas allow structured reuse of short-lived allocations, dramatically reducing GC scan work. (Note: the `arena` experiment that shipped behind `GOEXPERIMENT=arenas` in the Go 1.20 cycle never graduated and was withdrawn, so "arena" here means a bump allocator you own, not a stdlib package.) And while Go exposes SIMD intrinsics only experimentally (`simd/archsimd` behind `GOEXPERIMENT=simd` since 1.26, amd64 only), careful data layout still pays: arrays of structs versus structs of arrays, contiguous slices over linked lists, fixed-size arrays over variadic slices. Be precise about why it pays, though, because this is the most commonly mis-stated fact in Go performance writing. The gc compiler **does not auto-vectorize**, and no loop shape will persuade it to. What good layout buys is cache-line utilization, fewer bounds checks, and loops the CPU's own out-of-order machinery can pipeline. That is a real win, and it is not SIMD.

CPU profiling with `pprof` gives you a flame graph. Hardware performance counters via `perf stat` give you the deeper story - instructions per cycle (IPC), L1/L2/L3 cache miss rates, branch misprediction rates, and TLB miss frequency. These metrics tell you not just where time is spent but why: is a hot function slow because it does too much work, or because it does very little work but stalls on memory? The two problems require completely different solutions. This chapter builds the full mental model and practical toolkit for diagnosing and fixing both categories.

**What this chapter covers:**

- Applying CPU cache hierarchy knowledge - L1/L2/L3 sizes, cache line width (64 bytes), false sharing, and prefetching - to design cache-friendly Go structs and slice access patterns
- Using `go build -gcflags="-m"` escape analysis output to systematically eliminate heap allocations in hot paths, and validating results with allocation benchmarks
- Using `sync.Pool` and hand-rolled arenas for safe, structured object reuse without introducing use-after-free bugs or lock contention
- Designing cache-friendly data layouts (struct-of-arrays vs array-of-structs), and knowing why the gc compiler will not auto-vectorize them for you, plus where real SIMD in Go actually comes from
- Applying branchless programming and sorted-data techniques to eliminate pipeline stalls from mispredicted branches in tight inner loops
- Using `perf stat`, `perf record`, and Linux PMU events to measure IPC, cache miss rates, and branch misprediction ratios for Go binaries
- Implementing memory-mapped I/O with `syscall.Mmap` for zero-copy processing of large files and shared-memory IPC
- Reading and interpreting CPU flame graphs, cache miss annotations, and off-CPU profiles to triangulate the true bottleneck

**Why this matters at scale:**

VictoriaMetrics (the high-performance time-series database written in Go) and ClickHouse's Go client libraries depend heavily on cache-friendly columnar data layouts and zero-copy I/O paths to achieve their published benchmarks. CockroachDB's Go storage engine (Pebble) uses carefully padded structs and explicit cache-line alignment to eliminate false sharing, the kind of contention that can meaningfully degrade throughput as core counts climb. When Shopify's flash sale infrastructure needs to sustain 80,000 checkouts per minute with sub-100ms p99 latency, every unnecessary allocation and every cache miss in the hot path is a direct threat to the SLA. The techniques in this chapter are what the engineers at these companies reach for when profiling reveals that the algorithm is already optimal but the hardware is still unhappy.

**Prerequisites:** Chapter 27C (Go runtime and GC internals), familiarity with Go benchmarks (`testing.B`), and a working Linux or macOS environment with `go tool pprof` available. Access to a machine with `perf` installed is helpful for the hardware counter sections.

## Two readers, one chapter

**Junior engineer on the FAANG track.** Hardware-conscious code feels intimidating because the vocabulary (cache lines, IPC, branch misprediction, false sharing) is unfamiliar, but the underlying intuition is within reach after a weekend of deliberate practice. The single most valuable move you can make is to memorize four numbers: an L1 hit is about 1 ns, an L2 hit about 4 ns, an L3 hit about 15 ns, and a main memory load about 80 ns. Every optimization in this chapter is trying to turn a slow fetch into a fast one, and knowing the numbers is what lets you reason about which optimizations are worth the complexity. The second move is to actually run the benchmarks. Do not just read about false sharing. Write the padded and unpadded versions, run `go test -bench`, and feel the 10x difference in your terminal. FAANG interviewers for infrastructure roles routinely ask "walk me through a time you optimized a hot path," and having one real story where you measured a cache miss, flattened a struct, and watched p99 improve is worth more than any textbook knowledge.

**Senior engineer at FAANG.** The techniques here are familiar. The value the chapter is trying to add at staff level is judgment about when to apply them. Most services are not cache-bound, and applying cache-oriented optimizations prematurely creates code that is harder to read, harder to modify, and no faster. The staff-engineer question is always "what does the profile show as the actual bottleneck, and is this technique the minimum intervention that addresses it." Chapters in this range tend to produce engineers who optimize for cleverness rather than for the SLO. Your job is to push back: insist on `perf stat` or `pprof` evidence before any struct flattening, insist on `benchstat` evidence before any claim of improvement, insist on a written trade-off analysis before any technique leaves the benchmark and enters production code. Each section of this chapter closes with framing for design review, capacity planning, and code review. That is where your attention should sit.

A final calibration: most Go services do not need any of this. The chapter is written for the minority that do, and for the interviews that probe whether you understand the underlying machine. Knowing when not to apply these techniques is as important as knowing how.
