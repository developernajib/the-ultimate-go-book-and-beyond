## 36.3 goose

### Installation

Goose, originally created by Liam Staskawicz in 2012 and forked by Pressly in 2016, remains one of the most popular Go-native migration tools in 2026 - particularly for codebases that need to run data transformations in Go code rather than pure SQL. Install the goose CLI with `go install`. Goose supports both SQL-based and Go-based migrations, and you choose the type when creating each migration file.

```bash
go install github.com/pressly/goose/v3/cmd/goose@latest
```

### Creating Migrations

Goose uses timestamp-based versioning by default. Pass `sql` or `go` as the final argument to generate the appropriate file type. SQL migrations work for straightforward DDL changes. Go migrations handle cases where you need application logic during the migration (e.g., hashing passwords, transforming JSON columns).

```bash
goose -dir migrations create create_users_table sql
goose -dir migrations create add_users_index go
```

### SQL Migrations

Goose SQL files use `-- +goose Up` and `-- +goose Down` annotations to separate the forward and reverse migrations within a single file. Wrap multi-statement migrations in `-- +goose StatementBegin` / `-- +goose StatementEnd` blocks so goose treats them as a single execution unit rather than splitting on semicolons.

```sql
-- migrations/20240101000001_create_users_table.sql

-- +goose Up
-- +goose StatementBegin
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    email VARCHAR(255) UNIQUE NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW()
);
-- +goose StatementEnd

-- +goose Down
-- +goose StatementBegin
DROP TABLE users;
-- +goose StatementEnd
```

### Go Migrations

Go migrations register their up and down functions via `goose.AddMigrationContext` in an `init()` function. Goose passes a `*sql.Tx` to each function, so the migration runs within a transaction automatically. This is the right choice when a migration needs to read data, apply transformations, and write results back. These are operations that pure SQL handles awkwardly or not at all.

```go
// migrations/20240101000002_seed_users.go
package migrations

import (
    "context"
    "database/sql"

    "github.com/pressly/goose/v3"
)

func init() {
    goose.AddMigrationContext(upSeedUsers, downSeedUsers)
}

func upSeedUsers(ctx context.Context, tx *sql.Tx) error {
    _, err := tx.ExecContext(ctx, `
        INSERT INTO users (name, email) VALUES
        ('Admin', 'admin@example.com'),
        ('Test User', 'test@example.com')
    `)
    return err
}

func downSeedUsers(ctx context.Context, tx *sql.Tx) error {
    _, err := tx.ExecContext(ctx, `
        DELETE FROM users WHERE email IN ('admin@example.com', 'test@example.com')
    `)
    return err
}
```

### Running goose

Goose supports both SQL migration files and Go-coded migrations, where Go migrations are ordinary functions registered with `goose.AddMigration(Up, Down)` and are useful for data migrations that require application-level logic beyond what SQL can express. Goose records applied migrations in a `goose_db_version` table with a timestamp-based version number, and the `goose status` command shows which migrations are applied and which are pending without requiring the migration files to be re-read. The `goose fix` command renumbers out-of-order migration files (common when feature branches are merged) to restore the sequential numbering invariant that Goose requires for deterministic ordering.

```bash
# Run pending migrations
goose -dir migrations postgres "postgres://..." up

# Rollback
goose -dir migrations postgres "..." down

# Status
goose -dir migrations postgres "..." status

# Specific version
goose -dir migrations postgres "..." up-to 20240101000002
```

### Programmatic Usage

You can run goose migrations from Go code by calling `goose.Up(db, dir)` after setting the dialect. The embedded-file variant uses `goose.SetBaseFS` to point goose at an `embed.FS`, bundling migrations into the binary just like `golang-migrate`'s `iofs` source.

```go
package main

import (
    "database/sql"
    "embed"
    "log"

    "github.com/pressly/goose/v3"
    _ "github.com/lib/pq"
)

func main() {
    db, err := sql.Open("postgres", "postgres://...")
    if err != nil {
        log.Fatal(err)
    }

    if err := goose.SetDialect("postgres"); err != nil {
        log.Fatal(err)
    }

    if err := goose.Up(db, "migrations"); err != nil {
        log.Fatal(err)
    }
}

// With embedded files
//go:embed migrations/*.sql
var embedMigrations embed.FS

func runEmbedded(db *sql.DB) error {
    goose.SetBaseFS(embedMigrations)
    return goose.Up(db, "migrations")
}
```

### Junior → FAANG: When to reach for goose instead of golang-migrate

Both tools do the same primary job: read numbered files, track what ran, apply the rest. You pick goose when one of these three things is true. First, your team already has goose (the bigger reason than anyone admits, and a legitimate one, because tool consistency across a codebase is worth more than small feature differences). Second, you have a migration that needs Go code, not SQL. Third, you prefer a single file per migration with Up and Down separated by annotations, rather than the paired `.up.sql` and `.down.sql` files of golang-migrate. Preference three is cosmetic. Preference two is the real differentiator.

Worked example: hashing existing passwords. Your `users` table has a `password_plaintext` column from an era your team does not talk about. You are adding a `password_hash` column and migrating data. In pure SQL you could call `crypt()` from `pgcrypto`, but you want bcrypt with your application's cost factor and your application's salt policy, and you want the same `golang.org/x/crypto/bcrypt` package that the auth service uses so the values are verifiable with the same code path. This is a goose Go migration. The body runs `SELECT id, password_plaintext FROM users` into a cursor, loops, hashes each password, updates the row, and commits inside the `*sql.Tx` goose provides. The paired down function cannot restore plaintext (it is unrecoverable, which is why you are hashing in the first place), so the down is an intentional no-op with a log line saying "this migration is irreversible." Do not pretend otherwise.

Interview entry-point. "Why does goose pass a `*sql.Tx` rather than a `*sql.DB`?" Answer: goose wraps each migration in a transaction so the migration and the version tracker update atomically. If you need a migration that cannot run inside a transaction (Postgres `CREATE INDEX CONCURRENTLY`), register it with `goose.AddMigrationNoTxContext` instead of `goose.AddMigrationContext`. The signature takes a `*sql.DB` and goose commits the version tracker separately.

Gotcha. Goose Go migrations are compiled into your binary, which means the migration files and the application code share a dependency graph. If your goose migration in 2023 imported a package that has since been removed from your codebase, the binary will not build until you remove the migration or vendor the package. Teams manage this by keeping goose Go migrations minimal and by treating old migrations as archaeology: they ran once in every environment, they can be compressed to a single "baseline" dump after a year, and the original files retired.

### Senior @ FAANG: Go migrations for data backfills and the ownership question

The reason goose exists in a world that already has golang-migrate is that data migrations are first-class. At staff level you will own the pattern library for data backfills, and goose Go migrations are one of three legitimate vehicles (the others being a standalone backfill Job driven by a worker queue, and a database-native approach like Postgres `pg_background` or a CDC-triggered reprocessor). Picking between them is the ADR.

When a goose Go migration is the right tool. The data transformation is small (fits in minutes), fits a single transaction budget (under the `statement_timeout` and not holding `AccessExclusive` locks), and is logically coupled to a schema change that must be applied in the same deploy unit. Example: adding a `slug` column to `articles` and backfilling from `title` via your application's slug-normalization code. The whole thing runs in a minute against a million rows, the slug logic lives in `internal/slug`, and you want the migration to fail if the slug logic changes incompatibly later. Goose Go migration is ideal.

When a goose Go migration is the wrong tool. The backfill touches tens of millions of rows. Running it inside a single transaction will bloat the WAL, hold locks for minutes, cause replication lag to spike, and starve other writes. The correct pattern is a pure-SQL goose migration that creates the new column (fast, metadata-only on Postgres 11+), followed by a separate backfill pipeline: a Kubernetes Job reading IDs in batches of 1000 to 10000, calling a stored function or an application worker, committing each batch independently, sleeping between batches to bound WAL churn, and marking progress in a `backfill_progress` table so restarts resume rather than reprocess. The schema migration and the backfill pipeline are separate deliverables with separate observability and separate runbooks. The schema migration merely adds the shape and does not attempt to fill it. A "contract" migration later adds the `NOT NULL` constraint as `NOT VALID` and runs `VALIDATE CONSTRAINT` as a separate, cheap step once the backfill pipeline reports complete.

When to use goose AddMigrationNoTx. Postgres `CREATE INDEX CONCURRENTLY` is the canonical use case. Also `REINDEX CONCURRENTLY`, `ALTER TYPE ... ADD VALUE` on older versions, `CREATE DATABASE`, `CREATE TABLESPACE`. Goose's NoTx variants accept a `*sql.DB` and handle the version tracker outside the statement's transaction. The staff discipline: one statement per NoTx migration, check post-condition at the end of the migration body (for example `SELECT indisvalid FROM pg_index WHERE indexrelid = 'idx_name'::regclass` must return `true`, otherwise return an error so the migration is marked failed and dirty), and a runbook entry explaining how to clean up a failed NoTx migration (typically `DROP INDEX CONCURRENTLY IF EXISTS`).

Versioning scheme: goose timestamps and the `goose fix` trap. Goose defaults to `YYYYMMDDHHMMSS` timestamps. This avoids merge collisions on the filename but introduces the clock-drift anomaly discussed in 36.1. `goose fix` renumbers out-of-order files sequentially after the fact, which fixes ordering but rewrites version numbers that may already be applied in other environments. Never run `goose fix` on a repo whose migrations have been applied to production. The safe pattern is: use timestamps during development, rely on CI to reject PRs whose new migration timestamp is not greater than `max(timestamp_in_main)`, and never run `goose fix` after the first production deploy. Alternatively, switch to sequential numbering from day one and deal with merge rebasing.

Embedded migrations gotcha. `goose.SetBaseFS` mutates package-level state. If you run goose migrations from multiple binaries in the same process (rare but real, for example a test harness that runs migrations for two different schemas), the second `SetBaseFS` call wins. Use `goose.NewProvider` (available in v3.7+) instead, which returns a `*goose.Provider` with its own FS, dialect, and table name. The provider API also supports options like `WithDisableVersioning`, `WithAllowOutOfOrder`, and `WithExcludeNames`, which are the hooks you need for unusual deployment scenarios (e.g. re-applying migrations against a partially-baselined database during a data center migration).

Locking and concurrent runs. Goose acquires a Postgres advisory lock via `pg_advisory_lock` with a fixed hash key derived from the migration table name. This prevents two goose processes from racing but does not prevent a goose process from racing with a golang-migrate process pointed at the same database, because they use different lock keys. Do not mix migration tools against the same database. If you are migrating from one tool to the other, freeze migrations in the old tool, write a bridging document that maps old versions to new versions, baseline the new tool to match, and never run the old tool again.

Goose vs golang-migrate vs Atlas at the ADR level. Goose wins when you have Go-code migrations that cannot be expressed in SQL and are logically coupled to a schema change. Goose also wins for teams that value the single-file Up/Down annotation style. Golang-migrate wins for polyglot shops and for teams that want the simplest possible runner with the fewest behavioral surprises. Atlas wins when declarative schema-as-code and CI linting are higher-priority than runner simplicity. A common large-org pattern is Atlas generating migrations, golang-migrate or goose applying them, and the ADR explicitly records this split so reviewers know which PRs touch which layer.

Observability. Goose's `SetLogger` accepts a `goose.Logger` interface. Wrap it to inject correlation IDs and to emit structured logs with the migration filename, version, duration, and rows-affected when available (goose does not capture rows-affected, so you must emit that from inside Go migrations yourself). Emit the same `migration_duration_seconds` histogram and `migration_failure_total` counter discussed for golang-migrate. Add a goose-specific metric: `migration_go_code_seconds`, histogrammed by migration filename, so you can see which Go migrations are getting slower over time as data grows. This is the signal that a Go migration has outgrown its single-transaction budget and needs to be rewritten as a backfill pipeline.
