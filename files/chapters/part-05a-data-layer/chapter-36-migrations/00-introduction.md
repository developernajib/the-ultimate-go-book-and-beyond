# Chapter 36: Database Migrations

*The schema is code. Version it, review it, and deploy it with the same rigor you apply to everything else that runs in production.*

Every production database outage story has the same chapter: someone changed the schema manually, or the migration ran on staging but not production, or a deployment added a NOT NULL column to a table with 200 million rows and locked it for 45 minutes. Schema changes are the most dangerous operation in software deployment: they touch shared persistent state, they are often irreversible without data loss, and they interact with live application code in ways that are easy to overlook during local development. Yet many teams still manage schema changes through ad-hoc SQL scripts, Slack messages to the DBA, or the "just run it in psql" workflow that works fine until it doesn't.

In Go applications, the database migration tooling ecosystem has matured to the point where there is no good reason to manage schema changes manually. As of 2026, four tools dominate the Go landscape and each offers a different philosophy: `golang-migrate` (driver-agnostic SQL file execution with version tracking, still the most widely deployed option), `goose` from pressly (adds Go-based migration functions for complex data transforms that cannot be expressed in pure SQL, maintained actively and embedded in many Go-native projects), Atlas from ariga (treats schema as declarative code and generates migration SQL through diffing - the same approach Terraform takes for infrastructure, with migration linting and CI integration that has driven fast adoption since 2023), and `pgroll` from Xata (Postgres-specific, serves multiple schema versions simultaneously through views for true zero-downtime migrations without application coordination). Understanding which tool fits which context - SQL-only simplicity, Go-coded data transforms, declarative schema-as-code, or lock-free multi-version cutover - is part of the professional Go data layer skill set.

This chapter covers database migrations end to end, from the mechanics of version ordering and idempotent rollback to the operational discipline of zero-downtime deployments. You will learn how to structure migration files, embed them in your Go binary with `go:embed`, implement advisory-lock-based migration guards to prevent concurrent runs, and execute the expand-and-contract pattern that allows schema changes to deploy without downtime by making them backward-compatible with the previous application version.

**What you'll learn in this chapter:**
- How migration versioning works - sequential vs. timestamp ordering, dirty state detection, and the `schema_migrations` tracking table
- How to use `golang-migrate` with embedded SQL files using `go:embed` and run migrations programmatically at service startup
- How to use `goose` for Go-based migration functions that execute complex data transformations alongside schema changes
- How to implement Atlas declarative migrations by writing schema HCL or SQL and letting Atlas generate the diff, including migration linting against destructive-change rules
- How to execute zero-downtime migrations using the expand-and-contract pattern (add columns, backfill data, deploy, then drop old columns), and when `pgroll`'s view-based multi-version approach is the better choice
- How to apply Postgres-specific lock-avoidance techniques (`CREATE INDEX CONCURRENTLY`, `ADD CONSTRAINT ... NOT VALID` + `VALIDATE CONSTRAINT`) and their MySQL 8 equivalents (`ALGORITHM=INPLACE, LOCK=NONE`, `ALGORITHM=INSTANT`)
- How to implement advisory locking in migrations to prevent concurrent runs in multi-instance deployments
- How to write and run migration tests that verify both up and down migrations and check data integrity post-migration
- How to integrate migrations into CI/CD pipelines with automated schema drift detection and dry-run validation

**Why this matters at scale:**
Stripe's engineering blog documents its four-phase online migration pattern (dual-write, backfill, switch reads, clean up), which is the expand-and-contract discipline this chapter teaches applied to billions of live records. GitHub built and open-sourced gh-ost specifically to run live schema migrations over hundreds of millions of rows with zero downtime, the online schema change approach this chapter covers.

**Prerequisites:** Chapter 32 (Database Fundamentals in Go), Chapter 33 (Advanced PostgreSQL with Go).

### Junior → FAANG: Why migrations deserve a whole chapter

If you are early in your career you probably learned databases by running `CREATE TABLE` in a local psql shell and never writing the SQL down. That works for toy projects and fails the first time two developers touch the same schema. A migration is just a versioned SQL file plus a tracking row that records whether that file has been applied. The tracking row lives in a table called `schema_migrations` (golang-migrate) or `goose_db_version` (goose) and it is the whole contract: if the row exists, the migration ran, otherwise the tool runs it next time the binary starts.

Worked example. You need to add a `phone_number` column to a `users` table. The junior workflow is `ALTER TABLE users ADD COLUMN phone_number TEXT` pasted into Slack. The professional workflow is a file named `000023_add_user_phone.up.sql` containing that statement, a paired `000023_add_user_phone.down.sql` containing `ALTER TABLE users DROP COLUMN phone_number`, committed to the same repo as the Go code, reviewed on a pull request, and applied by CI against staging before production. The diff is the same SQL. The difference is that six months later you can answer the question "when did that column appear and who approved it" by running `git blame`.

Prerequisite gaps to close before reading this chapter. You should be comfortable with transactions and know that most DDL in Postgres is transactional but a few statements (like `CREATE INDEX CONCURRENTLY`) cannot run inside a transaction block. You should know the difference between a shared lock and an exclusive lock. You should have read enough `pg_catalog` to understand that `information_schema.columns` and `pg_class` are how tools introspect schemas. You should know that Postgres stores row versions (MVCC) so an `ALTER TABLE` that rewrites the table doubles disk usage during the rewrite.

First-job context. On day one at a FAANG you will not be writing migrations unsupervised. You will be reading them in code review, watching them deploy through an internal tool (Google has Spanner schema updates, Meta has `OSC` for MySQL online schema changes, Amazon has per-service RDS tooling with change-management tickets), and asking why the senior engineer added `NOT VALID` to their `CHECK` constraint. The answer to that last question is in section 36.5 and it is one of the most common interview probes for L4 to L5 promotion: "walk me through adding a non-null foreign key to a 500 million row table without taking the service down."

Interview entry-point questions you should be able to answer after this chapter. What does `schema_migrations.dirty = true` mean and how do you recover from it? What happens if two replicas of your service boot at the same time and both try to apply migration 42? Why is `ALTER TABLE users ADD COLUMN email TEXT NOT NULL DEFAULT ''` dangerous on a large table in Postgres 10 but safe in Postgres 11+? Name three reasons to prefer `goose` over `golang-migrate`. Name two reasons to prefer `atlas` over both.

### Senior @ FAANG: Migration strategy as a staff-level ADR

At staff and principal levels the question is not "which tool do I type the SQL into." It is "what is the migration contract for this organization, who owns the migration repo, how do we enforce it in CI, and what is the cost model when it goes wrong." The chapter material below is operator-grade. This section frames the decisions that belong in an architecture decision record before a single migration runs.

Expand-and-contract vs blue-green vs pgroll view-based cutover. Expand-and-contract is the default for any schema change that touches a column application code reads or writes. You deploy in at least three waves: (1) expand, which adds the new shape while keeping the old shape valid and writable (2) migrate, which backfills and flips writes to dual-write or to the new shape (3) contract, which removes the old shape once no deployed binary references it. The contract step cannot run until every rolling-deploy pod, every canary, every long-running batch job, and every read replica consumer has rotated past the old code. Blue-green, by contrast, brings up an entire new database alongside the old one and cuts traffic over with DNS or a proxy. Blue-green is appropriate for major version upgrades (Postgres 16 to 18, Aurora engine swaps) but prohibitively expensive for everyday DDL because it requires double the storage and a replication pipeline. pgroll by Xata inverts the model: both schema versions coexist in the same database behind Postgres views, and the application pins a version via `search_path`. This gives you reversibility for free until the old version is dropped, at the cost of query-planner overhead on every view access and a strict limitation to Postgres. The staff decision is not "which is best." It is "which compatibility window can the organization afford to maintain and for how long." A team that deploys twice a day can contract in 48 hours. A team with a quarterly release train cannot contract for 90 days and needs pgroll or a formal dual-schema period with lint enforcement.

Backwards and forwards compatibility windows. Every schema change has a direction. Forwards-compatible means old code can run against the new schema. Backwards-compatible means new code can run against the old schema. Expand steps must be backwards-compatible (so new code deploys against still-old schema during rollout). Contract steps must be forwards-compatible (so old code can still read the already-contracted schema in case of rollback). The window is the time between expand and contract, and it is the operational burden. At Google the default window is at least one release cycle plus one rollback cycle. At Stripe it is documented as "long enough that the oldest still-running binary has rotated out twice."

Long-running transactions and ACCESS EXCLUSIVE LOCK avoidance in Postgres. Any `ALTER TABLE` that rewrites the table takes `ACCESS EXCLUSIVE` which blocks every read and every write. A concurrent long-running transaction (for example an analytical query or a pg_dump) blocks the `ALTER TABLE` from acquiring the lock, and the `ALTER TABLE` then blocks every subsequent query behind it. This is the single most common migration-induced outage pattern in Postgres shops. The staff-level mitigations are: set a `lock_timeout` of a few seconds on every DDL session so the migration fails fast rather than queuing (`SET lock_timeout = '3s'`), use `statement_timeout` as a secondary guard, kill any transaction older than the migration budget before running (`pg_terminate_backend` on entries in `pg_stat_activity` with `xact_start` older than N minutes, behind policy), and prefer lock-free variants where available: `CREATE INDEX CONCURRENTLY`, `ADD CONSTRAINT ... NOT VALID` followed by `VALIDATE CONSTRAINT`, `ALTER TABLE ... ADD COLUMN` without a volatile default (Postgres 11+ stores the default as metadata rather than rewriting rows), and `REINDEX CONCURRENTLY` for bloat recovery. MySQL 8 offers `ALGORITHM=INSTANT` for a growing set of operations and `ALGORITHM=INPLACE, LOCK=NONE` for others, and Aurora MySQL adds fast DDL for many column additions.

Online DDL beyond Postgres and MySQL. Spanner and CockroachDB execute schema changes asynchronously in the background and expose state through schema jobs. Cassandra schema changes replicate through gossip and can produce disagreement windows you must design around. DynamoDB has no schema in the traditional sense but GSIs take minutes to hours to build. The staff engineer must know which engine the service uses and which online DDL guarantees it offers, because the migration tool cannot protect you from the underlying engine's locking model.

Tool comparison at the staff level. `golang-migrate` is SQL-only, driver-agnostic, stable, and does one thing: apply numbered files and track the version. It is the correct default for polyglot shops where the migration repo is shared with services written in other languages, and it has the smallest behavioral surface area to argue about in code review. `goose` adds Go functions as first-class migrations, which makes data backfills expressible in the same migration pipeline without a separate batch job. The cost is that goose migrations depend on your application's Go module graph, which complicates running them from a bare container during disaster recovery. `atlas` treats the schema as declarative HCL or SQL and generates the migration by diffing desired state against observed state, the same model Terraform uses. Atlas ships a linter with rules for destructive change detection, non-concurrent index creation, implicit table rewrite, and missing `NOT VALID` on constraint adds, and the linter runs in CI against the PR diff. Atlas also offers schema visualization and a schema registry (Atlas Cloud) for cross-service references. The cost is a tool that controls the schema rather than accepting your SQL, which some teams resist philosophically. `sqldef` is the minimalist declarative option (idempotent `apply` of a desired SQL file) with no version tracking, good for internal tools, wrong for regulated environments. `dbmate` is a language-agnostic versioned runner similar to golang-migrate with a cleaner CLI, often chosen by teams that want golang-migrate's simplicity without the Go dependency. `pgroll` is Postgres-only and solves the multi-version coexistence problem via views, which is a capability none of the other tools offer. `reshape` is the older academic cousin of pgroll (Fabian Lindfors' thesis project) and is worth reading as background but less production-ready. For polyglot enterprises, `Liquibase` (XML or YAML changelog, heavyweight, Java-centric, strongest compliance features) and `Flyway` (SQL-first, lighter, closer to golang-migrate) remain the lingua franca and are often chosen because DBAs already know them. The staff ADR template I recommend documents: which tool, why the alternatives were rejected, which tool the migrations repo is authored in if the primary tool differs (e.g., Atlas generating `golang-migrate` compatible files), the destructive-change lint policy, the approval workflow, and the disaster-recovery runbook for re-applying migrations from scratch into a fresh database.

Migration repo ownership. There are three common models. Platform-owned: a central team maintains the migration tool, the CI pipeline, and reviews every PR. This scales to compliance needs (SOX, PCI, HIPAA) and produces consistent migrations but becomes a bottleneck. Service-owned: each service team owns its own migration repo and the platform team provides only the tool. This scales team velocity but produces inconsistent patterns and is where you see every outage-causing migration in practice. Federated: the platform team owns the tool, the lint rules, and the approval workflow, and service teams own the SQL. This is the model most large orgs converge on. In the federated model the staff engineer's job is to write and evolve the lint rules (enforced in CI by Atlas or by a custom linter over golang-migrate files), to own the migration reviewer rotation, and to codify the approval workflow in a way that matches the blast radius: single-reviewer for additive backwards-compatible changes, two-reviewer for contracts and drops, DBA sign-off for anything that locks a table larger than a threshold. A schema registry (Atlas Cloud, Buf Schema Registry for Protobuf data definitions, or a homegrown equivalent) becomes essential once services depend on each other's schemas through logical replication, CDC pipelines, or shared analytic warehouses.
