## Summary

Database migration essentials for 2026:

1. **Tools**: golang-migrate (most widely deployed, driver-agnostic SQL), goose (Go-coded migrations, actively maintained by Pressly), Atlas (declarative schema-as-code with `atlas migrate lint` for CI-gated safety checks), pgroll (Postgres-only, view-based multi-version schema serving for true lock-free zero-downtime)
2. **Zero-Downtime**: Expand-and-contract pattern for cross-version compatibility. `CREATE INDEX CONCURRENTLY` and `ADD CONSTRAINT ... NOT VALID` + `VALIDATE CONSTRAINT` on Postgres. `ALGORITHM=INPLACE/INSTANT, LOCK=NONE` on MySQL 8. `pgroll` when application-side coordination is too expensive
3. **Safety**: Advisory locks for multi-replica startup, short `lock_timeout` to prevent lock queue pileup, `statement_timeout` caps, idempotent `IF [NOT] EXISTS` guards everywhere, forward-only with fix-forward migrations preferred over down migrations at scale
4. **Testing**: `testcontainers-go` with pinned Postgres major version matching production. Shadow-DB schema diff via `information_schema`, and backward-compatibility tests of old binary against new schema. Migration duration measured against production-sized row counts
5. **CI/CD**: Automate migration testing with containerized databases. gate PRs on `atlas migrate lint` or `squawk`, with a separate migration step (Kubernetes Job or init container) from the app Deployment. app refuses to start on schema-version mismatch
6. **Validation**: Check for dangerous patterns (non-concurrent indexes, NOT NULL without default on large tables, blocking FK validation) before applying. Block deploys automatically on lint failures

### Junior to FAANG: what to carry from this chapter into your first production on-call

If you internalize only six things from this chapter before your first on-call rotation, make them these. One, migrations are a deploy problem disguised as a SQL problem. The DDL is five percent of the work. The other 95 percent is the order in which you deploy code and DDL. Two, `ALTER TABLE ADD COLUMN` nullable without a default is near-instant on Postgres 11 and newer, and this single fact solves half of real-world column additions. Three, every destructive migration should be gated by a minimum two-release soak so that rolling back to the previous release does not require restoring the column. Four, `CREATE INDEX` without `CONCURRENTLY` is almost always wrong on any production table larger than a few thousand rows. Five, the `schema_migrations` table is operational state, not application data. Six, the advisory lock around migration start is not optional in any environment with more than one replica running the migrator.

Worked micro-example for final cementing. A product engineer asks you to "add a `last_login_at` timestamp to the `users` table, which has 80 million rows, and use it in a welcome-back email sent by a new cron job." The junior plan is three lines of SQL. The FAANG-ready plan is a sequence: one, open an ADR documenting table size, lock expectations, rollback plan. Two, write migration 0145 that adds the column nullable, no default. Three, write migration 0146 held for a later release that adds the index concurrently. Four, deploy code that writes `last_login_at` on successful login and tolerates `NULL` everywhere it reads. Five, deploy the cron job that reads the column, tolerating `NULL` as "never logged in." six, after two release cycles, decide whether to backfill existing users, and if yes, write a batched backfill job with a checkpoint table. Each step is a PR. Each PR is reviewed. Each PR is lintable. This cadence is the difference between a junior who ships and a junior who outages.

First-on-call reading list. Before your first shift, read the Postgres docs on `MVCC`, `pg_locks`, `pg_stat_activity`, and `CREATE INDEX CONCURRENTLY`. Read your team's migration runbook end to end. Page yourself through the dirty-migration recovery flow on a staging copy so your hands know the commands. The first time you run `pg_cancel_backend` should not be at 3 AM on a Tuesday.

### Senior at FAANG: maturity checkpoint, platform charter, and where to invest next

Use the summary above as a self-assessment. If your organization is not yet automating the lint step in CI, you are at L2 or L3 maturity and the next investment is a lint pipeline. If you have lint but not shadow-database replay, you are at L3 and the next investment is staging-replay benchmarking with production-sized data. If you have both but migrations still require human execution, you are at L4 and the next investment is a choreography engine such as a Temporal workflow or a Postgres-backed state machine that executes phases idempotently. If all of this exists and foundational-table changes still cause incidents, you are at L4+ and the next investment is governance: a schema review council with explicit authority, a data-contracts regime for foundational tables, and a quarterly metric of "lint-preventable versus test-preventable versus platform-preventable versus novel" postmortem ratios.

Platform charter for a migration team, abbreviated. Mission: reduce migration-induced incident minutes to zero while enabling high-frequency schema evolution. Scope: schema registry, lint, execution runtime, rollback controller, observability, developer documentation. Out of scope: application data modeling, backup and restore, data quality. Staffing: 6 to 10 engineers plus PM plus technical writer. Success metrics: migration lead-time median, migration-induced incident minutes, self-service rate (migrations completed without platform team intervention), and lint false-positive rate because developer trust in the platform matters.

Decision record for adopting `pgroll` or a declarative tool. ADR Context: application-side expand-contract coordination costs engineering hours per migration and introduces human-error risk. Decision: evaluate `pgroll` for Postgres workloads where view-based multi-version schema eliminates the coordination cost, and Atlas declarative for schema-only changes that do not require data transforms. Consequences: reduced coordination cost, new dependency on a specialized tool, requires investment in training and runbook updates, does not solve the data-migration subset which remains imperative. Alternatives considered: continuing with versioned migrations plus stricter lint rules, or in-house view-based pattern, both rejected on cost.

Where to invest next given the 2026 landscape. The frontier for migrations in 2026 is not tools but contracts. The tooling for expand-contract is mature. The hard problem is organizational: how do you let 50 teams evolve schemas on a shared foundational table without coupling? The answers emerging in the industry are data contracts with explicit consumer registration, event-sourced projections that decouple read schemas from write schemas, and CQRS-style split between canonical write tables and denormalized read tables that each team owns. Invest your staff-plus cycles here rather than on a fifth migration lint rule.

Closing signal for senior interviews. When a bar-raiser asks "where is migration engineering headed," the strong answer does not say "better tools." It says "from tool-level safety to contract-level coupling management, because the biggest remaining risk is not the DDL, it is the downstream consumers who do not know the DDL is coming." That is the staff-level insight this chapter builds toward.
