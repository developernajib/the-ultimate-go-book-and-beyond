## Exercises

1. **Zero-Downtime Column Rename (Expand-Contract Pattern)**: You have a `users` table with an `email` column used by a live application. Rename it to `email_address` without any downtime. Implement the full expand-and-contract cycle: add the new column, write a Go migration that dual-writes to both columns via a trigger, backfill existing rows in batches of 500 with a 25ms pause between batches, deploy the application to read from the new column, then drop the old column in a separate migration. Verify at each phase that no queries are blocked for more than 50ms and that zero rows are lost.

2. **Safe Rollback of a Failed Data Migration**: Write a goose migration that promotes a `status` string column to a foreign key referencing a new `statuses` lookup table. Simulate a failure mid-migration (after the lookup table is created but before all FK constraints are validated) and implement a `Down` function that rolls back cleanly without leaving orphaned rows or broken constraints. Your solution must be idempotent - running `Down` twice must not error. Add a test using `testcontainers-go` that injects the failure and asserts the database is left in its original state.

3. **Migration Testing with testcontainers-go**: Build a reusable test harness in Go that spins up a PostgreSQL 18 container, applies all `golang-migrate` migrations from a local `migrations/` directory, runs a suite of assertions (all expected tables exist, all indexes are valid, no orphaned foreign keys), then tears the container down. The harness must run in under 60 seconds in CI. Include tests for both `Up` and `Down` on every migration, and assert that running `Up` twice is idempotent. Parameterize the PostgreSQL image version so the same suite can test against Postgres 16, 17, and 18 in parallel.

4. **Struct-Driven Migration Generation**: Write a Go CLI tool that compares two versions of a Go struct annotated with `db:` tags (the current committed version and a modified version) and generates a `golang-migrate`-compatible SQL migration file for the diff. The tool must handle: added fields (new nullable column), removed fields (drop column with existence check), renamed fields (detected via a `db_old:` tag), and type changes (emit a warning and skip, requiring manual intervention). Include unit tests covering each case and an integration test that applies the generated SQL to a live Postgres container and verifies the schema matches the new struct definition.

5. **Multi-Tenant Schema Migrations**: You operate a SaaS application where each tenant has its own PostgreSQL schema (e.g., `tenant_acme`, `tenant_globex`). Implement a Go migration runner that: discovers all tenant schemas dynamically from a `tenants` table in the `public` schema, runs pending migrations against each tenant schema in parallel (up to 10 concurrent), records per-tenant migration history in each tenant's own `schema_migrations` table, and aborts the entire run (with rollback) if any tenant's migration fails. Add a dry-run flag that prints the SQL that would be executed without applying it. Write an integration test with three tenant schemas that asserts correct isolation - a failure in tenant B must not affect tenants A and C.

6. **Blue-Green Database Migration**: Design and implement a blue-green database migration strategy for a PostgreSQL-backed Go service. Provision a "green" database as a replica of the current "blue" database using logical replication. Apply forward-only schema changes to the green database while the blue database serves live traffic. Write a Go cutover controller that: waits for replication lag to drop below 500ms, pauses writes to blue (via an application-level circuit breaker), lets green catch up to zero lag, atomically updates the connection pool to point at green, and re-enables writes. Implement a rollback path that re-points traffic to blue if a health check fails within 60 seconds of cutover. Include metrics instrumentation (Prometheus) tracking replication lag and cutover duration.
7. **Dirty State Recovery Tool**: Build a CLI tool in Go that detects dirty migration state in a `schema_migrations` table, reports which migration version is dirty and what partial changes were applied (by inspecting `information_schema` against the expected migration SQL), and offers three recovery options: force the version back to the last clean state, re-run the dirty migration with idempotent guards, or execute the down migration for the dirty version. Include a `--dry-run` flag that reports the diagnosis without making changes. Write integration tests using `testcontainers-go` that simulate a dirty state by partially applying a migration and verify that each recovery path restores the database to a consistent state.

### Junior to FAANG: how to approach these exercises as a first-job learning ladder

Do not try to attempt all seven exercises in one sitting. They are laid out as a ladder. Exercises 1 and 3 are the foundation, and you should land them cleanly before touching the others. Exercise 2 introduces failure-handling, which is where most junior engineers first learn that migrations are ultimately a recovery problem. Exercise 4 is a language exercise that doubles as a gentle intro to code generation. Exercises 5, 6, and 7 are distribution-level concerns that mirror what you will hit in your second or third year.

Worked starting point for exercise 1. Create a fresh Postgres container locally using Docker. Seed 200,000 rows into `users` with a mix of short and long email values. Write your migration in four separate files so you can apply each phase independently. Use `psql` in a second terminal running `SELECT pid, state, wait_event_type, query FROM pg_stat_activity` on a loop so you can observe what your migration actually does. The instinct to *watch the database* while your migration runs is the single most important habit to build from day one.

Common traps to avoid.

Trap 1 on exercise 1. Attempting to wrap all four phases in a single Go function. Phases must be separated by code deploys in the real world, so your exercise should reflect that by separating them into distinct invocations even when the code deploy is simulated by a manual pause.

Trap 2 on exercise 2. Writing a `Down` that depends on state created by `Up`. If `Up` failed halfway, `Down` cannot assume all its inputs exist. Make every `Down` statement guarded with `IF EXISTS`.

Trap 3 on exercise 3. Spinning up a new Postgres container per test. This blows your 60-second CI budget instantly. Use a single container per test package, share it across tests, and use `TRUNCATE` or schema isolation to reset state between tests.

Trap 4 on exercise 5. Running migrations against tenant schemas in a goroutine loop without a bounded semaphore. This thunders your database connection pool. Use `golang.org/x/sync/errgroup` with `SetLimit(10)`.

Entry-point interview signal. When asked to present one of these exercises in an interview, narrate the decisions you did *not* make. "I did not wrap phases 1 through 4 in one function because in production they are separated by deploys." That single sentence is worth 20 minutes of implementation detail.

Prerequisite gaps to close before attempting the exercises. You should be comfortable with `context.Context` cancellation, `errgroup` patterns, `database/sql` transactions versus non-transactional commands, and `testcontainers-go` lifecycle. If any of those are new, read the Go standard library docs for `context` and `database/sql` first, then do `testcontainers-go` tutorials, and only then attempt exercise 3.

### Senior at FAANG: staff-level extensions, rubric for grading these exercises, and portfolio-building use

Each of these exercises is a reasonable technical-screen prompt. Below are staff-level extensions that turn them into design-interview material or portfolio pieces you can reference in L6 loops.

Staff extension on exercise 1, zero-downtime column rename. Add adaptive throttling based on replication lag: read `pg_stat_replication.write_lag` each batch and sleep proportional to lag beyond a threshold. Add a resumable checkpoint: store `last_processed_id` in a dedicated `backfill_progress` table so a crashed backfill resumes at the last committed batch rather than from zero. Add observability: emit Prometheus counters for rows processed, histogram for batch duration, gauge for estimated-remaining-rows. These three additions convert a homework exercise into a production primitive.

Staff extension on exercise 2, safe rollback. Rewrite the exercise as a Temporal workflow. Each step becomes an activity with idempotent keys. The rollback is expressed as compensations. Demonstrate that killing the worker mid-migration and restarting recovers cleanly. This is how production migration systems are actually built at scale and it is directly relevant to L6 system design.

Staff extension on exercise 3, testcontainers harness. Add a "shadow schema" mode where the harness also runs the migrations against a snapshot of production schema (no data, just structure) and produces a diff report. Add a performance mode where the harness seeds 10 million rows and measures migration duration, asserting that it falls within a configured budget. Add a compatibility matrix: old app binary against new schema, new app binary against old schema, both combinations must pass.

Staff extension on exercise 4, struct-driven migration generation. Build it as a CI-enforced tool. On every PR, run the generator, diff against the migration file checked in, fail the PR if they do not match. This is the declarative-schema pattern in miniature and is a small but real version of what Atlas does.

Staff extension on exercise 5, multi-tenant. Add a phased execution strategy: migrate tenants in rings, with ring 1 being 5 percent of tenants as a canary, ring 2 being 20 percent, ring 3 being the rest. Include an abort condition per ring based on error rate. This is how large SaaS platforms roll out schema changes safely.

Staff extension on exercise 6, blue-green database migration. Document it as an ADR with explicit risk analysis: failover window duration, data consistency guarantees during switchover, rollback criteria and timing budget, impact on long-running transactions open during cutover, cost analysis against expand-contract as an alternative. Submit the ADR to a simulated review board and defend the choice of blue-green over expand-contract. The defense is the exercise, not the implementation.

Staff extension on exercise 7, dirty state recovery. Turn it into an on-call runbook. Include pre-flight checks, decision tree, communication templates for the incident channel, and a postmortem template. Add telemetry: emit a metric whenever dirty state is detected so the platform team can observe baseline and regression.

Grading rubric for these exercises at L5 and L6. At L5, the correctness bar is "exercises compile, tests pass, code is idiomatic Go, operational concerns are addressed in comments or README." At L6, the bar adds "extensions are shipped, observability is built in, the exercise is wrapped in a platform-ready abstraction rather than a one-off script, and an ADR documents the design choices." The level distinction is not code quality. It is scope of thinking.

Portfolio use. If you are interviewing at L5 or higher, pick two of these exercises and build them to the staff-extension level over a few weekends. Publish them to GitHub with a thorough README that walks through the design decisions. Reference them in your interview loops. Candidates who show up with a working migration choreographer built on Temporal get calibrated higher than candidates who only answer hypothetically.

Bar-raiser prompt tying this together. "Pick one of these exercises. Walk me through how you would extend it so a team of 50 engineers could use it safely for five years without you being in the critical path for any single migration." The answer is the difference between senior and staff. It must include: lint at PR time, automated tests, runtime observability, on-call runbook, documented rollback, ADR template, platform team charter, and an explicit plan for the five-year evolution of the tool as traffic grows.
