## 36.4 Atlas

### Installation

Atlas is distributed as a standalone binary. Install it via the official install script or download it directly from the Atlas releases page.

```bash
curl -sSf https://atlasgo.sh | sh
```

### Declarative Schema

Atlas (by ariga.io), first released in 2021, has seen rapid adoption through 2025-2026 as the "Terraform for databases." It takes a different approach from golang-migrate and goose: instead of writing imperative up/down scripts, you declare the desired schema state in HCL (or SQL). Atlas compares this declaration against the actual database and generates the migration SQL automatically. This eliminates an entire class of bugs where the migration scripts drift from the intended schema. Atlas also supports classic versioned migration workflows (so teams can adopt it without abandoning their existing migration files), along with a dev-database concept where Atlas computes diffs against a disposable ephemeral database to avoid any drift or side effects on production.

```hcl
// schema.hcl
table "users" {
  schema = schema.public
  column "id" {
    type = serial
  }
  column "name" {
    type = varchar(255)
    null = false
  }
  column "email" {
    type = varchar(255)
    null = false
  }
  column "created_at" {
    type    = timestamptz
    default = sql("NOW()")
  }
  primary_key {
    columns = [column.id]
  }
  index "idx_users_email" {
    unique  = true
    columns = [column.email]
  }
}

table "posts" {
  schema = schema.public
  column "id" {
    type = serial
  }
  column "user_id" {
    type = int
    null = false
  }
  column "title" {
    type = varchar(255)
    null = false
  }
  column "body" {
    type = text
  }
  primary_key {
    columns = [column.id]
  }
  foreign_key "fk_posts_user" {
    columns     = [column.user_id]
    ref_columns = [table.users.column.id]
    on_delete   = CASCADE
  }
}
```

### Atlas Commands

Atlas computes the diff between the desired schema (defined in HCL or SQL schema files) and the current database state, then generates the minimal set of ALTER TABLE statements needed to reconcile them, avoiding redundant changes that manual migration authoring might produce. The `atlas schema inspect` command reverse-engineers an existing database into an HCL schema file, making it easy to adopt Atlas on a database that was not originally managed with it. Atlas's cloud integration tracks migration history, validates migrations against configured lint rules (e.g., no `DROP COLUMN` without a prior deprecation migration), and provides a visual diff of schema changes across deployments.

```bash
# Inspect current schema
atlas schema inspect -u "postgres://..." --format '{{ sql . }}'

# Generate migration from diff
atlas migrate diff create_posts \
  --dir "file://migrations" \
  --to "file://schema.hcl" \
  --dev-url "docker://postgres/18"

# Apply migrations
atlas migrate apply \
  --dir "file://migrations" \
  --url "postgres://..."

# Schema apply (declarative)
atlas schema apply \
  --url "postgres://..." \
  --to "file://schema.hcl" \
  --dev-url "docker://postgres/18"

# Lint pending migrations against destructive-change rules
atlas migrate lint \
  --dir "file://migrations" \
  --dev-url "docker://postgres/18" \
  --latest 1
```

### Migration Linting in CI

The `atlas migrate lint` command is the feature most often cited as the reason teams adopt Atlas alongside another tool. Lint rules inspect the generated SQL and flag risky operations: dropping a column, renaming a table, adding a `NOT NULL` column without a default on a large table, creating a non-concurrent index, or adding a foreign key without `NOT VALID`. Integrating lint into a GitHub Actions workflow with `ariga/atlas-action@v1` gates pull requests so destructive changes require explicit review and sign-off before they can merge. This is how teams operationalize the "schema changes get the same rigor as code changes" principle without relying on every reviewer to remember every Postgres locking rule.

```yaml
# .github/workflows/atlas-lint.yml
name: atlas
on: [pull_request]
jobs:
  lint:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:18
        env:
          POSTGRES_PASSWORD: pass
        ports: ["5432:5432"]
    steps:
      - uses: actions/checkout@v4
      - uses: ariga/atlas-action/migrate/lint@v1
        with:
          dir: "file://migrations"
          dev-url: "postgres://postgres:pass@localhost:5432/dev?sslmode=disable"
```

### Junior → FAANG: The declarative mental model

Atlas inverts the workflow you learned in the previous two sections. In golang-migrate and goose you write the `ALTER TABLE` statements and the tool records that they ran. In Atlas you write the desired end state (the HCL or SQL schema file) and the tool writes the `ALTER TABLE` statements for you by diffing desired state against observed state. This is the same model Terraform uses for cloud infrastructure and Kubernetes controllers use for cluster resources. Once you have seen it you will never again want to hand-author the hundredth `ALTER TABLE ADD COLUMN` in your career.

Worked example. You want to add a `deleted_at TIMESTAMPTZ` column to `users`. With golang-migrate you create a new migration file pair and write the SQL. With Atlas you open `schema.hcl`, add `column "deleted_at" { type = timestamptz null = true }` inside the `users` block, and run `atlas migrate diff add_users_deleted_at --dir file://migrations --to file://schema.hcl --dev-url docker://postgres/18`. Atlas spins up a disposable Postgres 18 container, replays the existing migration directory into it to reconstruct the last-known schema, compares that schema to your desired HCL, and writes the minimal SQL into a new migration file. You review the generated SQL, commit both the HCL change and the generated migration, and a reviewer verifies the two match. The dev-url container is ephemeral and Atlas destroys it after the diff.

Why the `--dev-url` is load-bearing. Atlas does not trust the production database as its source of truth for diffing, because production may have drift (manual edits, partially-applied migrations). Instead Atlas computes "what my migration directory says the schema should be" by replaying the directory into a fresh disposable database, then diffs that against the desired HCL. This makes the diff deterministic and reviewable, and it is the single most important design decision Atlas made. Internalize it.

Interview entry-point. "What happens if production has drift from the migration directory?" Answer: `atlas schema diff` against the production URL will show the drift explicitly. Atlas will not silently absorb it. The remediation is either to roll production forward to match (apply the pending migrations) or to author a new migration that captures the manual change (with sign-off, because drift is an audit finding). "Why HCL and not SQL?" Answer: HCL is strongly typed and resource-oriented, which makes cross-table references like foreign keys statically checkable before you apply. Atlas also accepts SQL schema files if HCL is unfamiliar to your team, and the diffing works the same way.

Gotcha. Atlas destructive lint rules (DS101 drop table, DS102 drop column, DS103 drop schema) fire on diffs that remove objects. If your PR genuinely needs to drop something, you add an `atlas:txtar` or `atlas:nolint` annotation with a reason, and the PR reviewer sees the exception. Do not disable the rule globally to silence the noise. The noise is the signal.

### Senior @ FAANG: Atlas at organizational scale

Declarative vs versioned workflow, and why both matter. Atlas supports two modes. Declarative (`atlas schema apply`) takes the desired HCL and applies the diff directly to the target. Versioned (`atlas migrate diff` then `atlas migrate apply`) generates a migration file and applies that. In production you want versioned, always. Declarative apply has no version tracker, no review step between diff computation and apply, and no audit trail of which SQL ran. Declarative is appropriate for local development scratch databases and for ephemeral CI test environments where the database is disposable. Staff engineers codify this in the ADR: "Atlas versioned workflow is the only approved mechanism for production schema changes. `atlas schema apply` against a production URL is a P0 incident."

HCL schema-as-code as a first-class artifact. The HCL file is the source of truth. The migrations directory is a generated artifact plus a history. Some teams go further and mandate that every PR touches the HCL first, then regenerates migrations, so that code review focuses on the declarative intent and the generated SQL is a check rather than the primary artifact. Other teams accept either HCL-first or SQL-first authoring and require only that the two agree after diff. The staff decision is which flow your reviewers can police consistently. HCL-first is more expressive but requires the whole team to learn HCL. SQL-first is closer to what DBAs already know and is often the migration path from golang-migrate.

Linting policy as code. The `atlas migrate lint` ruleset should be checked in as `atlas.hcl` in the repo root with explicit severity levels for each rule. Minimum recommended rule set for a Postgres shop as of Atlas v0.30: DS101 (table drop) = error, DS102 (column drop) = error unless annotated with a two-phase marker, DS103 (schema drop) = error, MF101 (column rename without expand-contract) = error, MF103 (add NOT NULL without default on non-empty table) = error, MF104 (add unique constraint on non-empty table) = error, MF105 (add primary key) = error, MF106 (add NOT NULL default with volatile expression) = error, CD101 (non-concurrent index) = error, PG101 (Postgres-specific: ADD CONSTRAINT without NOT VALID) = error. Every rule you downgrade to warning should be defended in the ADR. The reason the ruleset is so aggressive is that Atlas linting is the automated enforcement of everything in 36.1: if you relax the rules, you are saying the team does not need those protections, and every incident review after a lock-induced outage will ask why.

Atlas Cloud vs self-hosted. Atlas Cloud (ariga.io's hosted offering) adds centralized migration history, visual schema diffs across environments, a schema registry for cross-service references, and PR bot integration that posts the lint output and a rendered schema diagram into the PR conversation. Self-hosted Atlas gives you the CLI and the open-source lint rules but no cloud UI. The staff decision: for small organizations with a handful of services, self-hosted plus Atlas Action is sufficient. For organizations with dozens of services and cross-service dependencies, the schema registry in Atlas Cloud (or a homegrown equivalent) is what prevents "service A renamed a column and service B's CDC pipeline broke." Evaluate Atlas Cloud the same way you evaluate any vendor dependency: price per seat at scale, data residency (the registry stores your schema metadata), SOC 2 and ISO certifications, and the exit path if you later self-host.

Schema visualization. `atlas schema inspect -u <url> --format '{{ json . }}'` emits JSON that can be rendered by Atlas's `erd` command or by third-party tools into an ER diagram. Atlas Cloud does this natively in the UI. The visualization is how non-engineering stakeholders (product, data analytics, compliance) understand the data model, and it is how cross-service reviewers spot that two services accidentally introduced the same logical entity under different names. A staff habit: generate the diagram on every merge to main, check it into the repo under `docs/schema.svg`, and include it in onboarding material.

Declarative vs versioned pitfalls with drift. Because Atlas can both read the current schema and compute a diff, there is a tempting failure mode: a developer runs `atlas schema apply --to schema.hcl` directly against staging to test a change, the apply succeeds, now staging is one migration ahead of the versioned directory, and the next `atlas migrate diff` tries to undo the manual change. The staff mitigation is to lock down apply credentials (service accounts for CI only, no human write access to production or staging), to run `atlas schema diff` on a schedule as a drift detector (emit a metric and page on non-zero diff), and to treat drift as an incident. This is identical in spirit to Terraform drift detection and the same organizational discipline applies.

Comparison with polyglot tooling. Liquibase (XML or YAML changelogs, Java-centric, strongest compliance features including tagged rollbacks and precondition checks) and Flyway (SQL-first, closer in spirit to golang-migrate, Java-based but with a native CLI that does not require JVM knowledge from users) are the incumbents in polyglot enterprises. Atlas competes with both by offering declarative schema-as-code, which neither Liquibase nor Flyway do natively. Flyway recently added `flyway desired-state` as a beta, which is an acknowledgment of Atlas's pressure on the incumbent model. For a Go-heavy shop that occasionally ships a Python or Java service, Atlas is the most defensible unified choice because the CLI is language-agnostic. For a Java-heavy shop with occasional Go services, Liquibase or Flyway is often already entrenched and Atlas has to earn its keep on lint quality and declarative authoring.

pgroll as a complement, not a competitor. pgroll (Postgres-only, view-based multi-version schemas) solves a different problem than Atlas. Atlas generates and applies migrations, pgroll manages the compatibility window between two schema versions coexisting in the same database. A production pattern that is increasingly common: use Atlas for schema authoring and diff generation, output the migration into a pgroll `migration.json`, and let pgroll orchestrate the expand-and-contract steps via views. This gives you declarative authoring, lint enforcement, and reversible multi-version cutover. The staff ADR should name this combination explicitly if reversibility is a hard requirement (regulated industries, long compatibility windows, infrequent deploys).

Migration reviewers and approval workflows. At scale, the reviewer pool for migrations must be curated. Not every engineer should be able to approve a column drop or a constraint add on a large table. Atlas Cloud supports CODEOWNERS-style policies where migrations touching specific tables require specific reviewers, and the same can be implemented in plain GitHub CODEOWNERS pointing `atlas.hcl` and `migrations/` at a migration reviewers group. Rotation policy: two senior engineers plus one DBA per region, reviewed quarterly, with explicit escalation to the database platform team for anything that `atlas migrate lint` flags as error-level even with an override annotation. Track approval latency as a metric, because the reviewer bottleneck is often where staff engineers need to invest in automation or in growing the reviewer pool.

Disaster recovery: re-applying from scratch. Every migration system must answer "if I lose the production database entirely and must restore from backup plus re-apply all migrations since the backup, how long does it take and what breaks." Atlas's answer is `atlas migrate apply --dir file://migrations --url <new_db>`, and the time is bounded by the sum of migration durations. Long-running data migrations (backfills in Go migrations) are the failure point because they replay the whole backfill. The staff mitigation is to separate schema migrations (Atlas-managed, fast, replayable) from data backfills (separate pipeline with checkpoint state), and to snapshot the post-backfill state as a baseline migration periodically so new environments do not replay years of data transformation. Atlas supports baselining via `atlas migrate hash` and explicit baseline markers.
