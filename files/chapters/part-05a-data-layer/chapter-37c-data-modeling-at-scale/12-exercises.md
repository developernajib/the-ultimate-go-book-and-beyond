## Exercises

1. **Time-Series Schema for IoT Data**: Design a PostgreSQL schema for an IoT platform that ingests 50,000 sensor readings per second from 10,000 devices, each reading containing a device ID, metric name, float value, and UTC timestamp. Implement the schema using TimescaleDB hypertables with a 1-day chunk interval, a compression policy that activates after 7 days, and a retention policy that drops chunks older than 90 days. Write Go code using `pgx` that bulk-inserts readings in batches of 1,000 using `COPY`. Add a continuous aggregate that pre-computes per-device hourly averages. Benchmark raw insert throughput and verify that a query for the last 24 hours of data for one device executes in under 10ms.

2. **Polymorphic Association Patterns**: A notifications system must send notifications to three entity types: `users`, `teams`, and `organizations`. Implement all three polymorphic association approaches - nullable foreign keys, generic foreign key (type + ID strings), and abstract parent table - as separate schema designs in Go migration files. Write a Go repository for each approach that fetches all unread notifications for a given recipient. Benchmark a JOIN query across 1 million notifications for each approach. Write a comparison document (as Go test output via `t.Log`) summarizing referential integrity guarantees, query performance, and migration cost for adding a fourth entity type.

3. **Denormalization for Read Performance**: You have a normalized e-commerce schema with `orders`, `order_items`, `products`, and `users` tables. A dashboard query joins all four tables and takes 800ms at 5 million orders. Implement a denormalized `order_summary` materialized view that pre-joins the data and reduces the query to under 20ms. Then implement an incremental refresh strategy using a `BEFORE INSERT/UPDATE` trigger on `order_items` that keeps a `orders.total_amount` denormalized column in sync. Write Go integration tests that insert an order, update a line item quantity, and assert that both the column and the materialized view reflect the correct total within one transaction.

4. **Partitioning Strategy for a 10-Billion-Row Table**: Design a PostgreSQL partitioning strategy for an `events` table projected to reach 10 billion rows within two years. The table has columns: `id` (uuid), `tenant_id` (uuid), `event_type` (text), `occurred_at` (timestamptz), and `payload` (jsonb). Implement range partitioning by month on `occurred_at` with sub-partitioning by `tenant_id` hash (8 sub-partitions per month). Write a Go migration that creates 24 months of partitions upfront and a scheduled job that creates the next month's partitions on the 25th of each month. Demonstrate via EXPLAIN ANALYZE that a query scoped to a single tenant and single month performs partition pruning, touching at most 1 of the 8 sub-partitions.

5. **JSONB vs. Normalized Columns Decision Framework**: A product catalog stores variable attributes per product category (e.g., electronics have voltage and connectivity specs, while clothing has size and material). Implement two schemas: one using a normalized `product_attributes` EAV-style table and one using a `attributes` JSONB column on `products`. Populate each with 500,000 products across 20 categories (25 attributes each on average). Write five representative queries (filter by attribute value, aggregate by attribute, full-text search within attributes, list all distinct attribute keys per category, update a single attribute) and benchmark both schemas for each query. Output a Go test that asserts the JSONB schema is faster for reads and the normalized schema is faster for integrity-constrained writes, with actual measured timings.

6. **Event Sourcing Schema Design**: Design an event sourcing schema in PostgreSQL for an order management domain. The schema must include an `events` table (aggregate_id, aggregate_type, sequence_number, event_type, payload JSONB, occurred_at) with a unique constraint on `(aggregate_id, sequence_number)` for optimistic concurrency. Implement a Go `EventStore` with `Append` (using optimistic locking, failing if the expected version does not match), `Load` (replay all events for an aggregate), and `LoadSnapshot` (load the nearest snapshot plus subsequent events). Add a separate `snapshots` table and a Go policy that creates a snapshot every 50 events. Write integration tests covering concurrent appends to the same aggregate (exactly one must succeed), snapshot creation, and full aggregate reconstruction from events.

### Junior → FAANG: Warm-Up Exercises for Data-Modeling Interview Prep

These exercises are a ramp into the six above. If the main exercises feel intimidating, start here. Each one is scoped to a half-day and each one produces an artifact you can reference in your first-job interviews when the data-modeling question comes up.

Warm-up A, the anti-pattern audit. Pick any open-source project on GitHub with at least 50 migration files. Clone the repo. Read the migrations in chronological order. For each migration, write a one-line note: what did this migration try to accomplish, and what anti-pattern did it narrowly avoid or accidentally introduce? Produce a markdown table with columns `migration_id`, `intent`, `smell_present`, `smell_type`, `suggested_fix`. Target 30 migrations. This trains the "why did this fail?" reflex on a live codebase and gives you concrete stories to tell in interviews.

Warm-up B, the soft-delete GDPR drill. Take the schema from exercise 3 and add a `deleted_at` column to `users`. Now implement the GDPR-deletion flow. The user requests deletion. Your code must hard-delete or anonymize the `users` row, handle all foreign-key references (including referential integrity on `orders`), preserve aggregate analytics (totals must not regress), and log the deletion with a retention-compliant audit trail. Write a Go integration test that submits a deletion request, asserts the user row is gone or anonymized, asserts orders still sum to the pre-deletion total, and asserts the audit row is present. This is the exact drill a junior will face within the first six months at any B2C FAANG.

Warm-up C, the composite key decoder. You inherit a table where the primary key is `concat(tenant_id, '_', user_id, '_', period)`. Write a migration that splits the composite into typed columns, backfills the existing rows, adds a composite primary key on the new columns, keeps the old string column around as a computed generated column for backward compatibility, and drops it after a 90-day deprecation window. Write the migration in the expand-and-contract style covered in section 37C.5. Produce a PR description that an on-call reviewer would approve without follow-up questions.

Warm-up D, the first-job schema review. Find a PR in a public repository that adds a new table. Read it as if you were the assigned reviewer. Write a review comment that includes three questions (access pattern, cardinality, `NULL` semantics), one nit (naming, indentation, or missing `created_at`), and one blocking concern (anti-pattern present, or unsafe migration, or missing index on foreign key). Save the review. Repeat weekly for three months. This is the exact practice that separates juniors who get promoted in 18 months from juniors who stall at 30.

Worked example outcome, warm-up A scaled up. If you do warm-up A against three projects, you will have roughly 90 anti-pattern case studies. Pick the ten most interesting. Draft a short write-up for each. Publish as a blog or internal doc at your first job. Promotion packet material, produced before you start the job.

### Senior @ FAANG: Staff-Level Extensions to the Main Exercises

The six main exercises above are L4-plus-a-stretch in scope. Each has a staff-level extension that turns the same exercise into a promotion-packet artifact for L6 and L7 candidates. Work these only after the base exercise is complete and reviewed.

Extension to exercise 1, the time-series IoT schema. Build a schema lint tool that reads a directory of migration files and flags any table without a declared retention policy, any hypertable without a compression policy, any `timestamp without time zone` column, and any index on `occurred_at` without a tenant predicate. Produce a CLI that exits non-zero on violations and prints a fix suggestion for each. Integrate into a sample CI pipeline. The deliverable is the lint tool plus a README that names the org size at which each rule pays for itself. Staff signal: you built the mechanism, not the one-off fix.

Extension to exercise 2, the polymorphic association comparison. Draft an ADR that recommends one of the three approaches as the organizational standard. The ADR has eight sections: context, access patterns considered, options considered (all three), decision, consequences (what we give up), rollback plan, consumer impact, revisit trigger. Circulate the ADR to three peer engineers and collect written review comments. Revise. The deliverable is the final ADR plus the review thread. Staff signal: you can drive a cross-team decision to closure, not just produce code.

Extension to exercise 3, the denormalization. Design and document a data contract for the denormalized `order_summary` view. Specify freshness SLO (p95 lag under 60 seconds), completeness SLO (no more than 0.01 percent missing rows per day), schema stability window (90 days minimum between breaking changes), and on-call rotation for contract violations. Build a contract-assertion test that runs in CI and fails if any SLO is violated by the reference implementation. The deliverable is the contract document plus the assertion test. Staff signal: you operate the thing you build.

Extension to exercise 4, the partitioning strategy. Write a postmortem for a hypothetical incident where the partition-creation cron failed silently for 48 hours, causing writes to fall into the default partition and the production database to stall at 2 AM. The postmortem follows the standard five-part structure (summary, impact, timeline, root cause, action items). The action items include at least one detection mechanism (alert on default-partition writes), one preventative mechanism (pre-create 60 days of partitions rather than 30), and one governance mechanism (schema review board must approve any table that uses deferred partition creation). The deliverable is the postmortem as it would be filed internally. Staff signal: you think in failure modes before they occur.

Extension to exercise 5, the JSONB decision framework. Build a data contract CLI that accepts two schema versions (v1 and v2) and reports breaking changes against a declared contract. Breaking-change detection covers: column removals, type narrowings, `NOT NULL` additions on columns without defaults, index removals on columns declared as queryable in the contract, JSONB path removals for paths declared as extracted. The CLI exits with a distinct code for each severity class. The deliverable is the CLI binary, a sample contract file, and a CI integration example. Staff signal: you ship tooling that makes the right thing the easy thing.

Extension to exercise 6, the event sourcing schema. Write a postmortem for a data-modeling mistake in an event-sourced system: the team added a required field to an event schema without versioning, and replays against archived events from 18 months prior now crash. The postmortem names the five-whys, the preventative mechanism (event versioning policy, upcaster pattern, archived-event compatibility test in CI), and the governance mechanism (schema review board must approve any event schema change). Bonus: implement the upcaster policy in Go and demonstrate it over an archived event fixture. The deliverable is the postmortem plus the working upcaster. Staff signal: you know that events are forever and you have the discipline to treat them that way.

Capstone extension, the maturity model self-assessment. Pick your current organization (or a hypothetical one at your target level). Assess it against the L1-through-L5 maturity model from section 37C.8. Write a one-page per-level assessment with evidence. Propose a 12-month roadmap to advance one notch. Name the staff-engineer headcount investment required, the platform team dependencies, the consumer-team migration cost, and the one initiative you would kill to fund this one. The deliverable is the one-pager plus the roadmap. This is L7 material. If you can produce this and defend it in a 45-minute review, you are ready to interview at the next level.
