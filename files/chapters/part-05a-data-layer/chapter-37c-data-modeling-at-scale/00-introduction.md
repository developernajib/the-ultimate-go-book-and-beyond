# Chapter 37C: Data Modeling at Scale

*Bad data models last forever. Good data models last longer than the engineers who designed them.*

Data modeling decisions made during a product's early weeks have a way of persisting long after the team has tripled in size, the traffic has grown by three orders of magnitude, and the original engineers have moved on. A product_tags column stored as a comma-separated string is defensible at 10,000 rows. At 50 million rows it becomes an unmigrated performance liability that touches every query in the system. A user table with a polymorphic role column that seemed elegant at schema design time becomes an index-resistant WHERE clause filter that makes authorization queries unoptimizable at scale. Data modeling is one of the few engineering decisions where the cost of a wrong choice compounds continuously over the system's lifetime rather than being absorbed in a single refactor.

For Go engineers, data modeling precision matters more than in languages with heavier ORM layers, because Go's `database/sql` ecosystem exposes the schema directly in struct tags, query code, and repository interfaces. A poorly normalized schema does not hide behind an ORM's magic. It manifests as complex joins in every repository method, as race conditions in concurrent update logic, and as cross-service synchronization bugs in microservice architectures where each service owns its own database. Conversely, a well-modeled schema makes Go data access code clean, its repository interfaces narrow and focused, and its test fixtures simple to construct and reason about.

This chapter covers data modeling at the level of rigor that production systems require. You will work through normalization theory and its pragmatic exceptions, master schema patterns for semi-structured data, polymorphic relationships, temporal records, and full audit trails, and learn how to model hierarchical data efficiently using closure tables and PostgreSQL's `ltree` extension. The chapter also covers modeling for microservices (maintaining consistency across service boundaries without distributed transactions) and designing time-series schemas for high-ingest workloads using partitioning, TimescaleDB, and ClickHouse.

**What you'll learn in this chapter:**
- How to apply normalization theory through 3NF and BCNF, and when deliberate denormalization is the correct engineering trade-off
- How to choose between JSONB columns, entity-attribute-value tables, and typed columns for schema-flexible and polymorphic data
- How to model temporal data with valid-time and transaction-time bitemporal patterns for auditable, point-in-time queryable records
- How to represent hierarchical data (categories, org charts, threaded comments) using adjacency lists, closure tables, and PostgreSQL `ltree`
- How to design schemas for microservices with clear ownership boundaries, outbox patterns for cross-service event consistency, and CQRS read models
- How to execute zero-downtime schema migrations using the expand-and-contract pattern and backward-compatible deploy sequencing
- How to model high-ingest time-series data using PostgreSQL table partitioning, TimescaleDB hypertables, and ClickHouse column stores
- How to recognize and avoid the most costly data modeling anti-patterns: EAV table abuse, overloaded status columns, and unindexed polymorphic foreign keys

**Why this matters at scale:**
A single poorly designed polymorphic relationship in a core schema can take a multi-year migration touching hundreds of services to unwind, which is the recurring shape of the schema-cleanup retrospectives large marketplaces publish. And the biggest query-performance wins at data-platform scale consistently come from time-series partitioning and deliberate denormalization decisions made with explicit cost models rather than ORM conventions.

### Junior → FAANG: Where Data Modeling Actually Starts

If you arrived here from a bootcamp or a CRUD-heavy first job, the prerequisite gap is usually not SQL syntax. It is relational theory. Before you read further, make sure you can explain functional dependency, transitive dependency, and why 3NF exists without reaching for a textbook. A worked example to anchor it. Given `orders(order_id, customer_id, customer_email, product_id, product_name, product_price)`, identify every partial and transitive dependency, then decompose into `orders`, `order_items`, `customers`, and `products`. If you cannot do that decomposition on a whiteboard in five minutes, the rest of this chapter will feel like arbitrary rules rather than engineering trade-offs.

First-job context. At a small company the schema is probably `users`, `posts`, `comments`, with a handful of JSON columns holding whatever the last sprint needed. That is fine for 100k rows. The interview entry-point at a FAANG-adjacent company is usually a system design prompt ("design Twitter's timeline storage", "design Uber's trip table") where the interviewer is watching for three things. One, do you ask about read-to-write ratio before proposing a schema. Two, do you distinguish OLTP from OLAP modeling. Three, do you know when to pick a primary key that is not `SERIAL`. If those three are reflexive for you, you clear the data-modeling bar for L4/E4. Everything else in this chapter is how you clear L5/L6.

### Senior @ FAANG: Modeling as an Irreversible Architecture Decision

At staff and principal level, data modeling is the one architecture decision you usually cannot roll back. Code can be rewritten in a quarter. A schema that has accumulated 50 billion rows, 200 downstream consumers, and three years of query patterns is effectively immutable. The framing shift is that every modeling choice is an ADR (architecture decision record) with a half-life measured in years, and your job is to make the decision legible to the engineers who inherit it.

Normalization versus denormalization at scale. The textbook answer is "normalize until it hurts, denormalize until it works." The FAANG answer is that 3NF is almost never the right choice past a billion rows in a hot OLTP path. The reasoning is query amplification. A 3NF schema that requires a four-table join to render a single UI card will collapse under fanout at p99, and no amount of index tuning recovers it. At that scale the correct move is a precomputed materialized projection, a CQRS read model, or an outright denormalized wide row. The ADR must document the write amplification cost, the consistency window, and the reconciliation job that detects drift. Without that documentation the next engineer will "fix" your denormalization and cause an outage.

Star and snowflake schemas are the OLAP counterpart. Fact tables with foreign keys to dimension tables, surrogate keys on every dimension, slowly changing dimensions (SCD Type 2 with `valid_from`/`valid_to` columns) for attributes that evolve. Snowflake adds further normalization on dimensions, which is almost always the wrong call because modern columnar engines (Snowflake the product, BigQuery, ClickHouse, Druid) make the extra joins expensive and the storage savings irrelevant.

Wide-column and query-first design. For Cassandra, ScyllaDB, and DynamoDB, you model the query first and the entity second. Partition key selection determines whether your system scales or degenerates into hotspots. The anti-pattern is porting a relational ERD into a wide-column store. The correct pattern is to enumerate every access path, then design one table per access path with the partition key chosen to distribute load and the clustering key chosen to order within partition. DynamoDB's single-table design (Rick Houlihan's pattern) collapses multiple entity types into one physical table using composite keys like `PK=USER#123, SK=ORDER#2026-04-22#abc`. It is powerful and unreadable, and it requires a data dictionary that explains every access pattern. Do not adopt it without that dictionary.

Event sourcing and CQRS. Event sourcing stores every state change as an immutable event and derives current state by folding the event log. CQRS splits the write model (commands against the event log) from the read model (projections optimized for queries). The combination gives you perfect auditability and arbitrary read-model flexibility at the cost of eventual consistency, snapshot management, and event-schema evolution complexity. Adopt it only where the audit requirement is regulatory (finance, healthcare) or where the read patterns are genuinely heterogeneous. For a standard CRUD service it is resume-driven overkill.

Bitemporal data. Valid-time (when the fact was true in the world) and system-time (when the database knew it) are orthogonal. SQL:2011 temporal tables standardize system-time via `PERIOD FOR SYSTEM_TIME`, supported in DB2, SQL Server, MariaDB, and partially in PostgreSQL via extensions. At FAANG scale, bitemporal modeling is mandatory for anything touching money, compliance, or legal hold. The worked consequence is that you cannot `UPDATE` a row. You insert a new version with `valid_from = now()` and close the prior row with `valid_to = now()`. Every query must carry an `AS OF` clause or default to current. Get this wrong and a single reconciliation bug becomes a regulatory filing.

Key strategy. UUIDv4 is random and destroys B-tree locality, causing write amplification on clustered indexes. UUIDv7 (time-ordered, RFC 9562, finalized 2024) restores locality while keeping global uniqueness. ULID and KSUID are earlier approaches with similar properties. Prefer UUIDv7 for new systems. Surrogate keys beat natural keys for internal references because natural keys change (email addresses, SSNs that get reissued, country codes that split). Composite primary keys are correct for junction tables and for wide-column partition-plus-clustering designs. Never use a natural key as the sole PK on an entity you expect to reference from other tables.

Schema governance at scale. Meta layers Ent, the typed entity framework it later open-sourced, over MySQL with mandatory schema review. Airbnb's Midas data-quality program enforces ownership, SLAs, and lineage on certified production tables. Mature data platforms treat schemas as products with versioned contracts. The common thread is that at FAANG scale, a schema change is a cross-team negotiation, not a developer convenience. Chapter 37C teaches the modeling craft. The governance layer is what keeps the craft from collapsing under the weight of two thousand engineers each doing their best.
