# Chapter 35: Redis for Go Applications

*Redis is not a cache that happens to have persistence. It is a data structure server that happens to be fast enough to use as a cache.*

The engineers who get the most out of Redis are not the ones who use it only to cache database query results. They are the ones who recognize that Redis's sorted sets are a leaderboard, that its streams are a durable message queue, that its atomic `INCR` and `EXPIRE` commands are a rate limiter, and that its `SET NX` operation is a distributed lock primitive. Twitter's timeline fanout, GitHub's background job queues, and Instagram's early feed infrastructure all leaned on Redis data structures far beyond a simple key-value store. When you understand Redis as a toolkit of data structures rather than a cache layer, you gain the ability to solve coordination, counting, queuing, and ranking problems with microsecond latency and a single infrastructure dependency.

For Go applications, the `go-redis/v9` client exposes the full Redis command set with a clean, context-aware API that integrates naturally with Go's concurrency model. Pipelining - sending multiple commands without waiting for individual responses - maps directly onto Go's batching patterns and can reduce round-trip overhead by an order of magnitude on bulk operations. The client's built-in connection pooling means each Go service maintains a healthy pool of Redis connections without additional infrastructure, and its cluster-aware routing handles key distribution transparently when you need to scale beyond a single Redis node. For latency-sensitive services at the top end of throughput requirements, the newer `redis/rueidis` client uses RESP3 and automatic pipelining to batch concurrent in-flight commands onto a single connection, and independent benchmarks have shown multi-x throughput and large reductions in allocations versus `go-redis` - at the cost of a less idiomatic API surface.

**Redis vs Valkey (as of 2026).** In March 2024 Redis Ltd. relicensed Redis under the dual RSALv2/SSPL model. Neither license is OSI-approved, and within two weeks the Linux Foundation forked Redis 7.2.4 as **Valkey** under BSD-3-Clause, with AWS, Google Cloud, Oracle, Ericsson, and the former Redis maintainers backing the project. AWS ElastiCache and Google Cloud Memorystore both shipped managed Valkey offerings, and Valkey 8.x has added measurable I/O-threading improvements over upstream Redis. Redis Ltd. subsequently added AGPLv3 as a third license option for Redis 8. For Go engineers this is mostly a licensing and support decision: Valkey is wire-compatible with Redis 7.2, all commands and the RESP protocol behave identically, and `go-redis/v9` and `rueidis` connect to either without changes. Throughout this chapter "Redis" refers to the data model and protocol. Everything applies to Valkey unchanged unless noted.

This chapter covers Redis from first principles through production deployment. You will learn each data structure - strings, hashes, lists, sets, sorted sets, and streams - with concrete Go examples for each, then move into advanced patterns: cache-aside and write-through caching with TTL strategies, distributed locking with Redlock, rate limiting using the token bucket and sliding window algorithms, and real-time messaging with Pub/Sub and Streams. Each pattern includes the failure modes and the production safeguards that distinguish toy implementations from systems that run at scale.

**What you'll learn in this chapter:**
- How to configure `go-redis/v9` with connection pooling, timeouts, and retry policies for production use
- How to use Redis strings, hashes, lists, sets, and sorted sets with idiomatic Go, including TTL management and atomic operations
- How to implement cache-aside, write-through, and cache invalidation strategies with tagged cache keys
- How to build a distributed lock using `SET NX EX` and the Redlock algorithm for multi-node correctness
- How to implement sliding window and token bucket rate limiting using Redis atomic operations and Lua scripts
- How to use Redis Pub/Sub and Streams for real-time event broadcasting and durable message queuing in Go goroutines
- How to pipeline Redis commands in Go to batch operations and dramatically reduce network round-trip overhead
- How to configure and connect to Redis Sentinel (high availability) and Redis Cluster (horizontal scaling) from Go

**Why this matters at scale:**
Twitter's engineering team uses Redis sorted sets to maintain per-user home timelines in memory, serving timeline reads in under a millisecond for hundreds of millions of users. Presence systems at chat platforms broadcast online/offline events over Redis Pub/Sub to millions of concurrent WebSocket connections, a pattern that would be impossible to implement with database polling at that scale. Since 2024 the same infrastructure is increasingly deployed as Valkey - AWS ElastiCache for Valkey, Google Memorystore for Valkey, and self-managed clusters - with no client-side code change required.

### Junior → FAANG: what "a cache" actually means before your first on-call

If you arrive at a FAANG or late-stage startup with only a hobby-project understanding of Redis, your first outage will be humbling. The mental model most bootcamp graduates carry is "Redis is a fast key-value store, SET and GET, done." That model is correct for about a week. The moment you are handed a production service it breaks down into questions nobody answered for you: what happens when the Redis node restarts, what happens when the cache is colder than the database can survive, what happens when two pods try to write to the same key at the same millisecond, and what happens when a key grows to 500 MB and blocks the event loop for three seconds.

Start with the protocol. Redis speaks RESP (REdis Serialization Protocol) over TCP on port 6379 by default. RESP2 is the classic text-plus-length-prefix protocol. RESP3 is the newer binary-safe variant introduced in Redis 6, negotiated per connection via the `HELLO` command. go-redis v9 and rueidis both negotiate RESP3 by default (set `Protocol: 2` on go-redis to force RESP2). You do not need to parse RESP by hand (go-redis and rueidis do it for you), but you do need to know two things. First, one TCP connection processes commands serially, which is why pipelining matters. Second, the server is single-threaded for command execution, which is why one slow `KEYS *` or one 500 MB value will stall every other client.

Next, internalize the six core data types as a junior would meet them in interviews and early tickets. Strings (used as counters, JSON blobs, bitmaps). Hashes (a record with fields, the poor-person's row). Lists (queue or stack, LPUSH/RPOP). Sets (unique membership, SADD/SISMEMBER). Sorted sets (leaderboards, priority queues, time-ordered indexes via ZADD with a score). Streams (append-only log with consumer groups, the XADD/XREADGROUP pair). A common first-job task is "cache the user profile." The junior answer is `SET user:42 <json>`. The slightly-senior answer is `HSET user:42 name ... email ...` so you can update one field without rewriting the blob, plus an `EXPIRE user:42 3600` so a stale profile self-heals.

Worked example you will be asked to reason about in a phone screen. A product page needs the user's recent-view list, the product's price, and a rate limit on "add to cart." A junior does three round trips. A FAANG candidate pipelines them, uses a hash tag like `{user:42}:views` and `{user:42}:ratelimit` so they land on the same Redis Cluster slot, and knows that the price lookup must NOT share that hash tag because it is owned by a different service. Knowing when to co-locate keys and when to deliberately spread them is the entry-point skill that separates "I used Redis in a side project" from "I can be trusted with the cache tier."

One more thing nobody tells juniors: Redis is not magic. It is a C program that trades durability for latency. If the box loses power between two fsyncs, you lose data. If you use Redis as the system of record, you are one `kill -9` away from an incident. Caches are derived state. Sources of truth go in Postgres, DynamoDB, Spanner, or whatever the parent service mandates. Learning this before your first outage is cheaper than learning it during one.

### Senior @ FAANG: the 2026 Redis-ecosystem ADR you own

At staff or principal level you are not the person typing `redis-cli`. You are the person who owns the architecture decision record that says "this organization standardizes on Valkey 8.0 managed by ElastiCache in us-east-1 and us-west-2, with failover via Global Datastore, with rueidis as the Go client for latency-tier-1 services and go-redis/v9 for everything else." Everything below is what that ADR has to defend.

**The license fork and why it is a real architectural input, not drama.** In March 2024 Redis Ltd. pulled Redis out of the BSD family into a dual RSALv2 and SSPL license. Neither license is OSI-approved, which disqualifies Redis from any project that requires OSI-open dependencies, including most Linux distributions and the CNCF. Within two weeks the Linux Foundation forked Redis 7.2.4 as Valkey under BSD-3-Clause. The original Redis maintainers Madelyn Olson, Zhao Zhao, Viktor Söderqvist, and Ping Xie moved to Valkey. AWS, Google Cloud, Oracle, Ericsson, and Snap funded it. Valkey is hosted directly by the Linux Foundation under an open-governance model with BSD-3-Clause licensing. By 2026 AWS ElastiCache for Valkey and Google Memorystore for Valkey are GA, Oracle OCI Cache runs Valkey, and Valkey 8.0 has merged asynchronous I/O threading that measurably beats Redis 7.4 on multi-core boxes. Redis Ltd. responded by adding AGPLv3 as a third option with Redis 8.0 in May 2025, which technically puts the server back in the OSI world but under a copyleft license that most legal teams still reject for linked modules. The practical consequence for a staff engineer: if you deploy on a managed cloud, Valkey is now the default for new workloads at AWS and GCP, the wire protocol is identical to Redis 7.2, go-redis and rueidis connect to either, and you migrate by changing the DNS endpoint. If you self-host, your choice is between Valkey (BSD, community-governed, faster on multi-core since 8.0) and Redis (AGPLv3 or SSPL, Redis Stack modules, Redis Enterprise commercial features like Active-Active CRDT). Write this into the ADR explicitly so the next VP does not relitigate it in a quarterly review.

**The alternatives that are NOT Redis or Valkey and when they win.** DragonflyDB is a from-scratch rewrite in C++ with a shared-nothing multi-threaded architecture and BSL license. It claims 25x throughput on a single box and is genuinely faster for throughput-bound workloads, but its cluster story is weaker, its Lua semantics differ subtly, and the license is not OSI. KeyDB was the original multi-threaded Redis fork, now owned by Snap and effectively in maintenance after Valkey landed the same thread model upstream. Garnet is Microsoft Research's RESP-compatible C# server, interesting academically, not production-common outside Azure teams. Upstash is Redis-compatible serverless on HTTP, priced per request, useful for edge workloads on Cloudflare Workers and Vercel. The principal-level answer when somebody says "should we use Dragonfly" is: only if you have measured a single-node CPU bottleneck that Valkey 8.0's I/O threading cannot absorb and you are willing to take a non-OSI license and a smaller ecosystem.

**Topology decisions, ordered by blast radius.** A single primary with one replica and Sentinel handles the long tail of workloads. Sentinel promotes the replica on failure and every go-redis and rueidis client supports `FailoverClient` mode. The cost is that you scale vertically only and any write outage during failover is 5 to 30 seconds. Redis Cluster shards across 16384 hash slots computed as `CRC16(key) mod 16384`. You pay for this with two hard constraints. First, CROSSSLOT errors: any multi-key command (MGET, MSET, SUNIONSTORE, pipelines that span keys, Lua scripts with KEYS from multiple slots) fails unless every key hashes to the same slot. Second, hash tagging: when you write `user:{42}:profile` and `user:{42}:sessions`, Redis only hashes the substring inside the first pair of braces, forcing those keys onto the same slot. Used correctly this is the power tool that lets you keep MGET in a cluster. Used carelessly it creates a hotslot that defeats the point of sharding. Redis Enterprise Active-Active uses CRDTs (Conflict-free Replicated Data Types) to give you multi-region writable replicas with last-writer-wins for strings and counter-merge semantics for INCR. It is the only supported path for true multi-master and it is a commercial-only feature. Valkey does not have a CRDT equivalent yet. If you need multi-region active-active on open source, the answer today is application-level conflict resolution with per-region key prefixes.

**Persistence and the durability vs latency ADR.** RDB is a point-in-time fork-and-dump snapshot, compact, fast to restore, and loses every write since the last snapshot on crash. AOF is an append-only log of commands with three fsync policies: `always` (fsync every write, 2x to 5x latency penalty, near-zero data loss), `everysec` (fsync once per second, loses up to 1s on crash, default, almost always correct), and `no` (let the kernel decide, do not use in production). Running both RDB and AOF is the standard durable configuration: RDB for fast restart, AOF for the tail. For a cache-only workload the correct answer is often to disable persistence entirely and let the service warm from the source of truth after restart, but you must verify the thundering-herd behavior of your cache-aside code first. Replication is asynchronous by default. `WAIT numreplicas timeout` gives you a weak synchronous acknowledgment but not true quorum. Redis 7.4 added `CLIENT NO-EVICT` and tighter replication backlog controls that matter for high-throughput writers.

**Eviction at scale.** `maxmemory-policy` is the knob most teams set wrong. `noeviction` (reject writes when full) is correct for durable stores and catastrophic for caches. `allkeys-lru` evicts the approximate least-recently-used key across the entire keyspace. `allkeys-lfu` uses a counter-based approximation of frequency with decay and is almost always the better choice for caches with skewed access (product catalogs, user profiles, anything with a power-law distribution), because LRU gets defeated by one-time scans. `volatile-lru` and `volatile-ttl` only consider keys with a TTL, which is what you want when a single Redis is shared between cached data and durable structures like rate-limiter state. The LFU tuning parameters `lfu-log-factor` (default 10, raise for skewed distributions) and `lfu-decay-time` (default 1 minute) are tunable and rarely tuned. Plot your hit rate against `INFO stats:keyspace_hits/misses` and adjust.

**Hotkeys, bigkeys, and the operational disasters.** A bigkey is any single key large enough that a DEL on it blocks the event loop. For strings over 1 MB or for hashes, sets, sorted sets, or lists with more than 10K elements, use `UNLINK` instead of `DEL` (lazy free, introduced in Redis 4.0, still missed in code reviews in 2026). Detect them with `redis-cli --bigkeys` or the `MEMORY USAGE key` command. Hotkeys are the opposite problem: a single key receiving so many requests that one shard's CPU saturates. Mitigations in priority order are client-side L1 cache (an in-process LRU in front of Redis, which Uber and Netflix do ubiquitously), client-side tracking with `CLIENT TRACKING ON` so Redis pushes invalidations when the underlying key changes (RESP3 only, supported by rueidis natively and by go-redis via callbacks), sharded counters (write to `counter:N` where N is `hash(requestID) mod 16` and sum on read), and as a last resort horizontal replicas with read-from-replica client routing. A mature prefix-governance document is the standard answer at scale: every new key prefix must be registered with owner, TTL policy, max size, and eviction class, and violations block deploys. This sounds bureaucratic until the day an untagged prefix eats a large fraction of your cluster memory.

**Client choice in Go for 2026.** go-redis/v9 is the default, idiomatic, battle-tested client. It supports Sentinel, Cluster, RESP3, OpenTelemetry hooks, and has a stable API. rueidis v1.0 is the performance option. It uses RESP3 exclusively, automatically pipelines concurrent commands onto a single connection (which is safe because RESP3 pushes are out-of-band), and in independent benchmarks (including the one Redis Ltd. publishes) delivers 2x to 5x the throughput of go-redis with an order of magnitude fewer allocations. It also has first-class client-side caching: `rueidis.NewClient` with `CacheCall` gives you local-cache-then-broadcast-invalidate semantics for free. The cost is an API surface that does not look like database/sql and a steeper learning curve for new hires. The ADR pattern that has held up at multiple FAANGs is rueidis for tier-1 latency-critical paths (timeline fanout, rate limiting, session lookup) and go-redis for everything else (job queues, pubsub, admin tools). Do not mix them behind the same abstraction, because their error types and connection management differ.

**The forward horizon.** Redis 7.4 (released 2024) shipped hash field TTLs (`HEXPIRE`, finally, after years of pain). Redis 8.0 (released May 2025) moved vector similarity search and the JSON, time-series, and probabilistic data structures into core (previously separate Redis Stack modules) and re-added an OSI-approved license via AGPLv3. Shard-scoped pubsub (`SSUBSCRIBE`/`SPUBLISH`) has been available since Redis 7.0. Valkey 8.0 shipped async I/O threading and a new RDMA transport experiment. Both have RESP3 client tracking as a first-class feature. If you are writing a multi-year roadmap in 2026, budget for RESP3 and client-side caching as the default, budget for hash field TTLs to simplify session-management code that used to need one key per field, and budget for a cluster migration if you are still on a single primary above 50 GB of working set.
