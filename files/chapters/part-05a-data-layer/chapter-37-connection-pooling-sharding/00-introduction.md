# Chapter 37: Connection Pooling & Sharding

*A database connection is not free. Each one holds memory, a file descriptor, and a slot in the server's process table. Treat them as the scarce resource they are.*

When a Go service starts receiving real traffic, the first database bottleneck is almost never query performance - it is connection exhaustion. PostgreSQL maintains a process or thread per connection, and each idle connection consumes roughly 5 to 10 MB of server memory. A Go service with 50 goroutines making simultaneous database calls will attempt to open 50 connections. Scale to 20 service instances and you have 1,000 connections hammering a database configured for 100. The application never gets a chance to be slow. It simply fails with "too many connections" before a single query executes. Connection pooling is not an optimization. It is the mechanism that makes multi-instance Go deployments possible at all.

Sharding is the next frontier when a single database node's write capacity becomes the ceiling. Pinterest scaled to billions of pins by sharding MySQL across a large fleet of nodes. Vitess, originally built at YouTube to manage tens of thousands of MySQL nodes and now used by Slack, Block (Square), and JD.com, wraps MySQL with a sharding proxy layer that makes horizontal partitioning transparent to application code - Slack used Vitess splitting workflows to horizontally scale one of its busiest keyspaces without downtime. For Postgres, Citus (now part of Microsoft) and the Rust-based pgcat proxy extend the ecosystem with distributed query execution and transparent sharding. The engineering challenge is not the sharding itself but everything around it: choosing a shard key that distributes load evenly without creating hot keys, implementing scatter-gather queries when you must fan out, and rebalancing shards online when you add nodes. Cross-shard transactions are almost always the wrong answer - production systems denormalize, use sagas, or accept eventual consistency instead.

This chapter covers both problems with production-grade depth. You will learn how to tune `database/sql` and `pgxpool` connection pool parameters for different traffic shapes, how to implement read/write splitting with primary and replica routing, how to add PgBouncer as a connection multiplexer between your Go services and PostgreSQL, and how to design and implement a sharded data layer using consistent hashing, with proper cross-shard query patterns and a shard rebalancing strategy.

**What you'll learn in this chapter:**
- How to size `database/sql` and `pgxpool` connection pools correctly using `MaxOpenConns`, `MinConns`, `MaxConnLifetime`, and `MaxConnIdleTime`
- How to implement a read/write splitting router in Go that directs writes to the primary and distributes reads across replicas
- How to integrate PgBouncer as a session, transaction, or statement-mode connection multiplexer and the trade-offs of each mode
- How to design a hash-based sharding strategy with a consistent hash ring that minimizes resharding when nodes are added or removed
- How to implement a shard-aware repository layer in Go that routes queries to the correct shard transparently
- How to execute scatter-gather queries that fan out to multiple shards and merge results correctly in Go
- How to expose connection pool metrics to Prometheus and build alerting on pool saturation and wait time percentiles
- How to handle shard rebalancing - migrating data between nodes while keeping the system live and consistent

**Why this matters at scale:**
Improper connection pool sizing is responsible for an entire class of production outages, and the postmortems all share the same arithmetic. The math is unforgiving: your application pool size multiplied by replica count must be less than the PgBouncer pool size, which must be less than Postgres `max_connections` minus reserved slots - violate this chain and the database rejects connections before a single query runs. Vitess, originally built at YouTube to handle 300,000 QPS on MySQL, now powers the database infrastructure of companies like Slack and Block by making sharding a transparent infrastructure concern. On the Postgres side, pgcat (PostgresML's Rust rewrite of PgBouncer) adds built-in sharding and load balancing across replicas, and PgBouncer 1.21+ finally supports prepared statements in transaction mode - a decade-old limitation that blocked many Go applications from adopting transaction pooling.

### Junior → FAANG: bridging from database/sql to production pool thinking

If you arrive here having only used `sql.Open` in a tutorial, the first mental shift is that `sql.DB` is not a connection. It is a pool handle. The defaults (`MaxOpenConns=0` meaning unlimited, `MaxIdleConns=2`) are the worst of both worlds in production. Unlimited open connections will march your service straight into Postgres `max_connections` rejection under a spike, and 2 idle connections means every burst pays reconnection cost. A reasonable first-job starting point is `MaxOpenConns=25`, `MaxIdleConns=25`, `MaxConnLifetime=30m`, `MaxConnIdleTime=5m`, then tune from metrics.

Worked example. Your Go service runs 4 replicas. You size the pool at 25 per instance. You have a primary Postgres 17 with `max_connections=200`. The math: `4 * 25 = 100` connections for the app, plus replication slots, admin connections, and migrations. Leave at least 30 percent headroom. If a second service joins the database, this math breaks, and the symptom is not slow queries but `FATAL: sorry, too many clients already` during deploy rollouts when old and new pods both hold connections.

Interview entry-point question you will get: "What happens when all pool connections are in use and a new request arrives?" Answer: the goroutine blocks on `db.Conn` acquisition until either a connection frees up or the context deadline fires. This is why every query MUST use a context with a timeout. Without it, pool saturation becomes unbounded goroutine growth, then OOM, then cascading failure into upstream services.

### Senior @ FAANG: pool economics, sharding governance, and platform design

At staff level your job is not to tune one pool but to set the organization-wide contract for how services talk to Postgres. The dominant constraint is the Postgres `max_connections` ceiling, which in practice you cannot raise past 500 to 1000 on a single primary without hitting process-table and lock-manager contention (Postgres pre-17 serialized parts of the snapshot mechanism across backends, and even in PG17/18 the per-backend memory cost means going higher trades availability for connection count). This ceiling is the forcing function for every architectural decision in this chapter.

The Little's Law framing: `active_connections = arrival_rate * avg_service_time`. If your service handles 2000 requests per second and each request averages 8ms of database work (query + network roundtrip + decode), you need `2000 * 0.008 = 16` active connections. Everything above that is idle headroom for burst. A pool of 25 is rational. A pool of 200 is pathological, and the symptom is not a bug, it is that your DBA asks why one service holds 40 percent of the primary's connection budget.

The pooler layering decision is an ADR you will own. Native pgx v5 pool sits in-process and gives you transactional affinity, prepared statements, and full protocol features. PgBouncer 1.23 in transaction mode multiplexes thousands of client connections onto a small backend pool, at the cost of losing session state (SET LOCAL, advisory locks across statements, prepared statements pre-PG14, temp tables). PgCat 0.4 is the Rust rewrite that adds query routing, sharding, and load balancing with a cleaner auth story. Supavisor is Supabase's multi-tenant Elixir pooler designed for serverless fan-in. AWS RDS Proxy solves Lambda cold-start connection storms at the price of IAM auth complexity and regional failover semantics you cannot control. The wrong layering is running native pgx pools of 100 connections in front of a PgBouncer of 25 backend connections, which just moves the bottleneck one hop and adds latency. The right layering is native pgx pool sized to service concurrency, PgBouncer transaction mode in front for multi-service fan-in, and strict prepared-statement discipline (either disable them, or require PG14+ with `pgbouncer = 1.21+ prepared_statements=1`).

Sharding is a last resort, not a first reach. Before sharding, exhaust: vertical scaling on the primary (Aurora r7g.16xl or equivalent bare metal), read replicas for read-heavy workloads, table partitioning for time-series or tenant-scoped data, and moving cold data to object storage. When sharding becomes unavoidable, the decisions that matter are shard key selection (you are choosing the axis along which you accept cross-shard joins become expensive or impossible), rebalancing strategy (consistent hash ring with virtual nodes so adding shard N+1 moves only `1/N` of keys), and the cross-shard transaction policy (the answer is almost always "we do not do them", and the design work is in sagas, outbox, and idempotent retries). Vitess, Citus, and Spanner all embody the same lesson: the hardest part of sharding is not the router, it is the operational tooling for online resharding, schema changes across shards, and query observability when a single logical query fans out to 64 physical nodes.
