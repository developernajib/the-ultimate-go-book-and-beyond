## Exercises

1. **Tuning pgxpool Min/Max Connections Under Load**: Configure a `pgxpool.Pool` for a Go service that runs on 4 instances, each targeting a PostgreSQL server with `max_connections = 200`. Derive the correct `MaxConns` per instance to leave 20% headroom. Implement a load test using `golang.org/x/sync/errgroup` that fires 500 concurrent queries and measures p50, p95, and p99 latency as well as the number of `pgx.ErrNoRows` and connection-wait timeouts. Vary `MinConns` between 0, 5, and 20 and plot the effect on cold-start p95 latency. Write a `BeforeAcquire` hook that logs a warning when a connection has been idle for more than 30 seconds and a `AfterRelease` hook that resets the `search_path` to prevent tenant data leakage. Assert in tests that pool exhaustion never causes more than 100ms of additional latency per request.

2. **Read Replica Routing with Consistency Guarantees**: Implement a Go `DBRouter` that wraps two `pgxpool.Pool` instances (one primary, one read replica) and routes queries automatically: writes and explicit transactions always go to the primary, reads go to the replica by default. Add a read-your-writes consistency mode: after any write, pin all subsequent reads from the same logical session to the primary for 500ms, implemented using a per-session `sync.Map` with expiry timestamps. Implement a health-check goroutine that detects replica lag exceeding 5 seconds (via `pg_stat_replication`) and temporarily promotes all reads to the primary. Write integration tests using two PostgreSQL containers that verify: (1) reads route to the replica under normal conditions, (2) reads route to the primary immediately after a write within the 500ms window, (3) replica lag above threshold triggers automatic failover.

3. **Consistent Hash Sharding for User Data**: Implement a consistent hash sharding layer in Go for distributing user data across 8 PostgreSQL shards. Use a ring with 150 virtual nodes per shard (1,200 total) and `fnv.New64a` as the hash function. The `ShardRouter` must map a `userID` (uuid) to a `pgxpool.Pool` deterministically. Simulate adding a 9th shard to the ring and compute what percentage of keys would need to move (assert it is within 15% of the ideal 1/9). Implement a `MigrateKey` function that copies a user's rows from the old shard to the new shard within a transaction and then deletes from the source. Write a test that verifies the ring is balanced - no shard handles more than 15% of 100,000 sample keys - and that adding one shard moves fewer than 15% of keys.

4. **Connection Leak Detection and Prevention**: Write a Go middleware layer around `pgxpool.Pool` that wraps `Acquire` to automatically track every acquired connection with a stack trace and a timestamp. Run a background goroutine that scans for connections held longer than 10 seconds and logs a warning with the originating stack trace. Implement a strict mode that forcibly returns connections held beyond 30 seconds and increments a Prometheus counter `db_connection_leaks_total`. Write a test that deliberately leaks three connections (by calling `Acquire` without `defer conn.Release()`) and asserts that the detector fires within 15 seconds, logs the correct stack trace, and that the pool is fully recovered afterward. Include a context-based safeguard: connections are automatically released when the parent context is canceled.

5. **Cross-Shard Query Aggregation (Scatter-Gather)**: Implement a scatter-gather query executor in Go that fans out a read query to all shards concurrently, collects results, and merges them. The executor must: issue queries in parallel using a `semaphore` limited to 4 concurrent shard queries, merge results in-memory (implementing a k-way merge for sorted result sets), propagate partial failures gracefully (return results from successful shards plus a list of failed shards rather than aborting entirely), and enforce a per-scatter timeout via context cancellation. Implement two aggregation modes: `SUM/COUNT` (reduce numeric results from each shard) and `TOP-N` (merge sorted per-shard top-N results into a global top-N). Write a test with 8 mock shards where 1 shard times out and assert the response contains data from the 7 healthy shards with a non-nil `PartialError` field.

6. **Shard Rebalancing Without Downtime**: Design and implement a live shard rebalancing process in Go that moves data from an overloaded shard to a new shard without taking either shard offline. The process must follow four phases: (1) dual-write - configure the application to write new records to both the source and destination shard for the migrating key range. (2) backfill - copy existing rows from source to destination in batches of 1,000 with a 10ms pause, using `SELECT ... FOR UPDATE SKIP LOCKED` to avoid conflicting with live writes. (3) verification - run a row-count and checksum comparison between source and destination for the migrated key range. (4) cutover - atomically update the shard routing table and disable the dual-write. Implement a rollback trigger that re-routes to the source shard if error rate exceeds 1% within 60 seconds of cutover. Write an integration test that rebalances a 50,000-row dataset across two containers while a background goroutine continuously inserts and reads, asserting zero data loss throughout.

### Junior → FAANG: How to Actually Run These Exercises and What to Measure

These exercises look like code assignments. They are actually measurement assignments. A junior engineer who completes Exercise 1 as "I got the pool working and tests pass" has done 20 percent of the work. The other 80 percent is the table of results across the `MinConns` sweep and a written explanation of the shape of the curve.

Worked approach for Exercise 1. Run each configuration three times and record p50, p95, p99, and acquire-wait time. You will see that `MinConns=0` has the best steady-state latency but a cold-start tail of 50 to 200ms on the first request because of the TCP plus TLS plus Postgres startup handshake. `MinConns=5` eliminates the cold-start tail for the first 5 concurrent requests. `MinConns=20` eliminates it entirely but costs 20 idle backends per instance times 4 instances equals 80 permanently held server-side slots. Write up the trade-off in a one-page document. That document is the artifact that demonstrates L4-level thinking.

First-job context for Exercise 2. The read-your-writes window of 500ms is not a magic number. Measure your actual replication lag at p99 over a week and set the window to `p99_lag * 1.5`. If your p99 lag is 300ms, set the window to 450ms. If your p99 lag is 2 seconds, you have a replication-health problem before you have a read-routing problem, fix that first. The point of the exercise is to teach you to derive constants from measurement, not to memorize defaults.

"Why did this fail?" drill for Exercise 3. You implement the consistent hash ring and the balance test shows one shard holds 22 percent of keys instead of the target 12.5 percent. Why. Most likely the 150 vNodes per shard are generated with a weak hash seed (shard name as a plain string), so vNode positions cluster. Fix by using `hash(shard_name + ":" + vnode_index)` with FNV-1a 64 or xxhash, and re-test. A deeper fix is bounded-load consistent hashing which caps per-shard imbalance at epsilon regardless of vNode placement quality.

Interview entry point. Any of these six exercises can appear as a take-home or a system-design prompt. The grader is looking for (1) correct core implementation, (2) explicit handling of the failure mode you were warned about, (3) a test that demonstrates the failure mode is caught, and (4) a written trade-off note. Three out of four is hire, four out of four is strong hire. Two out of four is no hire regardless of how clean the code is.

### Senior @ FAANG: Staff-Level Extensions and the Reshard Choreography

At staff level these six exercises become the starter pack for a six-quarter platform program. Each exercise extends into a production-grade platform primitive.

Staff extension for Exercise 1. The adaptive pool sizer is not a per-service concern, it is a platform concern. Extend the exercise to build a control plane that observes all services' pool utilization, replica-lag signals, and server-side connection count, and publishes per-service pool-size recommendations via a config endpoint. Services poll the endpoint hourly and apply the recommendation through `SetMaxOpenConns`. Ship with a kill switch that pins the last static config. The real artifact is the control-plane observability, the SLA on recommendation freshness, and the rollback runbook.

Staff extension for Exercise 2. The read-router becomes a sidecar or a gRPC service, not a library. The shared library is fine for a 10-service org, but at 400 services a library upgrade takes 18 months. A sidecar centralizes routing logic, exposes replica lag as a platform signal, and upgrades independently. The trade-off is a network hop per query, typically 0.5 to 1ms p99. For services where that hop is acceptable (most transactional workloads), prefer the sidecar. For services where it is not (high-QPS internal APIs), ship the library with a strict versioning policy.

Staff extension for Exercise 3. Replace plain consistent hashing with bounded-load consistent hashing (Mirrokni et al. 2016). Add tenant-affinity overrides so the top 1 percent of tenants route to dedicated shards regardless of hash. Add a per-shard read-only flag for maintenance windows. Ship as a standalone library with a published API contract, a Prometheus metrics namespace, and a runbook for on-call.

Staff extension for Exercise 4. Connection-leak detection becomes a signed, auditable trail. Every acquire records goroutine ID, stack trace, and trace span ID. Leaks above 30 seconds emit a structured event to the platform incident stream. The control plane correlates leaks across services to identify shared root causes (a bad ORM default, a library regression). The leak detector itself must not leak under pathological load, instrument it with its own memory ceiling.

Staff extension for Exercise 5. Scatter-gather becomes a bounded-fanout primitive with explicit per-query budget. Every scatter-gather declares its max concurrent shards, max total latency, and max total memory for result aggregation. The library enforces these and rejects queries that exceed them. Analytics queries (fanout to all shards) are routed to a separate analytics replica set, not the OLTP shards, to isolate the tail-latency blast radius.

Staff extension for Exercise 6, the resharding choreography. Model the reshard as a Temporal workflow with explicit state transitions, per-vNode children, a verification gate requiring two independent signals (row count plus sampled checksum), and a rollback gate requiring operator sign-off. Integrate with the deploy pipeline so application deploys are blocked during active cutover windows. Publish per-shard progress to a dashboard. Require a written runbook per state with rollback commands. This is the 18-month program that distinguishes L5 from L6.

Governance rule for all six. Every exercise ships with an observability package (metrics, dashboards, alerts), a runbook (normal operation, common failures, rollback), and an ADR documenting the design decisions. If any of the three is missing, the exercise is not complete regardless of test coverage. This is the bar the database-platform charter enforces.

Final staff challenge. Take Exercise 6 and make the reshard survive a 30-minute coordinator outage without operator intervention. You will find the answer requires durable workflow state, idempotent per-vNode operations, and a heartbeat timeout that conservatively fails safe. The exercise that forces these three constraints is the one that produces production-grade code. Most candidates do not attempt it, which is why resharding incidents keep happening.
