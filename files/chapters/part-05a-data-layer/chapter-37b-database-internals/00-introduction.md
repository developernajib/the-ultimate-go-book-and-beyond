# Chapter 37B: Database Internals - What Every Senior Engineer Must Know

*You can't tune what you don't understand. Every query you write eventually becomes a page read, a WAL write, and a lock acquisition. Knowing that chain is what separates a senior engineer from a staff engineer.*

Every production incident that begins with "the database is slow" is actually a story about misunderstood internals. The query planner chose a sequential scan because stale statistics made the index look unselective. The write latency spiked because a checkpoint flushed gigabytes of dirty pages in a single burst. The read replica fell behind because a long-running transaction on the primary held back the replication slot. Each of these failures has a mechanical explanation rooted in how databases actually work - in B-trees, Write-Ahead Logs, MVCC visibility chains, and vacuum cycles. Engineers who understand these mechanisms diagnose and resolve incidents in minutes. Those who do not escalate tickets and hope for autovacuum to quietly fix things overnight.

For Go engineers specifically, database internals knowledge unlocks a different tier of system design. Choosing between a UUID and a BIGSERIAL primary key is not an aesthetic decision - it is a choice between random and sequential B-tree insertion patterns that determines whether your index fragments at scale or stays compact. Deciding whether to use a GIN index or a partial B-tree index on a JSONB column determines write amplification and update overhead across millions of rows. Understanding MVCC means knowing exactly why `SELECT COUNT(*)` is expensive in PostgreSQL, why long transactions poison the dead tuple accumulation rate, and why connection pool sizing interacts with lock contention in ways that naive horizontal scaling cannot fix. These are the decisions that separate schema designs that crumble at 10 million rows from those that serve 10 billion rows without a full rewrite.

This chapter is structured as a systematic tour from storage primitives to application-level implications. You will start with the physical layer - how B-trees store and retrieve data, how LSM-trees differ, and why each suits different workloads. From there you move to the durability layer - how the Write-Ahead Log guarantees crash recovery and enables point-in-time restore and replication. Then MVCC: how PostgreSQL allows concurrent readers and writers without blocking, and the vacuum machinery that prevents unbounded space growth. Finally, you will apply this foundation to practical query analysis, index selection, isolation level choice, and connection pool tuning.

**What you'll learn in this chapter:**
- How B-tree and LSM-tree index structures work from first principles, including insertions, deletions, page splits, and LSM compaction strategies
- How PostgreSQL's Write-Ahead Log guarantees durability, enables streaming replication, and powers point-in-time recovery
- How MVCC visibility rules work, how dead tuples accumulate, and why autovacuum configuration is a performance-critical concern
- How to read and interpret `EXPLAIN ANALYZE` output including actual vs. estimated row counts, cost model breakdowns, and buffer hit rates
- How to choose the correct index type (B-tree, GIN, GiST, BRIN, partial, expression) for a given access pattern and data distribution
- How the four transaction isolation levels differ and the specific anomalies (dirty reads, non-repeatable reads, phantom reads) each prevents
- How to size a connection pool correctly and understand the trade-offs between PgBouncer session, transaction, and statement pooling modes
- How to diagnose and resolve common production pathologies: bloat from dead tuples, checkpoint write spikes, and query plan regressions after data distribution shifts

**Why this matters at scale:**
Teams that operate Postgres at global scale treat this knowledge as a prerequisite, and the best public documentation proves it: GitLab publishes its Postgres tuning and bloat-management runbooks in the open, and Figma's database-scaling series walks through decisions that only make sense once you understand MVCC and WAL mechanics. Index and isolation-level choices made against a WAL-amplification budget, rather than by habit, are exactly the practice this chapter's internal mechanics enable.

**Prerequisites:** Chapter 36 (Database Migrations) and Chapter 37 (Connection Pooling and Sharding). Basic familiarity with SQL and Go's `database/sql` package.

### Junior to FAANG: Prerequisite Gaps and First Job Context

If you are reading this from a junior position the single biggest gap is almost always the mental model of a page. A database does not read rows, it reads 8 KB pages (Postgres, default) or 16 KB pages (InnoDB, default) from disk into a shared buffer cache. Every query is a sequence of page reads and every write is ultimately a page modification plus a WAL record. Once that mental model lands the rest of the chapter clicks into place. A worked example to anchor it: a `SELECT * FROM users WHERE id = 42` on a 10 million row table with a B-tree primary key touches roughly four pages (three index pages plus one heap page) and returns in under a millisecond when cached. The same query without an index touches every heap page in the table, which at 100 bytes per row is around 125000 pages or 1 GB of buffer traffic. That factor of 30000 is not a micro-optimization, it is the difference between a working product and an outage.

The interview entry point for this material is almost always a variant of "walk me through what happens when I run `INSERT INTO orders VALUES (...)`". A junior answer stops at "it writes to the table". A hiring-bar answer walks through: parse and plan, acquire row-level lock, write WAL record, modify the heap page in shared buffers, update every index, mark the page dirty, return to the client after the WAL flush, and much later a checkpoint writes the dirty page to the data file. If you can narrate that sequence fluently you have already cleared the bar for most mid-level database rounds at FAANG companies.

For your first job the practical advice is narrow. Learn to read `EXPLAIN (ANALYZE, BUFFERS)` output on Postgres or `EXPLAIN FORMAT=JSON` on MySQL before you learn anything exotic. Ninety percent of the database problems you will be handed in your first two years are a missing index, a bad join order caused by stale statistics, or a transaction held open by an idle client. All three are visible in plan output if you know what to look for. The rest of this chapter gives you the vocabulary to name what you see.

### Senior at FAANG: Staff and Principal Framing

At staff level the introduction to database internals is not about knowing the mechanics, it is about using the mechanics to set organizational policy. Every design review you attend will contain at least one decision that hinges on storage engine choice, index strategy, or durability guarantee, and the staff engineer in the room is expected to make that choice explicit rather than let it accrete by default. The canonical trap is a team picking Postgres because "we already run Postgres" for a workload that is 95 percent append-only time-series with point lookups by recent key, which is a near-textbook LSM workload. The cost of that wrong default shows up two years later as WAL volume exceeding replication bandwidth, autovacuum falling permanently behind, and a forced migration to a time-series store under production pressure.

Principal-level framing goes one step further and treats the storage engine as a distributed systems primitive rather than a black box. A B-tree backed engine like Postgres or InnoDB has read-optimized properties and a write amplification profile dominated by random I/O and index maintenance, which interacts poorly with cloud block storage billed per IOPS. An LSM engine like RocksDB, ScyllaDB, or CockroachDB amortizes writes into sequential SSTable flushes and pays the cost back as compaction CPU and read amplification mitigated by bloom filters. The choice propagates all the way up to capacity planning. A Postgres fleet sized for peak write IOPS needs provisioned IOPS storage. A RocksDB fleet sized for the same write rate needs CPU headroom for compaction and a carefully tuned block cache. Getting this wrong at the platform layer costs seven figures a year on any substantial service.

The other thing senior engineers do with this material is set the durability contract for the company. Synchronous replication, `synchronous_commit = remote_apply`, group commit with short `commit_delay`, and WAL archiving to object storage each have specific latency and RPO implications, and those implications need to be written down as an SLO rather than assumed. The engineers who get promoted to principal on the database track are the ones who can draw the curve from `fsync` cost through group commit batching through replication lag to the business-visible RPO number, and who can defend each point on that curve against a cost-cutting VP who wants to turn fsync off on the replicas. That is the real scope of this chapter at senior level.
