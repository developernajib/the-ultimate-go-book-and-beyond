# Chapter 34: Query Builders and ORMs

*Abstractions are not free. The cost of an ORM is paid in the queries you didn't write, the N+1 bugs you didn't see, and the migration conflicts you didn't expect.*

Every engineering team writing database code faces the same tradeoff: raw SQL gives you absolute control and transparency at the cost of verbosity and manual type mapping, while ORMs accelerate development at the cost of abstraction leakage, hidden query generation, and framework lock-in. Getting this choice wrong is expensive. A team that reaches for a heavy ORM to build a CRUD API may find themselves fighting the ORM's conventions when they need a complex analytical query. A team that writes every query by hand may find themselves drowning in boilerplate when the schema evolves across dozens of tables.

Go's database tooling ecosystem has matured into a spectrum of options, each occupying a deliberate position. As of Go 1.27 (August 2026), `sqlc` has become the canonical choice for SQL-first teams: you write plain SQL, and it generates type-safe Go code at compile time, with first-class `pgx/v5` integration. `squirrel` and `goqu` give you a programmatic query builder that generates SQL dynamically, solving the "build a search API with 12 optional filters" problem without string concatenation. `bun` (uptrace/bun) is the modern, explicit-by-design ORM that trades GORM's magic for predictable SQL. `ent` (Meta-backed) takes a schema-as-code, graph-first approach that scales well to large relational models. GORM remains the most popular ORM for rapid CRUD, but its silent N+1 problems, Preload-vs-Joins semantics, and hook ordering surprises have pushed many teams toward sqlc or bun. `sqlboiler` generates fully typed code from a live database schema for teams that treat the schema as the source of truth. The right answer depends on your team's SQL fluency, the complexity of your data access patterns, and how much magic you are willing to accept in exchange for speed.

This chapter gives you the practical knowledge to make that decision confidently and to use each tool effectively. You will learn how `sqlc` eliminates an entire class of runtime type errors, how GORM's association system works internally (including the N+1 trap), how to build safe dynamic queries with `squirrel`, and how to wrap any of these tools in a repository interface that keeps your business logic testable regardless of which database library is underneath.

**What you will learn:**
- How `sqlc` works end-to-end: defining queries in `.sql` files, running code generation with the `pgx/v5` driver, and integrating type-safe generated code into a Go service
- How `bun` builds queries with explicit `NewSelect`/`NewInsert` methods, and why its predictable SQL generation is preferred over GORM in new projects
- How `ent` models data as a graph with schema-as-code and generates a strongly typed client for complex relational traversals
- How to structure a GORM application with models, associations, hooks, and scopes while avoiding Preload N+1 surprises, hook-ordering pitfalls, and soft-delete footguns
- How N+1 query problems arise in ORMs, how to detect them (SQL logging, `explain`, query counters in tests), and how to fix them with eager loading, explicit joins, or DataLoader batching
- How to build dynamic, composable queries with `squirrel` for search APIs with optional filters, whitelisted sort columns, and cursor pagination
- How to implement the repository pattern as a Go interface, making data access swappable and unit-testable with mocks and fakes
- How `sqlboiler` generates fully type-safe model code from an existing database schema and when database-first generation is preferable
- How to benchmark different database access approaches and measure the real performance cost of abstraction layers
- How to choose between raw SQL, query builders, and ORMs based on team size, query complexity, and maintenance requirements

**Why this matters at scale:**
Many Go-heavy infra teams converge on a hybrid approach: `sqlc`-generated code for hot read paths where type safety and query predictability are critical, and query builders for the dynamic filtering APIs behind merchant and driver dashboards, avoiding the ORM overhead on queries that run millions of times per hour. Brandur Leach's widely-cited post "How We Went All In on sqlc/pgx for Postgres + Go" articulates the 2026 consensus among Go-heavy infra teams: ORMs only perform well on easy CRUD, and the more complex the query, the harder it is to express cleanly through them. sqlc plus pgx flips that calculus. You write the SQL you would have written anyway, and you get type-safe Go as a byproduct.

### Junior → FAANG: Entering the Query Builder and ORM Conversation

If you are coming from Rails ActiveRecord, Django ORM, or Hibernate, your instinct is to reach for a class that magically syncs with a table. Go's community pushes back on that instinct, and the interview question you will hit at Stripe, Datadog, or any infra-heavy shop is: "How do you access Postgres from Go, and why not GORM?" The senior answer is that Go values explicitness, and an ORM that hides the SQL hides the performance profile. Your prerequisite gaps before tackling this chapter are: being able to read an `EXPLAIN ANALYZE` plan, knowing what a prepared statement is, understanding `database/sql` versus `pgx/v5` (native Postgres protocol, no driver wrapping), and having written at least one nontrivial join by hand.

Worked example. A product-listing endpoint returns `Product` rows plus their `Category` name. In Rails you write `Product.includes(:category).limit(20)` and move on. In Go with sqlc you write the SQL: `SELECT p.id, p.name, c.name AS category_name FROM products p JOIN categories c ON c.id = p.category_id LIMIT 20`, place it in `query.sql` with a `-- name: ListProductsWithCategory :many` tag, run `sqlc generate`, and call `q.ListProductsWithCategory(ctx)` which returns `[]ListProductsWithCategoryRow` with typed fields. Compilation fails if you rename a column. No reflection at runtime. No N+1 possible because the join is literally in the source. That transparency is the first-job superpower: your code review shows the exact query the database will run.

Interview entry-point. When asked "ORM or not," do not answer dogmatically. Say: "For CRUD-heavy internal tools I would accept GORM or bun to move fast. For user-facing read paths I want sqlc because I want the query in source control, reviewable, with `EXPLAIN` plans I can attach to the PR. For dynamic filter APIs I want squirrel or goqu because string-concatenating SQL is a Bobby Tables bug waiting to happen." That answer shows you understand the tool is a function of the workload, which is exactly what the interviewer is probing.

### Senior @ FAANG: Staff-Level Decision Framework for Data Access Layers

At staff and principal level the question is never "which ORM," it is "what is the contract between the service and the database, who owns the schema, how do we evolve it, and what is the blast radius when the query planner changes its mind." The decision matrix across sqlc, GORM, ent, sqlboiler, bun, and squirrel is not a feature checkbox chart, it is a statement about your engineering culture.

Decision matrix. sqlc wins when the team is SQL-fluent, the schema is stable enough to commit to migrations, and you want compile-time safety with zero runtime reflection cost. The generated code is plain `pgx` calls underneath, so there is no framework to blame when a query misbehaves. GORM wins when the team is junior-heavy, the domain is CRUD-dominant (admin panels, internal tools, early-stage startup MVPs), and the productivity delta on week one beats the N+1 bugs you will eat on month six. ent wins when your domain is a graph and you want a schema-as-code workflow that generates both the migration and the client. sqlboiler wins when the database is the source of truth and owned by a separate DBA team, so you reflect schema changes by regenerating. bun wins when you want an ORM feel without GORM's magic, with explicit query construction and a predictable SQL output. squirrel wins as a composition layer underneath any of the above for dynamic `WHERE` clauses.

Compile-time safety versus runtime reflection is the axis that divides these tools. sqlc and sqlboiler generate code, so a schema drift becomes a compile error. GORM and ent (at the client layer) use reflection, so the same drift becomes a 500 at runtime, caught only by integration tests. At Google and Meta scale this is non-negotiable: reflection-based ORMs are effectively avoided in latency-sensitive services because the schema invariants must be enforced by the type system. Across large Go shops the observable pattern is a preference for code-generation approaches like sqlc, with some (Uber, for example) running a custom in-house layer that predates sqlc but expresses the same philosophy. Where a Rails or Django monolith owns the primary product, the newer Go service teams frequently reach for sqlc rather than a reflection-based ORM.

Query plan visibility is the other axis. An ORM that generates `SELECT * FROM t WHERE a = ? AND (b = ? OR b IS NULL)` hides the planner's choice to do a seq scan when the index is partial. sqlc puts the SQL in a file next to the code, which means a senior reviewer can run `EXPLAIN (ANALYZE, BUFFERS)` on the exact string during PR review. This is why FAANG-scale teams make "attach the EXPLAIN plan to the PR" a review standard for any new query on a hot path, and it is structurally easier with sqlc than with any ORM.

N+1 detection belongs in code review, not production. With sqlc, a loop that calls a per-row query is visible in the diff because the query name appears inside the loop body. With GORM, the same loop looks like `db.First(&user).Related(&posts)` and the N+1 is invisible until you enable query logging in staging. Principal-level practice: write a linter or a `go/analysis` pass that flags `.Preload`, `.Related`, or per-row SQL calls inside `for` loops. Pair it with a test helper that counts queries using `pgx`'s query tracer and fails the test if a request exceeds a budget. This is how Datadog, Honeycomb, and similar observability shops keep regressions out.

sqlc codegen in CI. The pipeline is: `sqlc vet` validates queries against a live Postgres using `sqlc/dev` plus pgxpool, `sqlc diff` fails the build if generated code is stale, `sqlc generate` produces the typed code, `golangci-lint` runs, then `go test ./...` runs against a `testcontainers-go` Postgres. The plugin ecosystem matters for polyglot shops: `sqlc-gen-python`, `sqlc-gen-kotlin`, and `sqlc-gen-typescript` let a single `queries.sql` feed a Go backend, a Kotlin Android client, and a TypeScript Next.js surface, all type-safe against the same schema. That is a staff-level architectural win because it collapses three type drifts into one.

GORM v2 pain points, cataloged honestly. Magic conventions: the struct field `CreatedAt time.Time` is auto-populated, but only if you name it exactly that. Soft delete surprises: `gorm.DeletedAt` changes every query to add `WHERE deleted_at IS NULL`, which silently breaks partial indexes and confuses new engineers reading the SQL log. Preload N+1: `db.Preload("Posts").Find(&users)` issues two queries, but `db.Preload("Posts.Comments.Author")` issues four, and the developer rarely notices until p99 blows up. Hook side effects: `BeforeSave` hooks run inside the transaction, and a hook that calls an external service holds the row lock for the HTTP round trip. Open transactions on goroutine leaks: `db.Begin()` without deferred rollback leaks the connection. When GORM wins: the admin dashboard behind a feature flag, the migration from a Python side service, the MVP that needs to ship next week. Do not let a principal-level purity argument block a GORM choice when the workload is CRUD and the team is three engineers.

sqlboiler's database-first philosophy inverts sqlc's query-first model. You point it at a live database, it introspects the schema, and it generates a full object graph with getters, setters, and relationship eager-loading. The trade-off is that your Go code becomes a consumer of the DBA's schema decisions, which is the right model in regulated industries (fintech, healthcare) where schema changes are gated by a DBA team and Go services must not drive migrations. sqlc's query-first model is the right model when the app team owns the schema.

Repository pattern ADR with ORMs. Write an ADR that says: "The repository interface lives in `internal/domain`, the implementation lives in `internal/adapter/postgres`, and the implementation is free to use sqlc, GORM, or raw SQL without changing the interface." This is hexagonal architecture with driver ports. The business logic depends on `UserRepository`, not on `*gorm.DB`. The test double is a fake implementation backed by an in-memory map. The integration test uses `testcontainers-go` to spin a real Postgres. The mock-db approach (sqlmock) is a junior-trap: it tests that your code calls the SQL you think it calls, not that the SQL does what you think it does. Principal-level practice: mock-db is banned, real-db integration tests via `testcontainers-go` or `pgtestdb` are required, and unit tests target the repository interface.

ORM escape hatches for hot paths. Every ORM supports raw SQL. The rule is: if a query shows up in the top 10 of `pg_stat_statements` by total time, rewrite it as raw SQL (or sqlc) regardless of what the rest of the repository uses. This is what the Crunchy Data postmortem means by "ORMs only perform well on easy CRUD." Hybrid repositories are normal and correct.

Batch operations through ORMs are where hidden costs compound. GORM's `CreateInBatches` issues one multi-row `INSERT`, but `FindInBatches` still materializes each batch in memory and runs hooks per row. sqlc with pgx's `CopyFrom` beats any ORM by an order of magnitude on bulk writes. Connection ownership: ORM-managed pools hide the pool configuration, which becomes a problem when you need to tune `MaxConns`, `MaxConnIdleTime`, or `HealthCheckPeriod` under load. App-managed pools via `pgxpool.New` give you the knobs. Principal-level default: own the pool, pass it into whatever query library you use, never let a library own the pool.

FAANG stance, explicit. Google's internal Go services talk to Spanner and BigQuery through dedicated clients, not ORMs. ent, the graph-shaped entity framework, was authored inside Meta and open-sourced, and that pedigree tells you exactly which domains it fits. Across the rest of the industry's large Go shops, the observable pattern in public repos, talks, and job postings is sqlc or raw SQL for new services, with full ORMs confined to legacy code. The common thread: at scale, the query is the source of truth, and the Go code is a type-safe wrapper over it. Internalize that and the chapter's tool choices become obvious.
