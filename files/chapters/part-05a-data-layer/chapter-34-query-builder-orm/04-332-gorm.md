## 34.2 GORM

### Setup and Basic Usage

GORM connects to the database through a dialect driver (here `gorm.io/driver/postgres`), and you define models as Go structs with struct tags controlling column types, indexes, and defaults. The `gorm.Model` embed or individual fields like `CreatedAt` and `DeletedAt` add automatic timestamping and soft-delete behavior. `AutoMigrate` creates or alters tables to match your struct definitions, useful in development, though production systems should use versioned migrations.

```go
package main

import (
    "log"
    "time"

    "gorm.io/driver/postgres"
    "gorm.io/gorm"
    "gorm.io/gorm/logger"
)

type User struct {
    ID        uint           `gorm:"primarykey"`
    Name      string         `gorm:"size:255;not null"`
    Email     string         `gorm:"uniqueIndex;size:255;not null"`
    Status    string         `gorm:"size:50;default:active"`
    Orders    []Order        `gorm:"foreignKey:UserID"`
    CreatedAt time.Time
    UpdatedAt time.Time
    DeletedAt gorm.DeletedAt `gorm:"index"`
}

type Order struct {
    ID         uint
    UserID     uint
    TotalCents int64
    Status     string
    CreatedAt  time.Time
}

func main() {
    dsn := "host=localhost user=postgres password=secret dbname=myapp sslmode=disable"

    db, err := gorm.Open(postgres.Open(dsn), &gorm.Config{
        Logger: logger.Default.LogMode(logger.Info),
    })
    if err != nil {
        log.Fatal(err)
    }

    // Auto migrate
    db.AutoMigrate(&User{}, &Order{})

    // CRUD operations
    user := User{Name: "Alice", Email: "alice@example.com"}
    db.Create(&user)

    var found User
    db.First(&found, user.ID)

    db.Model(&user).Updates(User{Name: "Alice Smith"})

    db.Delete(&user)
}
```

### Advanced Queries

GORM's query API chains method calls to build SQL incrementally. `Where` accepts raw SQL fragments with placeholders, struct values (zero values are skipped), or map conditions. `Preload` triggers eager loading of associations in a separate query, while `Joins` generates a SQL JOIN. For aggregations and custom result shapes, `Select` with `Scan` maps results into an ad-hoc struct rather than the model itself.

```go
// Find with conditions
var users []User
db.Where("status = ?", "active").
    Order("created_at DESC").
    Limit(10).
    Find(&users)

// Or using struct
db.Where(&User{Status: "active"}).Find(&users)

// Complex conditions
db.Where("created_at > ? AND status IN ?", time.Now().AddDate(-1, 0, 0), []string{"active", "pending"}).
    Find(&users)

// Select specific fields
db.Select("id", "name", "email").Find(&users)

// Joins
var usersWithOrders []struct {
    User
    TotalOrders     int
    TotalSpentCents int64
}

db.Model(&User{}).
    Select("users.*, COUNT(orders.id) as total_orders, SUM(orders.total_cents) as total_spent_cents").
    Joins("LEFT JOIN orders ON users.id = orders.user_id").
    Group("users.id").
    Scan(&usersWithOrders)

// Preload (eager loading)
var user User
db.Preload("Orders").First(&user, 1)

// Preload with conditions
db.Preload("Orders", "status = ?", "completed").First(&user, 1)

// Nested preload
db.Preload("Orders.Items").First(&user, 1)
```

### GORM Footguns to Know Before You Ship

GORM is productive for CRUD and still the most popular Go ORM in 2026, but it carries a set of well-documented surprises that bite teams in production. Learn them before they show up in an incident:

- **`Preload` is two queries, not one.** `db.Preload("Orders").Find(&users)` issues one SELECT for users and then a second SELECT against `orders WHERE user_id IN (...)`. That is fine until you nest it: `Preload("Orders.Items.Product")` can become four round-trips. If you are in a hot path, use an explicit `Joins` and `Scan` into a flat DTO instead.
- **`Joins` does not populate the association field.** A common mistake is expecting `db.Joins("Orders").Find(&users)` to fill `User.Orders`. It does not: it issues a JOIN for filtering and leaves the slice empty. For eager loading you still need `Preload`. For filter-by-relation plus eager load, you need both, and issue #6988 on the GORM repo documents cases where combining them reintroduces an N+1.
- **Hooks fire in unexpected orders.** `BeforeSave`, `BeforeCreate`, `BeforeUpdate`, `AfterSave` have a precedence that is not always obvious, particularly with associations. Mutations inside hooks can also trigger other hooks, producing recursive behavior. Keep hooks strictly for cross-cutting concerns (audit, timestamps) and put business rules in the service layer.
- **Zero values are silently skipped.** `db.Where(&User{Status: ""}).Find(&users)` drops the `Status` filter because `""` is the zero value. Use `map[string]any{"status": ""}` or raw SQL placeholders to pass zero values intentionally.
- **Soft delete changes every query.** Embedding `gorm.DeletedAt` adds `deleted_at IS NULL` to every SELECT globally. This is useful, but it surprises developers who write raw SQL in the same codebase and see row counts disagree. Document it loudly and use `.Unscoped()` when you really mean "include deleted".
- **`Updates` with a struct skips zero fields.** Just like `Where`. Use `Select("name", "email").Updates(...)` or a map to update to zero values.
- **Global `Logger: logger.Default.LogMode(logger.Info)` is fine in dev, noisy in prod.** Use `logger.Silent` in production and attach a slow-query logger via `Callback().Query().After("gorm:query")` instead.
- **`AutoMigrate` is not a migration tool.** It is best-effort schema sync: it will add columns but will not drop them, will not reorder them, and cannot express renames. Use it only in development. In production, use golang-migrate, goose, or Atlas with versioned SQL files.

The generics API introduced in GORM v1.30 (`gorm.G[User](db).Where(...).Find(ctx)`) closes some of these gaps with type-safe association loading and `LimitPerRecord` for has-many eager loading, but it is a new surface layered on top of the classic API, not a replacement.

### Transactions

A database transaction groups multiple statements into an atomic unit of work: either all succeed and commit, or all fail and roll back. In Go, transactions begin with `db.BeginTx`, and a deferred function checks the error to call either `tx.Commit` or `tx.Rollback`.

```go
type Account struct {
    ID           uint
    BalanceCents int64
}

func transferMoney(db *gorm.DB, fromID, toID uint, amountCents int64) error {
    return db.Transaction(func(tx *gorm.DB) error {
        var fromAccount Account
        if err := tx.Clauses(clause.Locking{Strength: "UPDATE"}).
            First(&fromAccount, fromID).Error; err != nil {
            return err
        }

        if fromAccount.BalanceCents < amountCents {
            return errors.New("insufficient balance")
        }

        if err := tx.Model(&fromAccount).
            Update("balance_cents", gorm.Expr("balance_cents - ?", amountCents)).Error; err != nil {
            return err
        }

        if err := tx.Model(&Account{}).
            Where("id = ?", toID).
            Update("balance_cents", gorm.Expr("balance_cents + ?", amountCents)).Error; err != nil {
            return err
        }

        return nil
    })
}
```

### Scopes

GORM scopes encapsulate reusable query fragments as functions with signature `func(*gorm.DB) *gorm.DB`. Applying named scopes via `db.Scopes(...)` composes filters, ordering, and pagination without duplicating query logic across repositories.

```go
// Define reusable scopes
func Active(db *gorm.DB) *gorm.DB {
    return db.Where("status = ?", "active")
}

func Recent(days int) func(*gorm.DB) *gorm.DB {
    return func(db *gorm.DB) *gorm.DB {
        return db.Where("created_at > ?", time.Now().AddDate(0, 0, -days))
    }
}

func Paginate(page, pageSize int) func(*gorm.DB) *gorm.DB {
    return func(db *gorm.DB) *gorm.DB {
        offset := (page - 1) * pageSize
        return db.Offset(offset).Limit(pageSize)
    }
}

// Usage
var users []User
db.Scopes(Active, Recent(30), Paginate(1, 20)).Find(&users)
```

### Junior → FAANG: Learning GORM Without Learning the Bad Habits

GORM is the easiest Go database library to pick up and the easiest to misuse. Your first-job exposure will be a codebase where a previous engineer wrote `db.Where("id = ?", id).First(&user)` everywhere, and the p99 latency is bad because nobody ran `EXPLAIN` on the generated SQL. Your first win is to turn on SQL logging in a staging environment, copy three slow queries into a text file, run `EXPLAIN ANALYZE` on each, and write up what you found. That exercise teaches you more about GORM than any tutorial.

Worked example of the N+1 trap. Code looks innocent: `db.Find(&users)` then `for _, u := range users { db.Model(&u).Association("Orders").Find(&u.Orders) }`. SQL log shows 1 + N queries for N users. Fix: `db.Preload("Orders").Find(&users)` collapses to 2 queries. Better fix if the join fan-out is small: `db.Joins("Orders").Find(&users)` issues one query, but remember it does not populate the slice (see the Footguns section). Best fix if you need a specific projection: drop to raw SQL via `db.Raw("SELECT ...").Scan(&result)` and own the shape.

Interview entry-point. "Find the N+1 in this snippet." If the snippet has `.Preload` inside a `for` loop over another `Find`, that is the N+1. The fix is to flatten: fetch all parent IDs first, then one `Preload` with `WHERE parent_id IN (?)`. Say that out loud during the interview. Then mention you would add a query-count assertion in the test so the regression cannot return silently.

First-job context. You will inherit GORM models with `gorm.DeletedAt` and wonder why a `COUNT(*)` in psql disagrees with what the app returns. That is the soft-delete scope at work. Use `.Unscoped()` when you debug. Document the soft-delete contract in a CONTRIBUTING note so the next engineer does not lose a day on the same discovery. That kind of institutional-knowledge capture is what distinguishes a junior who gets promoted from one who does not.

### Senior @ FAANG: When GORM Wins, When It Loses, and How to Put It in a Cage

The senior stance on GORM is not "never use it," it is "know exactly when it earns its keep and where to escape it." GORM wins on CRUD-heavy admin panels, internal tools behind feature flags, and early-stage startup code where the velocity delta on weeks one through four beats the N+1 cleanup on month six. GORM loses on hot read paths, any query with a window function or CTE, bulk writes above a few hundred rows, and anywhere the query plan matters more than the developer's convenience. A principal-level architecture uses GORM where it wins and raw SQL or sqlc where GORM loses, within the same service, behind the same repository interface.

GORM v2 pain points, cataloged for a postmortem-ready memory. Magic conventions: field name `CreatedAt` triggers auto-population, but `CreatedOn` does not. The convention is a silent contract that new engineers trip over. Soft delete surprises: `gorm.DeletedAt` adds `deleted_at IS NULL` to every SELECT globally, which breaks partial indexes (`CREATE INDEX ... WHERE active = true`) because the planner's row estimates no longer match the index's predicate. Preload N+1: `Preload("A.B.C.D")` issues four queries, and each `IN` list can grow unbounded, causing parser OOM on Postgres for large parent sets. Hook side effects: `BeforeSave` runs inside the transaction, and a hook that calls an external HTTP service holds the row lock for the round trip. Connection leak via `db.Begin()` without `defer tx.Rollback()` leaks the connection, which pgbouncer does not release until client disconnect. Zero-value filter skipping: `Where(&User{Active: false})` silently drops the filter and returns all rows because `false` is the zero value of `bool`, which has shipped as a security bug more than once (listing disabled users to non-admin roles).

When GORM's productivity actually wins. The honest scenario: a five-engineer startup building an admin panel that reads and writes 12 tables with simple relationships, where time to market beats long-term query discipline. GORM plus AutoMigrate plus hooks for audit logging ships in two weeks. The same service in sqlc ships in three weeks because every query needs a `.sql` file and a regeneration step. If your runway is 18 months and you need feature velocity, the productivity delta is real. The principal's job is to know when to pay the delta back: at around 30 tables or when p99 on a user-facing endpoint matters, migrate the hot paths to sqlc and leave the CRUD on GORM. This is the hybrid that works at Shopify, at several YC companies, and is documented in the bun project's own "why we built bun" readme as the observed migration pattern.

Putting GORM in a cage. The discipline that makes GORM tolerable at scale: (1) repository interface with a small method set, so GORM stays below the interface and service code never sees `*gorm.DB`. (2) Query-count assertions in tests, with a budget per HTTP handler (for example, "list-users returns at most 2 queries"). (3) Slow-query callback in production that emits an OpenTelemetry span with the query text for anything over 50 ms. (4) Lint rule (go/analysis) forbidding `.Preload` inside a loop body. (5) Ban on `AutoMigrate` in production, migrations run via goose or atlas. (6) Ban on business logic in hooks, hooks only do audit and timestamps. (7) Documented soft-delete contract with explicit `.Unscoped()` guidance. (8) Escape hatch to raw SQL via `db.Raw(...).Scan(...)` for hot paths, used freely.

GORM v1.30 generics API assessment. `gorm.G[User](db).Where(...).Find(ctx)` is an improvement because it returns a typed `[]User` rather than scanning into a pointer, and `LimitPerRecord` fixes the has-many eager-loading pathology where one parent with 10k children blows up memory. But the generics API layers on top of the reflection engine, it does not replace it. The underlying query still goes through GORM's reflection-based scanner. Performance is unchanged. Type safety is improved at the call site. A principal evaluating the upgrade should treat it as "better syntax for the parts of GORM you keep," not "GORM is now sqlc." If you want compile-time guaranteed SQL, use sqlc. If you want GORM with better call-site ergonomics, use the generics API.

Hook side effects and the transaction lock problem. `BeforeSave` inside a transaction is a trap when the hook does I/O. Example: audit hook calls an HTTP API to send a notification. The row lock (from `FOR UPDATE` or the implicit lock from the UPDATE statement) is held for the duration of the HTTP call. Under burst load, the connection pool and the lock queue exhaust together. Postmortem-ready rule: hooks are synchronous and fast, any side effect goes to an outbox table within the same transaction, a separate worker drains the outbox after commit. That outbox pattern is the standard solution and it is completely compatible with GORM as long as the hook writes to a table instead of calling an external service.

Preload versus Joins, with numbers. Preload is two queries with an `IN` list of parent IDs. For N=10k parents, the IN list is 10k entries, which Postgres's parser handles but the planner may downgrade to a seq scan. Joins is one query with a JOIN, cardinality is N times average fan-out, which for a one-to-many relationship can produce more rows than the parent count. Rule of thumb: if fan-out is bounded and small (under 10), Joins is cheaper. If fan-out is unbounded or variable, Preload with a Limit or LimitPerRecord is safer. Measure before choosing. GORM's documentation does not give you numbers, so attach EXPLAIN ANALYZE output to the PR for any Preload introduced on a hot path.

Testing GORM at senior level. sqlmock is still common for GORM tests and still a trap because it tests the generated SQL string, not the behavior. Use testcontainers-go with a Postgres container, spin it once per package, run parallel tests with pgtestdb-style template cloning for speed. For the repository interface tests, fake implementations in memory suffice for unit tests, with the real-Postgres tests covering the GORM-backed implementation. Resist the temptation to unit-test GORM's reflection logic, that is GORM's own test suite, not yours.

Migration path off GORM when needed. When a service outgrows GORM, the migration is gradual. Introduce sqlc alongside GORM, share the same `*pgxpool.Pool`, move queries one handler at a time, starting with the highest-traffic read path. GORM and sqlc can coexist on the same pool because sqlc's generated code is thin over pgx. The service's repository interface does not change. The adapter implementation becomes half sqlc, half GORM. This gradualism is a commonly described migration path and lets a team de-risk the move across a release cycle rather than a big-bang rewrite.
