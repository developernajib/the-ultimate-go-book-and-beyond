## Interview Questions

**Q: How do namespaces provide isolation and what are the 7 types?**

A: Linux namespaces create isolated views of global system resources for a group of processes - each namespace type wraps a different resource. The 7 types: (1) **PID** - separate PID numbering. Container PID 1 is the host's PID N. (2) **NET** - separate network stack, interfaces, IP addresses, routing tables, and port numbers. (3) **MNT** - separate filesystem mount tree. The container sees a different root filesystem. (4) **UTS** - separate hostname and NIS domain name. (5) **IPC** - separate System V IPC objects and POSIX message queues. (6) **USER** - separate UID/GID numbering. Container UID 0 maps to an unprivileged host UID. (7) **CGROUP** - separate view of the cgroup hierarchy. Namespaces are created with `clone()` flags (`CLONE_NEWPID`, etc.) or `unshare()`. Every container runtime creates all 7 for isolation.

**Q: What's the difference between cgroups and namespaces?**

A: They solve different problems and are complementary. **Namespaces** provide *isolation* - they create the illusion that a process group is in its own OS, controlling what resources the group can see and interact with. A process in a PID namespace cannot send signals to processes outside it. A process in a NET namespace cannot see host network interfaces. **cgroups** provide *resource control* - they limit how much CPU, memory, block I/O, and other resources a process group can consume. cgroups don't hide resources. They cap them. Docker and containerd always use both: namespaces for isolation, cgroups for resource limits. Without cgroups, a single container could starve the entire host of memory.

**Q: How does overlay filesystem work and why does it need upper, lower, and work directories?**

A: OverlayFS presents a merged view of multiple directory trees. **Lower** is one or more read-only layers (the image layers, stacked). **Upper** is a writable layer (the container's working changes). **Work** is an internal scratch directory for atomic operations on the upper layer - it must be on the same filesystem as upper. Read semantics: check upper first, then search lower layers top-to-bottom. Write semantics: if the file doesn't exist in upper, copy it from lower (copy-on-write), then modify the copy in upper. Delete semantics: create a whiteout file in upper that masks the lower layer's file. The container image (lower layers) is never modified - all changes are in the upper layer and discarded when the container is removed.

**Q: What is seccomp and how does it reduce the attack surface of a container?**

A: Seccomp (Secure Computing Mode) is a Linux kernel feature that filters which system calls a process is allowed to make. Without seccomp, a containerized process with a kernel vulnerability exploit can call any syscall available to its UID - including dangerous ones like `ptrace`, `keyctl`, `perf_event_open`, or `socket` with exotic protocols. A seccomp profile defines an allowlist (default-deny + explicit allows) or denylist (default-allow + explicit denials) of syscall numbers and argument patterns. Docker's default seccomp profile blocks ~44 syscalls including `ptrace`, `mount`, `reboot`, `kexec_load`, and `create_module`. In Go, you apply a seccomp filter before `exec()` using `golang.org/x/sys/unix.SyscallSeccomp` or via `go-seccomp-bpf`. Seccomp filters are enforced by the kernel's BPF verifier - they cannot be bypassed by a userspace exploit.

**Q: What are Linux capabilities and which ones should a container drop?**

A: Linux capabilities split the monolithic `root` privilege into ~40 distinct capabilities. A process can have a subset. Default Docker capabilities include `CAP_NET_BIND_SERVICE` (bind to ports < 1024), `CAP_KILL` (send signals), `CAP_CHOWN` (change file ownership), and `CAP_SETUID/SETGID`. Capabilities that should be dropped for most production containers: `CAP_SYS_ADMIN` (broad admin - effectively root, enables many container escapes), `CAP_NET_ADMIN` (reconfigure network interfaces), `CAP_SYS_PTRACE` (trace any process), `CAP_SYS_MODULE` (load kernel modules), `CAP_DAC_READ_SEARCH` (bypass file permission checks). In Go, drop capabilities before exec using `syscall.Prctl(syscall.PR_CAP_AMBIENT, syscall.PR_CAP_AMBIENT_CLEAR_ALL, 0, 0, 0)` combined with an explicit capability set.

**Q: How would you debug a container that is consuming more memory than expected?**

A: Start with cgroups v2: read `/sys/fs/cgroup/<container-path>/memory.current` for current usage and `memory.stat` for breakdown (anon, file cache, slab, etc.). The `memory.events` file shows OOM kill counts. If the container process is still running, use `/proc/<host-pid>/status` for `VmRSS` (resident set size) and `VmPeak` (peak virtual memory). For heap analysis: if the container runs a Go binary, expose pprof (`/debug/pprof/heap`) and use `go tool pprof`. For non-Go processes, use `nsenter -t <pid> -m -p, cat /proc/<container-pid>/smaps_rollup` to see a breakdown of anonymous memory, file-backed memory, and shared memory. If memory is growing unboundedly, check for: goroutine leaks (unbounded goroutine counts in pprof), Go's GC not running (very long GC cycles), caches growing without eviction, or fragmentation from `mmap`-based allocators.

**Q: What is the OCI specification and why does it matter?**

A: The Open Container Initiative (OCI) defines three specifications: (1) **Image spec** - how container images are structured (manifest, config, layers as tarballs in a content-addressable store). (2) **Runtime spec** (`config.json`) - defines the filesystem bundle, namespaces, capabilities, mounts, hooks, and process to execute. (3) **Distribution spec** - the API for pushing and pulling images from registries. OCI compliance means any OCI runtime (runc, crun, gVisor's runsc, Kata Containers' kata-runtime) can run any OCI image. This portability is why you can build an image with Docker, push it to a registry, and run it with containerd or Podman without modification. In Go, the `opencontainers/runtime-spec` package provides the Go types for `config.json`, and `opencontainers/image-spec` provides types for image manifests.

### Junior → FAANG: Using Interview Questions to Build Diagnostic Fluency

The interview questions in this chapter are not just questions to memorize: they are the diagnostic framework for container incidents. The namespace question maps to "which layer is this failure in?" The cgroup question maps to "is this a resource limit issue?" The seccomp question maps to "is this a syscall permission issue?" The capability question maps to "does this process have the privileges it needs?" When you encounter a container failure in production, the first five minutes of diagnosis is mentally running through this question set to identify which layer to investigate first.

The OCI spec question is the one that most juniors underestimate. Interviewers ask it specifically to filter candidates who have only used Docker from candidates who understand the ecosystem. The key points: OCI compliance is why runc, crun, gVisor, and Kata are interchangeable from containerd's perspective. The runtime spec's `config.json` is the complete description of a container: reading it tells you exactly what namespaces, capabilities, mounts, and seccomp profile the container will have. Any container behavior question can be answered by reading `config.json`.

Practice answering each interview question out loud, with a 90-second time limit. The discipline of concise verbal explanation reveals gaps in understanding that silent reading does not. When you get stuck on a specific mechanism (like how cgroup hierarchies work in v2, or what exactly the workdir directory does for overlayfs), that is a signal to go deeper on that topic before the interview.

### Senior @ FAANG: Container Interview Signals at the Bar-Raiser Level

Bar-raiser interviewers for container platform roles ask follow-up questions that go beyond the standard answers. After "how do namespaces provide isolation," the follow-up is: "What are the security implications of user namespaces, and does your organization enable them?" After "how do cgroups v2 limit resources," the follow-up is: "How do you detect CPU throttling in production, and how do you distinguish it from actual CPU saturation?" After "what is seccomp," the follow-up is: "How do you generate and maintain seccomp profiles for a fleet of services that update their dependencies frequently?"

The system design question for container internals at the senior level: "Design a container security posture management system that continuously validates that all running containers in a Kubernetes cluster meet the organization's security baseline." A strong answer covers: a Kubernetes controller that watches pods and reads their seccomp profiles, capability lists, and runtime class. Comparison against a policy database (seccomp profile approved, capabilities in allowed set, runtime class appropriate for workload sensitivity). Violation events published to an audit stream. Automated remediation for fixable violations (like adding a missing seccomp annotation) and human escalation for violations that require container restart.

The runtime selection design question: "Your organization runs ML training jobs (compute-bound, trusted code, needs GPU) and a customer-facing code execution service (untrusted customer code, CPU-bound). How do you select container runtimes for each?" ML training jobs: runc with GPU device plugin (gVisor does not support GPUs, Kata adds unnecessary overhead for trusted workloads). Customer code execution: Kata Containers (full VM isolation for untrusted code, preventing kernel exploits from escaping to the host) or gVisor (if GPU is not needed and the performance overhead is acceptable). The ADR documenting this choice, including the performance benchmarks that justify it, is L6-level deliverable.
