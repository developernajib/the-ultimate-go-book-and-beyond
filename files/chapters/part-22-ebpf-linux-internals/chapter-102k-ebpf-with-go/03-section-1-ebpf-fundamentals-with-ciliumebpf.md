## Section 1: eBPF Fundamentals with cilium/ebpf

### 1.1 Project Setup

The `cilium/ebpf` Go library manages the full eBPF lifecycle, compiling C programs to BPF bytecode, loading the bytecode into the kernel, and reading events back in userspace, without requiring kernel module privileges. The `bpf2go` code generator produces Go bindings from a C source file at build time, so the compiled eBPF program is embedded as a byte slice in the binary and loaded at runtime without external files. The directory layout below establishes the standard project structure used throughout this chapter.

```go
// go.mod
// require github.com/cilium/ebpf v0.13.0

// Directory structure:
// ebpf/
//   ├── main.go          - Go userspace code
//   ├── bpf/
//   │   ├── execve.c     - eBPF C program
//   │   └── headers/     - vmlinux.h, bpf_helpers.h
//   └── gen.go           - //go:generate directive

package main

// gen.go
//go:generate go run github.com/cilium/ebpf/cmd/bpf2go -cc clang -cflags "-O2 -g -Wall -Werror" Execve ./bpf/execve.c -- -I./bpf/headers
```

### 1.2 Process Execution Tracer

An eBPF kprobe on `sys_execve` fires in kernel context every time any process calls `execve`, allowing you to record which binaries are spawned and by which parent, a capability that is invaluable for both security auditing and performance profiling. The C program below uses a BPF ring buffer (preferred over perf buffers in modern kernels) to deliver events to userspace with minimal overhead, and `BPF_CORE_READ` to access kernel struct fields in a way that remains correct across kernel versions.

```c
// bpf/execve.c - Trace all execve() calls
//go:build ignore

#include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_tracing.h>
#include <bpf/bpf_core_read.h>

// Event sent to userspace
struct exec_event {
    __u32 pid;
    __u32 ppid;
    __u32 uid;
    char  comm[16];    // process name
    char  filename[256];
};

// Ring buffer for sending events to userspace
struct {
    __uint(type, BPF_MAP_TYPE_RINGBUF);
    __uint(max_entries, 1 << 24); // 16MB
} exec_events SEC(".maps");

// Kprobe on sys_execve entry
SEC("kprobe/sys_execve")
int kprobe_execve(struct pt_regs *ctx)
{
    struct exec_event *event;

    // Reserve space in ring buffer
    event = bpf_ringbuf_reserve(&exec_events, sizeof(*event), 0);
    if (!event)
        return 0;

    // Get current process info
    struct task_struct *task = (struct task_struct *)bpf_get_current_task();

    event->pid  = bpf_get_current_pid_tgid() >> 32;
    event->uid  = bpf_get_current_uid_gid() & 0xFFFFFFFF;
    event->ppid = BPF_CORE_READ(task, real_parent, tgid);

    bpf_get_current_comm(&event->comm, sizeof(event->comm));

    // Read filename from first argument
    const char *filename = (const char *)PT_REGS_PARM1(ctx);
    bpf_probe_read_user_str(event->filename, sizeof(event->filename), filename);

    // Submit event
    bpf_ringbuf_submit(event, 0);
    return 0;
}

char LICENSE[] SEC("license") = "GPL";
```

### 1.3 Go Userspace Loader

The Go userspace component loads the compiled eBPF object, attaches it to the kprobe, opens the ring buffer reader, and dispatches events to a handler function. Proper resource cleanup requires closing the reader, kprobe link, and objects in reverse order, the `defer` chain in `NewExecTracer` ensures this even if loading fails partway through. The `binary.Read` call deserializes the raw ring buffer record into a typed `ExecEvent` struct using the same field layout as the C-side struct.

```go
package main

import (
	"bytes"
	"context"
	"encoding/binary"
	"fmt"
	"log/slog"
	"os"
	"os/signal"
	"syscall"

	"github.com/cilium/ebpf"
	"github.com/cilium/ebpf/link"
	"github.com/cilium/ebpf/ringbuf"
	"github.com/cilium/ebpf/rlimit"
	"golang.org/x/sys/unix"
)

// ExecEvent mirrors the C struct
type ExecEvent struct {
	PID      uint32
	PPID     uint32
	UID      uint32
	Comm     [16]byte
	Filename [256]byte
}

func (e ExecEvent) CommString() string {
	return unix.ByteSliceToString(e.Comm[:])
}

func (e ExecEvent) FilenameString() string {
	return unix.ByteSliceToString(e.Filename[:])
}

// ExecTracer traces process executions
type ExecTracer struct {
	objs    *ExecveObjects // Generated by bpf2go
	kprobe  link.Link
	reader  *ringbuf.Reader
	logger  *slog.Logger
	handler func(ExecEvent)
}

func NewExecTracer(handler func(ExecEvent)) (*ExecTracer, error) {
	// Remove memlock limit (required for eBPF)
	if err := rlimit.RemoveMemlock(); err != nil {
		return nil, fmt.Errorf("remove memlock: %w", err)
	}

	// Load compiled eBPF objects
	objs := &ExecveObjects{}
	if err := LoadExecveObjects(objs, nil); err != nil {
		return nil, fmt.Errorf("load objects: %w", err)
	}

	// Attach kprobe to sys_execve
	kp, err := link.Kprobe("sys_execve", objs.KprobeExecve, nil)
	if err != nil {
		objs.Close()
		return nil, fmt.Errorf("attach kprobe: %w", err)
	}

	// Open ring buffer reader
	rd, err := ringbuf.NewReader(objs.ExecEvents)
	if err != nil {
		kp.Close()
		objs.Close()
		return nil, fmt.Errorf("open ringbuf reader: %w", err)
	}

	return &ExecTracer{
		objs:    objs,
		kprobe:  kp,
		reader:  rd,
		logger:  slog.Default(),
		handler: handler,
	}, nil
}

// Run starts reading events from the ring buffer
func (t *ExecTracer) Run(ctx context.Context) error {
	for {
		select {
		case <-ctx.Done():
			return ctx.Err()
		default:
		}

		record, err := t.reader.Read()
		if err != nil {
			if err == ringbuf.ErrClosed {
				return nil
			}
			t.logger.Error("read ringbuf", "error", err)
			continue
		}

		var event ExecEvent
		if err := binary.Read(bytes.NewReader(record.RawSample), binary.LittleEndian, &event); err != nil {
			t.logger.Error("parse event", "error", err)
			continue
		}

		if t.handler != nil {
			t.handler(event)
		}
	}
}

// Close cleans up all eBPF resources
func (t *ExecTracer) Close() {
	t.reader.Close()
	t.kprobe.Close()
	t.objs.Close()
}

func RunExecTracer() {
	logger := slog.New(slog.NewTextHandler(os.Stdout, nil))

	tracer, err := NewExecTracer(func(event ExecEvent) {
		logger.Info("exec",
			"pid", event.PID,
			"ppid", event.PPID,
			"uid", event.UID,
			"comm", event.CommString(),
			"file", event.FilenameString(),
		)
	})
	if err != nil {
		logger.Error("create tracer", "error", err)
		os.Exit(1)
	}
	defer tracer.Close()

	ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
	defer stop()

	logger.Info("exec tracer running, press Ctrl+C to stop")
	tracer.Run(ctx)
}
```

### Junior → FAANG: Building Your First eBPF Program with cilium/ebpf

The `cilium/ebpf` library is the right starting point for eBPF development in Go because it handles ELF parsing, map creation, program loading, and verifier error formatting. The first gap to close is understanding the `bpf2go` code generation workflow: you write a C eBPF program, run `go generate` which invokes `bpf2go`, and get back a Go file with typed structs for your maps and a `Load` function for your programs. This workflow keeps the C and Go in sync at compile time rather than relying on runtime string-based lookups.

The most common mistake with `cilium/ebpf` at the junior level is not handling map cleanup correctly. Maps are kernel resources with file descriptor lifetimes. If the Go process exits without closing a pinned map, the map persists in the BPF filesystem (`/sys/fs/bpf`). The first-job habit is to always pair every `Load` call with a `defer objs.Close()` and to document explicitly whether maps are pinned and who is responsible for cleaning them up in production.

A worked example: after loading a kprobe program that tracks `sys_execve` events, use `cilium/ebpf/ringbuf.NewReader` to read events from the ring buffer in a goroutine, and use a `context.WithCancel` to stop the reader cleanly on SIGINT. This pattern, a goroutine reading from the ring buffer with a cancellable context, is the standard production pattern for event-driven eBPF consumers in Go. Practice it until it is automatic.

Interview framing: when asked how you would instrument a service to detect abnormal process spawning, describe the kprobe on `sys_execve`, the ring buffer event containing the PID and command name, and the Go consumer that publishes events to a metrics pipeline. This shows you understand the full stack, not just the kernel side.

### Senior @ FAANG: cilium/ebpf Integration Patterns for Production Platforms

At the senior level, `cilium/ebpf` is not just a library but a dependency with its own compatibility matrix. The library's version support policy tracks the minimum kernel version for each feature, and upgrading `cilium/ebpf` can introduce changes in how verifier errors are formatted, how BTF is handled, or which program types are supported. Platform teams must pin `cilium/ebpf` versions in their `go.mod`, test upgrades in a kernel matrix, and maintain a changelog of behavioral differences between versions.

The `bpf2go` code generation step is a build-time contract between the C eBPF program and the Go consumer. When the C program changes a map key or value struct, the generated Go types change, and any Go code that uses the old types fails to compile. This is the correct failure mode: compile-time errors are better than runtime misinterpretation. Platform teams enforce this by never allowing handwritten map accessors and always routing all map access through the generated types.

Error handling for eBPF operations in production requires distinguishing transient errors from permanent failures. A program load failure due to a verifier rejection is permanent: retrying will not help. A map update failure due to `E2BIG` (map full) is a capacity error that requires either LRU eviction or a capacity increase. A ring buffer read failure due to `ENOENT` signals the reader goroutine should exit. Implementing a structured error taxonomy in the Go consumer, with different handlers for each class, prevents the common pattern of logging "bpf error" and retrying indiscriminately.

Observability of the eBPF layer itself is often overlooked. Platform teams should export metrics for: number of programs loaded, number of map entries, ring buffer drop counts (from the drop counter map the eBPF program maintains), and program execution latency (from `bpf_ktime_get_ns` timestamps). These metrics go into the same monitoring system as application metrics, enabling correlation between eBPF-level events and application-level symptoms.

Staged rollout of new eBPF programs requires a mechanism to load the new program without immediately attaching it to its hook point, verify its behavior in shadow mode against a sample of real traffic, and then atomically swap the attachment. `cilium/ebpf` supports this through link types: a `kprobe.Link` or `tracepoint.Link` object controls the attachment and can be updated via `link.Update` to replace the attached program while the link itself remains alive. Designing your deployment tooling around link-based atomic swaps avoids the window where no program is attached during a rolling update.
