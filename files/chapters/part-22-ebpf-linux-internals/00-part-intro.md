# Part XXII: eBPF & Linux Internals (Optional Track)

*"eBPF is to Linux what JavaScript is to the browser."* - Brendan Gregg

Every container you deploy, every network packet your service processes, and every performance profile you collect ultimately depends on Linux kernel primitives. At FAANG companies, the engineers who understand what happens beneath the application layer - inside the kernel, the container runtime, and the network stack - are the ones who solve the hardest performance problems and build the most innovative infrastructure tools. eBPF has transformed this space by allowing engineers to safely extend kernel behavior without writing kernel modules, and it has become the foundation of modern cloud-native infrastructure.

The adoption of eBPF across the industry is accelerating rapidly. Cilium, now the default Container Network Interface on Google Kubernetes Engine, Amazon EKS, and Azure AKS, uses eBPF for high-performance networking and security enforcement. Falco uses eBPF for runtime security monitoring. Pixie uses it for zero-instrumentation observability. Go has emerged as the primary language for building eBPF-based tools, with the cilium/ebpf library providing a mature, well-documented interface for loading and interacting with eBPF programs from user space.

Understanding Linux internals goes hand-in-hand with eBPF. Namespaces, cgroups v2, the OCI runtime specification, containerd, and systemd are the building blocks that make containers work. When a container misbehaves, when resource limits are not enforced correctly, or when network policies fail silently, the engineer who understands these internals can diagnose the root cause while others are still reading documentation.

### Junior → FAANG: Entering the eBPF and Linux Internals Domain

Before tackling eBPF with Go, a junior engineer must close several foundational gaps. The first is a working mental model of the Linux kernel itself: user space versus kernel space, the role of system calls as the boundary between them, and what happens when a Go program calls `os.Open` all the way down to the VFS layer. Without this model, eBPF programs feel like magic spells rather than structured kernel extensions. Start by reading a few hundred lines of a simple kernel driver or tracepoint definition in the kernel source tree on GitHub, even without compiling anything, to build familiarity with the vocabulary.

The second gap is understanding the BPF instruction set and the verifier. Every eBPF program is checked by a kernel-resident verifier before it runs. The verifier enforces bounds on memory accesses, loop counts, and stack depth. Juniors often hit verifier rejections without understanding why. The key habit is to read verifier log output carefully: it tells you exactly which instruction failed and why. Practice writing small kprobe or tracepoint programs with `cilium/ebpf` and intentionally triggering verifier errors, then reading the error messages until they become interpretable.

A worked entry point: write a Go program using `cilium/ebpf` that attaches to the `sys_enter_openat` tracepoint and prints the filename argument to user space via a perf event ring buffer. This exercises the full loop: writing a C eBPF program, compiling it with `clang` and `bpftool gen skeleton` or `bpf2go`, loading it from Go, and reading events. The common first-job habit to build is always verifying that your eBPF program loads cleanly on the target kernel version before deploying, because kernel version differences in available helpers and tracepoint signatures are a constant source of production incidents.

In interviews, eBPF questions at the entry level probe whether you understand why eBPF is safer than a kernel module (the verifier, no arbitrary memory access, bounded execution), what the difference between kprobes, tracepoints, and uprobes is, and how maps work as the shared memory channel between kernel and user space. Frame your answers around the verifier as the safety boundary and maps as the data highway.

### Senior @ FAANG: Platform Thinking and Governance for eBPF Infrastructure

At the senior and staff level, eBPF is not a debugging curiosity but a platform primitive. The architectural decision record (ADR) question is not "should we use eBPF" but "which eBPF program types own which kernel attachment points, and how do we govern conflicts between teams." In large organizations, multiple services may independently try to attach kprobes to the same kernel function. Without a coordination layer, this creates ordering dependencies, unexpected side effects, and tail-latency interference. A staff engineer's job is to design the ownership model before the first production incident forces one.

CO-RE (Compile Once, Run Everywhere) is a non-negotiable requirement for any eBPF infrastructure that spans more than one kernel version. FAANG fleets are heterogeneous: kernel 5.10 LTS, 5.15, 6.1, and 6.6 may all be live in the same region. CO-RE with BTF (BPF Type Format) allows a single compiled eBPF object to adapt its struct field offsets at load time using the target kernel's BTF metadata. Designing your eBPF toolchain around CO-RE from the start avoids the alternative: maintaining per-kernel-version binary artifacts, which scales poorly and creates a combinatorial testing burden.

Maturity model thinking applies to eBPF deployments. Level 1: eBPF programs run in development environments only, verified manually. Level 2: programs are deployed via a central loader service with version pinning and automatic detachment on failure. Level 3: programs are governed by a policy engine (similar to how Cilium uses Kubernetes CRDs to declare network policy) with audit logging of every attach and detach event. Level 4: the eBPF platform itself exposes a stable API so that product teams can declare observability or security intent without writing C. Driving your organization from level 1 to level 3 is staff-level work that compounds across every team.

Security governance for eBPF is a bar-raiser interview signal. eBPF LSM (Linux Security Module) programs can enforce security policy at the kernel level, which is more reliable than user-space enforcement but also harder to audit. At L6/L7, the concern is the blast radius of a buggy LSM program: it can deny legitimate syscalls fleet-wide and cause an outage that looks like a kernel panic. The mitigation strategy involves staged rollouts with canary kernels, automatic fallback to a permissive mode if the LSM program returns an unexpected error count above threshold, and integration with your incident response runbooks before the program is deployed to production.

Performance analysis of eBPF programs at scale requires understanding that the BPF JIT compiler, map lookup costs, and perf ring buffer contention all appear in production profiles. `bpftool prog profile` provides per-instruction cycle counts on supported kernels. On high-throughput XDP paths, a single map lookup that touches a cache line not in L1 costs 40-100 cycles, which at 10 Gbps line rate becomes the bottleneck. Staff-level work here involves designing map schemas that maximize cache locality: using per-CPU maps to eliminate atomic operations, sizing maps to fit hot working sets in L2, and using tail calls to break long programs into stages that the JIT can optimize independently.

Observability platform design is where eBPF earns its place in the FAANG infrastructure stack. The key insight is that eBPF programs produce structured events (via ring buffers or maps) that must be funneled into the same telemetry pipeline as application metrics and traces. A senior engineer designs the schema contract between the eBPF layer and the ingestion pipeline: protobuf or FlatBuffers definitions, versioning strategy, and the rollout plan for schema changes when the eBPF program changes a field. Without this contract, every eBPF program update becomes a coordination problem with the observability team.

At the L7 level, the framing shifts from "how do I use eBPF" to "what infrastructure does my organization need so that any team can safely deploy eBPF-based tooling." That means a central eBPF program registry, a CI/CD pipeline that runs verifier checks on every pull request, kernel compatibility testing in a matrix of supported kernel versions, and on-call runbooks for eBPF-related production issues. Building this platform is the kind of work that appears in promotion documents as "enabling N teams to ship observability features with zero kernel expertise required."
