## Exercises

1. **Instrument a Go HTTP Service End-to-End**: Take a simple Go HTTP service with at least three handlers and instrument it fully with OpenTelemetry. Initialize a tracer provider with a resource that includes `service.name`, `service.version`, and `deployment.environment`. Use `otelhttp.NewHandler` to wrap all routes, add custom child spans inside handler business logic, and attach at least three meaningful span attributes per span. Export traces to a local Jaeger instance via OTLP and verify that parent-child relationships appear correctly in the Jaeger UI.

2. **Correlate Traces, Metrics, and Logs**: Extend the instrumented service so that every log line emitted by `log/slog` includes `trace_id` and `span_id` extracted from the current context via `trace.SpanFromContext`. Simultaneously expose an OTel Prometheus histogram of request durations. For a single HTTP request, demonstrate that you can: (a) find the Prometheus histogram observation, (b) find the log line containing the matching trace ID, and (c) view the full trace in Jaeger. Document the three-signal correlation workflow in a short markdown runbook.

3. **Implement and Compare Sampling Strategies**: Configure the same service with three sampling strategies (`AlwaysSample`, `TraceIDRatioBased(0.1)`, and `ParentBased(TraceIDRatioBased(0.1))`) and run a load test sending 1,000 requests with `hey` or `vegeta`. Compare the number of traces captured by each strategy, confirm that `ParentBased` preserves parent sampling decisions for child spans, and write a comment block explaining when each strategy is the right production choice and why `ParentBased` is critical for multi-service systems.

4. **Deploy and Configure the OpenTelemetry Collector**: Write a `docker-compose.yml` that runs your Go service, an OpenTelemetry Collector, Jaeger, and Prometheus. Configure the Collector pipeline with a `batch` processor and a `memory_limiter` processor, and export traces to Jaeger and metrics to Prometheus. Verify via the Collector's `zpages` extension that all pipeline stages are healthy and that both backends receive data independently. Explain what would happen if the Collector restarted while the service was processing requests.

5. **Add Semantic Convention Attributes for a Database Client**: Wrap a `database/sql` query so that each call creates a child span with the OTel semantic convention attributes `db.system`, `db.name`, `db.statement` (truncated to 200 characters), and `db.operation`. Record any returned error with `span.RecordError` and set the span status to `codes.Error` with a descriptive message. Write a table-driven unit test using a `tracetest.SpanRecorder` (it is itself a span processor) registered on a test `TracerProvider`, asserting that the correct attributes, status code, and error event appear on the captured span.

6. **Benchmark Instrumentation Overhead and Optimize**: Benchmark your instrumented HTTP handler with `go test -bench` against an uninstrumented baseline, capturing allocations per operation via `-benchmem`. Run once with `AlwaysSample` and once with `NeverSample` to isolate sampling cost from SDK overhead. Use `go tool pprof` on the benchmark output to identify the dominant allocation source, apply at least one optimization (such as pre-allocating the attributes slice or reusing span options with `sync.Pool`), and document the before/after numbers along with the trade-off each sampling configuration imposes at high request rates.

### Junior → FAANG: Exercise Strategy for Interview Preparation

Exercises 1 through 3 map directly to common FAANG interview scenarios. Exercise 1 tests end-to-end implementation ability. Exercise 2 tests cross-pillar understanding. Exercise 3 tests your ability to reason about trade-offs.

Do exercise 3 twice: once with a single service (to understand head-based sampling) and once with two services calling each other (to understand why `ParentBased` matters). In a multi-service system, if service A uses `TraceIDRatioBased(0.1)` and service B uses `AlwaysSample`, then 90% of traces that enter at service A are discarded at A but would have been fully traced at B. `ParentBased` ensures that the sampling decision made at service A is respected downstream.

### Senior @ FAANG: Using Exercises to Define Platform Requirements

Exercise 4 (deploying the Collector) should be extended with a failure mode exercise: kill the Collector mid-test and observe what happens to spans in the SDK's batch processor buffer. Measure the span loss rate during the Collector outage. This exercise reveals whether the batch processor's queue size and timeout settings are adequate for your service's traffic pattern, and informs the platform sizing guidelines for the Collector fleet.

Exercise 5 (database instrumentation with semantic conventions) is the basis for a platform library acceptance test. Before a shared database wrapper is published to the internal package registry, it must pass a test that verifies all required semantic convention attributes are present, the `db.statement` is truncated and sanitized, and errors are recorded with `span.RecordError`. This test is the automated gate that enforces the platform standards document.
