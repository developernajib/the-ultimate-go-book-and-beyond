## Exercises

1. **Build a Production-Grade Alert Set with Runbooks**: Audit an existing service (or a sample service) and identify every alert it currently lacks. Write a complete Prometheus alerting rule file that covers: SLO burn rate (multi-window), pod restart loop, PVC near capacity, and a dead man's switch for each scheduled job. For every alert include a `runbook_url` annotation pointing to a local file. Write the corresponding runbook for the SLO burn rate alert with diagnosis steps that use only copy-paste `kubectl` and `promtool` commands, requiring no prior knowledge of the system.

2. **Practice the Incident Commander Role**: Using a simulated or staging environment, introduce a failure (e.g., set the error rate to 20% via a feature flag) and role-play the full incident response process. Designate an incident commander (yourself or a partner), open a dedicated Slack channel, write the initial incident update within 5 minutes, send status updates every 15 minutes, declare mitigation, and close the incident with a final update. Evaluate the exercise against these criteria: time to first update, update cadence, clarity of mitigation steps, and quality of the incident summary.

3. **Automate a Toil-Heavy Runbook Step**: Identify a runbook step that requires manually running several commands and interpreting their output (e.g., checking which pods are in crash loop, fetching their recent logs, and correlating with a Prometheus query). Write a Go CLI tool that performs all three steps automatically and prints a structured summary with a recommended action. The tool must handle the case where the Kubernetes API or Prometheus is unreachable and must not require cluster-admin permissions. Measure the time saved per incident compared to the manual approach.

4. **Configure Alertmanager Routing and Inhibition**: Write an Alertmanager configuration that routes critical SLO alerts to PagerDuty (use a test webhook if you don't have PagerDuty), warning-level alerts to a Slack channel, and all database alerts to a separate DBA channel regardless of severity. Add an inhibition rule that suppresses all warning and info alerts for a service when a critical alert for that service is already firing. Test the inhibition by firing both a critical and a warning alert for the same service and confirming only the critical alert is delivered.

5. **Instrument a Go Service for Maximum Debuggability During Incidents**: Enhance a Go HTTP service so that an on-call engineer has everything needed to diagnose any incident in under 10 minutes. Requirements: structured JSON logs with correlation ID, trace ID, and span ID on every log line. `net/http/pprof` exposed on an internal-only port (not the public port). `/health/live` and `/health/ready` endpoints. A `runtime.MemStats` Prometheus gauge updated every 30 seconds. Graceful shutdown that drains in-flight requests before exiting. Write a checklist that verifies each capability and document how each one is used during a real incident.

6. **Write and Execute an Error Budget Policy**: Draft a formal one-page error budget policy for a fictional service with a 99.9% availability SLO. The policy must specify: what engineering work is allowed when the budget is above 75%, between 25-75%, and below 25%. Who has authority to override the policy and under what conditions. And how the budget resets. Present the policy to a colleague and walk through three scenarios (a planned feature release, an emergency security patch, and a month where a third-party dependency caused most of the budget burn), explaining what the policy prescribes in each case and whether the policy handles edge cases appropriately.

### Junior → FAANG: Exercise Sequencing for Maximum Learning

Complete exercise 5 (instrument a Go service for debuggability) before any interview. Being able to describe your instrumented service, show the pprof endpoint, and explain how each diagnostic capability is used during a real incident is a concrete, demonstrable answer to the "how would you diagnose a production issue?" interview question.

Complete exercise 2 (IC role-play) with a colleague if possible. The IC role-play reveals skills that you cannot develop alone: communication under pressure, status update cadence, and the discipline of stabilizing first before investigating.

### Senior @ FAANG: Exercises as Launch Criteria

At L6, exercises 1 (alert set with runbooks), 4 (Alertmanager routing), and 5 (debuggability instrumentation) become launch criteria enforced by the platform team. No new service reaches production without: a validated alert rule file with runbook links, a tested Alertmanager routing configuration, and a debuggability checklist signed off by a senior engineer. The exercises in this chapter are the templates from which those launch criteria are derived.
