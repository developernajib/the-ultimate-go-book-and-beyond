## Exercises

1. **OIDC Discovery and Dynamic Client Registration**: Write a Go client library that bootstraps itself by fetching an OIDC provider's discovery document (`/.well-known/openid-configuration`), validates required fields (`issuer`, `authorization_endpoint`, `jwks_uri`), and dynamically registers a new client via the RFC 7591 dynamic registration endpoint. The library must cache the discovery document and refresh it on a configurable interval. Expected outcome: a zero-configuration OIDC client that works with any compliant provider (Keycloak, Auth0, Dex) without hardcoded endpoint URLs.

2. **JWKS Endpoint with Key Rotation**: Implement a Go HTTP server that serves a `/.well-known/jwks.json` endpoint using an in-memory key store holding two RSA-4096 key pairs (current and previous). Expose an admin endpoint that rotates keys: promotes the current key to previous, generates a new current key, and ensures existing tokens signed with the previous key remain valid for a configurable grace period. Expected outcome: clients that cache JWKS keys are never broken by rotation because the old key remains in the JWKS until the grace period expires.

3. **Social Login Aggregator**: Build a Go web service that supports "Sign in with Google" and "Sign in with GitHub" using the authorization code flow with PKCE. After successful authentication from either provider, normalize the user profile (sub, email, name, avatar) into a unified internal representation and issue your own application JWT. Handle account linking when the same email address appears from multiple providers. Expected outcome: a single `/callback` handler pattern that works for any configured OIDC/OAuth2 provider, extensible by adding new provider config entries.

4. **Device Authorization Flow**: Implement the OAuth 2.0 Device Authorization Grant (RFC 8628) server-side in Go. Issue a `device_code` and `user_code` pair, expose the polling endpoint that returns `authorization_pending` until the user completes the out-of-band authorization, and exchange the `device_code` for tokens. Implement rate limiting on the polling endpoint (`slow_down` error after too-frequent polls). Expected outcome: a working device flow that a CLI tool can use to authenticate without a browser on the same machine.

5. **Token Introspection with Caching**: Implement an RFC 7662 token introspection endpoint and a corresponding client-side introspection middleware. The middleware must cache active token metadata in Redis with a TTL equal to the token's remaining lifetime and immediately invalidate the cache entry on RFC 7009 revocation. Write a load test that demonstrates the cache reduces introspection endpoint calls by at least 90% under repeated requests with the same token. Expected outcome: a stateless resource server that scales without hammering the authorization server on every request.

6. **Refresh Token Family Invalidation with Concurrent Safety**: Implement refresh token rotation where concurrent refresh requests for the same token are handled safely using a Redis distributed lock (SET NX with TTL). If two requests race with the same refresh token, exactly one must succeed and the other must receive the RFC 6749 `invalid_grant` error that triggers family invalidation. The token endpoint has a fixed error set, so reuse detection reports `invalid_grant` rather than a custom code, and the real reason is recorded in your logs instead. Write a test that fires 50 concurrent refresh requests with the same token and asserts exactly one succeeds and all tokens in the family are invalidated. Expected outcome: a provably race-free refresh endpoint verified by a concurrent stress test.

The key principle: never store tokens where XSS can reach them, always validate all claims, rotate refresh tokens, and use PKCE universally.
