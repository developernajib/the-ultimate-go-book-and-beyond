# Chapter 31D: Mobile Backend Engineering with Go

*"Mobile backends have one job: be fast, be reliable, and don't drain the battery."* - Mobile Platform Engineering

Mobile clients impose constraints that general-purpose REST APIs are poorly equipped to handle. A cellular network in rural India or a subway tunnel in New York drops packets, delays acknowledgments, and reconnects unpredictably. A battery-powered device punishes backends that force polling, return oversized payloads, or require multiple round-trips to render a single screen. A user switching between Wi-Fi and LTE mid-session expects their shopping cart, draft message, or in-progress workout to survive the transition without data loss. These realities demand a backend architecture purpose-built for mobile - not an adaptation of a desktop web API. The gap between a "works on localhost" API and one that behaves correctly under real mobile conditions is where production systems succeed or fail.

The Backend for Frontend (BFF) pattern addresses this directly: rather than exposing a generic API that every client must adapt, the mobile BFF is a dedicated service layer that shapes data exactly as the mobile client needs it, aggregates multiple downstream calls into a single network request, compresses aggressively, and speaks the protocols (HTTP/2, gRPC-Web, WebSockets) that minimize latency on mobile connections. Go is the ideal runtime for this role - its goroutine model handles thousands of concurrent downstream fan-outs cheaply, its binary size and startup time make it deployable as a lean sidecar or edge function, and its HTTP/2 support is first-class. Paired with Firebase Cloud Messaging and Apple Push Notification service integrations, a Go BFF can serve push notifications with sub-millisecond dispatch latency at millions of devices per hour. Push notification reliability, token lifecycle management, and silent background refresh are all engineering concerns that belong in the backend, not the mobile client.

Offline-first architecture is the other dimension that separates a truly mobile-native backend from a basic API. When a user edits a record while offline, a sync engine must track the delta, assign a vector clock or last-write-wins timestamp, and reconcile conflicts when connectivity resumes - all without data loss or silent overwrites. Delta sync, which transmits only changed fields since the client's last sync token, can reduce payload sizes by 90% compared to full-object sync on repeat fetches. This chapter builds both layers: the BFF request shaping layer and the stateful sync engine that keeps mobile clients coherent across unreliable connections. You will leave with a deployable Go service that speaks the language of mobile platforms rather than forcing them to adapt to a web-centric interface.

**What you'll learn in this chapter:**
- Design Backend-for-Frontend (BFF) APIs in Go that aggregate downstream services into mobile-optimized single-request responses
- Implement push notifications via Apple Push Notification service (APNs) and Firebase Cloud Messaging (FCM) with delivery receipts and retry logic
- Build offline-first sync with vector clock conflict resolution and last-write-wins fallback strategies
- Implement delta sync using cursor-based sync tokens so clients receive only changed records since their last fetch
- Optimize bandwidth with Brotli/gzip compression, field-mask partial responses, and response shaping tailored to screen sizes
- Manage device registration, token rotation, and multi-device session lifecycles securely
- Handle deep linking, Universal Links (iOS), and App Links (Android) through a Go-based redirect and attribution service
- Instrument mobile backend health with per-device-tier latency percentiles, push delivery rates, and sync conflict metrics

**Why this matters at scale:**
Uber's mobile backends process millions of location updates per minute. Their Go BFF layer aggregates driver state, surge pricing, and ETA computations into a single response to avoid the over-fetching that plagued their earlier REST design. Spotify's offline sync for downloaded playlists uses delta-sync patterns nearly identical to those covered in this chapter, keeping mobile data usage within carrier limits while maintaining library consistency across hundreds of millions of devices.

**Prerequisites:** Familiarity with Go HTTP servers and middleware. Basic understanding of JWT authentication and relational databases.

### Junior → FAANG: Prerequisite Gaps Before Chapter 31D

If you arrived here expecting "mobile backend" to mean "REST API that a mobile app happens to call," you are missing the framing that makes this chapter make sense. A mobile backend is defined by three constraints that desktop web backends ignore: the client has no stable network, the client has no stable power budget, and the client cannot be redeployed on your schedule. Every architectural choice in this chapter follows from those three facts.

Worked example of the framing shift. A web backend returns `GET /user/profile` with fifty fields including settings, preferences, and notification history. A naive mobile port does the same. A junior engineer measures p99 latency over gigabit office Wi-Fi, sees 80ms, and ships. Three weeks later the on-call rotation fields complaints that the profile tab loads in eight seconds on a Delhi commuter train. The gigabit number was never the relevant number. On a real cellular link the payload is shaped by packet loss, radio wake-up latency, and TCP slow start, not by server CPU. The fix is not "add a cache." The fix is a BFF that returns a 2KB response with the four fields the profile screen actually renders, Brotli compressed, over a pre-warmed HTTP/2 connection. That is the mindset junior engineers need to install before the code in this chapter lands.

Interview entry point for new grads. If an interviewer asks "design an API for a mobile app," the signal they want is that you will ask about network conditions, payload shape per screen, offline behavior, push delivery, and token rotation before you draw a box. Candidates who jump to "I will use REST with JSON" without asking about connectivity fail the round. Candidates who say "I would start with a BFF per client surface, with a sync engine for offline edits, and push as the primary wake-up mechanism rather than polling" pass even if their subsequent diagram is imperfect. The signal is the vocabulary, not the diagram fidelity.

First-job context. On your first mobile backend rotation you will inherit a system where someone has already chosen the BFF framework, the sync engine, and the push provider. Your job in the first quarter is not to replace them. It is to learn why each was chosen, read the ADRs, and find the one place where the team knowingly accepted technical debt. That place is where your first useful contribution lives.

### Senior @ FAANG: The Staff-Level Mobile Backend Ownership Model

At staff and principal level the mobile backend is not one service. It is a portfolio of services with distinct ownership boundaries, and your job is to make the boundaries explicit so that teams can ship independently without corrupting each other's invariants. The portfolio typically contains at least six surfaces: the BFF layer per client (iOS, Android, web if it shares mobile shaping), the push fan-out service, the sync engine (state reconciliation, not transport), the device and session registry, the analytics ingest pipeline, and the feature-flag and remote-config delivery service. Each has its own SLO, its own on-call, and its own failure mode. Treating them as one "mobile backend" in a single repo with a single on-call rotation is the most common staff-level anti-pattern, and it is the reason mobile outages at medium-sized companies cascade across surfaces during a single bad deploy.

The BFF ownership question is the first ADR you will write or inherit. Three legitimate models exist. Per-client BFF, as Netflix and SoundCloud popularized, gives each client team a service they own end to end, written in their preferred language (Node, Kotlin, Go) and shaped around their screens. The cost is duplication: three BFFs reimplement auth, observability, and downstream client libraries. GraphQL federation, as Apollo and Netflix have both adopted in parts of their stack, replaces per-client BFFs with a single federated graph where each domain team owns a subgraph and clients issue persisted queries. The cost is coordination: schema evolution requires cross-team review and the gateway becomes a reliability pinch point. Single BFF for all mobile clients, as Instagram ran for years, minimizes duplication but forces the BFF team to become a bottleneck for every screen change across iOS and Android. There is no universally correct answer. At under fifty mobile engineers a single BFF is usually right. Between fifty and five hundred, per-client BFF wins because the coordination cost of a single BFF exceeds the duplication cost. Above five hundred, federation wins because per-client BFFs begin to duplicate domain logic, not just shaping logic, and you lose the ability to reason about the graph as a whole. Netflix's Falcor lessons are instructive here. Falcor solved the over-fetching problem before GraphQL existed but failed to get industry traction because it lacked a strong schema and tooling ecosystem. The lesson is not "Falcor was wrong." The lesson is that a shaping layer without a schema registry and a strong type contract degenerates into bespoke client-specific endpoints within eighteen months, which is exactly what BFF-without-governance becomes.

The staff-level deliverables for this chapter are ADRs, not code. The code in the rest of the chapter is the implementation of choices that you, at senior level, are responsible for making and defending. Expect to write at least: BFF model selection ADR, sync engine selection ADR (CRDT versus LWW versus operational transform, which this chapter expands in part 3), push provider redundancy ADR (single provider versus APNs-plus-FCM-plus-WebPush with failover governance), session and refresh token rotation ADR (with explicit threat model for token theft and device-bound tokens via DPoP or platform attestation), analytics ingest ADR (Kafka to Iceberg on object store versus managed warehouse direct ingest, with PII scrubbing boundaries and GDPR right-to-delete plumbing), and a mobile rollout ADR that documents how you ship changes to millions of devices without server-side deploys (feature flags with offline sync, forced-update floors, and staged rollout cohorts). Each ADR names the decision, the alternatives, the trade-offs, and the reversal cost. The reversal cost field is the one junior ADR authors omit and is the one that matters most. A decision with a low reversal cost can be made quickly. A decision with a high reversal cost (sync engine choice is the canonical example, because it ships to every installed client and the client version skew can persist for years) deserves a design review with at least three staff-level reviewers from outside the team.
