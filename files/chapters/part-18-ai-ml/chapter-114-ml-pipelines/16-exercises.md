## Exercises

1. **ONNX Inference Pipeline with Feature Preprocessing**: Build an end-to-end Go inference pipeline that accepts raw JSON input, applies a fitted feature preprocessing pipeline (StandardScaler + OneHotEncoder state loaded from disk), runs inference via a maintained ONNX Runtime binding such as `yalue/onnxruntime_go`, and returns a structured prediction response. Benchmark the pipeline under 1000 concurrent goroutines and measure p50/p95/p99 latency. Expected outcome: a fully integrated pipeline where feature preprocessing and ONNX inference are decoupled behind interfaces, with benchmark results proving sub-10 ms p99 latency.

2. **Feature Store with Online and Offline Serving**: Implement a Go-based feature store with two serving modes: offline (bulk retrieval from PostgreSQL for training jobs) and online (low-latency retrieval from Redis for real-time inference). Implement a `MaterializeFeatures(entityIDs []string, featureNames []string) (map[string]FeatureVector, error)` function that fans out to both backends and merges results. Expected outcome: a feature store where online latency is under 2 ms and offline bulk export handles 1 million rows without OOM.

3. **MLOps CI/CD Pipeline Orchestrator**: Write a Go CLI tool that orchestrates a full MLOps pipeline: pull the latest data from S3, trigger a Python training job via subprocess, parse the output metrics JSON, compare against the current champion model's metrics, and promote the challenger if its F1 score improves by at least 1%. Record every pipeline run to a SQLite audit log with timestamps, metrics, and promotion decisions. Expected outcome: a reproducible, auditable pipeline that can be triggered by a cron job or git hook without manual intervention.

4. **Data Validation and Schema Enforcement**: Implement a Go data validation layer for ML pipelines that enforces a schema (feature names, types, value ranges, null rates) defined in a YAML file. The validator must emit a structured report of schema violations, block pipeline progress when critical violations exceed a configurable threshold, and log warning-level violations for monitoring. Write tests covering type mismatches, out-of-range values, and unexpected null rates. Expected outcome: a validator that catches training data quality regressions before they corrupt a model artifact.

5. **Batch Inference Worker Pool**: Build a Go batch inference system using a worker pool pattern. A dispatcher reads entity IDs from a CSV file, distributes them across N workers (configurable), each worker loads features from the feature store, runs ONNX inference, and writes predictions to a results CSV. Implement graceful shutdown with `context.Context` cancellation and retry logic for transient feature store errors. Expected outcome: a batch inference job that processes 100,000 rows end-to-end, with worker count tuned via benchmarking to maximize throughput on available CPU cores.

6. **Model A/B Testing Router**: Implement an HTTP model gateway that routes a configurable percentage of traffic to a challenger model and the remainder to the champion, using a stable hash of a user ID to ensure request stickiness. Log every prediction with model version, user ID, and output to a structured event stream. Expose a `/metrics` endpoint reporting per-variant request counts, latency histograms, and prediction score distributions. Expected outcome: a production-grade A/B router where traffic split changes take effect without restarting the server and variant assignment is deterministic for any given user ID.

### Junior → FAANG: Exercise Selection Strategy

If you only complete two exercises from this set before a FAANG interview, choose exercises 2 (feature store with online/offline serving) and 6 (A/B testing router). These two exercises cover the components that appear most frequently in ML infrastructure system design questions and are the most difficult to fake knowledge about without having built them. Bring the code to the interview on a laptop or in a shared repository you can pull up to demonstrate concrete implementation choices.

Exercise 1 (ONNX inference pipeline with benchmarking) is the exercise to complete if you have a specific interview for an ML serving role. The benchmark results give you concrete numbers to cite: "I measured 3.2 ms p99 latency for a 100-feature input vector on an ONNX model with a 4-core VM using 1000 concurrent goroutines." Specific numbers from real experiments are dramatically more credible than estimated numbers in interviews.

### Senior @ FAANG: Exercises as Hiring Assessment Tools

These exercises, or variations of them, can be used as take-home assessments for senior ML infrastructure engineering candidates. A candidate who completes exercise 4 (data validation and schema enforcement) correctly demonstrates: precise thinking about what a schema actually constrains, the judgment to separate blocking violations from warnings, and production-oriented thinking (the exercise requires a structured report and a configurable threshold, not just a boolean). Evaluate the submission not just on whether the validation logic is correct, but on whether the failure output tells an on-call engineer what to do, whether the thresholds are configurable without a redeploy, and whether the code is testable with mock data sources.

Exercise 6 (A/B testing router) is particularly revealing because it requires understanding of consistent hashing (for request stickiness), atomic configuration updates (for traffic split changes without restart), and event logging design (for offline analysis). A senior candidate should implement all three correctly and should proactively handle edge cases: what happens when the challenger model is unavailable? Does the router fall back to the champion silently, alert and fall back, or return an error? How the candidate handles this failure mode reveals their production ML maturity.
