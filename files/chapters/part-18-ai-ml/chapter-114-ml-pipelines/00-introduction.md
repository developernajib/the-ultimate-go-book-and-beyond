# Chapter 114: Building ML Pipelines (Optional Track)

> *"A model that cannot be retrained automatically is not a product feature, it is a time bomb with an unknown fuse."*

The uncomfortable truth of production machine learning is that the model is the smallest part of the system. Sculley et al.'s "Hidden Technical Debt in Machine Learning Systems" (Google, NIPS 2015) put it memorably: "a mature system might end up being (at most) 5% machine learning code and (at least) 95% glue code." Worth reading that sentence precisely, because it is quoted loosely everywhere. It is an illustrative observation offered in the paper's discussion of the glue code anti-pattern, not a measured survey of real codebases, and the 95% it names is specifically glue code rather than all supporting infrastructure. The broader point survives the pedantry intact: data collection, validation, feature engineering, training orchestration, experiment tracking, model versioning, serving infrastructure, monitoring, and automated retraining are where the engineering effort actually goes, and they are what separates a research prototype from a reliable production service. This chapter is about that work.

An ML pipeline is the automated path from raw data to a deployed, monitored prediction endpoint. It encompasses a feature store that serves the same features consistently at training time and serving time (eliminating train-serve skew), a training pipeline that tracks experiments, versions models, and pushes artifacts to a registry, a serving layer that can deploy new model versions with A/B testing or canary rollouts, and a monitoring system that detects when the real-world data distribution shifts away from what the model was trained on. In Go, each of these stages is a well-defined service with clear interfaces, and Go's strengths in concurrent data processing, gRPC service definition, and cloud-native deployment make it an excellent language for stitching them together.

This chapter builds a complete end-to-end ML pipeline in Go: a streaming feature computation service backed by Redis for online serving and a data warehouse for offline training, a training pipeline that shells out to Python for the compute-intensive gradient descent but orchestrates all I/O in Go, a model registry using object storage, an ONNX-based serving engine with gRPC and REST interfaces, and a drift detection monitor that triggers retraining alerts when input distributions diverge. Every component is designed for operational simplicity: health checks, structured logging, graceful shutdown, and Prometheus metrics throughout.

**What you'll learn in this chapter:**

- ML pipeline architecture: the separation between offline training, online feature serving, and real-time inference, and why conflating them causes production failures
- Feature store design: building a dual-path store that serves pre-computed features at microsecond latency from Redis while maintaining training consistency with a batch feature warehouse
- Training pipeline orchestration in Go: experiment tracking, hyperparameter logging, model artifact versioning, and promotion gates
- Model serving at scale: implementing a gRPC inference server with ONNX Runtime, batching, and graceful model hot-swap
- MLOps practices: CI/CD for ML models, automated integration testing with golden datasets, and staged rollout with traffic splitting
- A/B testing and canary deployments for model updates with statistical significance testing built into the rollout gate
- Data drift and model performance monitoring: population stability index, feature distribution divergence, and label drift detection
- Automated retraining triggers: event-driven pipeline restarts when drift metrics exceed thresholds

**Why this matters at scale:**

Every company that operates ML at scale eventually builds the same thing, and several have written about it publicly. Airbnb's Bighead was built to standardize feature engineering and model serving across many models, with train-serve skew as an explicit target: the platform exists so that individual teams cannot accidentally compute a feature one way offline and another way online. Spotify named its ML platform Hendrix in 2022, and has described it as serving hundreds of ML practitioners across recommendation, search, and discovery. Uber's Michelangelo write-ups cover the same ground from the feature store angle.

Read these as convergent evidence rather than as trivia. The striking thing is not any single company's numbers, it is that independent teams solving this problem keep arriving at the same components: a feature store with a shared definition across training and serving, a model registry, a promotion gate, and drift monitoring wired to retraining. That recurrence is what makes the patterns in this chapter worth learning rather than merely worth reading.

**Prerequisites:** Go 1.27.1 baseline, Chapter 113 (ML fundamentals and ONNX inference), Go concurrency patterns (Chapters 17--22), gRPC in Go (Chapters 42C--46), and familiarity with Redis and object storage APIs.

### Junior → FAANG: The 95% That Interviews Test

The Google "Hidden Technical Debt" paper is referenced in virtually every serious ML engineering interview. Know the core insight: model code is 5% of the system. The other 95% is infrastructure. When an interviewer asks "design an ML system for fraud detection," they are not asking for a model architecture: they are asking for the 95%. Your answer should cover data collection and validation, feature engineering and the feature store, training orchestration and experiment tracking, model versioning and promotion, serving infrastructure, monitoring, and retraining triggers. A candidate who dives into neural network architecture selection before covering any of this infrastructure signals that they have read ML papers but have not shipped production ML systems.

The most practical first habit for a junior on an ML infrastructure team is to map every component of the current production pipeline and document what happens when each one fails. What happens if the feature store is unavailable? Does the serving layer fall back to cached features, use default values, or return an error? What happens if the training job fails halfway through? Does it restart from a checkpoint or from scratch? Documenting these failure modes is the fastest way to identify gaps, demonstrate engineering maturity to your manager, and prepare yourself for on-call rotations.

Build a minimal end-to-end ML pipeline in Go as a personal project: a data ingestion script that reads from a CSV, a feature engineering step that normalizes and encodes, a training orchestration wrapper that calls a Python training script and captures the output artifact, a model registry backed by local storage, and a serving HTTP server that loads the model and handles inference requests. This project, even at toy scale, gives you the vocabulary and the structural understanding to design much larger systems.

### Senior @ FAANG: Owning the 95% as Platform

Senior engineers at FAANG who own ML pipelines think of themselves as platform engineers who happen to serve ML workloads. The platform's job is to make the 95% invisible to the model team so they can focus on the 5% where they add unique value. A model team that has to manually manage feature computation, experiment tracking, model versioning, and serving configuration is spending their time on infrastructure, not on model quality. Every hour a data scientist spends debugging a feature store connection is an hour not spent improving the model that drives the business metric.

Designing ML pipelines as platforms means defining stable interfaces at each stage boundary. The interface between data ingestion and feature engineering is a schema-validated event or row format. The interface between feature engineering and model training is a versioned dataset artifact with recorded lineage. The interface between training and serving is a model artifact bundle that includes the model weights, the preprocessing configuration, the feature schema, and the evaluation metrics from the last evaluation run. These interface definitions, captured as protobuf schemas or JSON schemas, are the architectural contracts that allow each stage to evolve independently without breaking adjacent stages.

Retraining automation is where ML pipelines deliver their most significant long-term value, and it is also where the most subtle bugs live. Automated retraining pipelines must handle: training data preparation that is idempotent and reproducible, hyperparameter selection that does not overfit to the evaluation set used for selection, model promotion logic that compares the challenger model to the champion on a held-out test set using the same evaluation criteria, and rollback automation when the newly promoted model degrades in production. Each of these steps has failure modes that are not obvious until they occur in production, which is why senior engineers who have designed and operated these pipelines accumulate institutional knowledge that is extremely difficult to replace.

At L6, the ML pipeline is a product that has internal customers (model teams) and SLOs (pipeline runs complete within 4 hours, model promotions happen within 24 hours of a training trigger, serving latency P99 under 10 milliseconds). Treating it as a product means running quarterly reviews with model teams to understand their pain points, prioritizing pipeline improvements based on business impact, and publishing reliability metrics internally so customers can see the pipeline's health. This product-oriented mindset distinguishes staff engineers who build platforms that improve over time from those who build infrastructure that stagnates after the initial release.

The "Hidden Technical Debt" paper's warning about feedback loops is particularly relevant at staff level. An automated retraining pipeline that trains on the model's own predictions (common in recommendation systems where the only available signal is what the model recommended) can develop and amplify biases over time in ways that are extremely difficult to detect and correct. Designing the training data pipeline to preserve population diversity, implementing offline bias audits as a required step in the retraining workflow, and maintaining a holdout set of users who receive random recommendations as a ground-truth reference are the kinds of systemic safeguards that staff engineers are expected to design and champion.
