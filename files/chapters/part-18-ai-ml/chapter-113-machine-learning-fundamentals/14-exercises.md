## Exercises

1. **ONNX Model Inference Service**: Export a scikit-learn or PyTorch model to ONNX format and build a Go HTTP inference service using a maintained ONNX Runtime binding such as `yalue/onnxruntime_go`. The service must accept a JSON payload of feature values, run synchronous inference, and return predictions with latency under 5 ms at the 99th percentile. Add a `/health` endpoint that warms up the ONNX session on startup and reports model metadata (input names, shapes, ONNX opset version). Expected outcome: a production-ready inference server that serves a real ONNX model with measurable sub-5 ms p99 latency under load.

2. **Type-Safe Feature Engineering Pipeline**: Implement a Go feature engineering pipeline using the builder pattern that chains transformers: `StandardScaler`, `MinMaxScaler`, `OneHotEncoder`, and `MissingValueImputer`. Each transformer must implement a `Fit(data [][]float64) error` / `Transform(data [][]float64) ([][]float64, error)` interface, and the pipeline must serialize/deserialize its fitted state to JSON for reproducibility. Expected outcome: a pipeline that produces identical output when re-loaded from disk, verified by a round-trip test comparing pre- and post-serialization transform results on the same dataset.

3. **gRPC Model Serving with Streaming**: Define a Protobuf service `PredictService` with a unary `Predict(PredictRequest) PredictResponse` RPC and a server-streaming `PredictBatch(BatchRequest) stream PredictResponse` RPC. Implement the server in Go backed by a Gonum-based logistic regression model. Add TLS mutual authentication and a per-client rate limiter (token bucket, 100 req/s) as gRPC interceptors. Expected outcome: a gRPC inference server that handles both single and batch predictions securely, with load test results showing linear throughput scaling up to the rate limit.

4. **Gradient Descent Optimizer Comparison**: Implement vanilla SGD, SGD with momentum, RMSProp, and Adam optimizers from scratch in Go using `gonum/mat`. Train a multi-layer perceptron on a synthetic dataset (XOR or spiral) with each optimizer and plot convergence curves (loss vs. epoch) using `gonum/plot`. Expected outcome: a benchmarking harness with saved PNG plots showing epochs-to-convergence for each optimizer. Do not go in expecting a fixed ranking. The adaptive methods usually converge in fewer epochs on problems like these, but the ordering is sensitive to learning rate, initialization, and the random seed, and well-tuned SGD with momentum frequently matches or beats Adam. The real deliverable is the harness plus an honest account of how much the result moved when you varied the seed: an optimizer comparison that reports a single run is measuring noise.

5. **Cross-Validation and Hyperparameter Search**: Build a k-fold cross-validation harness for any model implementing a `Fit` / `Predict` interface. Wrap it in a grid search that evaluates all combinations of supplied hyperparameter ranges, records precision/recall/F1 per fold, and returns the configuration with the highest mean F1 score. Parallelize fold evaluation with goroutines. Expected outcome: a generic model selection utility that outperforms a default configuration on a held-out test set, demonstrated on a decision tree with varying `max_depth` values.

6. **Model Drift Detection Monitor**: Write a Go service that receives prediction requests, logs feature vectors and model outputs to a time-series store, and periodically computes the Population Stability Index (PSI) between the current week's feature distribution and the training baseline. Emit a structured warning log and increment a Prometheus counter when PSI crosses 0.25 for any feature, the conventional major-shift line. Expected outcome: a monitoring service that automatically flags distribution shift within one detection interval, verified by a test that injects a shifted distribution and asserts the alert fires.

### Junior → FAANG: Exercises as Interview Demonstrations

These exercises are not homework: they are portfolio artifacts. Complete at least exercises 1 and 6 and push them to a public repository with a README explaining the architecture decisions. The ONNX inference service (exercise 1) demonstrates that you can bridge the Python training world with Go serving infrastructure. The drift detection monitor (exercise 6) demonstrates that you understand production ML monitoring, which is the most underserved skill in most ML engineering portfolios.

When presenting these projects in an interview, lead with the engineering decisions rather than the implementation details. "I chose ONNX as the model format because it decouples the Python training environment from the Go serving infrastructure, and I implemented hot-reload using a read-write mutex and a background goroutine that polls the model registry every 60 seconds" is the kind of answer that signals production readiness. The decision framing matters more than the code volume.

Exercise 2 on the feature transformation pipeline is particularly valuable because it forces you to solve the training-serving consistency problem in practice. Implement the normalization statistics computation at training time, serialize them to JSON, load them in the serving pipeline, and apply them identically. Write a test that verifies identical outputs for identical inputs between training time and serving time. That test is worth mentioning explicitly in interviews as your approach to preventing training-serving skew.

### Senior @ FAANG: Exercises as Team Skill Builders

These exercises serve a different purpose for senior engineers: they are templates for internal workshops and onboarding exercises. Exercise 4 (gradient descent optimizer comparison) is an excellent onboarding exercise for engineers joining an ML platform team because it builds intuition for optimization dynamics that is directly applicable to understanding why model training pipelines fail to converge or converge slowly. Adapting these exercises for internal use and running them as team learning sessions is a concrete way to build team capability.

Exercise 5 (cross-validation and hyperparameter search with goroutines) demonstrates a pattern that senior engineers should ensure is implemented correctly in the team's model selection tooling. Parallelizing fold evaluation with goroutines is straightforward in Go but has subtle correctness requirements: the goroutines must not share mutable state, the results must be aggregated correctly, and the random seed for fold creation must be reproducible. Review the team's existing cross-validation tooling against these requirements and file issues for any gaps.

The exercise set as a whole represents a minimum viable skill demonstration for junior-to-mid-level ML infrastructure engineers. Senior engineers can use completion of this exercise set as a signal that a new team member is ready to contribute to production ML infrastructure work independently, and can structure probationary periods and code review checklists around the skills demonstrated by each exercise. Documenting this mapping explicitly helps managers conduct fair and consistent performance calibration.
