## Exercises

1. **Full RAG Pipeline from Scratch**: Build a complete Go RAG pipeline: ingest Markdown documents → chunk with 1000-char size and 200-char overlap → batch-embed with OpenAI `text-embedding-3-small` → upsert into pgvector → handle a user query by embedding it, retrieving top-5 chunks with cosine similarity, and sending them as context to the OpenAI Chat API. Return the final answer with source citations. Expected outcome: a working RAG pipeline that answers factual questions about the ingested documents with accurate citations.

2. **Vector Embedding Generation Service**: Implement a Go HTTP service that accepts batches of up to 2048 text strings, calls the embedding API in concurrent sub-batches (respecting the provider's batch size limit), and returns normalized 1536-dimensional vectors. Cache results in Redis keyed by SHA-256 of the input text. Expose Prometheus metrics for cache hit rate, embedding latency, and API error rate. Expected outcome: a shared embedding microservice where cache hit rate exceeds 60% in a typical RAG workload, verified by a replay test.

3. **Semantic Search with Metadata Filtering**: Extend a pgvector-backed search endpoint to support structured metadata filters (e.g., `source_domain`, `published_after`, `category`) combined with ANN search using pgvector's `<=>` operator. Implement the filter-then-search pattern using parameterized SQL and benchmark it against search-then-filter to demonstrate pre-filtering's performance advantage on filtered datasets. Expected outcome: sub-20 ms p99 search latency on 500,000 vectors when filters reduce the candidate set to under 10%.

4. **Hybrid Search with Reciprocal Rank Fusion**: Implement hybrid search in Go by running a dense vector ANN query (pgvector) and a BM25 full-text query (PostgreSQL `tsvector`) in parallel goroutines, then merging the ranked result lists using Reciprocal Rank Fusion (RRF) with `k=60`. Compare retrieval recall on a test query set against pure dense and pure sparse baselines. Expected outcome: hybrid search achieves at least 5% higher recall@10 than either pure approach on queries containing rare proper nouns.

5. **Embedding-Based Semantic Cache for LLM Responses**: Build a semantic response cache that stores (query embedding, LLM response) pairs in pgvector. On each new query, retrieve the nearest stored embedding, and if cosine similarity exceeds a configurable threshold (default 0.95), return the cached response without calling the LLM. Track cache hit rate, average similarity of hits, and estimated cost savings via Prometheus metrics. Expected outcome: a cache that reduces LLM API calls by at least 30% on a realistic question-answering workload with repeated or paraphrased queries.

6. **RAG Quality Evaluation Harness**: Write a Go evaluation harness that loads a JSONL file of (question, expected_answer, relevant_chunk_ids) test cases, runs each question through a RAG pipeline, and scores each result on: retrieval precision@k (did the correct chunks appear in the top-k?), answer exact-match, and LLM-as-judge faithfulness (call the LLM to rate 1-5 whether the answer is supported by the context). Output a summary report with mean scores and flag regressions against a stored baseline. Expected outcome: an automated RAG evaluation tool that detects quality regressions when chunking strategy or retrieval parameters are changed.

### Junior → FAANG: Building a Portfolio from These Exercises

Exercise 1 (full RAG pipeline from scratch) is the single most important exercise in this book for an AI infrastructure role. Complete it before any interview for a role that mentions RAG, semantic search, or vector databases. The exercise is designed to require you to solve each of the real engineering challenges: batch embedding with rate limiting, chunking with overlap, pgvector query with cosine distance, context assembly with token budget, and citation generation. Each solution you find to these problems is a story you can tell in an interview.

Exercise 6 (RAG quality evaluation harness) is the exercise that most clearly demonstrates senior-level thinking to interviewers. The question it addresses ("how do you know if your RAG is working?") is one that most junior engineers cannot answer. Implementing a systematic evaluation harness shows that you have thought about quality measurement, not just quality improvement. This is the difference between an engineer who ships a feature and an engineer who ships a feature and knows it works.

### Senior @ FAANG: Exercises as Hiring Assessment Tools

For senior vector search infrastructure candidates, exercise 4 (embedding cache with Redis) is the most discriminating implementation test. A strong implementation uses SHA-256 content hashing for cache keys (not fuzzy hashing or content truncation), implements LRU-like TTL management that refreshes TTL on cache hit, includes a background goroutine that monitors cache hit rate and emits it as a Prometheus metric, and handles Redis unavailability gracefully by falling back to direct API calls without surfacing the error to the caller. Each of these details requires both Go concurrency knowledge and production Redis expertise.

Exercise 6 (evaluation harness) is the best assessment for candidates with RAG system design experience. Strong submissions include: concurrent evaluation with a configurable worker pool (to evaluate multiple test cases in parallel), a statistical test that distinguishes true quality regressions from random variation (bootstrapped confidence intervals on the mean score), and a human-readable report format that shows per-category results alongside the aggregate. The design decisions visible in the evaluation harness reveal the candidate's maturity in thinking about AI system quality measurement, which is increasingly important as AI features become more prevalent in production systems.
