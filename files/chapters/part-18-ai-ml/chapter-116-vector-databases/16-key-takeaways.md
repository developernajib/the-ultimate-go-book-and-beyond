## 116.15 Key Takeaways: Vector Database Principles

1. **Vector Embeddings are Foundational**: Understanding how embeddings capture semantic meaning is crucial for building effective AI applications. OpenAI's text-embedding-3-small provides excellent quality at 1536 dimensions for most use cases.

2. **Distance Metrics Matter, and Matter Less Than You Think Once You Normalize**: Use the metric your embedding model was trained for. On unit-length vectors, cosine, dot product, and L2 all produce the *same ranking*, so the choice is purely about cost and dot product wins. On un-normalized vectors they genuinely diverge, because dot product rewards magnitude and will surface verbose documents over relevant ones. Normalize at write time and this stops being a correctness question.

3. **ANN Algorithms Enable Scale**: Exact nearest neighbor search is O(n) and impractical for production. HNSW provides the best recall for most workloads, while IVF-PQ enables billion-scale search with memory constraints.

4. **Choose the Right Vector Database**:
   - **Pinecone**: Best developer experience, managed service, serverless option
   - **Weaviate**: Hybrid search, GraphQL, built-in vectorization modules
   - **Milvus**: Open-source, billion-scale, partition strategies for multi-tenancy
   - **pgvector**: PostgreSQL extension, combines relational + vector, good for existing Postgres users

5. **RAG Architecture is Critical**: Document chunking strategy dramatically impacts retrieval quality. Start with 1000-character chunks with 200-character overlap, then optimize based on your documents and queries.

6. **Production RAG Requires Iteration**: The basic RAG flow (chunk → embed → retrieve → generate) is simple, but production systems need:
   - Reranking to improve top results
   - Hybrid search for better recall
   - Metadata filtering for relevance
   - Caching to reduce costs

7. **Index Selection Impacts Everything**:
   - < 100K vectors: HNSW (M=16, ef=200)
   - 100K - 10M vectors: HNSW or IVF-PQ
   - > 10M vectors: IVF-PQ with proper tuning
   - Rebuild indices as data grows

8. **Cost Optimization Matters**: Embedding API calls, vector storage, and query costs add up quickly. Strategies:
   - Cache embeddings aggressively
   - Batch operations when possible
   - Use smaller dimensions if quality allows
   - Monitor and cap query volumes

9. **Monitoring is Essential**: Track query latency, recall, cache hit rates, and error rates. Set up alerts for degraded performance and implement gradual rollouts for index changes.

10. **Common Pitfalls to Avoid**:
    - Don't embed entire documents (chunk first, on semantic boundaries where you can)
    - Don't ignore metadata (it improves relevance, and it is how you scope multi-tenancy)
    - Don't skip index optimization (default settings aren't optimal)
    - Don't let the index's metric disagree with your vectors. Normalize at write time, and then verify what metric the index is actually configured with. Note that normalizing does *not* fix cosine (cosine is already magnitude-invariant) - it makes inner product safe and lets all three metrics rank identically
    - Don't let the query operator disagree with the index's operator class, or you get a silent sequential scan
    - Don't hardcode a similarity threshold. Raw scores are model-specific - calibrate or don't threshold
    - Don't over-provision (start small, scale as needed)

### Junior → FAANG: Takeaways as Mental Models

"Vector embeddings are foundational" is a career-level statement: this technology is not going away, and engineers who understand it deeply will have a durable advantage for the next decade. Invest the time to understand embeddings at the mathematical level (what they are), the model level (how they are generated by neural networks), and the application level (what they enable). This three-level understanding makes you capable of evaluating new embedding technologies and use cases as they emerge rather than following trends reactively.

The "hybrid search outperforms pure vector search" takeaway has a practical implication for interview answers: when asked to design a search system, always mention hybrid search and explain why it is better than pure vector search for real-world query distributions. Pure vector search is the naive answer. Hybrid search with score fusion is the production-quality answer. The distinction signals that you have designed and evaluated real search systems, not just read about them.

### Senior @ FAANG: Takeaways as Engineering Principle Library

These takeaways, internalized as engineering principles, guide architecture decisions across all vector search use cases. "Start with pgvector, migrate when needed" prevents premature adoption of specialized infrastructure that adds operational complexity before the scale justifies it. "Chunk, then embed" prevents the most common quality mistake that new practitioners make. "Normalize vectors" prevents silent correctness bugs that appear only when mixing embedding sources.

At L7, engineering principles like these should be captured in the organization's internal engineering guidelines rather than in individual team knowledge. When these principles are discoverable by any engineer starting work on a vector search feature, the organization's collective knowledge is systematized rather than siloed. Contributing to and maintaining internal engineering guidelines is a staff-level knowledge sharing responsibility with organization-wide impact.
