## Exercises

1. **Multi-Provider LLM Client with Fallback**: Build a Go LLM client that wraps OpenAI and Anthropic APIs behind a common `Completer` interface. Implement automatic failover: if the primary provider returns a 5xx error or times out after 10 seconds, the client retries the request against the secondary provider. Track per-provider latency, token usage, and error rates via Prometheus counters. Expected outcome: a resilient client that transparently falls back to the secondary provider, with integration tests simulating primary failure.

2. **Streaming Chat with Cost Budget Enforcement**: Implement a streaming chat endpoint in Go that calls the OpenAI Chat Completions API with `stream: true`, forwards server-sent events to the HTTP client in real time, and enforces a per-session token budget. Reject the request with HTTP 402 *before* opening the stream if the session's budget is already exhausted. If the budget runs out mid-response, you face the central design constraint of this exercise: **you cannot send an HTTP status code once streaming has begun**, because the `200` and its headers went out with the first chunk. Design the SSE protocol to carry in-band errors instead, by emitting a terminal event (for example `event: error` with a JSON payload) that the client is written to recognise, then closing cleanly. Expected outcome: a streaming endpoint where budget exhaustion before the stream is a clean 402, exhaustion during the stream is a well-formed terminal event rather than a silently truncated answer, and the client can tell the two apart from a dropped connection.

3. **Prompt Template Registry with Version Control**: Design a Go prompt template registry backed by a PostgreSQL table with columns `(name, version, template, variables jsonb, created_at)`. Implement `Render(name, version string, vars map[string]any) (string, error)` with `text/template` execution and `Publish` / `Rollback` operations. Add middleware that logs which template version was used for every LLM call so prompt regressions can be traced back to specific template changes. Expected outcome: a versioned prompt management system that enables A/B testing of prompt variants without code deployments.

4. **RAG-Ready Chunking and Embedding Pipeline**: Implement a document ingestion pipeline that reads plain-text or Markdown files, splits them into overlapping chunks (configurable size and overlap), calls the OpenAI Embeddings API in batches of 100, and upserts chunk vectors with metadata into a pgvector table. Include retry logic with exponential backoff for rate-limit errors and a progress bar reporting chunks processed. Expected outcome: a reusable ingestion binary that fully indexes a 500-page document in under 5 minutes while respecting API rate limits.

5. **Circuit Breaker for LLM APIs**: Implement a circuit breaker (closed / open / half-open state machine) around any LLM API client using only the standard library. The breaker must open after 5 consecutive failures within a 60-second window, return an `ErrCircuitOpen` sentinel error immediately while open, and attempt one probe request after a 30-second cool-down. Write unit tests that simulate failure sequences and assert correct state transitions. Expected outcome: a generic circuit breaker that prevents cascading failures when the LLM API is degraded, verified entirely by unit tests with a mock clock.

6. **LLM Cost Analytics Dashboard Backend**: Build a Go HTTP API that aggregates token usage events and exposes endpoints for: total cost by model and date range, top-10 most expensive sessions, hourly cost trend (last 7 days), and a projection of monthly spend based on the current daily average. Implement all aggregations as parameterized PostgreSQL queries with proper indexing. Expected outcome: a cost analytics API that returns any aggregation in under 100 ms against a table of 1 million usage records.

### Junior → FAANG: Exercise Prioritization for Interview Readiness

Complete exercises 5 (circuit breaker) and 6 (cost analytics) as your highest priority exercises before an LLM infrastructure interview. Exercise 5 demonstrates Go concurrency skills (state machine with mutex, configurable timers, atomic state transitions) applied to a concrete production problem. Exercise 6 demonstrates data engineering skills (time-series aggregation, PostgreSQL query optimization, API design) applied to a domain that every LLM interviewer cares about deeply. Together, they cover reliability and cost, the two concerns that dominate production LLM engineering discussions.

When presenting these exercises in an interview, lead with the design decision that was hardest to get right. For the circuit breaker: "The hardest part was the half-open state transition. I needed to ensure that only one probe request goes through while the breaker is half-open, and that concurrent requests during half-open fail fast rather than all becoming probes. I solved this with a compare-and-swap operation on an atomic integer that only the first goroutine to enter half-open can claim." This level of technical specificity demonstrates that you actually built it rather than just knowing about it.

### Senior @ FAANG: Exercises as Engineering Assessment Rubric

For evaluating senior LLM infrastructure candidates, exercise 2 (streaming proxy with SSE) is the most discriminating. A candidate who implements it correctly with proper client disconnection detection, mid-stream error handling, and backpressure between the upstream SSE stream and the downstream HTTP response demonstrates Go concurrency mastery and production streaming knowledge simultaneously. Common failure modes in candidate submissions: forgetting to flush after each write (so all chunks arrive at once), not detecting client disconnection (wasting API tokens on canceled requests), not handling mid-stream errors (the SSE stream sends an error event, the proxy ignores it and returns a partial response).

Exercise 6 (cost analytics) is a good assessment for the combination of data engineering and API design skills. A strong submission includes: proper use of database indexes on the query dimensions (model, date, session ID), query parameterization to prevent SQL injection, a time-series aggregation that handles hourly bucketing correctly across DST boundaries, and a monthly projection that accounts for weekend versus weekday variance in usage patterns. These details distinguish candidates who have built production analytics systems from those who have only done toy implementations.
