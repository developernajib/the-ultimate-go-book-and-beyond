## 117.15 FAANG Interview Questions

**Q: When should a team reach for an AI agent instead of a deterministic workflow?**

A: Agents are right when the task requires dynamic tool selection, iterative reasoning, or open-ended planning under uncertainty. They are wrong when the task is a well-defined sequence of steps that you could write as a state machine. Agents cost more in tokens, latency, and debugging difficulty, so the default is a deterministic pipeline and the exception is an agent. Customer support triage, research assistance, and exploratory code navigation favor agents. Payment processing, scheduled reports, and validated form submissions do not.

**Q: Design an agent runtime that safely executes tool calls on behalf of a model.**

A: Declare every tool with a schema (arguments, return type, side effects, required permissions). The runtime validates tool call arguments against the schema before execution. Each tool runs inside a sandbox with the minimum required privileges, a wall-clock timeout, and an output size cap. Dangerous tools (file write, shell, payments) require explicit user approval captured as a signed event. Every invocation emits a structured audit record with the agent ID, tool name, arguments, result hash, and latency. On error, the runtime returns a typed error to the model rather than a raw stack trace.

**Q: How do you prevent runaway token spend and infinite loops in a production agent?**

A: Hard caps at multiple layers. Per-conversation: maximum tokens, maximum tool calls, maximum wall-clock time. Per-user: daily cost quota and QPS limit. Per-tool: per-minute call budget so one bad plan does not hammer a downstream API. Detect loops with a simple signature over the last N tool calls and abort if the same signature repeats. Expose cost and step count in real time on an operator dashboard so humans can pause misbehaving agents.

**Q: Explain the ReAct pattern and where it breaks down.**

A: ReAct interleaves Reasoning ("thought") and Acting ("tool call") steps, with each tool observation feeding back into the next thought. It works well for tasks with clear intermediate feedback (search, calculator, code execution). It breaks down when the model fabricates plausible but false observations, when tools return ambiguous results that the model cannot interpret, or when the required plan is longer than the context window. Mitigations include structured tool outputs, persistent scratchpad memory, and a planner-executor split where a larger model plans and a smaller model executes.

**Q: How would you design a stateful agent that runs across many sessions?**

A: Split memory by lifetime and access pattern. Short-term is the conversation buffer: a bounded window replayed to the model each turn, with the bound enforced because the whole history is resent every step and cost grows with the run. Long-term is a vector store of past interactions and facts, retrieved by embedding the current state and pulling top-k. Between them sits summarization: when the buffer nears a token threshold, condense the oldest span into a summary that preserves decisions and results while dropping superseded reasoning.

Second-order concerns are what separate levels here. The vector store is a production dependency with its own SLA. The embedding model is versioned, and changing it invalidates every stored vector, so a migration means re-embedding the corpus. Retrieval introduces non-determinism that makes runs non-reproducible. And the memory holds user data, so it needs per-user deletion for erasure requests and a retention policy set deliberately, designed in from the start rather than retrofitted when legal asks.

**Q: Tool output is attacker-controlled. How do you design around that?**

A: This is the question that matters most, and the framing in it is the answer. A model receives system prompt, user turn, and tool results as one flat token sequence with no structural marker separating instruction from data. There is no prepared-statement equivalent, because the thing you would need to parameterize is the model's own judgment about what counts as an instruction. So injection is not a bug to be patched, it is the medium's property.

Design accordingly. Treat every byte a tool returns as adversarial: web pages, file contents, database rows, other agents' output, a support ticket body. Do not rely on instructing the model to resist, because any defense living inside the context window can be argued with by text arriving later in that same window. Put enforcement outside the model, where it gets no vote: a database role granted SELECT only, a host allowlist compared against a parsed URL, path containment via `filepath.Rel`, and a human approval gate on anything irreversible. Then assume the model is fully compromised and ask what it can still reach. That answer is your real blast radius, and it is set by the tool set, not the prompt.

Finally, audit tool *combinations*, not tools. Retrieval plus any outbound-request tool is an exfiltration channel even when both tools are individually reasonable and individually well reviewed. The agent that reads the web should not be the agent that holds database credentials.

**Q: How would you evaluate an agent system end to end before shipping to production?**

A: Build a benchmark of representative tasks with graded success criteria (exact match, rubric-based scoring, or task completion check). Run the agent against the benchmark with instrumentation that captures every tool call, token, and intermediate state. Score three dimensions: success rate, cost per task, and safety (no forbidden tool calls, no PII leaks, no destructive actions). Compare against a human baseline and a deterministic baseline. Add regression tests in CI so a prompt or tool change cannot silently degrade any of the three dimensions.

### Junior → FAANG: Using These Questions as a Structured Study Plan

Each Q and A pair in this list is one study unit. For each unit, the study process is: read the question and formulate your own answer before reading the provided answer, compare your answer to the provided answer and identify what you missed, identify one concrete Go implementation that demonstrates the concept, and then write one sentence that captures the core trade-off. The "when to use an agent" question's core trade-off is: dynamic reasoning versus reliability cost. The "stateful agent" question's core trade-off is: context window efficiency versus retrieval accuracy. The "tool output is attacker-controlled" question's core trade-off is: autonomy versus blast radius. Naming the trade-off explicitly is what FAANG interviewers are listening for, because it shows you understand the problem space rather than just the solution.

For behavioral interview questions that accompany technical rounds at FAANG, prepare an agent-related story for each standard behavioral prompt. "Tell me about a time you prevented a production incident" maps to implementing safety guardrails before deploying an agent. "Tell me about a time you made a technical decision with incomplete information" maps to choosing between building a multi-agent system and a simpler pipeline when the requirements were ambiguous. "Tell me about a time you simplified a complex system" maps to replacing an overengineered agent with a deterministic function that was more reliable and cheaper. Having specific, concrete agent stories ready for behavioral questions is as important as technical preparation.

The evaluation question at the end of this list is the one that most juniors cannot answer well, because building agent evaluation frameworks is rare junior experience. The key insight to internalize is that agent evaluation is multi-dimensional: you cannot optimize for success rate alone without considering cost and safety, and you cannot claim a high success rate without a benchmark that is representative of the production task distribution. Practice building a small benchmark for any agent you implement: write ten representative tasks, define a grading rubric for each, run your agent against all ten, and report the results. This practice, even at small scale, builds the evaluation mindset that interviewers are looking for.

### Senior @ FAANG: Interview Questions as Staff-Level Planning Tools

These interview questions map directly to the planning artifacts that staff engineers produce before shipping an agent system to production. "When should a team reach for an agent?" is the agent adoption proposal template: document the use case, the deterministic alternative considered, the reason the deterministic alternative is insufficient, the expected success rate, and the cost model. "How would you design a stateful agent?" is the memory architecture design document: specify the short-term memory type and capacity, the long-term memory storage technology and retrieval mechanism, the summarization strategy for context window management, and the data retention policy. "Tool output is attacker-controlled" is the safety review document: enumerate every tool's blast radius, specify the approval workflow for high-impact tools, define the content filtering rules for inputs and outputs, and identify the monitoring signals that would indicate a safety violation.

At senior level, preparing for FAANG interviews on agent systems also means being ready to evaluate candidate answers using these Q and A pairs as the rubric. An L5 candidate should give answers that match the provided answers closely, showing broad coverage of the key concepts. An L6 candidate should go beyond the provided answers to identify second-order concerns: for "how would you design a stateful agent?", an L6 candidate would note that the vector database backing the long-term memory must be treated as a production dependency with its own SLA, that the embedding model used to generate stored embeddings must be versioned and cannot be changed without re-embedding all stored memories, and that the retrieval mechanism introduces non-determinism that complicates reproducibility. Recognizing this depth of answer is itself a senior skill for hiring committees and calibration discussions.

The evaluation question is the highest-signal question in this list for senior candidates because agent evaluation frameworks are one of the least mature areas in production AI engineering. A strong senior answer would go beyond the provided answer to include: offline evaluation using a held-out task set, online evaluation using user feedback signals (implicit: did the user need to re-ask the question? explicit: did the user rate the response positively?), automated regression testing using LLM-as-judge for tasks where exact match is impossible, and adversarial evaluation using red-team prompts designed to test safety boundaries. The candidate who can describe all four evaluation modalities, explain when each is appropriate, and identify the failure modes of each is demonstrating the evaluation rigor that staff-level AI platform engineers are expected to establish as team standards.
