## Summary

- **AI agents as tool-augmented LLM loops**: An agent is a control loop that calls an LLM, parses its output for tool invocations, executes tools, feeds results back as context, and repeats until the LLM produces a final answer or the iteration cap stops it. Not magic, just bounded, structured iteration.
- **ReAct pattern for transparent reasoning**: ReAct (Yao et al., 2022) interleaves reasoning traces with actions so each helps the other: reasoning tracks and updates the plan, actions gather facts the model would otherwise invent. The resulting trace is what makes agent behavior auditable.
- **Tool design as the primary capability lever**: Agent quality is determined by tool quality. Well-typed, well-documented tools with clear error messages and narrow surface areas produce better agent behavior than prompt tuning alone, and a tool's description is part of its interface because it is all the model knows about it.
- **Short-term and long-term memory**: Agents need a sliding-window conversation buffer (short-term) and a vector-searched fact store (long-term). Without persistent memory, agents cannot learn from past interactions or maintain multi-session context.
- **Multi-agent orchestration patterns**: Supervisor (single coordinator delegates to specialist workers), peer-to-peer (agents directly invoke each other), and hierarchical (teams of teams) patterns each suit different task decomposition needs.
- **Go's strengths in agent infrastructure**: Goroutines run independent agents and parallel tool calls concurrently, channels stream agent output, and Go's type system enforces a single decode-and-validate boundary for the model's JSON. That boundary is a runtime check the compiler makes unskippable, not compile-time validation of the arguments themselves, which no language can do when the arguments are written by a model at runtime.
- **Safety guardrails are non-negotiable**: Production agents require iteration caps, per-session cost budgets, wall-clock deadlines, tool allowlists, circuit breakers, and human approval for irreversible actions. Content filters belong on the list as tripwires, not as boundaries.
- **Tool output is untrusted input**: Prompt injection is the defining security problem of agents, because the model reads instruction and data from one undifferentiated token stream and cannot reliably separate them. Defenses inside the prompt are mitigations - the real boundaries live outside the model, where injected text has no vote. Assume the model is compromised and ask what it can still reach.
- **LLM function calling for typed tool invocation**: Provider function-calling APIs return structured JSON tool invocations, letting Go unmarshal arguments into typed structs and validate before execution. Remember that JSON numbers decode into `any` as `float64`, never `int`, and that a model can emit arguments violating its own declared schema.
- **Observability for agent debugging**: Log every LLM call with its input messages, the chosen tool, tool arguments, tool output, and total tokens consumed. Correlation IDs link the full reasoning chain across steps for post-hoc debugging.
- **Use agents only when simpler solutions fail**: A well-designed deterministic API call is more reliable, cheaper, and easier to test than an agent. Introduce agent loops only when the task genuinely requires dynamic tool selection or multi-step reasoning that cannot be pre-specified.

### Junior → FAANG: Summary Bullet Points as Interview Flashcards

Each bullet in this summary is an interview flashcard. Before a FAANG interview for an AI engineering role, read each bullet and practice expanding it into a two-minute verbal explanation with a concrete example. "AI agents as tool-augmented LLM loops" becomes: "An agent is not a magic system. It is a for loop that calls the LLM, reads the response to see if the LLM wants to call a tool, executes that tool in Go code, appends the result to the message history, and loops. When I implemented this in Go, the loop was about 40 lines, and every complexity above that came from the tools, the memory, and the safety checks, not from the loop itself." This kind of concrete, demystifying explanation signals implementation experience rather than conceptual familiarity.

The safety guardrails bullet is the one most interviewers probe because it separates candidates who have thought about production from those who have only built demos. Practice answering "what could go wrong with an agent in production?" by walking through each guardrail: without a MaxIterations limit, the agent loops forever. Without a cost budget, one user can exhaust the monthly LLM budget. Without a content filter, a user can prompt-inject instructions that cause the agent to call dangerous tools. Without a circuit breaker, a failing tool causes the agent to retry indefinitely rather than gracefully degrading. Each guardrail has a concrete failure mode. Knowing the failure modes is more important than knowing the implementation.

The function calling bullet maps to a specific technical question that appears frequently: "how does your Go code know which tool to call when the LLM decides to use a tool?" The answer is: the LLM returns a JSON object with a "name" field that is the tool name and an "arguments" field that is a JSON object. The Go agent code reads the "name" field, looks up the tool in a registry (a map from string to Tool interface), unmarshals the "arguments" JSON into the tool's parameter struct, validates the struct, and calls the tool's Execute method. This five-step process is what function calling actually does, and explaining it in these terms shows that you understand the mechanism rather than treating the API as magic.

### Senior @ FAANG: Summary as Architecture Decision Record Seed

Each bullet in this summary can seed an Architecture Decision Record (ADR) for a production agent system. The "LLM function calling for typed tool invocation" bullet becomes ADR-001: Tool Invocation Protocol. Context: our agent system needs to invoke tools based on LLM decisions. Decision: use the OpenAI function calling API format (tool name plus JSON arguments) as the standard interface, with Go structs for argument deserialization and JSON Schema for argument validation. Consequences: tool definitions must be maintained in two forms (Go struct for runtime validation, JSON Schema for the LLM prompt), but argument type errors are caught before tool execution rather than causing runtime panics. This ADR format, applied to each bullet, produces the documentation artifact that senior engineers are expected to leave behind for the teams that will maintain the system.

The "observability for agent debugging" bullet deserves particular depth at the senior level because it defines the difference between a debuggable and an undebuggable system. The minimum viable observability layer for an agent includes: a trace ID generated at the start of each agent run and propagated through every LLM call and every tool call. A structured log entry for each LLM call with the full message array, the model used, the token counts, and the latency. A structured log entry for each tool call with the tool name, the input arguments, the output, and the execution duration. And an error log for every retry attempt with the error type and the backoff duration. This data enables reconstruction of the full agent reasoning chain from logs alone, which is the capability required for post-hoc incident analysis when an agent takes an unexpected action.

The "use agents only when simpler solutions fail" bullet is the organizational decision-making principle that separates mature AI teams from teams that reach for agents as a default. At senior level, you are expected to apply this principle not just to your own work but to the proposals you review from other engineers. A practical decision framework: can the task be expressed as a finite state machine with known states and transitions? Then use a state machine. Can the task be expressed as a sequence of deterministic steps with known inputs and outputs at each step? Then use a pipeline. Can the task be expressed as a database query or API call? Then use a query or API call. Only when none of these alternatives is sufficient does the task genuinely require an agent. Enforcing this decision framework as a code review and design review standard prevents the accumulation of unnecessary complexity that makes AI systems expensive to operate and difficult to debug.
