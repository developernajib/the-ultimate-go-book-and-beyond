## Further Reading

- **Research Papers**: "ReAct: Synergizing Reasoning and Acting in Language Models" (Yao et al., 2022). Read the paper rather than a summary of it: the folklore version ("make the model think first") is not the claim, and the actual claim about interleaving is more useful.
- **Agent Security**: the OWASP Top 10 for LLM Applications, whose LLM01 entry is prompt injection. Track Simon Willison's ongoing writing on prompt injection and the "lethal trifecta" (private data, untrusted content, and an outbound channel in the same agent), which is the clearest framing of why tool *combinations* rather than individual tools set your blast radius.
- **Protocols**: the MCP specification at modelcontextprotocol.io and the A2A specification at a2a-protocol.org. Both move quickly. Read the dated spec revision, not a blog post about it. Chapter 118B covers both in depth.
- **LangChain Documentation**: Study the agent architectures (though we built ours in Go!)
- **Tool Use Best Practices**: the current function-calling and tool-use guides from whichever providers you actually use. These are the fastest-rotting entries on this list.
- **Production AI Systems**: "Designing Data-Intensive Applications" Chapter 11 on streaming processing
- **Go Concurrency**: "Concurrency in Go" by Katherine Cox-Buday for multi-agent patterns

### Junior → FAANG: Building a Reading Practice Around Agent Engineering

The ReAct paper (Yao et al., 2022) is mandatory reading before any FAANG interview that touches agents. Read the abstract, the experimental setup, and the results table. The key finding is that combining reasoning traces with action execution outperforms either reasoning alone (chain-of-thought) or action alone (Act). Understanding why this matters requires connecting it to production agent architectures: the "think" step in the observe-think-act loop is the reasoning trace, and the "act" step is the action execution. The paper provides the academic grounding for a design decision that otherwise looks arbitrary.

OpenAI's function calling guide and Anthropic's tool use documentation describe the same capability from different API perspectives. Reading both side by side reveals that the underlying mechanism is the same (the LLM returns a structured JSON object identifying the tool and its arguments, the caller executes the tool and returns the result), but the exact JSON schema differs. Understanding both prepares you to implement multi-provider agent systems where the same tool definitions must be translated between OpenAI's format and Anthropic's format. This translation layer is a common implementation task in platform engineering roles at companies that use both providers.

The Go concurrency book is particularly relevant for multi-agent systems because Go's goroutine and channel model maps cleanly onto agent coordination patterns. Each agent runs in its own goroutine. Tool calls can be parallelized with goroutine fan-out and a results channel. Context cancellation propagates through the goroutine tree to terminate all agents when the parent context is canceled. The patterns in chapters 3 through 6 of the concurrency book (pipelines, fan-out/fan-in, done channels, errgroups) are directly applicable to multi-agent architectures.

### Senior @ FAANG: Curating a Technical Reading List for an AI Platform Team

At senior level, the further reading list becomes a team resource that you curate and maintain. The ReAct paper should be supplemented with its successors: the Toolformer paper (Schick et al., 2023) demonstrates that models can learn to use tools autonomously, and the HuggingGPT paper (Shen et al., 2023) demonstrates orchestrating specialized models as tools within a planning agent. These three papers together form the theoretical foundation for understanding why agent architectures work and what their current limitations are, which is the knowledge base needed to evaluate new agent designs critically rather than accepting vendor marketing claims.

"Designing Data-Intensive Applications" Chapter 11 is specifically about stream processing, which maps onto the event-driven agent architectures that production systems use. An agent that processes a stream of user requests is a stream processor with state (the memory system) and side effects (the tool calls). The chapter's discussion of exactly-once semantics, checkpointing, and failure recovery applies directly to agent systems that must guarantee that tool calls are not duplicated when the agent process restarts after a failure. Understanding these guarantees, and knowing when they are necessary versus when at-least-once semantics are acceptable, is a senior-level design judgment that the DDIA chapter develops rigorously.

For platform engineering specifically, the Google SRE book's chapters on toil, service level objectives, and production readiness reviews apply directly to AI agent infrastructure. The key adaptation is that agents introduce non-determinism: the same input can produce different outputs on different runs, which complicates traditional SLO definitions. A senior engineer designing the observability layer for an agent platform must define SLOs in terms of outcomes (task completion rate, cost per completed task, time to completion at P50/P95/P99) rather than in terms of output correctness, because correctness is not mechanically verifiable for agent outputs. This adaptation of the SRE framework to non-deterministic AI systems is a staff-level technical contribution at FAANG AI platform teams.

The practical complement to these theoretical resources is the GitHub repositories of production-grade agent frameworks: the LangGraph source code demonstrates how to represent agent execution as a directed acyclic graph with conditional edges. The AutoGen source code demonstrates multi-agent conversation patterns. And the Semantic Kernel source code demonstrates how Microsoft's production agent SDK handles tool registration, memory management, and provider abstraction. Reading framework source code reveals the design decisions that documentation omits, and implementing the same patterns in Go (as done in this chapter) builds the understanding needed to evaluate framework trade-offs and make build-versus-buy decisions at the team level.
