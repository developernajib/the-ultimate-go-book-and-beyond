# Chapter 118: AI-Assisted Development & Vibe Coding

*"The question is not whether AI will replace engineers. The question is whether engineers who use AI will replace engineers who don't."* - A principle that defines the next decade of software engineering

The evidence on AI-assisted productivity is real, but it is far messier than the headline numbers suggest, and learning to read it correctly is the first skill this chapter teaches. GitHub's 2023 study (arXiv:2302.06590) randomized 95 developers to write an HTTP server in JavaScript with and without Copilot, and the Copilot group finished 55% faster, averaging 1 hour 11 minutes against 2 hours 41 minutes. That result is statistically solid and almost universally misquoted: it measures one greenfield task, in one language, on a codebase with no history, with a 95% confidence interval running all the way from 21% to 89%. It does not measure what happens when you work in a large repository you already know. METR's 2025 randomized trial measured exactly that, and found the opposite. Sixteen experienced open-source maintainers working 246 real tasks in their own mature repositories were roughly 19% *slower* with AI tools, while estimating afterward that they had been 20% faster. Both studies are correct. They measured different work.

The organizational numbers are equally worth reading carefully. Sundar Pichai told Alphabet's Q3 2024 earnings call that more than a quarter of new code at Google is AI-generated and then reviewed and accepted by engineers. Anthropic has said Claude wrote a large majority of the code merged into its own production codebase, with engineers directing and reviewing throughout. These are meaningful signals about drafting volume. Neither is a productivity measurement, and neither says anything about the review burden those drafts create. The question for any working software engineer is not whether to engage with these tools but how to engage with them in a way that accelerates output without compromising the correctness, security, and maintainability that define professional engineering.

AI code generation is genuinely useful for certain tasks and genuinely dangerous for others. Writing boilerplate, generating test cases for known-good logic, explaining unfamiliar library APIs, translating between serialization formats, scaffolding CRUD handlers: for these tasks, AI tools help most, because the output is easy to verify and a wrong answer is obvious. Designing concurrent systems, implementing cryptographic protocols, building authentication flows, writing database transactions with complex invariants: for these tasks, AI-generated code requires the same rigorous review as code from a junior engineer, because the failure modes are subtle, the blast radius is large, and the model's training data contains as many examples of insecure patterns as secure ones. The engineers who extract value from AI are those who have developed precise intuition for which category any given task falls into. The METR result is the cautionary half of that intuition: the tasks where AI feels fastest are not reliably the tasks where it is fastest, and feel is not evidence.

This chapter builds that intuition. You will understand the AI tool ecosystem, including Claude Code, GitHub Copilot, Cursor, and the underlying models, and how each is designed to be used. You will learn prompt engineering for Go specifically: how to communicate interface contracts, concurrency requirements, error handling expectations, and performance constraints in ways that produce idiomatic, production-quality output. You will develop a systematic code review methodology for AI-generated Go that catches the patterns models consistently get wrong: goroutine leaks, unchecked errors, SQL injection via format strings, and incorrect mutex usage. And you will learn to build a `CLAUDE.md` project context file that encodes your architecture, conventions, and constraints so that AI tools operate as informed collaborators rather than generic code generators.

**What you'll learn in this chapter:**
- The vibe coding philosophy and its appropriate scope: when moving fast without reading code is acceptable and when it is engineering malpractice
- The AI tool ecosystem: Claude Code, GitHub Copilot, Cursor, and the frontier models behind them, including their architectural differences, context window behaviors, and optimal use cases
- Prompt engineering for Go: communicating interfaces, type constraints, error handling contracts, concurrency requirements, and performance expectations precisely
- Senior-engineer-level code review methodology for AI output: the checklist of goroutine leaks, unchecked errors, security antipatterns, and correctness issues to audit first
- Patterns where AI consistently fails in Go: concurrent data structures, context propagation, interface satisfaction, generics constraints, and cryptographic implementations
- Building `CLAUDE.md` project context files that encode architecture decisions, naming conventions, testing patterns, and security requirements
- AI-augmented SDLC integration: using AI for requirement decomposition, architecture review, test generation, documentation, and postmortem analysis
- Go-specific AI techniques: using AI to navigate the standard library, generate table-driven tests, explain compiler errors, and refactor toward idiomatic patterns

**Why this matters at scale:**
The organizations reporting sustained gains are the ones that treated AI output as draft material entering an existing review pipeline, not as finished work bypassing it. The mature pattern at security-critical shops is consistent: AI writes the draft, and an engineer who understands the threat model reviews every line before it touches anything related to payments or authentication. The failure pattern is equally consistent, and the METR result names it. Teams that measure adoption by how fast the code appears, rather than by how fast it ships correctly, can move backwards while everyone involved is certain they are moving forwards.

**Prerequisites:** Chapters 1-20 (Go fundamentals and idiomatic patterns), Chapter 28 (HTTP and middleware), Chapter 106 (Application Security). Strong Go foundations are the prerequisite for AI-augmented engineering, not a replacement for it

### Junior → FAANG: Framing AI-Assisted Development for Interview Conversations

The framing in this introduction is the framing you should use in FAANG interviews when asked about your engineering productivity, and the important part is not the numbers but what you do with them. Citing "Copilot makes you 55% faster" demonstrates that you read a headline. Citing the GitHub study *and* the METR study, and explaining that they measured different work, demonstrates that you can evaluate evidence about your own tools, which is the actual signal the interviewer is listening for. More importantly, the framing positions AI as a tool that amplifies the engineer's existing skills rather than replacing them. The engineer who understands Go's type system, error handling patterns, and concurrency model uses AI to express that understanding faster. The engineer who lacks those foundations uses AI to generate code they do not understand, which fails review and produces maintenance debt.

For FAANG interview behavioral questions about productivity and impact, AI tool usage is now a valid and expected part of the answer. "How do you approach implementing a new feature?" should include a description of your AI-assisted workflow: how you use AI for initial scaffolding, how you review AI-generated code for correctness and security, how you iterate when the AI output does not meet your standards, and how you measure the quality of the result. This workflow description is not separate from engineering judgment. It is an expression of engineering judgment applied to the use of a new class of tools.

The calibration that matters most is this: AI-generated code that is not reviewed with the same rigor as human-generated code carries the same risk profile as code written by a junior engineer who does not fully understand the system. The review discipline described in this chapter, where every AI-generated function is checked for correctness of types, error handling, edge cases, and security, is the discipline that separates engineers who improve with AI assistance from engineers who accumulate debt with AI assistance.

### Senior @ FAANG: Leading the AI-Assisted Engineering Transition

The data points in this introduction are the starting point for an organizational capability assessment that senior engineers are expected to lead, and the first thing that assessment has to establish is what is actually true on your team rather than what is true in a vendor study. The senior engineer's role is to understand the organizational adoption barriers (security review, data privacy policy, workflow integration friction, measurement framework), address them systematically, and measure the result on your own codebase. The measurement half is not optional. METR's participants were experienced engineers who sincerely believed they had been sped up while the stopwatch said otherwise, and a rollout justified by self-reported velocity will reproduce that error at organizational scale.

The "engineers who use AI will replace engineers who don't" framing is a calibration statement, not a prediction. At FAANG, the calibration is more specific: engineers who use AI to amplify their engineering judgment will advance. Engineers who use AI as a crutch that masks weak foundations will be identified quickly because AI-generated code without engineering judgment is distinguishable in code review by its failure to handle edge cases, its generic error handling, and its violation of project-specific constraints. The platform strategy for AI-assisted development must include review standards that catch AI-assisted code quality issues, not just human-written code quality issues.

At L6, the staff engineer's contribution to AI-assisted development is the organizational capability model: what does Level 1 AI adoption look like (individual tool usage with no organizational coordination), what does Level 3 look like (team-standard CLAUDE.md, shared prompt libraries, AI review in the PR pipeline), and what does Level 5 look like (AI agents operating autonomously on defined task categories with human review at merge boundaries)? This maturity model, applied to the current team state and used to define a 12-month roadmap toward higher levels, is the planning artifact that staff engineers are expected to produce when asked about AI adoption strategy.
