## Toolchain Setup

Setting up a C++ development environment is more complex than Go's single `go` binary. C++ has multiple compilers, multiple build systems, and platform-specific considerations. This section covers the practical setup for each major platform.

### Compilers

There are three major C++ compilers. You should know all three because FAANG companies use different ones.

**GCC (GNU Compiler Collection)**
- Default on most Linux distributions
- Supports C++23 features extensively
- Command: `g++`

**Clang (LLVM)**
- Default on macOS (Apple Clang)
- Preferred at Google, Apple, and many FAANG companies
- Generally provides better error messages than GCC
- Command: `clang++`

**MSVC (Microsoft Visual C++)**
- Default on Windows
- Tightly integrated with Visual Studio
- Command: `cl.exe`

### Installation by Platform

**Linux (Ubuntu/Debian):**

```bash
# Install GCC (latest)
sudo apt update
sudo apt install build-essential

# Install Clang
sudo apt install clang

# Verify installations
g++ --version
clang++ --version

# Install specific C++ standard support
# GCC 13+ supports most C++23 features
sudo apt install g++-13

# For the latest Clang (if distro version is old):
# Add LLVM APT repository
wget https://apt.llvm.org/llvm.sh
chmod +x llvm.sh
sudo ./llvm.sh 18  # Install Clang 18
```

**macOS:**

```bash
# Install Xcode Command Line Tools (includes Apple Clang)
xcode-select --install

# Verify
clang++ --version

# For GCC on macOS (via Homebrew)
brew install gcc
g++-14 --version  # Note: 'g++' on macOS may still point to Clang

# For latest LLVM Clang (not Apple's fork)
brew install llvm
/opt/homebrew/opt/llvm/bin/clang++ --version
```

**Windows:**

```powershell
# Option 1: Visual Studio Build Tools (MSVC)
# Download from https://visualstudio.microsoft.com/downloads/
# Select "Desktop development with C++" workload
# After install, use "Developer Command Prompt" or "Developer PowerShell"
cl /EHsc hello.cpp

# Option 2: MSYS2 (provides GCC and Clang on Windows)
# Download from https://www.msys2.org/
# In MSYS2 terminal:
pacman -S mingw-w64-x86_64-gcc
pacman -S mingw-w64-x86_64-clang

# Option 3: WSL2 (run Linux environment on Windows)
# Install WSL2, then follow Linux instructions above
wsl --install
```

**Go comparison:** In Go, you run `go install golang.org/dl/go1.22.0@latest` and you are done. One binary, one toolchain, one build system. C++ requires choosing a compiler, possibly a separate linker, a build system, and a package manager. This complexity is the price of C++'s 40-year history across every platform.

### Build Systems

C++ does not have a single standard build tool like Go's `go build`. Here are the major options.

**CMake** is the de facto standard build system generator. It does not build code directly. It generates build files for other tools (Make, Ninja, Visual Studio projects).

```cmake
# CMakeLists.txt (the CMake equivalent of go.mod)
cmake_minimum_required(VERSION 3.20)
project(MyApp LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

add_executable(myapp main.cpp utils.cpp)
```

```bash
# Build with CMake
mkdir build && cd build
cmake ..              # Generate build files
cmake --build .       # Compile
./myapp               # Run

# Compare to Go:
# go build -o myapp .
# ./myapp
```

**Bazel** is Google's build system, used internally for their entire monorepo. It provides hermetic builds (every dependency is pinned), remote caching, and distributed compilation.

```python
# BUILD file (Bazel)
cc_binary(
    name = "myapp",
    srcs = ["main.cpp", "utils.cpp"],
    deps = [
        "@abseil-cpp//absl/strings",
    ],
)
```

```bash
# Build with Bazel
bazel build //src:myapp
bazel run //src:myapp

# Install Bazel
# Via Bazelisk (recommended, like Go's version manager):
go install github.com/bazelbuild/bazelisk@latest
# Bazelisk automatically downloads the right Bazel version
```

**Ninja** is a small, fast build system designed to be generated by tools like CMake. It is to Make what Go's compiler is to GCC: stripped down and optimized for speed.

```bash
# Use Ninja as the CMake backend (faster than Make)
cmake -G Ninja ..
ninja
```

**Meson** is a newer build system popular in the Linux/GNOME ecosystem. It is fast, user-friendly, and uses Ninja as its backend.

```meson
# meson.build
project('myapp', 'cpp', default_options: ['cpp_std=c++20'])
executable('myapp', 'main.cpp', 'utils.cpp')
```

```bash
meson setup build
meson compile -C build
```

### Package Management

C++ does not have a standard package manager like Go modules. Here are the options:

**vcpkg** (Microsoft, cross-platform):

```bash
# Install vcpkg
git clone https://github.com/microsoft/vcpkg.git
cd vcpkg && ./bootstrap-vcpkg.sh

# Install a library
./vcpkg install fmt
./vcpkg install nlohmann-json
./vcpkg install boost

# Integrate with CMake
cmake -DCMAKE_TOOLCHAIN_FILE=/path/to/vcpkg/scripts/buildsystems/vcpkg.cmake ..
```

**Conan** (community-driven):

```bash
pip install conan

# Create conanfile.txt
# [requires]
# fmt/10.1.1
# nlohmann_json/3.11.2

conan install . --build=missing
```

**Go comparison:** `go get` and `go.mod` handle everything. One command, declarative dependency management, automatic version resolution. C++ package management is fragmented because libraries predated package managers by decades, and many C++ libraries have complex build requirements that do not fit a simple model.

### Recommended Setup for a Go Engineer Learning C++

Here is the minimal setup to get productive:

```bash
# On Linux/macOS:
# 1. Install compiler
sudo apt install g++ clang  # Linux
# or: xcode-select --install  # macOS

# 2. Install CMake and Ninja
sudo apt install cmake ninja-build  # Linux
# or: brew install cmake ninja  # macOS

# 3. Install vcpkg for package management
git clone https://github.com/microsoft/vcpkg.git ~/vcpkg
~/vcpkg/bootstrap-vcpkg.sh

# 4. (Optional) Install Bazel via Bazelisk
go install github.com/bazelbuild/bazelisk@latest

# 5. Editor: VS Code with the "C/C++" and "CMake Tools" extensions
code --install-extension ms-vscode.cpptools
code --install-extension ms-vscode.cmake-tools
```

### Junior → FAANG: Matching Your Toolchain to the Target Environment

Go engineers are accustomed to a single toolchain (`go build`, done). C++ has multiple compilers (Clang, GCC, MSVC), multiple standard libraries (libc++, libstdc++, MSVC STL), and multiple build systems (CMake, Bazel, Meson). The first time you touch a C++ codebase, identify all three before writing any code.

Practical checklist for a new C++ environment: check which compiler is pinned (Clang version matters for C++20 support), check which sanitizers are enabled in the debug build (missing ASan means you will not catch memory errors in local testing), and check whether the build system uses a hermetic toolchain (Bazel with a `cc_toolchain` definition) or relies on the system compiler (fragile and non-reproducible).

Interview entry point: if asked about C++ tooling in a system design interview, mention sanitizers (ASan, TSan, UBSan) as part of your quality story, not just compilation. FAANG interviewers at L5+ expect that you know sanitizers exist and use them in development.

### Senior @ FAANG: Hermetic Toolchains, Reproducible Builds, and Supply Chain Security

At the staff level, the toolchain is not a personal developer choice. It is an organizational asset that requires governance.

**Hermetic toolchain definition.** A hermetic toolchain means that the compiler, linker, standard library, and all system headers are versioned and pinned in the build system, not pulled from the host OS. In Bazel, this is a `cc_toolchain_suite` that downloads a specific Clang release and uses it exclusively, regardless of what the developer has installed. Hermetic toolchains eliminate "works on my machine" build failures and are required for reproducible builds. A staff engineer is responsible for ensuring the team's toolchain is hermetic before onboarding contributors.

**Reproducible builds.** A reproducible build produces bit-for-bit identical binaries from the same source, regardless of build machine. This is a security property: it allows you to verify that the deployed binary was built from the claimed source. The C++ ecosystem has lagged behind the Go and Rust ecosystems on reproducibility (Go achieves reproducible builds by default). For C++, achieving reproducibility requires hermetic toolchains, deterministic linker flags, and careful handling of `__DATE__` and `__TIME__` macros.

**Supply chain security for C++ dependencies.** When your C++ service pulls in vcpkg or Conan packages, each package is a supply chain risk. A staff engineer defines the policy: are packages pinned by content hash (not just version)? Is there an SBOM (Software Bill of Materials) generated per release? Are transitive dependencies audited? The C++ ecosystem has less mature supply chain tooling than Go (no `go.sum` equivalent by default), so the policy must compensate manually.

**Toolchain upgrade coordination.** When upgrading from Clang 15 to Clang 16 across a large team, the upgrade has dependencies: CI must update before developers can update, the sanitizer runtime must be compatible with the new compiler, and any compiler warnings that become errors under the new version must be fixed before the upgrade lands. A staff engineer writes the upgrade plan, gates each phase on CI green status, and communicates the timeline to dependent teams. The upgrade document includes a rollback plan with a defined rollback trigger.
